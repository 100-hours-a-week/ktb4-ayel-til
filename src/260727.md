## 1. RBAC (Role-Based Access Control)
> "누가, 어떤 Kubernetes 리소스에, 어떤 작업을 할 수 있는지" 역할을 기준으로 통제하는 인가 방식

### 필요한 이유
> 쿠버네티스에서는 많은 주체가 Kubernetes API Server를 사용한다

```
k get pods 
k get ns
k apply -f pod. yaml

# 직접 파드를 조작하거나, 네임스페이스 <- 리소스들을 직접 컨트롤 
# kubeconfig.yaml ADMIN 권한
# Kubernetes API Server <- Control Plane (Master Node)
```
- 다른 파드들, 다른 요소들도 똑같이 CP 에 API Server 요청를 보낼 수 있음
  - ArgoCD
  - Prometheus <- 모니터링 + 시각화
  - Ingress Controller <- 인입 트래픽 컨트롤하는 컨트롤러
  - CI/CD 도구 <- CI Jenkins, Github actions
  - Kubernetes Operator
  - Pod 안에서 실행되는 애플리케이션
    - 다음 요청을 어디로 릴레이?, 같은 Label Set 갖고 있는 Pod List 요청
- 쿠버네티스에서는 권한 관리 체계
```
누가 요청했는가?
어떤 리소스에 접근하려는가?
어떤 작업을 수행하려는가?
어느 네임스페이스에서 수행하려는가?
```
---
### RBAC가 없으면
#### 1. 모든 사용자한테 관리자 권한 주는 거랑 똑같다
- 우리는 CP에게 모든 권한 양도
  - 스스로, 애플리케이션을 "다수의" 개수로 조정하기 힘듬
  - 그래서 오케스트레이션 툴을 만들었음
    - 과도한 권한을 갖고 있는 구조
- 사용자: 나, 개발자 (주니어, 시니어), 데이터 분석가

#### 2. 네임스페이스 분리 <- 의미가 없어진다
- 네임스페이스는 논리적으로 분리한 것
  - RBAC 가 없으면 BE -> FE 접근해서, Secret 수정 가능

#### 3. 애플리케이션 권한을 가진다
- PLG Stack (Pod)
  - 프로메테우스, 로키, 그라파나 (매트릭, 로그 중앙 집중형 수집 + 대시보드)
  - 모든 노드, 파드, 네임스페이스 접근
- 모니터링 툴 = 누군가 봐야함 
  - 운영팀, 개발자, 운영자, 보안 담당자 등
  - 많은 사용자가 사용할 수 있고, 외부에서 사용할 수 있어야 함
- 보통 내부인이 무너뜨린다

#### 4. 권한을 사용자마다 개별 관리 힘들다
- 적은 개발자 = 손으로 관리 가능함
- 개발자 100명일 시, `개발자 100명 * 접근하는 리소스 종류 * 작업의 종류 * NS = 관리해야할 권한의 개수`
```
개발자 역할
- Pod 조회
- Deployment 조회 및 수정
- 로그 확인

운영자 역할
- 대부분의 워크로드 관리
- Namespace 운영

모니터링 역할
- Node, Pod, Service 상태 조회
```
- 사용자를 해당 역할에 연결만 하는 방식

---

### 인증과 인가

#### 인증
> 누구인지 확인하는 과정
- 클라이언트 인증서 (pem key), Token, OIDC, kubeconfig 인증 정보

#### 인가
> 확인된 주체가 해당 작업을 수행해도 되는지 판단하는 과정
- API Server <- 나에게 명령을 보낸다
  - 인증은 이미 된 요청이라고 가정하여, 인가 과정만 본다
- k8s 클러스터
  - 내부 리소스
    - 인증/인가된 누군가가 만들어낸 리소스
    - Pod, Ingress Controller
  - 외부 사용자
    - k8s <- 클러스터 구성
    - ssl, kubectl 명령어를 넣으려면, pem 키 같은걸로 인증 과정을 수행하고 왔다라고 판잔

💡 RBAC는 인가 과정만 확인

---

### 동작 방식
권한 관리를 두 가지 방식으로 나눔
- Role: 어떤 작업을 허용할지
- Binding: 그 권한을 누구에게 줄 것인지

RBAC 로 만들기
```
주체
ServiceAccount: backend-reader -> RoleBinding으로 연결

역할
Role: pod-reader -> 권한 내용

대상
backend Namespace의 Pods

작업
get, list, watch
```

---

### 핵심 리소스
- Role: 특정 Namespace에서 사용할 권한을 정의
- ClusterRole: 클러스터 범위 또는 여러 Namespace에서 재사용할 권한을 정의
- RoleBinding: 특정 Namespace 안에서 Role 또는 ClusterRole을 주체에게 부여
- ClusterRoleBinding: ClusterRole을 클러스터 전체 범위로 주체에게 부여
---
#### 1. Role
특정 네임스페이스 안에서 허용할 권한을 정의
- 어디에서?: backend Namespace
- 무엇에 대해?: Pods
- 어떤 작업을?: get, list, watch

Role 를 만들었다해서 아직 누구도 그 권한을 사용할 수 있는건 아니다
- Role은 권한을 정의할 뿐 아직 그 권한을 받을 주체는 아직 정하지 않았다

#### apiGroups
- 리소스가 속한 API 그룹을 지정
- 빈 문자열은([""]) Core API Groups
  - Pod, Service, ConfigMap, Secret, NS, PV, PVC
- ["app"] 
  - Deployment, ReplicaSet, StatefulSet, DaemonSet

#### resources
- 권한을 적용할 쿠버네티스 리소스
- YAML Kind처럼 리소스 지정

#### verbs
- 리소스에 대해 허용할 작업을 지정

---
#### 2. RoleBinding
Role 에 정의된 권한을 특정 사용자, 그룹, ServiceAccount 에게 연결하는 역할

#### subjects
권한을 받을 주체를 정의
- 주체로 정의할 수 있는 것: 사용자, Ggroup, ServiceAccount
- 여러 주체한테 동일한 권한 주는 것이 가능함

#### roleRef
어떤 권한을 연결할지 정의

```
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: pod-reader
```
---
#### Role <-> RoleBinding 역할
```
Role
└─ 권한 정의
   ├─ Pods 조회
   ├─ Services 조회
   └─ ConfigMaps 조회

RoleBinding
├─ 위 Role을 참조
└─ backend-reader에게 부여
```
---
#### 3. ClusterRole
권한은 기본적으로 최소한만 주는게 원칙

클러스터 Role를 사용하는 경우
- 특정 NS에 속하지 않는 리소스
  - node, NS, PV, StorageClass
---
#### 4. ClusterRoleBinding
ClusterRole의 권한을 클러스터 전체 범위에서 주체한테 부여

---
#### Role <-> ClusterRole 비교
| 구분 | Role | ClusterRole |
| --- | --- | --- |
| 리소스 범위 | 특정 Namespace | 클러스터 범위 |
| Namespace 지정 | 필요 | 지정하지 않음 |
| Namespace 리소스 권한 | 가능 | 가능 |
| 클러스터 범위 리소스 권한 | 불가능 | 가능 |
| 여러 Namespace 재사용 | 직접 불가능 | 가능 |
| 예시 | 특정 팀의 Pod 조회 | Node 조회, 전체 Namespace의 Pod 조회 |
---
#### 실무 사용 예시, 방법
#### 1. 팀별 NS 권한 분리
```
Namespace
- frontend Namespace, backend Namespace, monitoring Namespace, argocd Namespace

frontend 개발자
- frontend Namespace의 Pod 조회, Deployment 수정, 로그 조회
- backend와 monitoring Namespace 접근 제한
```
#### 2. 개발자 - 운영자 권한 분리
개발자
```
허용
- Pod 조회, Pod 로그 확인, Deployment 조회, 제한된 Deployment 수정

제한
- Namespace 삭제, Node 수정, ClusterRole 생성, 전체 Secret 조회
```
운영자
```
허용
- 워크로드 관리, Namespace 관리, 스토리지와 네트워크 리소스 관리, 필요한 RBAC 관리
```

#### 3. App 별 Service Account 적용
```
ArgoCD -> ArgoCD 전용 ServiceAccount
Prometheus -> Prometheus 전용 ServiceAccount
Ingress Controller -> Ingress Controller 전용 ServiceAccount
개인 프로젝트 -> 프로젝트 전용 ServiceAccount
```

---

#### 💡 정리
- RBAC: 역할을 기준으로 Kubernetes API 접근 권한을 제어한다
- Role: 특정 Namespace의 권한을 정의한다
- ClusterRole: 클러스터 범위 또는 재사용할 권한을 정의한다
- RoleBinding: Role 또는 ClusterRole을 특정 Namespace에서 주체에게 부여한다
- ClusterRoleBinding: ClusterRole을 클러스터 전체 범위에서 주체에게 부여한다

## 2. Service Account
> Pod와 같은 애플리케이션이 Kubernetes API를 사용할 때 사용하는 클러스터 내부의 신원

- 사람은 kubectl <- 이걸로 통신
- 파드, 내부 프로그램은 "인가"를 할 때 ServiceAccount를 만들어서 사용한다

```
사람
-> User Account로 인증
-> kubectl을 통해 Kubernetes API 사용

Pod 내부 애플리케이션
-> ServiceAccount로 인증
-> Kubernetes API 사용
```

### 모든 파드는 kubernetes API를 사용하는가? X
- WAS <- 
  1. 사용자 요청
     - Ingress, API Gateway = Ingress Traffic
  2. Service -> Endpoint Slices
  3. WAS Pod
  4. WAS Container
  5. DB Container -> DB Headless Service
- k8s API 필요 없음
- 예를 들어
  - Prometheus가 Pod와 Node 상태를 조회
  - `Prometheus Pod -> Kubernetes API Server -> Pod, Node, Service 상태 조회`
  - ArgoCD가 Deployment와 Service를 생성하거나 수정
  - Ingress Controller가 Ingress와 Service 상태를 감시
  - 애플리케이션이 ConfigMap이나 다른 Pod 정보를 직접 조회
- k8s API 사용하기 위해서는 2가지
  - 인증과 인가

### 어떻게 ServiceAccount 사용하나?
- 보통 사용하는 구조
```
Pod -> 사용
ServiceAccount -> 인증 정보
Kubernetes API Server -> 권한 검사
RBAC -> 요청 허용 또는 거부
```
#### 1. SA 생성
```
# be-sa.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: backend-api-sa
  namespace: backend
```
#### 2. Role
```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
  namespace: backend
rules:
  - apiGroups: [""]
    resources:
      - configmaps
    verbs:
      - get
      - list
      - watch
```
#### 3. RoleBinding
```
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-configmap-reader
  namespace: backend
subjects:
  - kind: ServiceAccount
    name: backend-api-sa
    namespace: backend
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: configmap-reader
```
#### 4. Pod에 연결하기
```
apiVersion: v1
kind: Pod
metadata:
  name: backend-api
  namespace: backend
spec:
  serviceAccountName: backend-api-sa

  containers:
    - name: backend-api
      image: example/backend-api:1.0
```
```
apiVersion: apps/v1
kind: Deployment
~
    spec:
      serviceAccountName: backend-api-sa

      containers:
        - name: backend-api
          image: example/backend-api:1.0
```
---

#### Default Service Account
> Pod에 ServiceAccount를 지정하지 않으면 해당 Namespace의 default ServiceAccount를 사용함
```
kubectl create ns backend

kubectl get serviceaccounts -n backend
# default sa
```
- 권한을 지정한다 해도 NS에 있는 모든 파드가 다 해당 권한을 사용할 수 있음
  - 워크로드별 SA, NS별 SA

---

### ServiceAccount 는 NameSpace 에 속함
```
system:serviceaccount:backend:backend-api-sa

system:serviceaccount:frontend:backend-api-sa
```
#### 하나의 SA를 여러 Pod 사용할 수 있나요? O
- 같은 애플리케이션의 Replicas
  - 여러 개의 파드
    - 파드 템플릿에 있는 SA
    - -> 다수의 파드는 하나의 SA 사용할 수 있다

#### 하나의 SA에 여러 권한을 줄 수 있나요? O
- RoleA
- RoleB -> 둘 다 하나의 SA에 할당 가능함

---

#### 실무에서 사용하는 방식
#### 1. 애플리케이션
```
frontend
→ frontend-sa

backend
→ backend-sa

batch-worker
→ batch-worker-sa

prometheus
→ prometheus-sa
```
#### 2. defaulrServiceAccount <- 권한 주지 않기
- 디폴드 SA에 권한을 주면 NS 내에서 "SA를 지정하지 않은" 리소스들이 권한을 가지게 된다
#### 3. 최소 권한 원칙을 적용
```
필요한 것
- Pods get, list, watch

부여하면 안 되는 불필요한 권한
- Pods delete, Secrets get, Namespaces create
- 🚨 모든 리소스
```
- cluster-admin-sa
  - pod, user account
  
#### 4."생성", "삭제", "수정" 권한은 상당히 유의해서 사용
- 생성 <- 권한을 잘못 주면, 클러스터에서 "삭제" <<<<<< "생성"이 훨씬 위험하다
- 자원 잘 만들었으면 문제가 안 될 수 있는데
- 생성은 리소스 node affinity, anti-affinity
- 하나의 노드 여러 파드가 들어올 수 있거나
    - 노드의 최대 파드 개수를 뭘 보고 정하냐면..
        - 보통 여기에 들어오는 애들을 특정하거나 제한, 해당 노드에는 WAS만 들어와야 해
        - node selector, label selector <- 필수 조건
        - node affinity - 권장
- 네임스페이스 삭제는 훨씬 위험

#### 💡 정리
- ServiceAccount: Pod와 프로그램을 위한 Kubernetes 내부 신원
- Role / ClusterRole: 허용할 리소스와 작업 정의
- RoleBinding / ClusterRoleBindina: ServiceAccount와 권한 연결
- serviceAccountName: Pod가 사용할 ServiceAcCount 지정

### User Account
User Account는 사람이 사용하고, ServiceAccount는 Pod와 자동화 프로그램이 사용합

| 구분 | User Account | ServiceAccount |
| --- | --- | --- |
| 주요 사용자 | 개발자, 운영자 | Pod, 애플리케이션, 운영 도구 |
| 사용 목적 | 사람이 클러스터를 관리 | 프로그램이 API Server에 접근 |
| Kubernetes API 리소스 | 기본 `User` 리소스가 없음 | `ServiceAccount` 리소스가 있음 |
| 생성·관리 | 인증서, OIDC 등 외부 인증 체계 | Kubernetes API로 생성 |
| 범위 | 인증 체계에 따라 관리 | Namespace에 속함 |
| 주요 인증 정보 | 인증서, OIDC Token 등 | ServiceAccount Token |
| 권한 부여 | RBAC | RBAC |
| 사용 예시 | 개발자, 클러스터 관리자 | Prometheus, ArgoCD |

#### AWS 클러스터에서 User account 관리하기
k8s 클러스터
1. EKS
2. `kubeadm` (kube-spray, k3s)

```
AWS IAM
-> 이 사용자가 누구인지 인증
-> EKS 클러스터에 들어올 수 있는지 결정

Kubernetes RBAC
-> 들어온 사용자가 어떤 리소스에
-> 어떤 작업을 할 수 있는지 결정
```
```
IAM Identity Center
├─ EKS-Admins 그룹
├─ EKS-Developers 그룹
└─ EKS-LogViewers 그룹
        ↓
각 그룹에 IAM Role 할당
        ↓
EKS Access Entry
        ↓
Kubernetes Group과 연결
        ↓
RoleBinding / ClusterRoleBinding
        ↓
실제 Kubernetes 권한 부여
```

#### 권한 설정 (IAM Role)
- AmazonEKSClusterAdminPolicy: 클러스터 전체 관리자
- AmazonEKSAdminPolicy: 관리자 수준의 Kubernetes 권한
- AmazonEKSEditPolicy: 워크로드 생성·수정
- AmazonEKSViewPolicy: 읽기 전용
- AmazonEKSAdminViewPolicy: 관리자 관점의 확장된 조회

이런 권한들을 특정 IAM 유저에게 붙여서 사용한다

- Access Entry
    - AWS IAM 사용자 IAM 역할 -> 쿠버네티스 리소스에 어떤 권한으로 연결할지 설정 하는 기능하며, EKS 클러스터 등록한다
```
IAM Role 만들거나 있는 걸 사용한다면
-> EKS 어디 클러스터에서 사용하고
-> 들어온 다음에는 어떤걸 할 수 있나
```

#### kubeadm 에서 사용자 권한 관리
- EKS 사용하지 않으니 EKS Access Entry 사용할 수 없음
- 방법이 몇 가지 있다
1. 사용자별 클라이언트 인증서 발급
2. OIDC
3. 인증 웹훅 구성

```
인증서 발급
-> Role Bindg 묶어서
- 사용자별 인증 서 발급
-> 인증서 그룹을 -> Kubernetes 인증서 그룹으로 만들어서 인식
-> RoleBinding 으로 그룹에 묶어서 사용한다.
```

- 실습은 해볼 수 있는데 실무에서는 적용하지 않음
    - 인증서 발급, 폐기, kubeconfig 연결 <- 이것들을 하기 어려워서
    - 만약 한다면
        ```
        1. 사용자별 인증서 + kubeconfig 발급
        2. k8s API Server 가 사용자 인증
        3. Role - ClusterRole 로 권한 정의
        4. RoleBinding - ClusterRoleBinding 으로 그룹에 권한 연결
        ```
    - 이렇게 준비해야하는데
        - 실제로 한다면
            1. 관리자가 사용자별 인증서 + 개인키 만들고
            2. 사용자별 kubeconfig 출력하고
            3. Role, ClusterRole 생성하고
            4. Binding 시키고
            5. 그 다음에 사용자에게 kubeconfig 출력 값 전달하면
- 실무적으로 keycloak, kota, OIDC 기반 인증 서비스

## 4. Ingress 
> 클러스터 외부의 HTTP, HTTPS 요청을 도메인과 경로에 따라 내부 Sevice로 연결하는 라우팅 규칙

```
외부 사용자
    ↓
Ingress Controller
    ↓ Ingress 규칙 확인
Service
    ↓
Pod
```

- Ingress: 외부 요청을 어떤 Service로 전달할지 정의한 규칙
- Ingress Controller: Ingress 규칙을 읽고 실제 요청을 전달하는 프로그램

### Ingress 왜 필요한가

#### 기존에 외부 요청을 어떻게 Kubernetes로 가져왔는지

- Pod는 재생성, 삭제, 생성된다.
- Pod는 고유한 IP를 가진다.
- 생성될 때마다 IP가 변경된다.
    - Service
        - 내부 IP, 내부 DNS
            - backend-service:8080
        - 사설망에서만 통신 가능
    - NodePort Service
      `사용자 -> NodeIP:NodePort -> Service -> Pod`

1. 서비스마다 포트 관리
    - FE, BE, Admin, Dashboard, Data-lab, Registry
    - 모든 노드에 열어둘 포트가 늘어난다.
        - 공격 지점 증가
            - 방화벽
            - 보안 그룹 규칙
            - 비용 증가

2. 일반적인 웹 방식이 아님
    - naver.com:65431
    - 사용자가 익숙하지 않음

3. HTTPS 설정이 분산된다.
    - 각 서비스마다 별도의 NodePort 사용
    - 각각 SSL Termination 처리 필요
        - FE → 300810 → (NodePort) Service → Pod
            - SSL Header를 붙일 필요는 없음
            - FE NodePort에서 SSL 종료
        - BE
        - Admin
        - Dashboard
        - Registry
    - SSL 인증서 관리 및 갱신 필요
      
---

### Ingress 의 해결방법
```
                      ┌→ frontend-service → frontend Pod
사용자 → Ingress Controller
                      ├→ backend-service  → backend Pod
                      └→ admin-service    → admin Pod
```
- 외부에서는 80, 443으로 요청
- Ingress Controller가 요청 정보를 확인
    - 요청 도메인(Host)
    - URL 경로(Path)
    - 미리 설정된 규칙(`Ingress`)
        - 적절한 Service로 요청 분배

---

### Ingress의 핵심 역할
#### 1. URL 기반의 라우팅
- 요청 도메인이 다르면, 서로 다른 서비스에게 전달
```
frontend.example.com → frontend-service
api.example.com      → backend-service
admin.example.com    → admin-service

example.com/admin -> admin-service
```
- 프록싱이 가능하다
---

### Ingress - Ingress Controller
- 이 부분이 인그레스 이해할 때 가장 중요함

#### Ingress 직접 요청을 처리하지 않는다
```
example.com으로 들어온 요청을
example-service의 80번 포트로 전달한다.

# 규칙을 적고, 저장한 것 "뿐"
# 이 규칙을 선언해도, 실제로 동작하지 않는다.
```

#### Ingress Controller 
> Ingress 리소스를 감시하고, 그 규칙에 맞게 실제 프록시나 로드 밸런서를 구성 하는 컨트롤러
- Ingress 규칙 적어두면 그걸 진짜로 실행하는게 Ingress Controller
- 구현체 여러 개 있음
    - ingress-nginx
    - Traefik
    - HAProxy Ingress
    - Kong Ingress Controller
    - AWS Load Balancer Controller
    - GKE Ingress Controller

---

### 전체 동작 과정
1. 사용자가 Ingress YAML 생성
2. API Server가 Ingress 리소스 저장
3. Ingress Controller가 변경 감지
4. Controller가 라우팅 설정 생성
5. 외부 요청 수신
6. Host와 Path 확인
7. 대상 Service 또는 Endpoint로 전달

- 동시에 두 개의 Ingress Controller

- IngressClass

    - `투자`

#### 💡 정리
- Ingress: 외부 HTTP HTTPS 요청을 Service로 전달하는 규칙
- Ingress Controller: Ingress 규칙을 읽고 실제 요청을 처리하는 프로그램
- IngressClass: 어떤 Controller가 Ingress를 처리할지 지정
- Host Routing: 도메인에 따라 Service 선택
- Path Routing: URL 경로에 따라 Service 선택
- TLS Termination: Controller에서 HTTPS 인증서와 암호화 연결 처리
