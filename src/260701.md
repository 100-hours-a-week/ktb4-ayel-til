# 260701

## 1. Bridge Network
> 컨테이너들이 동일한 호스트 내에서 서로 통신할 수 있도록 연결해주는 도커의 기본 가상 네트워크

- 한 대의 도커 호스트 안에서 **여러 컨테이너를 연결**하는 가상 내부 네트워크
- 컨테이너가 실행되면 인터넷이랑 통신하면 되는거 아닌가? 
  - 실제 서비스는 하나의 프로그램으로 구성되지 않는다

```사용자 -> Nginx -> API -> 외부 인터넷```

- 사용자 -> Nginx: 웹사이트 또는 API 요청
- Nginx -> API : 리버스 프록시 요청 전달
- API -> MySQL : 데이터 조회 및 저장
- API -> 외부 인터넷 : 외부 API 호출, 패키지 다운로드 등

#### 이 때 모든 컨테이너를 호스트가 사용하는 네트워크에 연결하면 어떻게 되는가?
- 어떤 컨테이너 어떤 포트를 사용하는지 관리하기 힘들다
- MySQL 보안성이 중요한 컨테이너가 외부 인터넷에 노출 될 수 있다
- 컨테이너는 삭제되고 재생성이 자주 되는 구조
  - IP 새롭게 할당 받는다
  - 연결 설정이 깨질 수 있다
  - 여러 프로젝트가 하나의 호스트에서 실행 중일 때 내부 프로젝트들이 서로 의도치 않게 통신할 수 있다
    - 본인 네트워크 범위에게 공지하는 네트워크 ping, 브로드캐스트

#### 문제 해결 - Bridge Network
- 도커는 컨테이너마다 독립적인 네트워크 환경을 만들고,
- 필요한 컨테이너끼리만 같은 네트워크를 연결할 수 있도록 한다

---

### 사용 이유
1. 컨테이너 간 안전한 격리 통신
2. 서비스 간 간편한 연결
3. 호스트 포트 충돌 방지 및 노출 최소화
4. 확장성과 운영 편의성

---

### 이해해야하는 개념
#### 1. Host
- 호스트는 Docker Engine 이 실행되는 실제 서버, Linux 머신
- EC2 Host
  - Docker Engine
    - Nginx Container
    - Spring Container
    - MySQL Container
- EC2 ubuntu server = Docker Host
- Nginx, Spring, Mysql = Container

- 도커 호스트는 컨테이너를 실행하고, 관리하는 기반 컴퓨터 
- 컨테이너는 호스트의 CPU, Memory, Network 자원을 함께 공유해서 사용하는데, 가능한 서로 분리된 환경에서 실행된다.

#### 2. 네트워크 인터페이스
- 네트워크 통신을 위한 출입구
  - 컴퓨터, 컨테이너도 통신하기 위헤서는 네트워크 인터페이스가 필요하다

- 물리 네트워크 인터페이스: 실제 서버가 VPC, 인터넷, 사내망과 연결되는 출입구
- 가상 네트워크 인터페이스: 컨테이너가 네트워크를 사용하는 출입구
- Docker 브리지 인터페이스: 여러 컨테이너의 가상 인터페이스를 연결하는 가상 스위치

#### 3. 컨테이너는 자신의 네트워크 공간을 가진다
- Bridge network <- 도커 엔진 내부에서 사용하는 네트워크 공간
  - 브릿지 네트워크에 연결된 컨테이너는 이런 정보를 가진다
    - 자신의 네트워크 인터페이스
    - 자신의 IP 주소
    - 자신의 기본 게이트웨이
    - 자신의 라우팅 테이블
    - DNS 설정
- 브릿지 네트워크 안에 연결된 컨테이너는 네트워크별 IP 주소를 자동 할당 받는다
  - 컨테이너가 생성될 때 할당
  - 각 네트워크에는 서브넷 + 기본 게이트웨이 설정
  - 컨테이너 IP가 생성될 때마다 변경된다

---

### Bridge Network 구조
- 실제 네트워크 장비를 통한 네트워크가 아님
- 리눅스 + Docker 소프트웨어로 만든 가상의 네트워크

#### 구성요소
- 컨테이너(`eth0`): 컨테이너 내부 네트워크 출입구 (각 집의 현관문)
- veth pair: 컨테이너와 호스트를 연결하는 가상 케이블 (집과 단지를 연결하는 케이블)
- Docker Bridge: 같은 네트워크의 컨테이너를 연결하는 가상 스위치 (집과 단지를 연결하는 케이블)
- Host NIC: 호스트가 외부 네트워크와 통신하는 실제 인터페이스 (집과 단지를 연결하는 케이블)

> 컨테이너 내부에서 보이는 `etho`이 실제로 호스트의 NIC 에 연결되는게 아니다.
>컨테이너는 먼저 도커 브릿지에 먼저 연결이 되고, 외부 통신이 필요한 경우 호스트의 라우팅, NAT, 방화벽 규칙을 통과해서 실제 네트워크 인터페이스로 나가게 된다.

### 같은 브릿지 네트워크 내부에서 통신하는 경우
- Nginx -> API 컨테이너 IP를 알 필요없다
  - Bridge Network에서 컨테아름 <-> 컨테이너의 IP -> DNS에 등록해서 관리해준다
  - 같은 네트워크라면 -p 옵션이 필요없다
    - docker run -d -p 8080:80
    ```
    docker run -d \
    --name api l
    -network app-net\
    my-api: latest
    ```
    - nginx
    ```
    proxy_pass http://api:8080;
    ```
  - API 외부 포트를 안 열면
  ``` 
    Nginx - api: 8080 가능
    호스트- api: 8080 가능
    외부 사용자 api: 8080 불가능 
  ```
  
### 기본 Bridge, 사용자 정의 Bridge
- 도커를 설치하면, 기본으로 Bridge 자동 생성

```
docker network ls
# 기본으로 설치된 네트워크 보인다.
```

- 컨테이너를 실행할 때 별도로 `-network`옵션을 주지 않으면, 기본 bridge 할당이 된다.
- 기본 bridge 보다 사용자 정의 bridge 더 선호한다.

#### 사용자 정의 브릿지 네트워크를 선호하는 이유
1. 자동으로 DNS
2. 격리 수준이 높다
3. 실행 중 연결 해제, 연결

### 네트워크 명령어
#### 1. 생성 관련 
```
# 생성
docker network create app-net 

# 명시적으로 bridge 드라이버
docker network create --driver bridge app-net

# 만들고 나서 네트워크 스펙
docker network inspect app-net
```

- Driver : 네트워크 드라이버 종류 
- Subnet: 컨테이너에 할당할 Ip 범위
- Gateway: 컨테이너의 기본 게이트웨이
- Containers: 연결된 컨테이너 목록
- IPv4Address: 각 컨테이너에 할당된 IP

2. 연결, 연결해제 
```
docker network connect app-net nginx-3
docker netowrk disconnect app-net nginx3-
```

### 실무적인 구조
#### 1. Network Segementation
Nginx- API- MySQL 분리
- API 컨테이너를 두 개의 네트워크 할당
  - Nginx -> API
  - API -> DB
  - Nginx -> DB x

#### 2. 사이드 카 패턴
- 메인 컨테이너 옆에 보조하는 컨테이너를 두는 방식
- 로그, 모니터링, 프록시, 보안, 포매팅 등등
  - 공통 관심사를 분리하는 방식

#### 3. 워커 패턴
- 사용자 요청을 바로 처리하지 않고 API, 메시지 브로커 등을 별도의 네트워크에서 분리해서 비동기로 작업을 처리하는 패턴

### 실무적으로 잘 사용하기

- 컨테이너 이름 DNS
- 프로젝트별 통신 범위 분리
- 컨테이너 IP 변경이되어 자동으로 DNS

```

# .env
DB_HOST = 172.24.0.3
# 권장 패턴

# Bridge DNS
```

#### 추가 내용
#### Docker Network Driver
- bridge
- host
- overlay 
- macvlan

##### Bridge Driver
도커 호스트 내에서 컨테이너를 가상의 스위치로 연결하는 네트워크 드라이버

##### Host Network
Host Network 컨테이너가 별도 네트워크를 만들지 않고 호스트의 네트워크 공간을 "직접" 공유하는 방식
- Host Network 에서는 컨테이너가 별도의 IP 주소를 할당 받지 않는다.
  - 호스트의 IP 주소를 사용한다.

장점
- Bridge Network 보다 네트워크 경로가 단순
- NAT, 포트 매핑이 필요없다
- 호스트에서 실행 중인 서비스가 localhost 직접 전근해야하는 경우에 접근하기 좋다

단점
- 컨테이너랑 호스트의 네트워크 격리가 사라진다
- 같은 포트를 사용할 수 없다
  - 호스트가 점유 중인 포트는 컨테이너가 사용하지 못한다
  - Nginx 80 -> 컨테이너는 80 포트 사용 못함
- 여러 서비스가 한 서버에 공존하는 경우
  - 일반적으로 사용하기 어렵다

##### Overlay Network
Overlay 여러 Docker Host 에 흩어져 있는 컨테이너를 하나의 가상 내부망처럼 연결하는 네트워크
- Bridge 한 대의 호스트에서 동작

```
EC2 한 대 안의 Nginx <-> API <-> MySQL
-> Bridge Network
```

- 컨테이너가 여러개의 호스트로 분리 되어 있으면, Bridge로 연결이 안된다.

#### 사용이유
- 여러 ec2 분산 된 서비스 컨테이너를 연결할 수 있다
- 서비스가 다른 호스트로 이동해도 같은 오버레이 네트워크를 쓰면 통신 가능하다

- Overlay -> Docker Swarm
  - docker swarm init
  - docker swarm join
  
- 오버레이 - 브릿지 비교

  | 구분 | Bridge | Overlay |
  | --- | --- | --- |
  | 통신 범위 | 한 대의 Docker Host | 여러 Docker Host |
  | 주 사용 환경 | Compose, 단일 EC2 | Swarm, 다중 서버 |
  | 관리 복잡도 | 낮음 | 높음 |
  | 네트워크 구성 | 로컬 가상 브리지 | 여러 호스트 위의 분산 가상망 |

##### Macvlan Driver
컨테이너마다 별도의 MAC 부여해서 컨테이너가 마치 "물리 네트워크에 직접 연결된 거처럼 보이게 하는 드라이버"
- 브릿지 네트워크 -> 외부에서 컨테이너를 직접 보지 못한다
  - 레거시 애플리케이션
  - 레거시 물리장비

---

#### 💡 정리
Bridge Network는 한 도커 호스트 안에서 컨테이너를 연결하는 가상 내부 네트워크
1. 컨테이너는 각자 IP, Network Interface 를 가진 독립적인 네트워크 환경
2. 같은 브리지 네트워크에 있는 컨테이너끼리는 내부 통신이 가능
3. 외부 공개할 서비스만 -p로 호스트 포트랑 연결해야한다.
4. 기본 브릿지 보단 사용자 정의 브릿지 사용하는게 좋다

## 2. Reverse Proxy
> 클라이언트의 요청을 대신 받아 서버에 전달하고, 서버의 응답을 클라이언트로 반환하는 중개 역할을 하는 서버

### 사용 이유
1. 서버 보안 강화
2. 로드 밸런싱
3. SSL 종단
4. 캐싱 및 압축
