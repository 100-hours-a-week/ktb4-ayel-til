## 1. Namespace
> 하나의 쿠버네티스 클러스터 안에서 리소스를 목적이나 팀별로 구분하여 논리적으로 분리하여 관리하는 고유 이름을 가진 공간
- 네임스페이스는 클러스터를 나누는 기능은 아니다
- 하나의 클러스터 안에서 논리적으로 공간을 구분한다

### 네임스페이스가 왜 필요할까?
- 클러스터에 리소스가 적게 있는 상태
- 리소스가 없을 때는 사실 네임스페이스 하나에 다 올려도 괜찮다
- k8s를 도입한다?
  - 팀의 규모가 커진 것
  - 서비스 자체도 여러 개의 애플리케이션 분리
  
### 네임스페이스가 없다면?
- 하나의 클러스터에
  - 개발 환경
    - EC2 한 대, DB, Session, RP, WAS
  - 스테이징
    - 운영 배포 전에 마지막으로 실제 운영 환경이랑 유사하게 만든 환경
    - 운영 환경이랑 비슷한 환경
      - DB 분리, Session 분리, RP -> ALB, WAS 이중화
  - 운영 환경
- 각 환경에서 애플리케이션 -> WAS
  - api sever를 띄운다면
```
클러스터
- api-server - 개발 환경
- api-server- 스테이징 환경
- api-server - 운영 환경
```

쿠버네티스에서는 동일한 종류의 리소스가 같은 이름을 가질 수 없다
  - Pod - api-server
  - Pod2 - api-server
- 리소스 구분이 힘듬
  - api-server 개발용, 운영용인지 구분이 안간다
- 쿠버네티스 자체 자동화 된 오케스트레이션이 가능
  - 사람이 실수한 가능성이 높아짐
  - 개발자가 운영 리소스인걸 모르고 삭제하거나 파드 수를 늘리거나
- 관리가 복잡해짐
  - DB, WAS, Session, Networking, Controller. Ingress
- 네임스페이스를 통해서 리소스들을 논리적으로 구분

---

### 네임스페이스
> 네임스페이스 하나의 클러스터 안에서 리소스 그룹을 논리적으로 구분하는 범위

```
Kubernetes Cluster
- dev Namespace
- staging Namespace
- production Namespace
```

```
Kubernetes Cluster
- dev
-- api-server Pod
-- database Service

- staging
-- api-server Pod
-- database Service

- production
-- api-server Pod
-- database service
```

---

#### 네임스페이스는 사무실의 부서랑 비슷하다
사무실의 부서 "공간"
- 개발팀, 디자인팀, 기획 팀 공간 분리
- 모든 팀이 다들 "회의실"이란 개별 공간을 부여 받았으면, 각각 팀의 회의실로 간다
- "회의실"이라는 공간의 이름은 같지만 실제로 서로 다른 리소스를 가리킨다

---

### 핵심 역할
#### 1. 리소스를 논리적으로 구분한다
네임스페이스에서는 관련된 리소스를 하나의 그룹으로 묶어 관리
- 환경별로 네임스페이스를 나누기도 한다
- 네임스페이스는 클러스터의 크기에 따라서 나누는 기준을 바꾼다
  - 규모가 작은 팀 -> 환경의 구분을 하기 위해 사용
  - 규모가 큰 팀 -> 네임스페이스를 팀 단위나 기능 단위로 나눈다

#### 2. 리소스의 이름 범위 제공
같은 네임스페이스 안에서는 같은 종류 리소스 이름이 중복될 수 없다
  - api-server <- 파드 리소스는 네임스페이스 내에서 유일하다
    - replicas <- 복제본
```
dev Namespace
─ Pod/api-server
─ Pod/api-server - 생성 불가
```

```
dev Namespace
─ Pod/api-server

production Namespace
─ Pod/api-server
```

#### 3. 명령어 범위를 구분하는 역할
네임스페이스를 사용하면, 특정 공간의 리소스 조회하거나 명령할 수 있다
```
# default namespace를 사용 중
kubectl get pods
kubectl get namespace # 네임스페이스 목록
kubectl get pods -n dev # 특정 네임스페이스만 보고 싶다
```

#### 4. 정책을 적용하는 단위가 된다
- 네임스페이스가 단순하게 리소스를 나누는것만 하는게 아니다
- 네임스페이스 기준으로 운영 정책을 설정할 수 있다

- ResourceQuota: Namespace 전체가 사용할 수 있는 CPU, 메모리, Pod 개수 등의 총량 제한
- LimitRange: Namespace 안의 개별 컨테이너나 Pod가 사용할 수 있는 리소스 범위 설정
- 접근 권한: 특정 사용자나 팀이 특정 Namespace만 관리하도록 구성
- NetworkPolicy: Namespace 또는 Pod 사이의 네트워크 통신을 제한

---

#### 오해하는 것들
#### 1. 클러스터를 나누지 않는다
- 네임스페이스 = 논리적인 구분
- 클러스터는 그대로 같이 사용함 -> 노드 자원을 같이 공유함
- 실제로 CPU, 메모리, 디스크 같은 자원을 공유
- 노드의 문제가 생기거나, 노드 리소스에 문제가 생기면, 네임스페이스 만으로 그 문제들이 격리되지 않는다
- 이 이해가 개발팀 전원에게 있어야 한다

#### 2. 네임스페이스만으로 네트워크가 차단되지 않는다
- 네임스페이스가 달라도 통신이 자동으로 차단되는게 아니고, Pod 간 통신이 가능하다
- 쿠버네티스에서 가장 흔하게 보안 문제가 생기는 패턴
  - 특정 파드를 과하게 노출 시킴
    - 포테이너, 사설 registry, bastion host, nat instance, self hosted runner
      - 네임스페이스 분리
  - 해당 파드로 접속한 쉘
    - 다른 네임스페이스에 curl 통신이 가능함
    - data pod에 요청을 날리고
    - was pod → deploy.env / production.env
      - folder scan 명령 -> 내 컴퓨터 scp (파일전송)
- 네임스페이스 간 통신을 제한하고 싶다면 CNI에서 Network Policy를 변경해야 한다

#### 3. 네임스페이스 만으로는 접근권한을 나눌 수 없다
- 쿠버네티스 <- 다수의 개발자가 접근할 수 있다
- 네임스페이스를 쪼개고 
  - FE, BE, DB
    - Team-A, Team B
    - Team B NS (namespace 약어 ns)
      - WAS Pod
    - Team A 사람들이 Team B NS 에 접근이 가능함
    - RBAC

---

#### 기본 네임스페이스
클러스터 만들면 기본으로 제공되는 NS
- default: Namespace를 지정하지 않은 일반 리소스가 기본적으로 생성되는 공간
- kube-system: DNS, kube-proxy 등 쿠버네티스 시스템 컴포넌트가 실행되는 공간
- kube-public: 클러스터 전체에서 공개적으로 읽을 수 있는 정보에 사용되는 공간
- kube-node-lease: 각 노드의 상태 확인을 위한 Lease 오브젝트가 저장되는 공간

### 구조적인 특징
#### 1. 네임스페이스는 중첩할 수 없다
구조가 폴더랑 비슷해서 중첩되는 거처럼 보이지만 그렇지 않다 -> 중첩되지 않는다
- production ns
  - backend ns
    - payment ns


#### 2. 하나의 리소스는 하나의 네임스페이스에"만" 속한다
- dev ns
- prod ns
- api-server ← dev ns 혹은 prod ns
- 하나의 리소는 하나의 네임스페이스에만 속할 수 있다

### 실무 사용 기준
#### 1. 네임스페이스는 너무 세세하게 나누지 않는다
- 파드 만들 때마다 NS 계속 만들지 않음
  - pod-a-namespace
- 개별 리소스를 기준으로 나누기보다는 팀 단위, 서비스 단위, 환경별로 나누자
    
#### 2. 명명 규칙 회사 단위 공유 필요함
- NS <- 클러스터 단위로 나뉘는 가상의 폴더
- 명명규칙을 잘 만들고 -> 네임스페이스 이름만 보고도 목적을 알 수 었어야 함
- 그걸 회사 단위로 공유한다

#### 3. default ns 사용하지 않는다
- 디폴트는 기본적으로 사용하지 않는다
- 애플리케이션을 디폴트에 배치하면 관리하기가 상당히 까다로워진다
- 다른 리소스들을 이미 ns에서 관리하고 있음 (네트워크 정책, 환경 분리 정책 등)

#### 4. 명령어로 관리할 때, 현재 NS를 잘 확인해야함
- `kubectl delete service backend-service`
  - test 네임스페이스를 정리해야지 -> 알고보니 운영꺼 -> 사고
- `kubectl delete service backend-service -n test`
  - 네임스페이스끼리 통신할 때 보통 service 로 통신

- 다른 Namespace: 동일한 이름의 리소스를 생성할 수 있음
- 기본 Namespace: default
- 정책 적용: ResourceQuota, LimitRange, NetworkPolicy 등의 기준으로 사용

## 2. ResourceQuota
> 하나의 Namespace에서 요청할 수 있는 CPU, 메모리와 생성할 수 있는 쿠버네티스 리소스의 총량을 제한하는 정책

### 왜 필요한가? 
네임스페이스를 사용하면 클러스터를 논리적 분리할 수 있음

``` 
Kubernetes Cluster
- team-a Namespace
- team-b Namespace
- team-c Namespace
``` 

- 네임스페이스 <- "논리적" 으로만 분리
  - 클러스터의 리소스를 같이 사용함 - CPU, MEM
- 워커 노드
```
Worker Node
CPU: 8 Core (Small x 4)
Memory: 16Gi (Small x 4)
- team-a°| Pod
- team-bel Pod
- team-co| Pod
```

---

### ResourceQuota 가 없으면?
- team-a pod -> 7 Core 요청
- team-b pod -> 1 Core 요청
- team-c pod -> 코어 할당이 안된다
- 네임스페이스 <- 클러스터를 물리적으로 분리하는게 아니기 때문에, team-c는 새로운 요청이 아무리 와도 파드가 배치가 안된다
  - pending 상태
- team-a ns 는 왜 저렇게 많이 할당됐을까?
  - pod 100개, service 50개, secret 100개
- 네임스페이스만으로는 자원량의 제한을 못한다
- ResourceQuota -> NS 마다 사용할 수 있는 총량을 지정함

```
team-a
- CPU requests 합계: 최대 2 Core
- Memory requests 합계: 최대 4G1
- Pod 개수: 최대 10개
- Service 개수: 최대 5개
```

---

### ResourceQuota 정의
> 네임스페이스 자원량의 상한선을 설정하는 리소스
- 제한할 수 있는 대상
  - 컴퓨팅 자원 -> CPU, Memory
  - 오브젝트 -> Pod 개수, Service의 개수, ConfigMap의 개수, 스토리지

---

#### 비유
- 사무실 <- 예산
- 리소스 쿼더 = 팀의 예산
- 회사 <- 개발팀, 디자인팀, 기획팀
- 예산을 팀별로 나누지 않으면 개발팀에 인건비로 50억을 씀
- 리소스 쿼터로 예산을 미리 제한
  - 개발팀 - 10억, 디자인 팀 - 3억, 기획 팀 - 20억

---
  
#### Pod의 Limit, Request 를 다시 가져와야함
- requests.cpu: 스케줄링할 때 CPU 0.n개가 필요하다고 판단
- requests.memory: 스케줄링할 때 메모리 nnnMi가 필요하다고 판단
- limits.cp: 컨테이너가 사용할 수 있는 CPU 상한
- limits.memory: 컨테이너가 사용할 수 있는 메모리 상한

---

### ResourceQuota, Pod Limits, Requests 의 관계
requests / limits
- 각 컨테이너가 얼마나 요청하고 사용할 것인가?

ResourceQuota
- Namespace 전체에서 requests / limits의 합계를 어디까지 허용할 것인가?

---

### ResourceQuota가 실제 사용량을 측정하지 않는다
CPU, Memory 할당량에 대해서 일반적으로는 현재 사용하고 있는 실제 양을 기준으로 하지는 않는다
- 파드에 선언되어 있는 limits, requests 를 기준으로 작동
- 실제로는 워커노드에 4cpu
  - Pod A → 1cpu
    - Request: 2vCPu 
  - Pod B → 200m 
    - Request: 2vCPu 
    - 실제사용량 - 1.2vCPu 
    - requests 합계는 - 4vCPU
    - resourceQuota - 4vCPU

#### Pod requests, limits 를 작성하지 않으면?
ResourceQuota가 있는 NS에 배치가 된다면? -> 생성 거절한다
```
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu:"2"
    requests.memory:"2Gi"
    limits.cpu:"4"
    limits.memory:"4Gi"
```
- 리소스쿼터 <- 실제 파드들의 사용량을 보지 않는다
- 파드가 선언한 requests, limits에 있는 요청량을 합산
- 파드에 해당 값이 없으면?
  - 계산할 수가 없다, 이미 우리 노드에 있는 다른 파드들에게 사이드 이펙트가 갈 수 있음

LimitrRange
```
Namespace 사용    
-> ResourceQuota
- Namespace 전체 총량 제한
    
-> LimitRange
- 개별 컨테이너의 기본값, 최소값, 최대값 관리
```

---

kubectl get resourcequota -n team-a

### 언제 사용하나
#### 1. 여러 팀이 하나의 클러스터를 공유할 때 (클러스터 규모가 클 때)
- 특정 팀이 자원을 다 가져다 쓰지 않게 적용

#### 2. 환경별로 자원 제한 (클러스터 규모가 작을 때)
- dev ns, stag ns, prod ns
- dev → 2vCPU Core, 4Gi Mem

#### 3. 오브젝트의 무한한 생성을 제한해야할 때
- pods 특정 조건에서 늘어나도록 설정
  - 트래픽이 많을 때, 요청 처리가 밀릴 때 잘 못 만들어질 수 있다
    - 데이터베이스 레벨에서 데드락이 생김 -> 처리 속도 느려짐 -> WAS Pods 를 생성
  - DB 에 있는 문제
    - 커넥션이 더 소진 -> 데드락이 더 안끝남 -> WAS Pods 더 생성 -> 무한의 인피니티
- 최종의 방어선 같은 느낌으로 자원의 총 개수를 정해놓음

---

#### 💡 정리
- 한 줄 정리: Namespace에서 사용할 수 있는 리소스의 총량을 제한하는 정책
- 적용 범위: 특정 Namespace 전체
- 컴퓨팅 리소스 : CPU, 메모리의 requests와 limits 합계
- 오브젝트 리소스: Pod, Service, ConfigMap, Secret, PVC 등의 개수
- 초과 시 동작: 새로운 생성 또는 수정 요청이 거부됨
- 계산 기준: 일반적으로 선언된 requests와 limits의 합계

---

## 3. LimitRange
> 특정 Namespace에서 생성되는 개별 컨테이너나 Pod의 requests와 기본값, 최솟값, 최댓값을 적용하는 정책

```
Namespace 사용
→ ResourceQuota
- Namespace 전체 총량 제한
→ LimitRange
- 개별 컨테이너의 기본값, 최소값, 최대값 관리
```

- 리소스쿼터 -> NS 전체 총량 제한
- 리미트 레인지 -> 개별 컨테이너 리소스 범위 제한

### 왜 필요할까?
개별 파드나 컨테이너 "얼마나 큰 값을 요구할지" 정하지 않았다

### 리소스 쿼터만 있으면 발생하는 문제
- CPU request = 4
- NS 하나에 cpu 코어 개수가 4인 컨테이너 하나가 만들어짐
  - 그리고 다른 파드들은 배치할 수 없다
  - 하나의 컨테이너가 네임스페이스 전체에 총량을 다 사용할 수 있다
- 정상이긴 하나, 운영 측면에서는 좋은 상황은 아니다
- 하나의 컨테이너가 전체 총사용량을 다 독점
- LimitRange 을 걸어서
```
컨테이너 하나의 CPU request
─ 최소: 100m
─ 최대: 1

컨테이너 하나의 CPU limit
─ 최대: 2
```

---

### Limit Range 정의
특정 네임스페이스 안에서 생성되는 개별 리소스에 대해서 이런 제약들을 설정할 수 있다

```
LimitRange
- 기본request
- 기본 Limit
- 최소 request
- 최대 Limit
- request와 Limit의 최대 비율 (Ratio)
- PVC의 최소•최대 요청 용량
```
---
#### 비유
- 네임스페이스 = 부서
- ResourceQuota = 예산
- LimitRange = 개인별 결제 한도
- 팀 전체 예산이 천만원 = 리소스 쿼터
- 개별 결제 규칙
  - 최소 결제 금액 만원
  - 최대 결제 200만원
  - 기본 결제 한도 100만원
  - LimitRange 유사

```
Namespace 사용
→ ResourceQuota
- Namespace 전체 총량 제한
- 네임스페이스 전체에 CPU Request 최대 16
→ LimitRange
- 개별 컨테이너의 기본값, 최소값, 최대값 관리
- 컨테이너 하나의 CPU Request 최대 2
```

---

### ResourceQuota vs LimitRange
| 구분 | ResourceQuota | LimitRange |
| --- | --- | --- |
| 적용 범위 | Namespace 전체 | 개별 Container, Pod 또는 PVC |
| 주요 목적 | 전체 리소스 총량 제한 | 개별 리소스의 범위 제한 |
| CPU 예시 | 모든 CPU request 합계 최대 4 | 컨테이너 하나의 CPU request 최대 1 |
| Pod 개수 제한 | 가능 | 주된 역할이 아님 |
| 기본값 적용 | 하지 않음 | 가능 |
| 최소값 설정 | 전체 총량의 최소값을 정하지 않음 | 개별 request의 최소값 설정 가능 |
| 최대값 설정 | Namespace 전체 합계의 최대값 | 개별 오브젝트의 최대값 |
| 초과 시 | 생성 또는 수정 요청 거부 | 생성 또는 수정 요청 거부 |

---

### ResourceQuota
```
spec:
  hard:
    requests.cpu:"4"
    requests.memory:"8Gi"
    limits.cpu:"8"
    limits.memory:"16Gi"
```

### LimitRange
```
spec:
  limits:
    - type: Container
      min:
        cpu:"100m"
        memory:"128Mi"
      max:
        cpu:"2"
        memory:"2Gi"
```

---

#### 네임 스페이스가 갖고 있는 특징
클러스터를 물리적으로 분할하지 않는다
- 단점
  - 다른 네임스페이스에서 에러나 활동이 현재 네임스페이스에 전달된다
  - 리소스 제한으로 인한 노드 장애
- 해결법
  - ResourceQuota
    - 네임스페이스 자원량을 할당 -> 제한
      - 컨테이너 하나에 제한을 두지는 못했다 -> 해결 -> LimitRange   

---
              
### LimitRange 설정
```
spec:
  limits:
    - type: Container
      min:
        cpu:"100m"
        memory:"128Mi"
      max:
        cpu:"1"
        memory:"1Gi"
      defaultRequest:
        cpu:"250m"
        memory:"256Mi"
      default:
        cpu:"500m"
        memory:"512Mi"
      maxLimitRequestRatio:
        cpu:"2"
        memory:"2"
```

- min: 개별 리소스가 요청해야 하는 최소 기준
- max: 개별 리소스에 설정할 수 있는 최대 기준
- defaultRequest: request를 생략했을 때 적용할 기본값
- default: limit을 생략했을 때 적용할 기본값
- maxLimitRequestRatio: limit이 request의 몇 배까지 가능한지 제한
- type: 규칙을 적용할 오브젝트 종류 (Container, Pod)

---

#### LimitRange가 실제 사용량을 제한하나?
- Limit range < min, max 값이 있음
  - min 값에 있는 request, limit 을 검사
  - max 값에 있는 request, limit 검사
- 스케줄링 할 때 같이 검사를 한다
- 스케줄링 이후에 요청이 스파이크 쳐서 CPU 코어가 조금 넘어갔다 하더라도 갑자기 파드를 종료 시키지는 않는다
- LimitRange <- 범위를 검사하는 용도로만 사용 한다
  - 범위 검사를 스케줄링 할 때 검사
  - LimitRange <- 이미 적용한 상태에서 배포된 파드
  - 파드의 최대 수치를 내려야지 limit 내려야지 -> max 수정

#### 네임스페이스에 여러 개의 LimitRange를 만들면 좋지 않다
- 네임스페이스 여러개를 바라보는 LimitRange 만들 수는 있음
- 어떤 값이 기본으로 설정되는지를 "결정" 하기가 어렵다
- 운영자가 딱 정하기가 어려움
- 네임스페이스 별로 하나씩만 만들어서 사용하는게 좋다

---

#### 💡 정리
- 한 줄 정리: Namespace 안의 개별 컨테이너 나 Pod에 리소스 기본값과 허용 범위를 적용하는 정책
- 적용 범위: 특정 Namespace
- 주요 대상: Container, Pod, PVC
- min: 개별 request의 최소 기준
- max: 개별 limit의 최대 기준
- defaultRequest: request를 생략했을 때 적용되는 기본값
- default: limit을 생략했을 때 적용되는 기본값
- maxLimitRequestRatio: limit과 request의 최대 비율
- 위반 시: 생성 또는 수정 요청 거부
- 기존 Pod: LimitRange 생성, 변경 시 자동으로 수정되지 않음
- ResourceQuota와 관계: ResourceQuota는 전체 총량, LimitRange는 개별 범위

## 4. ConfigMap
> 애플리케이션 코드와 일반 설정값을 분리하여, 동일한 컨테이너 이미지를 환경별로 다르게 실행할 수 있게 해주는 쿠버네티스 리소스

- 동적으로 생성되는 파드들에게 설정 값을 전달해야한다 
- 그때 사용하는 리소스가 ConfigMap (.env, application.yml, parameter store)
- 쿠버네티스 리소스로 관리되는 점이 다르다
  - CICD, env, Dockerfile, Docker compose
  - env들을 1개의 EC2 에 전달하는건 쉽다
    - 2개 이상일 때, 퍼블릭 IP 가 있으면 그냥 Bastion, SSM env 을 만들었다
  - 쿠버네티스는 "여러 개의 서비스가 동작함"
    - 서비스가 필요로 하는 env 값이 다르다
    - 해당 파드가 어떤 EC2에 뜨는지 우리가 알 수 없음
      - affinity < 특정 노드에 특정 파드가 뜨는걸 "선호" 하는 경향을 가지게 할 수 있다
  - 쿠버네티스 리소스를 사용해서 K-V Store 의 형식의 환경 변수를 담는 공간이 필요하다

---

### ComfigMap을 사용하는 이유
#### 1. 애플리케이션 코드 <-> 실행 환경을 분리하기 위해서
ConfigMap의 사용 이유가 아니라 코드 <-> 환경 변수의 분리

#### 2. 설정을 중앙에서 관리할 수 있음
- 쿠버네티스는 파드가 노드에 퍼져서 배포 된다
- 그래서 설정 파일도 같이 퍼져야 하는데 설정을 중앙에서 관리할 수 있도록 하는 용도로 사용한다
- ConfigMap 리소스 만들면 yaml 을 해석해서 master node etcd 에다가 key: value 형식으로 데이터를 저장
- Worker node → Pods 생성할 때 -> kubelet → Kube Server API → etcd
- 워커노드가 몇 번에서 어떤 파드가 뜨든 master node etcd 에다가 쿼리만 하면 설정 값을 가져올 수 있다

#### 3. 쿠버네티스 리소스
- 파라미터 스토어, Github Secrets <- 환경변수 관리하면 새롭게 배포할 때 "배포" 라는 프로세스가 단순하지 않음
  - 시간이 꽤 걸리고, 실패의 가능성, 롤백 대처
- ConfigMap - 파일 마운트 방식
  - 변경된 리소스를 애플리케이션이 감지, 감지하고나서 자동으로 reload 할 수 있음

---

### ConfigMap 어떤 데이터를 저장할까?
- LOG_LEVEL, SERVER_PORT, SPRING_ACTIVE_PROFILE, API_ENDPOINT, Nginx Conf 파일, Redis Conf, Mysql 설정 값
- 공통점
    - 민감하지 않은 데이터를 저장
```
kubectl get configmap -o yaml
# 값이 그냥 보인다
```
- 파드 중에서 과도하게 노출 된 파드가 있고
    - 네임스페이스가 권한 분리 x
    - 같은 클러스터를 사용
    - 과도한 노출의 파드로 접속 → configmap 을 스캔, secret 스캔
- 민감한 값은 → Secret 에 저장

---

### Config Map 데이터 구조
- config map 데이터 저장할 때 data, binary data
- data
```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  SERVER_PORT: "3000"
```

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  default.conf: |
    server {
      listen 80;

      location / {
        proxy_pass http://backend;
      }
    }
```
- binary data
  - UTF-8 ← 글자 입출력 양식
  - 이런 문자열로 표현하기 힘든 값들 Base64 형식으로 저장할 때 사용
      - `아주 작은 이미지`
      - UTF-8 이 아닌 다른 문자열
      - 임의 바이트가 들어있는 설정
          - → Base64 인코딩
              - 특정 문자열로 치환 그 값을 저장
  - ConfigMap ← 최대 크기
      - 1Mib 지정
      - 커지면 볼륨 (PV/PVC), S3 같은 외부 저장소를 고려

### ConfigMap 사용 방법
#### ConfigMap

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  MESSAGE: "Hello from ConfigMap"
```

#### Pod

```
apiVersion: v1
kind: Pod
metadata:
  name: configmap-pod
spec:
  containers:
    - name: express
      image: adapterz/k8s-configmap:latest
      env:
        - name: APP_MESSAGE
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: MESSAGE
```

| 구분 | env | envFrom |
| --- | --- | --- |
| 전달 범위 | 필요한 Key만 선택 | 모든 Key 전달 |
| 환경 변수 이름 | ConfigMap Key와 다르게 지정 가능 | 기본적으로 ConfigMap Key 사용 |
| 설정 가독성 | 어떤 값을 사용하는지 명확함 | 설정이 많을 때 간결함 |
| 권장 상황 | 일부 값만 필요한 경우 | ConfigMap 전체를 사용하는 경우 |

#### 파일 마운트
| 구분 | 환경 변수 | 파일 마운트 |
| --- | --- | --- |
| 적합한 설정 | 짧고 단순한 값 | 여러 줄의 설정 파일 |
| 사용 예 | 포트, 로그 레벨, API 주소 | Nginx, Redis, 애플리케이션 설정 파일 |
| 읽는 방식 | `process.env`, `System.getenv()` | 파일 읽기 |
| 변경 반영 | `실행 중인 컨테이너에는 자동 반영되지 않음` | `마운트된 파일은 일정 시간이 지나면 갱신될 수 있음` |
| 애플리케이션 처리 | 재시작 후 새 값을 읽음 | 파일을 다시 읽는 기능이 필요할 수 있음 |
- 파일 마운트가 볼륨이 갱신되어서 파드 내부에 값이 변경된다 하더라도 그 값이 “즉시” 실행 중인 파드에 적용되지는 않는다.
- 파일 마운트된 볼륨을 누가 감지하나? -> kubelet 이 감지
  - Config Map 수정 → etcd 로 저장
  - API Server 질의 하면 kubelet이 내 노드에 있는 파드들이 사용하는 ConfigMap 이랑 대조를 특정 시간 마다 다른 값을 Pod 에 적용
  - Polling - 특정 시간마다 질의하는 행위

```
metadata:
  name: app-config
  namespace: team-a
  
# 
metadata:
  name: app-config
  namespace: team-b
```

### ConfigMap 말고 다른 방법?
#### 1. Pod Yaml에 직접 기입
설정 <-> Pod Yaml에 붙는다 -> 관리하기 힘들다

#### 2. 도커 컨테이너 이미지에 붙인다
설정값이 바뀌면 도커 파일 재빌드 -> 배포를 다시 해야한다

#### 3. 외부 볼륨에 다 관리
대용량 설정 파일이 필요할 때만 사용하는 경향

#### 4. 외부 설정 관리 시스템
- Spring cloud config
- AWS System Manager -> Parameter Store
- 단점
  - 쿠버네티스 <- CSP에 종속적이지 않으려고 한다

---

#### 💡 정리
- 일반 설정값을 Key-Value 형태로 저장한다
- 환경 변수 또는 파일 형태로 Pod에 전달할 수 있다
- 동일한 컨테이너 이미지를 여러 환경에서 재사용할 수 있게 한다
- Kubernetes API 오브젝트이므로 일반적으로 API Server를 통해 etcd에 저장된다
- Pod가 etcd에 직접 접근하는 구조는 아니다
- 환경 변수로 전달된 값은 실행 중 자동으로 변경되지 않는다
- 볼륨으로 전달한 파일은 일정 시간이 지나면 갱신될 수 있지만, 애플리케이션이 다시 읽어야 실제 동작에 반영된다
- 비밀번호, API Key, 토큰과 같은 민감한 정보는 ConfigMap이 아니라 Secret을 사용해야 한다
- 간단한 설정은 Pod YAML에 직접 작성할 수 있지만, 공유•환경 분리•중앙 관리가 필요하면 ConfigMap이 적합하다

## 5. Secret
> 민감한 데이터를 안전하게 저장하고 Pod에 전달하기 위해 설계된 키-값 쌍 기반의 리소스
- 애플리케이션이 사용하는 데이터를 두 가지로 나눔
  - 일반 설정 값 -> ConfigMap
  - 민감한 설정 값 -> Secret
- 데이터베이스에 접근한다
  - 데이터베이스 주소 -> ConfigMap
  - 데이터베이스 포트 -> ConfigMap
  - 사용자 이름 -> ConfigMap
  - 비밀번호 -> Secret
- 어차피 ConfigMap에 있는거 다 Secret에 있어도 되는거 아닌가?
  - 데이터 성격
    - ConfigMap에서 관리하는 데이터
    - Secret에서 관리하는 데이터
      - LOG_LEVEL, PORT_NUMBER, APIENDPOINT, JWT_SECRET, DB_PASSWORD
      - 전부 다 Secret에 들어가 있다
      - 운영자가 이 목록만 보고 어떤 정보가 민감한 정보이고 어떻게 다뤄야하는지에 대해서 제대로 못다룰 가능성이 커짐

### Secret을 사용하는 이유
> 민감한 값을 애플리케이션 코드와 배포 설정으로부터 분리하여, 필요한 Pod에만 전달하기 위해서

### Secret 기본 구조
```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
data:
  DB_USERNAME: YWRtaW4=
  DB_PASSWORD: cGFzc3dvcmQxMjM0
stringData: 
	DB_USERNAME: charlie
```

---

### data , stringData

- data 
  - 사용자가 값을 직접 base64로 인코딩된 값을 넣는 경우

```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
data:
  DB_USERNAME: YWRtaW4=
  DB_PASSWORD: cGFzc3dvcmQxMjM0
```

- stringData
  - 평문으로 값을 작성 -> 실제 저장될 때 base64 로 저장

```
apiVersion: v1
kind: Secret
metadata:
  name: database-secret
type: Opaque
stringData:
  DB_USERNAME: admin
  DB_PASSWORD: password1234
```

---

#### Secret은 사실 Secret이 아니다

- 시크릿은 저장소가 etcd
- etcd 기본적으로 암호화 저장기능이 디폴트 값이 아니고 그냥 저장된다
- Secret 값을 만들면 → base64 인코딩 → etcd 저장
  - 암호화가 안 돼서 별도로 설정해야 한다
- 데이터 암호화를 별도로 활성화 해줘야한다
    - Encrpytion as Rest

---

### Secret의 타입
#### 1. Opaque
- 일반적인 시크릿 타입
- 특별한 형식 없고, KV 데이터 타입
  - 데이터베이스 비번, API Key

#### 2. kubernetes.io/tls
- TLS 인증서 + 개인키 저장할 때 사용
- 보통은 Ingress 쪽에서 사용
- Reverse Proxy 리소스 쪽에서 사용함

#### 3. kubernetes.io/dockerconfigjson
- Private Registry에 접근할 때 인증 정보가 필요하다
- 인증 정보를 담는 타입

---

### Secret의 한계지점
#### 1. Base64
base64 ← 인코딩 디코딩
    - 암호화 가 아님
- base64 를 사용함 -> 보안 기능이 아님

#### 2. etcd 보안 설정을 추가로 해야함
저장 시 암호화를 해야지만 데이터가 보호된다

#### 3. Kubernetes에 접근 권한 관리가 중요해짐
Secrets 조회할 수 있는 권한이 있으면 평문값이 튀어나온다
- `kubect get secret database-secret -0 json - base64 decode`

#### 4. 비밀번호 교체 자동화가 어렵다
- 현대 웹 환경에서는 민감한 보안 정보를 Rotation 시킨다
- 특정 주기마다 비밀번호를 바꿔서 사용한다

### 실무에서는 Secret 을 어떻게 사용할까

#### Valut 사용함

#### External Secret Operator
- 내부에 있는 Secret을 그 자체로 사용하는 것 보다 외부에 있는 오퍼레이터를 사용하는 경우가 많이 있다

---

#### 💡 정리
- ConfigMap은 일반 설정값에 사용한다.
- Secret은 비밀번호, API Key, 인증서처럼 민감한 값에 사용한다.
- Secret의 Base64는 암호화가 아니라 인코딩이다
- Secret도 API Server를 통해 etcd에 저장된다
- etcd 저장 시 암호화는 클러스터에서 별도로 설정해야한다
    - 환경 변수 또는 파일 형태로 Pod에 전달할 수 있다
    - Secret을 변경해도 환경 변수로 사용 중인 Pod가 자동으로 갱신되지는 않는다
- Secret YAML을 Base64 상태로 Git에 커밋해서는 안 된다
- RBAC, 저장 시 암호화, 로그 관리, 정기 교체가 함께 필요하다
- 실무에서는 Vault, AWS Secrets Manager와 같은 외부 관리 시스템을 사용할 수 있다
- External Secrets Operator는 외부 값을 Kubernetes Secret으로 동기화한다
