## 웹(WEB)

### 웹 1.0
- 시기: 1990년 초반
- 핵심 키워드: 정보 제공, 읽기 전용, 단방향 소통

#### 특징
- 이 시기의 웹사이트들은 주로 정보 제공이 목적
- 사용자들이 웹페이지에 있는 정보를 읽기는 하는데,
- 직접 내용 추가하거나 변경할 수는 없었다

### 웹 2.0
- 시기: 2000년 초반 ~ 현재
- 핵심 키워드: 참여, "공유", 양방향 소통, 사용자 제작 콘텐츠

#### 특징
- 사용자가 단순히 정보를 받아보기만 하지 않음
- 사용자가 정보를 직접 제작하고, 자신만의 콘텐츠를 만들어 공유하는 단계
- 영향: 이걸로 타인과 소통하기 시작함

### 웹 3.0
- 분산형 웹, 지능형 웹
- 시기: 아직 안 옴
- 핵심 키워드: 개인화, 신뢰성, 지능화

#### 특징
- 맞춤형: 인공지능, 머신러닝 등으로 사용자에게 더 개인화된 콘텐츠 전달
- 탈중앙화:
  - 데이터나 리소스가 중앙 집중식 서버가 아닌, 다수의 컴퓨터에 분산되어 저장된다
  - 개인이 자신의 데이터를 관리할 수도 있고, 데이터가 한 곳에 집중되지 않아서 보안성이 좋아진다

### 이걸 왜 알아야 하나
- 우리는 미래의 개발자
- 특징 흐름이 있다

2. 보안 강화
   - 우리가 점점 웹으로 할 수 있는 게 많아짐
   - 웹 = 정보 보는 것(사전), 금융, 자산, 개인정보
   - 보안이 필요한데 기업 입장에서 보안은 효용이 안 남

3. 탈중앙화와 블록체인 기술은 새로운 형태의 애플리케이션과 서비스를 가능하게 한다

## 클라이언트와 서버

### 클라이언트
- 식당에 들어와서 메뉴판 보고 음식을 요청하는 주체
- 기술적 정의: 서비스를 요청하는 단말기 또는 소프트웨어를 의미함
- 사용자와 맞닿아 있어서 기술적으로 유저 에이전트(User Agent)라고도 한다

#### 핵심 역할
1. 요청의 시작점
  - 네트워크 통신은 항상 클라이언트가 먼저 요청하면서 시작

2. 사용자 인터페이스 구현
- 서버가 전달한 데이터를 사용자에게 보여줌

3. 컴퓨팅 자원 사용

#### 실제 기술
- 웹 브라우저(사파리, 크롬)
- 모바일 애플리케이션(카카오톡)
- 기타(CLI)

### 서버
- 제공하는 주체
- 네트워크를 통해 클라이언트에게 서비스나 자원을 제공하는 컴퓨터 시스템이나 프로그램을 의미
- 클라이언트가 언제 요청할지 몰라서 24시간 내내 특정 포트를 열어두고 항상 대기함

#### 핵심 역할과 특징

1. 수동적 대기, 응답
- 서버는 스스로 통신을 시작하지 않는다

2. 비즈니스 로직, 데이터를 처리
- 비즈니스 로직 = 서비스 핵심 비즈니스가 어떻게 동작하는지
- 사용자의 데이터 같은 것들도 처리하는 역할

3. 중앙 집중식 자원 관리 + 보안
- 데이터의 무결성 유지
- 권한이 없는 사용자 접근 통제

4. 실제 예시
- Web Server
    - 클라이언트의 정적 요청을 빠르게 처리하는 서버
- Web Application Server(WAS)
    - 동적인 처리
- Database Server
    - 데이터를 저장하고 관리하는 서버

### 왜 클라이언트와 서버를 나눴을까?
- 원래는 합쳐져 있었다

#### 1970~80년대
- 인터넷 없는 초기 시절
- 이때는 클라이언트랑 서버가 같은 개념
- 컴퓨터가 상당히 무겁고 중앙 집중식 구조였음

1. 메인프레임
- 대부분의 연산을 처리하고 CLI 환경 제공

2. 더미 터미널
- 내부적으로 동작하지 않음

#### 문제점
- 중앙 컴퓨터가 상당히 비쌈
- 병목 현상이 심함

#### 1980년대 후반쯤
- 개인용 컴퓨터가 보급됨
- 개인용 컴퓨터 성능이 생각보다 좋아짐
- 중앙 컴퓨터는 비즈니스 로직, 데이터 로직 처리
- 클라이언트 - 서버 구조 등장

#### 얻은 것
1. 비용 절감

2. 사용자 경험 향상
- 클라이언트는 뼈대를 미리 만들어두고, 서버가 보내는 데이터만 끼워서 표시함

3. 확장성 향상

4. 유지보수 용이

## HTTP (Hyper Text Transfer Protocol)

- 텍스트 = 글자
- 종이책: 우리랑 상호작용하는 글은 아님
- 하이퍼텍스트 = 글을 뛰어넘는 글
- 하이퍼텍스트는 문제가 있다

1. 표현할 게 많다
2. 사람마다 표기법이 다르다

- 앞으로 하이퍼텍스트 전송할 때 약속하자
- HTTP, HTML, CSS, JS, PNG, JPEG <- 이런 구조화된 데이터
- 웹서버와 클라이언트 간 전송할 때
- 앞으로 이렇게 보내자고 정한 약속 = HTTP

### 왜 사용해야 하는 거지?
- 만약 표준 규약(HTTP)이 없다면
- 전 세계 수많은 컴퓨터와 서버들이 각자 자신만의 방식으로 하이퍼텍스트 전송
- 표준화: 전 세계에서 Hyper Text를 동일한 방식으로 처리
- HTTP는 OS 영향을 받지 않음
- 결과적으로 전 세계 공통의 통신 규약이 됨

### 어떻게 사용하는데?
- 클라이언트가 URL로 특정 웹 주소에 요청을 보낸다

## HTTP Message, Method, Status Code
- Request와 Response

### HTTP Message
- 클라이언트와 서버 간에 파일 등을 주고받는 통신의 기본 단위

#### 구조
1. 시작줄
- 어떤 방식으로 시작할지 정의
- 요청인지 응답인지 표시

2. 헤더
- HTTP Message = 편지
- 편지 봉투에 적힌 부가 정보 = 메타데이터

3. 빈 줄
- 헤더랑 본문을 구분하기 위해서 있다
- <특정키워드> CRLF(헤더와 바디를 구분하기 위한 줄바꿈 규칙)

4. 바디
- 편지지에 적힌 실제 알맹이 내용
- 로그인할 때 ID,PW

### HTTP METHOD
- HTTP <- 하이퍼텍스트를 전송하는 규약
- 클라이언트가 서버한테 무언가를 요청

- GET -> 데이터 조회
- POST -> 데이터 생성
- PUT -> 데이터 전체 변경
- PATCH -> 데이터 일부 변경
- DELETE -> 데이터 삭제

#### METHOD를 왜 나눈건가
- 기술은 이유없이 발전하지 않음
-> 이유 없이 복잡해지지 않는다

#### 웹이 커지면서 몇 가지 문제가 생김
1. 당연히 웹은 점점 사용자가 많아졌고 트래픽이 많아짐

2. 보안 문제
- 서버에서는 항상 중요한 데이터를 관리한다
- 서버는 항상 열려있는데 이를 권한이 있는 사람에게만 줘야함

요청을 뜯어보지 않고도 분류하고 안전하게 빠르게 처리하기 위해서 나누는 것

### HTTP Status Code
- 웹 통신 규약에서 요청의 처리 상태를 나타내는 코드
- 클라이언트가 웹 서버에 요청했을 때 통신 결과를 웹 서버가 클라이언트에게 명확하게 전달하기 위해 사용한다

- HTTP 상태 코드를 크게 5개의 번호대로 나뉨
- 1xx : 정보메세지
- 2xx : 성공
- 3xx : 리다이렉션
- 4xx : 클라이언트 오류
- 5xx : 서버 오류

## HTTP URL
- 리소스의 위치와 종류를 나타내는 주소
- 주소 = 어떤 것이 있는 공간, 약속
- 리소스 : 웹에서 제공하는 것

### 구조
#### 스키마
- URL의 첫 번째 부분은 브라우저가 리소스를 요청할 때 사용해야 하는 프로토콜을
#### 도메인, 포트
- 도메인은 요청하는 웹 서버를 나타낸다
- 포트는 웹 서버의 리소스에 접근하는데 사용되는 "게이트"를 나타낸다
#### 리소스 경로
- 폴더 내에 파일과 폴더를 민들 수 있는 것과 같이 컴퓨터의 폴더와 비슷한 개념으로 생각하면 이해에 도움이 
### 매개변수
-웹 서버에 제공하는 추가 매개변수(파라미터) 
‘?’ 뒤에 작성을 하고 ‘&’ 를 사용해 매개변수를 구분한다.

    - 퍼블릭한 세터

5. 테스트 용이성

## 한 줄 정리
- Web : 정보를 공유하고 상호작용하기 위한 인터넷 기반 공간
- 클라이언트 : 서버에 요청을 보내는 주체, 사용자와 맞닿아 있어서 기술적으로 유저 에이전트(User Agent)라고도 한다
- 서버 : 네트워크를 통해 클라이언트 요청에 응답하고 자원을 제공하는 주체
- HTTP : 웹에서 데이터를 주고받기 위한 통신 규약
- HTTP Message : 클라이언트와 서버 간 데이터를 주고받는 통신 단위
- HTTP Method : 클라이언트의 요청 목적과 행위를 나타내는 방식
- HTTP Status Code : 요청 처리 상태를 나타내는 코드
- HTTP URL : 리소스의 위치와 종류(접근 방법)을 나타내는 주소
- Query String : 정렬, 필터링 등 추가 조건 전달 방식
- Path Variable : 특정 자원을 식별하기 위해 사용

## 한 줄 정리 + 사용하는 이유

- RESTful API : 자원을 URI로 표현하는 설계 방식이며, 
 구조가 제각각이면 협업과 유지보수가 어려워지기에 일관성 있는 통신 규칙으로 개발자들의 업무 효율을 높이기 위해 사용한다

- Spring : 자바 개발을 편리하게 사용하기 위한 프레임워크이며, 
기존 자바는 객체 관리와 설정이 복잡하여 생산성과 유지보수성을 높이기 위해 사용한다

- IoC : 객체 생성과 관리를 컨테이너가 담당하는 방식이며, 
개발자가 객체 관리를 직접하면 코드 결합도가 높이지기 때문에 이를 낮추고 구조의 유연성과 테스트를 용이하게 하기 위해 사용한다

- DI : 객체 의존성을 외부에서 주입하는 방식이며, 
객체 간 결합도를 낮춰 변경에 테스트와 확장이 쉬운 코드 유지하기 위해서 사용한다

- POJO : 특정 기술에 종속되지 않은 순수 자바 객체이며, 
특정 프레임워크에 강하게 의존하면 재사용성과 유연성이 떨어지기에 가볍고 유연한 개발을 위해 사용한다

- AOP : 공통 기능을 분리하는 프로그래밍 방식이며, 
중복 코드를 줄이고 비즈니스 로직을 건드리지 않고도 유지보수를 쉽게 하기 위해 사용한다

- Spring Bean : 스프링 컨테이너가 생성하고 관리하는 객체이며, 
직접 객체를 생성하고 관리하면 일관성이 떨어지기에 효율적인 객체 관리와 의존성 관리를 위해 사용한다

- 스프링 컨테이너 : 빈의 생성과 생명주기를 관리하는 공간이며,
객체 생성을 개발자가 직접하면 복잡도가 증가하기에, 객체 관리와 의존성 주입을 자동화하기 위해 사용한다
