## 1. ECR
> Docker 이미지를 AWS 안에 안전하게 저장하고, ECS/EKS/EC2 같은 실행 환경에서 가져다 쓸 수 있 게 해주는 컨테이너 이미지 저장소

AWS에서 제공하는 컨테이너 이미지 저장소 서비스로, 사용자가 직접 서버를 구축하거나 운영하지 않아도 
이미지 저장, 버전 관리, 접근 제어, 보안 스캔까지 자동으로 처리되는 완전 관리형(fully managed) 레지스트리

- AWS에 Docker 이미지 저장소
- AWS 서비스이기 때문에
  - IAM 권한 제어
  - 이미지 스캔 -> 보안 취약점 스캔
  - ECS (컨테이너 실행환경 관리형 서비스), EKS (쿠버네티스 마스터 관리형 서비스)
  - 이미지의 수명주기 관리

---

### 컨테이너의 이미지, 레지스트리, 리포지토리
#### Image
- 도커에서 애플리케이션 실행에 필요한 코드, 라이브러리, 설정 묶은 실행 패키지

#### Registry
- 이미지를 저장하는 저장소
- ECR, Dockerhub, Github container registry

#### Repository
- 특정 이미지를 이름을 기준으로 버전을 모아두는 공간
- Registry 내에 폴더 같은 개념
  - ECR에서 backend Repository 만들면 backend image를 모아둔다

#### Tag
- Image에서 사용하는 태그
- my-backend: 1.0.0
- 같은 이미지에서 버전을 구분하는데 사용한다
  - latest - 가장 최근 태그
  - 1.0.0 - 버전 태그
  - 커밋 SHA 값 태그
- ECR 의 이미지 주소를 보면
```
123456789012.dkr.ecr.ap-northeast-2.amazonaws.com/my-backend:v1.0.0
```
- 123456789012
  - AWS 계정 ID
- ap-northeast-2
  - 리전
- my-backend
  - ECR 리포지토리 이름
- v1.0.0
  - 태그명

---

### 사용 이유
> 컨테이너 이미지를 AWS 환경 안에서 안전하게 저장하고, AWS 서비스가 빠르게 가져와 실행할 수 있도록 하기 위해 사용

- ECR은 AWS 서비스
  - 외부에서 접근할 때 제약 사항
  - IAM 권한, 권한 부여를 해서 특정 행동을 하게 한다
- ECR AWS에 종속 서비스
- 멀티 클라우드 사용한다
- AWS 서비스만 사용한다 -> ECR로 사용할 때 연동성이 더 좋다

#### 1. Docker Image를 보관 하기 위해
- 애플리케이션을 도커로 배포
- 구워져있는 빌드가 되어 있는 이미지가 필요하다
  - 그냥 실행해야하는 인스턴스에 가져온 다음 빌드해도 될까?
```
# EC2 A 접속
git pull origin <- 코드 가져오고
docker build . -t 1.0.0 <- 빌드

# 이렇게하면 굳이굳이 Registry 사용하지 않아도 되지 않나요?

# EC2가 300대면
# 1. 각각 접속해서 깃풀, 도커 빌드
# 2. 빌드해서 SCP 보내기
# EC2 A 에서 빌드 했고
docker build .
# 이 빌드로 만들어진 Docker Image -> SCP 명령어 300대에 전달하면 된다.
# 구찮아..
# 명렁어를 통해서만 해야하니 실수할 가능성이 높다.

# EC2가 300대 -> 300대가 전부다 같은 환경일 수 있나?

# 이미지를 만들었는데, 이미지는 변경 사항이 추적이 가능해야한다.
## 우리가 빌드했던 내역, 성공했던 내역을 관리 해야함. -> 롤백
## 300대 에다가 개당 800MB 하는 이미지를 전부다 내역을 남길 수도 없음
```

- Registry는 회사 내부 이미지를 관리할 때 사용함
  - 회사 내부 이미지 ← 이미지 내에는 외부에 노출하면 안되는 정보
  - 공유할 때, 권한 문제

#### 2. ECS, EC2, EKS 같은 AWS 내부 컴퓨팅 리소스랑 연결하기 위해서
- ECR은 내부 AWS 서비스랑 연결하기가 편하다
  - 비용적으로 저렴
  - AWS는 내부 네트워크 통신 비용 <- 외부 네트워크 비용
  - 이미지 크기가 1.2GB
    - Private Subnet에서 EC2 (WAS)
    - NAT Gateway
      - 컴퓨팅 비용
      - 네트워크 비용

#### 3. 보안 스캔
- ECR은 자동으로 보안 취약점 스캔
- Basic Scanning <- 이미지 올리면 자동으로 해주는 스캐닝
- AWS Inspector
  - 취약점 조사하는 서비스
  - 230개 서비스 중 하나
- 보통 실무에서는 
  - CI-CD 할 때도
    - PR 날릴 때 하는 작업
    - main Branch에서 Image 될 때 하는 작업이 다르다
  - 태그가 배포되는 태그가 아니다
    - Basic
  - 배포 태그다
    - Inspector를 같이 돌린다

### 실무에서 ECR 사용하는 방식
- ECR을 개발자가 직접 push하지 않고 CI/CD 파이프라인에서 자동으로 사용함

### EC2에서 가져온다
- 이미지가 쌓이는 문제
- 중단 배포 문제

### 사용할 때 주의할 점
#### 1. latest <- 태그만 사용하는 거
- 최근 이미지를 가져오니까 논리적으론 맞는 말
- 하지만 명확히 어떤 버전을 배포하고 있는지를 모를 수 있다
- 동시에 많은 개발자가 개발하고 있는 상황에서는 항상 최근 버전이 내가 마지막에 빌드한 버전이라는 보장이 안된다
- 태그명을 Alias
  - 이름 명명 규칙
  - Repository
    - dev-$(commit-sha}
    - prod-${commit-sha}
    - prod-${version}-$(commit-sha}

#### 2. ECR은 "서비스" = 돈이 나간다
- ECR 은 저장소
- 데이터를 저장하고 그 대가로 돈을 받는다
- 우리가 저장하는건 이미지
  - 1.2GB 하는 이미지들을 CI/CD 파이프라인 돌 때 그 때마다 저장된다
- Life Cycle 설정 필수
  - n일 삭제하기
  - 최근 N개 이미지만 보관하기
  - 태그별로 라이프사이클를 분리

#### 3. IAM 권한을 분리해서 주자
- ECR 권한 크게 보면 push, pull
- IAM 전체 권한을 주고 push, pull 할 수 있게 하고
- EC2, ECS, Github Runner
- 실행 서버는 pull
- CICD 서버는 push

#### 4. ECR 로그인은 "영구 로그인" 이 아니다
- Docker Hub <- 한 번 로그인하면 데스크톱이 유지되는 동안 로그인 유지
- ECR CLI Login
  - 인증 토큰 유효 시간 (12시간)
- CI/CD 스크립트에서는 항상 ECR 로그인을 넣어야 한다.

### Private Subnet -> ECR 에 접근하는 방법
- private subnet = 인터넷 연결 없는것
-  ECP = AWS 서비스
   - VPC 안에 없다
   - 연결하려면 인터넷으로 통신을 하긴 해야함
- NAT Gateway 사용할 수 있음
  - 돈이 나가고, AWS 서비스인데 굳이 외부 인터넷?
- VPC Endpoint
  - NAT, 인터넷망 없이
  - AWS 내부망에서 통신

#### 💡정리
- ECR: AWS에서 제공하는 컨테이너 이미지 저장소
- 저장 대상: Docker 이미지, OCI 이미지, OCI 호환 아티팩트
- 주요 역할: 이미지를 저장하고 ECS/EKS/EC2/Fargate에서 가져와 실행하게 함
- 실무 사용 위치: CICD 파이프라인의 빌드 결과물 저장소

## 2. Code Deploy
> AWS에서 제공하는 자동화된 애플리케이션 배포 서비스

- 깃헙 액션에서 배포 하면되는데 왜 굳이굳이 이걸 쓰냐?
- AWS CodeDeploy
  - 어떤 방식으로
  - 어떤 서비스에서
  - 어떤 순서로 배포할거냐?
    - 이거를 AWS 안에서 (반)자동화 해주는 서비스
    - 설정할 게 많다

#### 순서
1. 코드 푸시
2. 깃헙 액션 러너
   코드 풀
   - 2. 테스트 ~ 생략
   - 3. 도커 빌드
   - 4. 도커 ECR Registry에 푸시
   - 5. SSH 직접 접속 배포해야하는 서비스
   - 6. docker pull
   - 7. docker run -d name ~~
   
### Code Deploy를 통해서 할 때
#### 1. 서버가 여러 대일 떄, 반복 문제가 많이 사라진다
- 배포해야하는 타겟이 EC2 10대 정도면 병렬로 처리하는 방법
  - SSH 접속 > 도커 있냐 없냐 > 없으면 설치
- 만약에 VM이 동적으로 만들어지는 상황이면?
  - Auto Scaling Group 설정
  - EC2 2~10대까지
    - 기존에 이미 만들어진 2대는 IP를 알지만 8대는?
      - 배포하는 시점에 IP를 어떻게 알 수 있는지?
      - VM IP는 만들어질 때 할당
        - aws cli 로 가져올 수 있긴 함.
- Deployment Group
  - 마치 Target Group
  - 그룹 기준으로 배포를 실행함

#### 2. 배포 실패 시, 자동 대응이 조금 더 강화
- 배포 실패하면 롤백
  - 헬스 체크
  - 매트릭
- CodeDeploy
  - 이것들은 우리가 설정하는 값
  - 배포 실패했을 때 어떻게 할지, 롤백할지, 어떤 이미지로 롤백할지
  
### Code Deploy 구조
1. Application
- Code Deploy에서 사용하는 배포 단위
  - 백엔드 서비스
  - 프론트엔드 서비스

2. Deployment Group
- 어디에 배포할 지 정하는 그룹
- EC2 배포할 때 EC2를 지정하지는 않는다
  - 보통은 태그를 지정
- K-V Tag
  - key: app
    - value: was
  - key: env
    - value: prod
  - 이런 대상에게만 배포해줘
  - EC2 만들 때, 태그 설정 꼭 해라
  - 배포 대상 서버를 "목록"으로 가지고 있는게 아니라 태그의 조합으로 관리한다

3. Revision
- 배포할 결과물, 버전
- 배포 대상에 따라 결과물
  - EC2 -> S3 zip
  - ECS -> Task Definition + app Spec
- 배포할 패키지

4. AppSpec
- CodeDeploy에서 어떻게 배포를 진행할지 알려주는 배포 설명서
- 우리가 기존에 Github Actions yml 대체
  - Code Deploy

```
hooks:
  BeforeInstall: 기존 앱 정리
  ApplicationStart: 새 앱 실행
  ValidateService: 정상 실행 확인
```

5. Deployment Configuration
- 배포를 어떤 속도 + 어떤 방식으로 할 것인지
- 배포전략
  - Blue/Green
  - 롤링
- 대상마다 지원되는 배포 전략
- AllAtonce → 한 번에 다 배포하기
- OneAtATime → 한 대식 배포
- HalAtATime → 절반씩 배포하기

### Github Actions vs CodeDeploy
| 구분 | GitHub Actions | CodeDeploy |
| --- | --- | --- |
| 성격 | 범용 자동화 도구 | AWS 배포 자동화 서비스 |
| 주사용 | 테스트, 빌드, 스크립트 실행, 외부 도구 연결 | EC2/ECS/Lambda 배포 관리 |
| 배포 전략 | 직접 구현해야 함 | AWS 배포 전략을 설정으로 사용 |
| AWS 연동 | Credentials 설정 필요 | AWS 서비스와 네이티브 연동 |
| 적합한 사용 | 간단한 배포, 전체 워크플로우 제어 | AWS 리소스 대상 안정적 배포 |

- 실무에서는 이 둘을 같이 사용한다
  - Github Actions -> Git Trigger를 통해서 CI 과정
    - image build
  - CodeDeploy
    - AWS 배포

### 단점
#### 1. 설정한게 많은데 분리가 되어있다
- 시간이 많이 걸린다
- Github Actions -> CD.yml 작성
- 설정해야하는 것들
  - IAM
  - Role
  - AppSpec - 배포 정차 정의
  - Deployment -  배포 할 대상 타겟
  - Agent - 
    - EC2에서 Code Deploy 돌아가려면
    - 미리 Code Deploy Agent 설치
    - Agent가 설치되어 있는 AMI를 사용하는 경우가 많은데
  - ECR, S3도 설정해야한다

#### 2. Agent 문제
- EC2에 에이전트를 설치해야하고
- 에이전트가 항상 실행 중이여야 코드 배포가 된다
  - 관리 포인트가 늘어나는 것
  
### 장점
1. CD 장점 
2. 배포 전략을 직접 구현하지 않아도 된다
3. 표준화 되어 있다
4. 배포 타이밍 조절도 우리가 직접 설정하지 않아도 된다
5. EC2 같은 동적 자원에 배포하기 편하다

### 언제 Code Deploy를 선택하는가?
1. EC2 배포를 표준화 하고 싶다
   - 1. 수동 ssh 배포를 안하고싶다
   - 2. 왜냐면 실수할 수 있기 때문에
2. 여러 EC2가 동적으로 생기고 삭제되는 환경
3. AWS 중심으로 CD 가 동작한다
4. 배포 전략을 좀 더 다양하게 선택할 때
