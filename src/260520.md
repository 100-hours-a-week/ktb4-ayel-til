## OOP
객체 지향적 설계를 의미한다
지향한다 != 해야한다 = 하면 좋다, 하고싶다
- OOP 스럽게 개발하려면, 개발이 복잡해짐
  - 정말 간단한 개발도 OOP스럽게 개발하면 상당히 복잡해짐
  - 모든 개발이 대규모로 발전되나? 그건 아니다
  
### OOP란
현실 세계의 객체 개념을 기반으로 데이터를 속성(필드)과 기능(메서드)로 묶어 
프로그램을 설계하는 패러다임
-> 만약에 코드가 10만줄이여도, 내가 칼퇴할 수 있을까?

#### OOP를 안 쓰면 어떻게 될까
- 절차지향적 <- 코드가 순서대로 동작하는걸 의미
- 순서대로 동작하는 코드는 필연적으로 서비스 규모가 커지면 유지보수하기 힘들다
  - 유지보수라고 하는건, 유지하고 보수한다
  - 이미 프로젝트는 동작하고
  - 이미 유저는 10만 명 정도가 되고
  - 이미 기능들은 여기저기 붙어있다
  - 여기에서 새로운 기능 추가하고, 기존 기능 수정, 삭제
- 결제 기능을 처리하는 코드가
  - "결제 엔진을 변경해주세요" 라는 요청
  - OOP
    - 결제 로직 자체가 여기저기에 함수로 흩어져있다
    function paymentStart() {}
    function orderComplement() {}
    - 결제 엔진을 변경하려고 한다. 그러면 주문, 배송, 장바구니, 결제 전부 다 고쳐야 함
    - 내가 고치고 싶은건 그냥
      - 네이버 -> 카카오
      - 이 변경이 내가 고친 코드가 아니라 다른곳까지 영향을 줘서
      - 작업시간이 길어진다
    - 데이터, 로직 분리되어 있고, 
    절차지향 프로그램은 a->b->c 기능들이 서로 연계되어 있어서 서로 영향을 받는다

#### OOP가 뭔가요
누가 이 일 책임질래? 라는 기준으로 나눈 프로그래밍 기법
- 프로그래밍을 일의 처리 순서가 아닌
- 역할과 책임을 가지고 있는 주체(객체)들의 협력으로 바꾸는 것
- 객체에 대해서 잘못 알고 있는 데이터
  - 데이터를 담고 있는 상자 <- 설계 하신 분들이 많음
    - 커피 객체, 상속 받는 아이스아메리카노
      - 아이스 아메리카노는, 커피객체랑 다른게 온도 밖에 없다
    - 객체는 "자신의 역할이 있고, 그걸 책임지는 주체다"

##### OOP를 적용하지 않은 코드

    public class Car {

        private int speed = 0;

        public void start() {
            System.out.println("엔진 시동");
        }

        public void accelerate() {
            speed += 10;
            System.out.println("속도 증가: " + speed);
        }

        public void stop() {
            speed = 0;
            System.out.println("브레이크 작동");
        }
    }

##### OOP를 적용한 코드

    public class Engine {
        public void start() {
            System.out.println("엔진 시동");
        }
    }
    
    public class Brake {
        public void apply() {
            System.out.println("브레이크 작동");
        }
    }
    
    public class Car {

        private final Engine engine;
        private final Brake brake;

        public Car(Engine engine, Brake brake) {
            this.engine = engine;
            this.brake = brake;
        }

        public void start() {
            engine.start();
        }

        public void stop() {
            brake.apply();
        }
    }

#### 스프링 부트에서도 OOP는 적용되어 있는데
- 스프링 부트도 계층 구조에도 적용되어 있는데
  - controller - 요청 흐름 책임
  - service - 비지니스 로직
  - repository - 데이터 접근 책임


#### OOP 알아야 하는 이유
- 대규모 서비스를 안정적으로 유지보수 할 수 있게 하는 프로그램
- 스프링, 스프링부트는 OOP 규칙을 잘 지킬 수 있게 도움
- OOP에서 중요한 것은 객체는 "내가 이 일을 책임지는 주체다" 라고 이해하기

## SOLID가 뭐냐
- 유지보수성 + 확장성 높이려고 만든 다섯가지 핵심 원칙
  - S (SRP) - 단일 책임 원칙 -> 클래스를 수정해야 하는 이유는 한 가지다
  - O (OCP) - 개방-폐쇄 원칙 -> 확장은 열어두고, 기존 코드 수정은 닫아라
  - L (LSP) - 리스코프 치환 원칙 -> 자식 클래스는 언제나 부모 클래스를 대체할 수 있어야 한다
  - I (ISP )- 인터페이스 분리 법칙 -> 내가 안쓰는 거대한 인터페이스보다, 쪼개진 인터페이스를 쓰자
  - D (DIP) - 의존관계 역전 -> 구체적인 것에 의존하지 말고, 추상적인 것에 의존하라

## SRP (Single Responsibility Principle)
내가 만든 클래스는 "몇 가지 이유로 수정될 수 있느냐?" 라는 질문에
우리가 만든 클래스는 "한 가지 이유로만 수정되어야 한다" 라는 원칙이다
- 객체 지향에서 "객체"라는 애가 -> 책임을 가지는 주체라고 이야기
  - 엔진 -> 바퀴 동력 전달
    - 동력 전달의 방식 변경됨
          - -> 수정
      - 브레이크 방식이 변경됐는데, 그 변경이 내가 만든 엔진 클래스까지 변경해야하는 경우
    
  

### SRP 원칙을 적용하면 얻는 것
- 수정 범위 최소화
- 가독성
  - 코드를 눈으로 이해할 수 있다

### 그러면 모든 코드를 다 찢어야 하나?
- 그건 아니다
  - 설계는 정답이 없다
  - 팀이 다르고, 구성원이 다르고, 제품의 고객이 다르고, 고객 수가 다르고
  - 프로젝트의 중요도 다르고

## OCP (Open Closed Principle)
소프트웨어의 기능 확장은 열려 있고, 기존 코드의 변경은 닫혀 있어야 한다는 객체지향 설계 원칙

### 기존 코드를 건드리지 않고, 기능을 추가해야한다
- Open(개방) -> 새로운 기능을 추가하거나 확장에는 항상 열려 있어야 한다
- Closed(폐쇄) -> 그로 인해서 기존 코드가 수정되는 것에 닫혀 있어야 한다
  - 새 기능 넣을 때, 이미 잘 돌아가는 옛날 코드는 손대지 마라

#### 예시
- 컴퓨터를 사용할 때
  - 마우스를 바꿀 때, 어떻게 바꾸나?
    - 그냥 마우스 포트 뽑아서, 다른 마우스를 포트에 낀다.
  - 마우스를 바꿔야하는데
    - 본체 뚜껑열고,
    - 메인보드에 cpu 떼서
    - 마우스를 교체한다.
  - 새로운 기능을 추가해도, 내부에 있는 다른 코드, 로직을 수정하지 않는다

### 실무에서 OCP 원칙이 중요한 이유
- 내가 개발하지 않은 코드가 프로젝트 안에 99%가 넘는다
- 나는 그저 30만줄 코드 중에 내가 개발한건 300줄,
  - 300줄에서 30 줄을 추가함
- 다른 코드에 영향을 줄 수 있음

## LSP (Liskov Substitution Principle)
자식 클래스는 언제나 부모 클래스를 대체할 수 있어야 한다는 객체지향 설계 원칙

### 사용이유
- Spring Boot에서 상위 타입을 기준으로 작성된 코드가 구현체 교체나 확장에도 흔들리지 않도록, 
구조적 신뢰성과 안정성을 보장하기 위해서
- 실무 관점에서 LSP는 변경 비용과 장애 위험을 직접적으로 줄임

### 사용방법
자식 클래스가 부모 클래스의 동작 규칙과 의미를 그대로 따르도록 구현하여, 대체 가능한 구조를 유지

---

## ISP (Interface Segregation Principle)
클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다는 객체지향 설계 원칙

### 사용이유
- Spring Boot에서 각 계층의 클라이언트가 자신에게 필요한 기능에만 의존하도록 만들어, 
불필요한 결합과 변경 전파를 구조적으로 차단하기 위해서
- 실무 관점에서 ISP는 변경 범위를 통제하는 역할

### 사용방법
- 하나의 인터페이스에 여러 기능을 담지 않고, 역할에 따라 작고 명확한 인터페이스로 분리

---

## DIP (Dependency Inversion Principle)

상위 모듈(정책을 결정하는 코드)이 하위 모듈(세부 구현 코드)에 직접 의존하지 않고, 
양쪽 모두 추상화(인터페이스나 추상 클래스)에 의존해야 한다는 객체지향 설계 원칙

Q: 비즈니스 핵심 규칙 (pay, start, drive, stop), 세부기술(데이터베이스,엔진 부품)이 변경된다면, 
비즈니스 핵심 규칙이 변경되어야 할까요?
- 엔진은 동력 바퀴에 전달한다 ← 핵심 규칙 ← 상위모듈 (부모 클래스)
  - 가솔린 → 전기 모터 ← 세부 기술 ← 하위 모듈 (자식 클래스)

### - 실무에서의 예시
- 파일 저장소 객체를 OCP, DIP 원칙 적용하면
- 파일을 저장한다 ← 라는 원칙만 인터페이스로 만들고
    - 파일을 로컬에 저장한다 ← 라는 구현체가 코드로 만들어지고
    - 클라우드에 저장해라 ← 인터페이스를 바라보는 구현체로 만들면된다.

## JVM
자바 바이트코드를 실행하고 메모리를 관리하는 가상 머신

### 사용이유
JVM을 사용하는 이유는 자바 애플리케이션을 운영체제와 무관하게 동일하게 실행할 수 있다.

### 구성
1. 자바 소스 코드 작성 (.java)
- 개발자는 일반적인 텍스트 형식의 .java 파일로 자바 소스 코드를 작성한다.

2. 컴파일 단계 (javac 사용)
- 작성된 소스 코드는 javac 명령어를 통해 컴파일된다.
- 이때 생성되는 결과물은 바이트코드

3. 클래스 로더 (Class Loader)
   1. Loading
   - 프로그램 실행 필요한 .class 파일을 
     - 메서드 영역에 올리기
     - JVM에 가져오는 역할을 한다.
     
   2. Linking
  - 로딩된 클래스가 실제로 사용되기 전에, JVM은 해당 클래스가 올바르게 정의되어 있는지 확인하고 실행에 필요한 준비 작업을 수행
  -  Verifying, Preparing, Resolving 세 단계로 나뉜다.

   3. Initializing
   - 클래스의 static 변수들이 실제 코드에 정의된 값으로 초기화


#### 특징
  - 자바는 프로그램 시작할 때 모든 파일을 한 번 불러오지 않는다
    - 30만 개 클래스가 있다
    - 필요할 때 (Runtime) <- 필요한 파일을 찾아서 메모리에 올린다

4. 실행 엔진 (Execution Engine)
- 클래스 로더에 의해 메모리에 적재된 바이트코드를 실제로 실행하는 핵심 구성
- 인터프리터 방식과 JIT 컴파일 방식이라는 두 가지 실행 전략을 병행하여 프로그램을 수행
- 바이트 코드를 기계어로 바꿔주는 일

5. Runtime Data Areas
- 메서드 영역
  - 모든 스레드가 공유하는 구조로, 
  자바 프로그램의 클래스 구조와 실행 로직에 대한 핵심 정보
- 힙 영역
  - JVM이 실행 중 동적으로 생성하는 객체들을 저장하는 메모리 공간으로, 
  메서드 영역과 함께 모든 스레드가 공유
- 스택 영역
  - JVM이 메서드를 실행할 때 사용하는 임시 저장 공간으로, 기본형 변수나 메서드 실행 정보 등이 저장되는 곳
- PC 레지스터
  - 현재 해당 스레드가 실행 중인 JVM 명령어의 주소를 저장
- 네이티브 메서드 스택
  - 자바 코드가 아닌, C, C++, 어셈블리 등 다른 언어로 작성된 네이티브 코드를 
  실행하기 위해 사용되는 별도의 스택 메모리 영역
