## 1. kubectl 명령어

### kubectl
- 쿠버네티스 Server API 명령을 전달
- 클러스터 리소스 조회, 명령 같은 것들 전달

#### 기본적인 명령어 구조
``` 
kubectl [동작] [리소스] [리소스 이름] [옵션]

# 예시
kubectl get pods -o wide
kubectl describe pod express-pod -o wide -l app,env
```

---

| 전체 이름 | 축약형 | 의미 |
| --- | --- | --- |
| `pods` | `po` | Pod |
| `nodes` | `no` | Node |
| `services` | `svc` | Service |
| `namespaces` | `ns` | Namespace |
| `deployments` | `deploy` | Deployment |

나중에는 커스터마이징하는 축약어를 쓴다!

## 2. Pod
> 하나 이상의 컨테이너를 그룹화하여 실행 환경과 네트워크 자원, 스토리지를 공유하는 가장 작은 배포 단위

- 쿠버네티스에서는 컨테이너를 워커노드에 직접 배포하지 않는다
- 컨테이너를 Pod라는 실행단위로 감싸고 Pod를 워커노드에 배치한다

---

### 사용 이유 
1. 일관된 실행 환경 제공
2. 컨테이너 간의 상호작용
3. 공유 네트워크와 스토리지 자원
4. 단순화된 배포 프로세스
5. 플랫폼 간 이식성

---
### Pod 필요한 이유
컨테이너로 실행하면 안되나?

---

#### 노드와 Pod의 관계
- 워커 노드 : Pod가 실행되는 공간
- 쿠버네티스는 컨테이너를 가축으로 취급한다
- 컨테이너 때는 EC2에 이름을 붙였지만
- 쿠버네티스는 EC2에 이름이 아닌 역할(워커)과 숫자를 붙였다
  - 워커에는 어떠한 컨테이너도 들어올 수 있다
- 워커 1 -> 백엔드 컨테이너 직접 실행
  - 컨테이너가 1개일 때는 동작할 수 있다
  - 실행해야하는 최소한의 컨테이너 개수가 2개 이상일 때부터 문제가 생긴다
- 최소한의 "배포" 단위가 필요하다
  - 컨테이너가 "자동"으로 배치되길 바란다
  - 자동으로 배치되려면 최소한 뭐가 있어야 동작한다는 정의가 필요
  - 그래서 컨테이너를 "Pod" 라는 단위로 감싼다

#### Pod와 컨테이너
- Pod 안에 `nginx-container, backend-container`
- 보통 실무적으로는 보통 Pod 하나에, 컨테이너 하나를 두는 경우가 많다
- Pod는 컨테이너보다 한 단계 밖에 있다
  - Pod 자체가 애플리케이션을 실행하지 않음
  - 실제 애플리케이션 컨테이너 실행
  - Pod는 쿠버네이스의 관리

---

### Pod를 쓰면 얻는 것
- 컨테이너 하나만 쓰는 경우가 많은 굳이 Pod를 쓰면 얻는게 있다
- Pod 내부 컨테이너들 끼리는 이런 것들을 공유한다
  - 네트워크, IP 주소, 포트, 볼륨, 생성 주기
- 통신 중에서 가장 빠른 통신 = 로컬 호스트 통신
  - 만약에 Container -> 다른 컨테이너랑 통신을 해야한다

---

### Pod의 네트워크

#### 1. Pod 마다 IP가 할당된다.
쿠버네티스에서는 일반적으로 Pod 별로 IP를 할당한다

#### 2. 같은 Pod의 컨테이너는 IP를 공유
하나의 Pod에 만약에 여러 컨테이너가 있다면, 그 컨테이너들을 동일한 네트워크 공간을 공유
- 로컬호스트 통신이 가능한게 장점이나, 동일한 포트를 사용할 수 없다

---

### Pod 볼륨
- Pod에는 내부 컨테이너들이 접근할 수 있는 볼륨을 연결
- 이 볼륨은 내부 컨테이너 전부가 접근할 수 있다
- 메인컨테이너가 볼륨 작성한 값을 헬퍼 컨테이너가 읽을 수 있다
- 중앙 집중형 로깅 시스템
  - 메인 컨테이너 -> BE Container
    - 요청이 들어오면 볼륨에다가 로그를 남기고
  - 헬퍼 컨테이너
    - 특정 주기마다 쌓여진 로그를 중앙 집중 로그 저장소에 보내는 역할

---

### Pod 유형

### 1. Pod 1 (단일 컨테이너)
- 단일 컨테이너 구조
- 실무적으로 가장 흔한 구조
- 가장 쿠버네티스의 장점을 많이 가져가는 구조
```
frontend-pod
└── frontend-container

backend-pod
└── backend-container

database-pod
└── database-container
```

#### 왜 이렇게 분리해서 넣을까?
- 어플리케이션 파드
    ```
    application-pod
    ├── frontend-container
    └── backend-container
    ```
#### 무슨 문제가 생길까?
- 장애 파악이 힘들다
- 독립적으로 확장이 불가능하다
  - 쿠버네티스의 배포 단위 ⇒ `“파드”`
  - 스케일 아웃 → 처리량 더 필요해서 컨테이너를 늘려야 하는 상황
      - 애플리케이션 파드를 늘려야 한다
      - 실제 필요한구성
          - FE Container → 3개
          - BE Container → 10개
      - 애플리케이션 파드라면
          - FE Container → 10개 (7개) 필요 없는 자원
          - BE Container → 10개
---

### 2. Pod 2 (컨테이너 + 볼륨)
- 사이드카 패턴
- Pod에는 여러 컨테이너를 넣을 수 있다
- 보통 비즈니스 로직같은 컨테이너는 하나만 두는 경우, 보조 기능 컨테이너를 같이 넣는 경우가 있다
  - 로깅, 포맷팅
- Pod 2~4 -> 멀티 컨테이너

#### 멀티 컨테이너 패턴 주의 해야하는 사항
- 파드 안에서는 네트워크 공간, 볼륨 공유 한다
  - 포트 충돌, 볼륨에 대한 충돌, 생명 주기가 항상 길다
    - 우리의 트래픽이 스파이크 형태의 트래픽 -> 파드가 빠르게 늘어나고, 빠르게 제거
      - 멀티 컨테이너 파드에서 외부 의존성이 없어서 메인 비즈니스 로직 파드는 실행 되고 끝나고 빨리 실행
      - 헬퍼 컨테이너는 외부 의존성이 있어서 실행하기 까지 한참 걸리고 끝날 때도 의존성이 다 종료되어야 프로세스가 끝난다

---

#### 3. Pod (여러 컨테이너)
- 두 개 이상의 컨테이너 
- 동일한 IP 주소 공유

#### 4. Pod4 (복잡한 구성)
- 여러 개의 컨테이너 + 스토리지 볼륨,
- 동일한 IP 주소


--- 

### Pod는 일시적인 리소스다 ⭐️

파드는 언제든지 삭제되고, 언제든지 다시 만들어질 수 있다
- 파드는 영구적으로 유지되지 않는다
  - 사용자가 delete 치면 날아가고
  - 워커 노드가 장애가 발생하면, 파드 종료
  - 컨테이너가 반복 장애 파드 종료
  - 상위 관리 리소스에서 새로운 파드로 교체
  - 노드 유지 보수
  - Auto Scaling 이 걸릴 때 
    - 처리량이 많이 필요해서 pod를 늘렸다
    - 필요 처리량이 줄면 파드를 지움
- 쿠버네티스는 애초에 파드를 가축처럼 다룬다
    - 뭔가 장애나면 고치려고 안하고 그냥 죽인다
    - 새롭게 처리량이 필요하면 기존 파드 추가 자원 할당 하지 않고 새로운 파드를 만든다

---

### 새로 생성된 파드는 다른 파드다
- 새롭게 파드가 만들어져도
- 똑같은 이미지, 똑같은 라벨, 똑같은 규칙 적용해도
  - 이전 파드랑 완전히 다른 존재
- 새로운 파드
  - Pod 고유 식별자, IP 주소, 실행되는 워커 노드도 다를 수 있다
    • Pod 1 → node A
    • Pod 2 → Node A B → Node C
  - 내부에 있는 볼륨도 다르게 쓴다
  - 컨테이너가 가지고 있는 임시 쓰기 레이어

#### 주의 사항
- 파드 내부에 중요한 데이터를 저장하시면 안된다 
- Pod 요청 고정 Ip로 하면 안된다 ⭐️

### 파드 YAML 구조
일반적으로 쿠버네티스의 대부분 자원들은 다 YAML 파일로 관리

```
apiVersion: v1
kind: Pod

metadata:
  name: express-pod

spec:
  containers:
    - name: express-container
      image: adapterz/k8s-pod:latest
      ports:
        - containerPort: 3000
```

- apiVersion
  - 쿠버네티스 Docs API 버저닝
  - pod -> v1 버전
- kind
  - 쿠버네티스 리소스 종류
  - pod
- metadata
  - name: express-pod
  - 리소스 식별할 때 사용하는 공간
- spec
  - 파드가 어떤 모습으로 실행해야하는지 정의함
  - 파드 내부에서 실행해야하는 컨테이너, 이미지, 포드 등의 정보를 작성
- containers
  - 파드 내부에서 실행할 컨테이너 목록
  - container.name
    - 컨테이너 이름
  - container.image
    - 컨테이너가 사용할 이미지
  - container.ports
    - 포트 정보

## 3. Label

### Label
- 흔히 라벨, 태그 중요도가 낮음
- 쿠버네티스에서는 라벨이 상당히 중요하다

> 쿠버네티스 오브젝트에 붙이는 키-값 형태의 이름표

- 키 값 형태로 붙이는 메타데이터
- 라벨 사용하면 애플리케이션, 역할, 실행 환경, 버전 <- 이러한 기준으로 쿠버네티스 오브젝트를 구분할 수 있다

### 사용 이유
> 쿠버네티스는 리소스를 동적으로 생성한다. 그리고 그 동적으로 생성된 리소스들은 IP를 별도로 가진다. 
리소스의 이름이 아닌, 속성으로 관리하기 위해서 사용

- Pod <- IP, 식별자는 고정되지 않는다
- express 파드가 만약에 10개로 늘어나면, IP도 10개로 늘어나고, 예측하거나 고정시킬 수 없다
- 그런데 만약에 요구 사항으로 express 서비스에서 백엔드 서비스를 V1인것들을 v2로 업데이트 요청
  - express 서비스에서 백엔드 컨테이너를 가지고 있으면서 v1인 파드를 찾아야 한다

### 라벨 구성
- 키 값
```
key=value

env=production

metadata:
	labels:
		env: production
		app: community
```

---

### 실무에서 많이 차용하는 라벨
#### 1. app
- 리소스가 어떤 애플리케이션 속해 있는지를 구분

#### 2. tier
- 애플리케이션 내부에서 어떤 게층에 속해 있는지 나타낸다
  - frontes, backend, data
- layer

#### 3. env
- 어떤 실행환경에 속하는지 나타내는 것
- env
  - dev, staging, production
- 클러스터 구성을 
  - 하나의 클러스터에서 여러 네임 스페이스를 구분
    - 한 개의 클러스터
  - 여러 클러스터에서 여러 네임스페이스 (분리된 공간)

#### 4. version
- version=v1
- version=v2
- version =1.0.1

---

### Label은 어디에 붙이는가?
- 라벨은 파드에서 사용하는게 아님
- 라벨은 쿠버네티스 오브젝트
  - Pod, Node, Service, Configmap, Secret, Namespace 
  
---

### 실무에서 라벨 잘 사용하기
#### 1. 라벨명이 명확해야 한다
- type -> ?
- 명확하게 의미를 전달할 수 있어야 한다
  - 라벨은 보통 팀 단위의 공유
  - 같은 클러스터를 사용하면, 다른 팀의 라벨도 같이 보임

#### 2. 라벨명은 규칙을 정해놓고 사용하는 것이 일반적
- app
- application
- service
- 하나의 명명 규칙을 정하고 그걸 다같이 따르는 형식으로 한다

#### 3. 변할 수 있는 상태를 라벨로 지정하지 않는다
- cpu-usage <- 변함
- instance-id <- 변함
  - 변해도 가끔 변하는 것들은 라벨로 붙일 수 있다
  - 너무 자주 변하면 굳이 라벨로 붙이지는 않는다

## 4. Selector
> 라벨을 기준으로 조건에 맞는 쿠버네티스 오브젝트를 선택하는 방법
- 라벨을 오브젝트 붙이고 그걸 선택할 때 사용하는걸 셀렉
- 라벨: 리소스에 이름
- 셀렉터: 라벨을 기준으로 리소스를 선택한다

### 사용하는 이유
- 라벨이랑 같은
- 쿠버네티스 리소스는 동적으로 생성, 삭제
- IP, 식별자가 동적으로 움직이기 때문에 특정 식별자를 유지할 수 없다
  - 그래서 라벨의 조합으로 유지
- 파드 생성 -> 이름, IP가 변경
  - 특정 파드의 이름, IP 지정 불가능
  - 라벨로 지정한다

### 셀렉터의 주요 특징
- 라벨 기반으로 선택
- 동적 갱신 
  - 라벨을 붙인 파드가 새롭게 늘면 셀렉터의 결과 동적으로 갱신
  - 조건에 맞는 리소스가 생성, 삭제 -> 선택 결과도 자동으로 바뀐다
- 여러 조건 사용
  - AND 사용하는게 디폴트
- 리소스를 연결할 때 많이 사용한다.
  - Service < 쿠버네티스에서 Domain 역할을 해주는 리소스
  - 연결할 때도 기본으로 셀렉터를 사용함
