## 1. Controller
> 클러스터의 현재 상태를 지속적으로 모니터링하고, 사용자가 정의한 목표 상태와 일치하도록 조치를 취하는 자동화된 관리 루프

### 컨트롤러가 없으면
- 지금까지 파드로 작업을 수행
  - 파드 안에 컨테이너 배치 -> 파드를 직접 생성하고, 수정하고, 삭제하는 동작
- 파드는 일시적인 리소스
- 애플리케이션 내부에서 오류가 발생하거나, 노드가 죽거나, 업데이트 되거나 등 파드는 항상 교체되거나 삭제되는게 기본 값
- 이런 파드를 직접 생성하면 사라진 후 직접 만들어야 하고 사라진걸 모른다
- 파드를 자동으로 다시 만들어줄 상위 관리자가 없는 상태
```
Pod 직접 생성
->
Pod 장애 또는 삭제
->
Pod가 사라진 상태로 유지
->
운영자가 직접 다시 생성
```

컨트롤러가 수동 관리 문제를 해결햠
```
Controller 생성
->
Controller가 Pod 상태 확인
->
Pod 장애 또는 삭제 감지
->
새로운 Pod 자동 생성
->
**사용자가 지정한 상태 유지**
```
현업에서도 k8s 사용한다 -> 파드를 직접생성 하지는 않음
- Deployment, StatefulSet, Job, CronJob
- 컨트롤러가 파드를 관리하게 된다

---

### Controller 정의
> 클러스터의 현재 상태를 확인하고, 사용자가 선언한 목표 상태와 일치하도록 필요한 작업을 수행하는 제어 루프
- 컨트롤러 이해하기 위해서는 원하는 상태랑 현재 상태를 알아야 한다

```
spec:
  replicas: 3 # 파드가 복제본이 3개 있는 걸 원함
```

---

#### Desired State (원하는 상태)
- 운영자가 원하는 상태
- 컨트롤러 yaml 파일에 적어둠 `spec.replicas: 10`
- 클러스터 내에 목표로 하는 최종 상태

#### Current State (현재 상태)
- 클러스터에 실제로 존재하는 상태
- 원하는 상태, 현재 상태 일치하지 않음
- 컨트롤러가 이 상태 감지하고, 파드를 추가함

```
원하는 상태: Pod 3개
현재 상태: Pod 2개
ControlLer가 차이 감지 -> Pod 1개 생성
현재 상태: Pod 3개
```

---

#### Control Loop
- Reconciliation

#### ‼️ 컨트롤러는 리모컨 
- 온도 변화에 따라서 동작 수행
- 온도를 내리거나 바람을 키우거나, 사용자가 희망 온도로 주변 온도 맞추려고 함
- 컨트롤러도 k8s에서 같은역할 수행

---

### Controller 의 핵심 역할
#### 1. 원하는 상태를 유지
파드를 만들라는 일회성 명령 x
- 앞으로도 클러스터 내에 해당 파드를 3개로 "유지" -> 선언적 명령
- 파드가 하나 삭제되면 컨트롤러가 제어 루프로 감지 -> 다시 원하는 상태로 맞춘다

#### 2. Auto Healing (자동 복구)
- 파드는 리소스가 중지되거나, 실패한다 (liveness probe)
- 정상 상태가 아니여서 삭제된 파드가 있고, 그걸 감지하는 컨트롤러가 다시 원하는 상태로 만들기 위해서 다시 파드를 생성 자동 복구

#### 3. 자동 확장 축소
사용자가 원하는 Replicas의 숫자를 변경
- 자동으로 파드를 늘리거나 줄임

```
replicas: 3
->
replicas: 5로 변경
->
Controller가 Pod 2개 추가 생성
```

#### 4. 쿠버네티스의 “선언적” 관리
#### 명령형 방식

```
Pod을 하나 생성한다
Pod이 죽으면 다시 생성한다
Pod 수가 부족하면 추가한다
Pod 수가 많으면 삭제한다
-> 상황에 따라서 명령을 직접 내림
```

#### 선언형 방식

```
파드가 3개면 좋겠네
```

사용자가 원하는 최종 상태만 적기 때문에 이후의 생성, 삭제, 복구 작업은 컨트롤러가 알아서 함
- 운영자는 상태를 정의만 하면 되고 k8s 시스템이 알아서 그 상태를 맞춰간다
    - 대규모 컨테이너 오케스트레이션 (3천개)

---

#### Pod <-> Controller 차이

| 구분 | Pod 직접 생성 | Controller로 Pod 관리 |
| --- | --- | --- |
| Pod 생성 | 사용자가 직접 생성 | Controller가 `Pod 템플릿`으로 생성 |
| Pod 삭제 시 | 그대로 사라짐 | 새로운 Pod 자동 생성 |
| 복제본 유지 | 지원하지 않음 | 지정한 수량 유지 |
| 확장·축소 | Pod을 직접 추가·삭제 | 목표 수량만 변경 |
| 장애 복구 | 운영자가 직접 처리 | Controller가 자동 처리 |
| 운영 적합성 | 단순 테스트·학습 | 지속적으로 운영할 애플리케이션 |

---
### Controller Yaml
#### Pod Template
```
spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

Pod Template: 컨트롤러가 새로운 파드를 만들 때 사용하는 설계도
- replicas: 유지할 Pod의 수
- selector: Controller가 관리할 Pod을 찾는 조건
- template: 새로운 Pod을 만들 때 사용할 설계도

`Selector -> 관리 대상 Pod 검색 -> 현재 Pod 수 확인 -> Pod 부족-> Template을 사용하여 새 Pod 생성`

---

#### Label, Selector가 중요함 ⭐️
- 컨트롤러는 모든 파드를 관리하지 않음
- 자기가 label 로 관리할 파드의 라벨들을 모아두고 셀렉터로 그 라벨들이 있는 파드를 검색

---

#### Controller가 직접 수행하는 것과 요청하는 것
- 컨트롤러가 모든 작업을 직접 수행하지 않음
- 컨트롤러는 주로 API Server 통해서 클러스터 상태를 확인
- 필요한 리소스를 생성, 수정, 삭제를 "요청"한다

```
사용자
  ↓ YAML 적용
API Server
  ↓ 상태 저장
etcd
  ↑
Controller
  ↓ 필요한 변경 요청
API Server
  ↓
새로운 리소스 생성 또는 수정
```
- 컨트롤러가 API Server에게 요청 -> 현재 상태를 확인하고 파드가 부족하면 새 파드 생성 요청

- 파드는 Pod Template을 보고 "이렇게 만들어주세요"라고 API Server에게 요청
  - Scheduler가 현재 노드 상태를 확인하고 배치할 노드 선택
    - API Server를 통해 etcd의 노드 상태 확인
    - API Server → 워커 노드의 kubelet에게 생성 명령 전달
      - kubelet → Container Runtime에게 컨테이너 생성 요청
        - Container Runtime → 컨테이너 생성 및 실행
---

### Controller 종류
- ReplicaSet: 지정한 수의 동일한 Pod 복제본 유지
- Deployment: ReplicaSet을 관리하며 배포, 업데이트, 롤백 수행
- StatefulSet: 고유한 이름과 스토리지가 필요한 상태 기반 애플리케이션 관리
- DaemonSet: 조건을 만족하는 각 노드에 Pod을 실행
- Job: 완료를 목적으로 하는 일회성 작업 실행
- CronJob: 정해진 일정에 따라 Job을 반복 실행

관리 대상이나 목적이 다를 수 있는데 기본 원리는 똑같다

`원하는 상태 선언 -> 현재 상태 확인 -> 두 상태 비교 -> 차이가 있다면 조정`

---

#### Stateless 한 애플리케이션 관리

- WAS Pod
- k8s를 사용한다 = 서비스 규모가 커짐
    - 트래픽 변동 폭이 큼
        - DAU 100 → 300
        - DAU 30K → 300K
    - WAS 처리량이 급격히 증가할 수 있음

- 일부 파드에 장애 발생
  - 리소스 문제: 로그 과다 적재, 메모리 부족
  - 애플리케이션 문제: 데드락(Deadlock), 커넥션 점유, DB 커넥션 끊김

---

#### 💡 정리
- 컨트롤러 → 현재 상태를 원하는 상태와 일치시키는 자동 관리 장치
- 현재 상태랑 다르면?
  - 제어 루프에서 주기적으로 현재 상태 ↔ 원하는 상태 비교
  - 다르면 수정, 삭제, 생성하는 동작 수행 `“요청”`
  - Control Loop - Reconciliation
- 관리 상태를 Label, Selector을 통해 찾는다.

## 2. Controller - ReplicaSet
> 라벨 셀렉터로 관리할 Pod을 찾아, 사용자가 지정한 개수의 Pod가 항상 실행되도록 유지하는 Controller

```
원하는 상태: Pod 3개
현재 상태: Pod 3개
        ↓
Pod 하나 삭제
        ↓
현재 상태: Pod 2개
        ↓
ReplicaSet이 차이 감지
        ↓
새로운 Pod 1개 생성
        ↓
현재 상태: Pod 3개
```

---

### ReplicaSet을 언제 사용할까?

#### Stateless Application
ReplicaSet이 컨트롤 하는 대상을 정할 때 Label ← Selector 로 확인한다
- replicas로 정한 숫자와 비교만 하기 때문에 `Stateless Application` 일 때만 ReplicaSet을 사용한다 (WAS)
      
#### YAML 구조

```
apiVersion: apps/v1
kind: ReplicaSet

metadata:
  name: web-replicaset

spec:
  replicas: 3

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: web
          image: nginx:1.27
          ports:
            - containerPort: 80
```
---

### 라벨 사용 시 주의점
#### 1. 기존 Pod들도 관리 대상이 될 수 있다
```
apiVersion: v1
kind: Pod
metadata:
  name: existing-pod
  labels:
    app: web
spec:
  containers:
    - name: web
      image: nginx:1.27
```

이후에 ReplicaSet 을 만들었는데

```
selector:
  matchLabels:
    app: web
```

기존에 있는 파드들도 관리 대상으로 들어간다
- 발생 원인은 컨트롤러는 “라벨”만 봄
- 주의해야하는 이유: 컨트롤러는 삭제되면 관리하고 있는 파드들도 같이 삭제함
- Nginx ← LB, RP
    - app: web
- Nginx ← Blue, Green 배포 할 때 스위치 → 컨트롤러
    - app: web
- 블루그린 배포를 떼어내고 → 롤링배포

---

### ReplicaSet 한계
- ReplicaSet Pod의 복제본 수 유지에만 관심
- WAS -> 버전 업데이트

```
# image: nginx:1.27 
image: nginx:1.28
```

- ReplicaSet
    - Pod Template → 복제본의 수를 바라보고 있다
    - 기존에 실행 중이던 파드들도 “복제본 수” 포함
- 업데이트를 하고 싶다
    - image 만 바꾼다고 해서 복제본이 자동으로 다음 버전으로 재배포되지 않는다
    - 새롭게 만들어지는 파드들의 버전을 업데이트
    - 현재 동작하고 있는 파드들을 “업데이트” 하지 않음
- 파드는 계속해서 생성되고 삭제된다 -> 생성과 삭제 조건을 운영자가 직접 컨트롤 하기 힘들다
- 애플리케이션을 운영하는 경우에는 ReplicaSet 이 갖고 있는 “복제본 수” 컨트롤 기능만으로는 부족
    - 새로운 버전 배포
    - 기존 Pod과 새 Pod의 점진적 교체
    - 배포 진행 상태 확인
    - 이전 버전으로 롤백
    - 배포 이력 관리
        - → Deployment Controller
            - 내부적으로 ReplicaSet 을 갖고 있는데 배포 관련된 기능을 추가한 ReplicaSet
                - Deployment Controller 를 사용함
                    - pod.yaml ← 사용할 일이 없다

```
Deployment
    ↓ 배포 관련 된 관리
ReplicaSet
    ↓ 복제본 수 관리
Pod
```

- Deployment: 애플리케이션의 배포와 업데이트 관리 
- ReplicaSet: 지정된 수의 Pod 유지 
- Pod: 실제 컨테이너 실행 

---

### 헷갈릴 수 있는 부분
#### 1. ReplicaSet 이 파드를 수리한다? ❌
오토 힐링? -> 수리하지 않는다
- 쿠버네티스는 "수리하지 않음" 파드 = 가축
- 파드가 오류가 나면 삭제하고 재생성
- 파드가 사라지면 필요한 복제본 수 만큼 생성을 요청

#### 2. ReplicaSet -> 파드가 부족할 때만 동작한다? ❌
ReplicaSet 복제본 수를 맞추는거지 늘리는 것만 하지 않는다 (제거도 함)

#### 3. Probe랑 Controller가 같은 역할을 하나? ❌
- Probe -> Container 레벨 복구
- Controller -> Pod 레벨 복구
  - Pod 삭제 -> 새로운 Pod 생성
- 보통은 같이 사용한다
- Controller로 Pod 레벨 복구, Probe로 Container 레벨의 복구

#### 4. ReplicaSet이 트래픽을 분산하는가? ❌
Label -> 매치되는 파드를 보고 복제본 수가 부족하면 만드는 거 뿐
- template > label : app: web
- ClusterIP Service
  - label -> Endpoint Slices
    - label : app:web

---

#### 💡 정리
- ReplicaSet이란? -> 지정된 수의 Pod 복제본을 유지하는 Controller
- 원하는 Pod 수는 어디에 작성하는가? -> spec.replicas
- 관리할 Pod은 어떻게 찾는가? -> spec.selector와 Pod Label
- Pod이 부족하면 어떻게 하는가? -> spec.template으로 새 Pod 생성
- Pod이 많으면 어떻게 하는가? -> 초과된 Pod 제거
- 삭제된 Pod 자체가 복구되는가? -> X. 새로운 Pod이 생성됨
- 트래픽을 분산하는가?	-> X. 트래픽 전달은 Service의 역할
- 실무에서 직접 사용하는가? -> 일반적으로 Deployment를 통해 간접적으로 사용

## 3. Controller - Deployment
> ReplicaSet을 관리하여 Pod의 개수뿐 아니라 애플리케이션의 배포, 업데이트, 롤백까지 자동으로 관리하는 상위 Controller
- ReplicaSet <- 같은 Pod 개수를 유지하는 컨트롤러
- Deployment <- ReplicaSet 이용하고 + 배포, 업데이트, 롤백을 자동으로 관리하는 컨트롤러
  -  podyaml, replicaset yaml으로 만들지 않고 deployment.yaml 이 파일 하나로 만든다

### RelicaSet → Deployment
```
원하는 Pod 수: 3개
현재 Pod 수: 2개
->
ReplicaSet이 Pod 1개 생성
->
Pod 3개 유지
```

- 특정 파드의 개수를 유지하는거는 적합
- 애플리케이션은 버전 업데이트
- ReplicaSet < 개수를 유지하는건 가능한데, 배포 작업을 편리하게는 하기 어렵다
  - 기존 Pod과 새로운 Pod을 어떻게 교체할 것인가?
  - 모든 Pod을 한 번에 교체할 것인가?
  - 서비스 중단 없이 순차적으로 교체할 것인가?
  - 새로운 버전에 문제가 생기면 어떻게 이전 버전으로 돌아갈 것인가?
  - 현재 배포가 어느 정도 진행되었는지 어떻게 확인할 것인가?
    -> Deloyment가 해결해준다
> Pod과 ReplicaSet의 생성, 업데이트, 확장, 복구 과정을 선언적으로 관리하는 Controller
- Deployment가 파드를 직접 관리하진 않고 실제 구조적으로는
  - Deployment
    - 배포 관련 컨트롤러
    - ReplicaSet
      - 복제본 컨트롤러
        - Pod Template
          - Pod
            - Container
            
---

### Deployment 를 별도로 사용하는 이유
ReplicaSet 관심사는 파드 복제본의 개수만
```
v1 애플리케이션 실행 중 -> 새로운 기능 개발 -> v2 이미지 배포 -> 기존 Pod을 v2 Pod으로 교체

# 직접 한다면?
1. v1 ReplicaSet 축소
2. v2 ReplicaSet 생성
3. v2 ReplicaSet 확장
4. 배포 상태 확인
5. 문제 발생 시 v1 복구

# Deployment 는 이 과정을 자동화 

1. Deployment의 이미지 버전 변경 (yaml)
deployment.yaml 적어 놓은걸 k8s 에서는 Desired state 
원한 상태가 v1 지금은 원하는 상태가 v2 로 변경
현재 상태 v1 -> v2 로 변경하려고 하는 것
->
2. Deployment가 새 ReplicaSet 생성
->
3. 새 ReplicaSet 확장
->
4. 기존 ReplicaSet 축소
->
5. 새로운 버전으로 교체
```

---

#### Deployment 를 사용하면 해결되는 것들

| 운영 문제 | 해결 방법 |
| --- | --- |
| Pod을 여러 개 유지해야 함 | ReplicaSet을 통해 복제본 유지 |
| 새로운 버전을 배포해야 함 | 새로운 ReplicaSet 생성 |
| 서비스 중단을 줄여야 함 | RollingUpdate로 순차 교체 |
| 배포에 문제가 발생함 | 이전 Revision으로 롤백 |
| Pod 수를 변경해야 함 | `replicas` 값을 변경해 확장·축소 |
| 배포 진행 상태를 확인해야 함 | Rollout 상태 제공 |
| 이전 버전 기록이 필요함 | 이전 ReplicaSet을 Revision으로 보관 |

### Deployment 의 생성 흐름
사용자 deployment.yaml 파일을 만들고 apply 명령

```
1. 사용자가 Deployment 생성
->
2. Deployment가 ReplicaSet 생성
->
3. ReplicaSet이 Pod 생성
->
4. Pod 내부에서 컨테이너 실행
```

deployment 를 사용하면 아래 명령어로 이런 일들이 벌어진다

```
Deployment: web-deployment

        └── ReplicaSet: web-deployment-7f8b9c
                  │
                  ├── Pod: web-deployment-7f8b9c-a1b2c
                  ├── Pod: web-deployment-7f8b9c-d3e4f
                  └── Pod: web-deployment-7f8b9c-g5h6i

# 현업에서는 deployment만 사용한다
```

### Depolyment 로 업데이트 하기
#### 이미지 버전 업
변경된 yaml 파일을 apply 하면 deployment 가 pod template 에 있는 변경을 확인
```
기존 Template
limage: nginx:1.27
    
새로운 Template
image: nginx:1.28
```

템플릿 안에 내용이 변경되면 deployment는 새로운 ReplicaSet 을 생성

```
Deployment
   ├── 기존 ReplicaSet: nginx:1.27
   └── 신규 ReplicaSet: nginx:1.28
```

---

#### 템플릿이 변경되면 항상 ReplicaSet 이 새롭게 만들어지나요?
- Deployment yaml이 어떤거든 변한다 하더라도 항상 새로운 ReplicaSet이 만들어지지는 않는다
- 핵심 기준은 Pod Template 이 변경 되었는가?
  - 컨테이너 이미지 변경, 환경 변수 변경, Pod Label 변경, ConfigMap 또는 Secret 참조 변경, Volume 설정 변경, Probe 설정 변경, 리소스 requests와 limits 변경
- 복제본 수는 레플리카셋에 영향을 주지 않는다 (replicas 3 → 5)
  - 기존 레플리카셋을 유지하고 replicas 에 맞게 복제본만 조정

---

#### Deployment 배포전략
- RollingUpdate: 기존 Pod과 새로운 Pod을 점진적으로 교체
- Recreate: 기존 Pod을 모두 삭제한 후 새로운 Pod 생성

---

### RollingUpdate
> 기존 Pod을 한 번에 모두 종료하지 않고, 새로운 Pod으로 조금씩 교체하는 배포 전략

```
기존 버전 Pod
v1  v1  v1
        ↓
새 Pod 하나 생성
v1  v1  v1  v2
        ↓
기존 Pod 하나 제거
v1  v1  v2
        ↓
반복
v1  v2  v2
        ↓
배포 완료
v2  v2  v2
```

#### RollingUpdate YAML

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deployment

spec:
  replicas: 3

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1

  selector:
    matchLabels:
      app: web

  template:
    metadata:
      labels:
        app: web

    spec:
      containers:
        - name: web
          image: nginx:1.28
```

#### `maxSurge`
업데이트 중에 원하는 복제본 수를 초과해서 추가로 생성할 수있는 파드의 수를 의미함

```
기본 replicas : 3
maxSurge: 1

->
롤링 업데이트 중에는 파드의 최대 개수를 4까지 허용

기본 replicas : 3
maxSurge: 2

->
롤링 업데이트 중에는 파드의 최대 개수를 5까지 허용
```

#### `maxUnavailable`
업데이트 중 사용할 수 **없는** 상태를 허용하는 최대 파드 수를
```
기본 파드가 3이고
maxUnavailable: 1
-> 
업데이트 중에는 최소한 2개 이상은 사용이 가능해야한다.
```

### Rolling Update 동작 예시

```
replicas: 3
maxSurge: 1
maxUnavailble: 1

---초기 상태

v1 replicaset : 3개

v2 replicaset : 0개

-- v2 로 yaml 파일 변경

v1: 3개
v2: 1개

maxSurge: 1 -> 4개까지 파드를 허용
--
v2 파드가 준비가 되면

v1: 2개
v2: 1개

maxUnavailble: 1 <- 실패

-- 이 과정을 반복

v1: 1
v2 : 2

v1: 0
v2: 3

--
업데이트가 완료
```
---

#### Rolling Update가 항상 무중단이 될 수 있을까?

- 그렇지는 않음
    - Rolling Update는 서비스 중단을 **줄이는** 전략
    - 무조건 무중단이 되는 것은 아님

- 무중단 배포를 위해 필요한 조건
    - 새로운 Pod이 정상적으로 실행되어야 함 → `Probe 설정`
    - 애플리케이션이 요청을 받을 준비가 되어 있어야 함 → `Probe 설정`
    - Readiness Probe가 적절히 설정되어야 함 → `Probe 설정`
    - Service가 정상 Pod에만 요청을 전달해야 함 → `Probe 설정`
    - 기존 버전과 새로운 버전이 동시에 동작할 수 있어야 함
        - 데이터베이스 스키마가 양쪽 버전과 호환되어야 함
        - v1, v2를 동시에 운영할 수 있어야 함

- 클라이언트 버전 관리
    - 앱 버전에 따라 v1 API 또는 v2 API를 호출할 수 있음
    - 시간이 지나도 일부 사용자는 업데이트하지 않음
        - 예) 2주 내 80% 업데이트
        - 예) 1년이 지나도 약 5%는 업데이트하지 않음
    - Minimum Version을 지정하여 관리
        - Current Version: `23.0.1`
        - Minimum Version: `22.0.5`
        - Minimum Version 미만은 업데이트를 유도하고 메인 콘텐츠 접근을 제한

### Recreate
> 기존 파드를 다 날리고, 새로운 파드를 생성하는 배포 전략

```
기존 상태
v1  v1  v1
        ↓
기존 Pod 모두 삭제
-   -   -
        ↓
새로운 Pod 생성
v2  v2  v2
```

서비스 중단 당연히 생김

```
spec:
  strategy:
    type: Recreate
```

#### Recreate 를 고려하는 경우
- 개발 또는 테스트 환경
- 짧은 서비스 중단이 허용되는 환경
- `두 버전이 동시에 실행되면 안 되는 애플리케이션`
- 동일 리소스에 대한 동시 접근이 허용되지 않는 경우
- `기존 버전을 완전히 종료한 뒤 새 버전을 실행해야 하는 경우`
    - 라이브 게임

#### Revision
- Deployment의 변경 이력(버전)
- Deployment가 변경될 때마다 새로운 Revision이 생성됨
- 이전 Revision으로 Rollback 가능

- 사용 이유: 변경 이력 관리, 문제 발생 시 이전 버전으로 복구

#### Rollout
- Deployment를 새로운 버전으로 배포하는 과정
- 새로운 Pod를 생성하고 기존 Pod를 점진적으로 교체

- 사용 이유: 애플리케이션 업데이트, Rolling Update 진행, 배포 상태 확인 및 Rollback 수행

---

#### Deployment 에서 확인해야하는 항목
- READY: 준비된 Pod 수 / 원하는 Pod 수
- UP-TO-DATE: 최신 Pod Template으로 생성된 Pod 수
- AVAILABLE: 사용 가능한 상태의 Pod 수
- AGE: Deployment가 생성된 이후 경과 시간

#### Deployment 사용 하면
#### 1. ReplicaSet 이 복수개가 남아 있는 경우

```
kubectl get rs

NAME                        DESIRED   CURRENT   READY
web-deployment-7f8b9c       0         0         0
web-deployment-84d7f6       0         0         0
web-deployment-95e8a7       3         3         3

// 여러분들이 업데이트
// 새로운 ReplicaSet 를 만들고
// v2 옮겼다고 하더라도
// 기존 RS를 바로 삭제하지 않는다.

```

#### 실무에서 Deployment 사용하기
#### 1. Stateless App = Deployment 사용해야함
- WAS, WS, FE 서버, auth 서버 
- ReplicaSet ← Deployment

#### 2. 이미지 `latest` 태그를 사용하시면 “안된다”
- sha, semantic version (v1.0.3), digest 사용

#### 3. Controller ↔ Probe 랑 같이 사용해야 한다
- 가용성
- 복제본으로 안정성
- Pod는 새롭게 만들어지는데
    - Spring Container ← 준비될때까지 시간이 걸리는 편
    - Readiness Probe

#### 4. 배포 상태 확인
- YAML 이 정상적으로 변경되어도 항상 배포가 성공하지는 않는다
- 배포 하고나서 헬스체크를 잘 걸어두셔서 probe 를 설정하거나
    - `kubectl rollout status deployment/web-deployment`

#### 💡 정리

- Deployment란?: ReplicaSet을 관리해 애플리케이션의 배포와 업데이트를 자동화하는 Controller 
- Deployment가 직접 관리하는 주요 리소스는?: ReplicaSet 
- ReplicaSet은 무엇을 관리하는가?: Pod 
- ReplicaSet과 가장 큰 차이는?: Deployment는 업데이트, Rollout, 롤백을 관리 
- 이미지가 변경되면 어떻게 되는가?: 새로운 ReplicaSet을 생성하여 Pod을 교체
