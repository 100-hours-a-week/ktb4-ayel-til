## 1. Lambda
> 서버를 직접 관리하지 않고 코드만 실행할 수 있는 서버리스 컴퓨팅 서비스

#### 서버리스
- 서버가 사라진게 아니라, 서버 운영의 상당 부분을 AWS가 책임지는 방식
- 람다는 함수 코드 작성, 이벤트 트리거 연결, IAM 권한 설정만 하면 AWS가 알아서 관리한다

### EC2 vs Lambda
#### 1. EC2
- 서버를 켜 두는 방식, 사용자가 요청을 하면 켜져 있는 서버가 응답한다
- 사용자 요청이 없어도 켜져 있어서 시간당 과금

#### 장점
- 서버는 이미 켜져 있으니, 바로 응답
- 서버 내부 상태를 (디스크, 파일) 상대적으로 관리하기 쉽다.
- 필요한 라이브러리 자유롭게 사용할 수 있다.

#### 단점
- 요청이 없어도 비용이 발생한다

#### 2. Lambda
- 지정한 특정 이벤트가 발생하는데 그때 람다 실행
- 일정 시간이 지나면 사라진다

#### 장점
- 코드가 돌아가는 실행 시간만큼만 비용을 지불한다
- "코드" 단위의 실행이라 확장성이 좋다

### 사용 이유
1. 인프라 관리 불필요
2. 비용 효율성
3. 자동 확장성
4. 빠른 개발 및 배포
5. 이벤트 기반 실행

### 실행 방식
#### 이벤트
- 람다는 “누군가 버튼을 누르면 실행되는 코드” 라고 생각할 수 있다.
- 람다는 다양한 이벤트로 실행될 수 있다

### 실행 순서
1. 이벤트 발생

2. 람다가 실행 환경 준비
- 코드를 실행함 = 컴퓨팅 필요
- 실행될 격리된 공간을 준비한다 (함수)
- 실행 환경에 포함되는 것
  - 설정한 메모리, CPU 자원, Runtime, 함수 코드, /tmp 임시 저장소, 환경 변수

3. Init 단계
- 초기화 코드들이 실행되는 단계
  1. 함수 코드 + Lambda layer 다운로드
  2. Runtime 초기화
  3. 핸들러 밖에 작성한 코드들로 초기화

4. Invoke 단계
- 초기화 끝내고, "핸들러" 호출
- 코드 블럭이 실행이 끝나면 람다는 특정 대기 시간동안 이 실행환경을 유지한다

### Cold Start vs Warm Start
#### Cold Start
- 새 실행 환경을 만들고 Init 단계까지 수행한 뒤 요청을 처리하는 경우
- 실행 환경이 준비되어 있지 않아서, 환경을 준비하고 핸들러를 호출하는 경우
- 환경을 준비하는 시간이 걸리기에 요청 처리 시간이 상대적으로 길다

#### Warm Start
- 기존 만들어진 실행환경을 재사용하는 경우
- 실행 환경이 있으니 init 단계를 건너 뛴다
- 상대적으로 요청 응답 시간이 짧다

##### ‼️ 실행 환경 한 번 만들고 계속 키면?
- 컴퓨팅 자원을 오랫동안 들고 있으면, 그만큼 과금이 된다. (EC2 보다 비쌈)
- 해결: 람다 안에 설정(Warming UP)하면 특정 시간마다 헬스 체크 요청을 보낸다

### 언제 쓰는게 좋은지
1. 파일 업로드 처리
- 프로필 사진 리사이징, 이미지 형태 변환, 업로드 파일 바이러스 검사

2. 극초기 API
- 맨 처음부터 유저도 없는데 굳이 EC2에 올려야 할까?
- 사실 API는 Lambda와는 잘 맞지 않는다.
- 웜업 기능을 사용하지 않으면 자원을 잃는다
- 클라이언트가 응답을 기다리고 있기 때문에 API는 요청 응답 시간이 중요하다.

3. 예약 작업 (배치작업)
- 매일 새벽, 임시 데이터 삭제 등

4. 비동기 작업 처리
- 주문 생성
  - 주문 API는 먼저 응답한다.
  - 주문 정보를 큐에 저장한다.
  - 람다가 큐를 수신한다.
    - 이메일 발송, 통계 갱신 등을 비동기로 처리한다.

#### ⭐️ 람다는 상태를 오래 저장하지 않는다
- 람다는 기본적으로 짧은 작업에 적합하다.
  - 람다 함수 실행
    - 이벤트 처리 끝나면
    - 특정 시간 대기 후
    - 자원을 반납
    - 저장공간 
- 실행 환경 재사용 될 수 있으나 여기에 저장된 값은 언제가 사라진다
  - 전역 변수, /tmp
- 오래 저장되어야 할 상태가 필요하면 외부 저장소 사용

#### 람다 설정
1. 메모리
- 람다에서는 메모리가 늘어나면, 자동으로 CPU 할당도 늘어난다
  - 처리 속도를 빠르게 하고 싶어서
- 메모리를 낮게 설정하면 실행 시간이 길어져서 비용이 더 나올 수도 있다

2. 타임 아웃
- 람다 함수가 최대 얼마 동안 실행될 수 있는지 정하는 설정 (실행될 때, 실행이 몇 초까지만 된다)
- ‼️ 람다 함수는 15분 이상 실행되지 않는다
- 람다 사용할 땐, 작업에 따라서 타임아웃 설정을 매우 잘 해야함 ⭐️

#### 실무에서 잘 사용하기
##### 1. 함수 하나에 하나의 원칙만 둔다 (SRP)
- 무조건 평선 다 쪼개지 말고 독립적인 처리가 필요한 경우에 그걸 기준으로 함수를 쪼갠다

##### 2. Cold Start 대응하기
1. 애초에 실행 환경 무거운 코드 안쓰기
- 자바, Spring Boot, 의존 라이브러리 X

2. 프로비저닝 (Provisioned Concurrency)
- 람다 실행환경을 미리 준비해두는 것
- 람다 환경 <- 서버리스 + 동시성

3. 헬스체크
- 프로비저닝 보다 훨씬 더 원시적인 방식
- 이벤트 브릿지 <- 이벤트를 발생시키거나 수신해서 전달
  - N초마다 람다 함수 안에 헬스체크 평선을 만들어서 람다 환경이 죽지 않도록

#### 3. 동시성 문제 해결
- 람다는 limit까지 자동확장
- 람다가 RDS 연결 요청하면 동시에 수많은 요청이 들어와서 DB, RDS, WAS 처리 불가능
- 문제 해결 방식: 중간에 큐를 둔다

#### 4. 장기간 연결해야하는 요청 피하기
- 람다는 최대 15분까지 실행된다

#### 5. 람다를 모든 백엔드 기능의 서버로 두면 안된다
- 모든 API는 항상 람다랑 어울릴 수 없다
- 데이터베이스 연결을 지속적으로 해야하는 작업이 많기 때문에

---

#### 💡 정리
- Lambda: 이벤트가 발생할 때 코드를 실행하는 서버리스 컴퓨팅 서비스 
- Serverless: 서버가 없는 것이 아니라 서버 운영을 AWS가 대신하는 방식 
- Trigger: Lambda를 실행시키는 이벤트 소스 
- Handler: 이벤트를 받아 실제 로직을 처리하는 함수 
- Timeout: 함수가 실행될 수 있는 최대 시간 
- Concurrency: 동시에 실행되는 Lambda 수 
- Cold Start: 새 실행 환경 초기화로 첫 요청이 느려질 수 있는 현상
- /tmp: 임시 저장소이며 영구 저장소가 아님

## 2. API Gateway
> 클라이언트와 백엔드 서비스 사이에서 API 요청을 관리·변환·보호해주는 완전관리형 서비스

#### 백엔드 서비스가 커지면 생기는 문제
- 백엔드 하나에서 모든 요청을 처리한다
- 서비스가 커지면 API의 기능도 해야하고 공통 문제도 해결해야한다
- 백엔드는 비즈니스 로직을 처리 해야하고 동시에 API의 입구 역할을 같이 함

### API Gateway
- 설정된 규칙에 따라서 적절한 요청만 백엔드에 전달한다.
- API 요청에서 공용 출입구를 관리해주는 서비스
  - API 요청을 "공통" 기능을 대신 해주고 요청을 분리해주는 역할을 한다
- 여러 서버 요청을 나눠주는 것만 하는게 아닌 API를 안전하게 공개하고 관리하기 위한 서비스다

#### 사용 이유
##### 1. API의 입구를 하나로 줄이기 위해서
- 우리의 서비스는 백엔드가 하나다
- 서비스가 커지면 하나의 서버스에 여러개의 백엔드가 붙는다

MSA
- 맨 처음에는 하나의 커다란 코드
- 서비스가 커지면 필요한 기능을 별도로 분리하고, 각 서비스에 맞는 DB와 언어를 사용할 수 있다

##### 2. 인증 인가 분리할 때
- 분리된 코드들은 전부다 "인증 인가" 코드가 있다
- 모든 분리된 코드는 전부다 인증인가 기능을 구현한다
  - 인증 인가에 기능 변경
- API Gateway <- 인증 인가를 책임 전가

##### 3. 요청 수 제한 API Key 컨트롤
- 외부에 우리 APi 를 제공한다

##### 4. CORS도 중앙 관리
- 분리된 프로젝트에서 CORS 기능이 다 중복이 되는데, 이를 API Gateway에서 관리할 수 있다

##### 5. API Gateway -> Lambda 같은 AWS 서비스를 직접 호출할 수 있다

### 유형
- HTTP API: 단순하고 비용 효율적인 HTTP API
- REST API: 기능이 많고 세밀한 제어 기능
- Websocket API: 양방향 실시간 연결

#### API Gateway vs ELB
- 둘 다 요청을 받아서 백엔드 전달
- 주된 목적이 다르다
  - API Gateway는 API 관리해주는게 목적
  - ELB는 여러 서버에 트래픽 분산시키는게 목적

## 3. CloudTrail
> AWS 계정에서 발생하는 모든 API 호출과 콘솔 활동을 자동으로 기록하고 추적하는 서비스

### 사용 이유
1. 보안 감사
2. 컴플라이언스
3. 문제 해결 및 운영 개선
4. 운영 투명성 및 변경 관리

## 4. CloudWatch
> AWS 리소스와 애플리케이션에서 발생하는 로그, 지표, 이벤트를 수집·모니터링하는 통합 관제 서비스

### 사용 이유
1. 리소스 성능 모니터링 및 최적화
2. 문제 감지 및 자동화된 대응
3. 중앙화된 로그 관리 및 분석
4. 데이터 시각화 및 통합 뷰 제공
5. 비용 관리 및 최적화

서비스 장애 발생 시 보고 받는 형식인데, CloudWatch는 이런 문제를 먼저 감지하려고 한다

#### 목적
"장애를 더 빨리 발견, 복구하기 위해서" = 서비스의 안정성을 높이기 위해 = DevOps의 주된 목적

#### DevOps에서 모니터링이 왜 중요한가
모니터링은 운영의 선택 사항이 아니라 기본 장치다

### 핵심 기능
- Metrics: 시간에 따른 숫자 지표를 확인하는 기능 
- Logs: 시스템과 애플리케이션의 로그를 저장하는 기능 
- Alarms: 조건을 만족하면 알림을 보내거나 자동으로 대응하는 기능 
- Dashboards: 여러 지표를 한 화면에서 확인하는 기능 
- Logs Insights: 로그를 쿼리로 검색하고 분석하는 기능

#### 1. Metrics
- 시간에 따라 변하는 숫자 데이터(ex.CPU 사용률)

#### 2. Logs
- 로그는 "왜 생겼냐"를 기록 하게 된다
- CloudWatch 로그는 로그를 "중앙 집중화" 할 수 있다.
- 로그를 한 곳에 모으니, 확인하기 좋다

#### 3. Alarms
- 특정 조건이 일정 시간 유지될 때, 운영자에게 알림을 보내는 기능
- 알람은 "이상한 일이 생겼다"< X
  - 지금 당장하지 않으면 큰일난다
  - 알람은 자주 울리면, 무신경해진다.

### 옵저빌리티 ⭐️
> 옵저빌리티는 시스템 내부를 직접 열어보지 않아도, 시스템이 밖으로 남기는 메트릭 로그 트레이스를 통해 "무슨 일이 일어났고 왜 일어났는지" 추론할 수 있는 능력

#### 왜 필요할까?
- 서버가 적으면 SSH로 확인하면 된다.
- 서버가 많아지면 SSH만으로는 관리하기 어렵다.
- 여러 서버와 계층의 상태를 한 번에 확인하기 위해 필요하다.

#### 목적
옵저빌리티는 장애를 추측으로 해결하지 않고, 데이터로 원인을 좁혀 나간다

### 모니터링 - 옵저빌리티 차이
#### 모니터링
이미 예상한 문제를 감지하고 확인하는 것

#### 옵저빌리티
예상하지 못한 문제도 데이터로 원인을 추론할 수 있다. 알람, 모니터링 만으로는 부족하다.

### 옵저빌리티 3가지
- Metrics: 현재 시스템 상태를 숫자 지표로 확인하는 기능(지금 상태가 어떤가?)
- Logs: 시스템과 애플리케이션에서 발생한 기록을 저장하는 기능(어떤 일이 발생했는가?)
- Traces: 요청이 어디에서 얼마나 시간이 걸렸는지 추적하는 기능(어디에서 시간이 오래 걸렸는가)

#### Traces
요청이 어디를 거쳤는지 추적하는 것

#### Trace ID
- 하나의 사용자 요청은 여러 시스템을 거친다
- 요청에 항상 traceId=abcd

#### 옵저빌리티가 높은게 무엇인가?
- CloudWatch 있나? X

#### 실무에서 옵저빌리티 높이기
1. 로그를 구조화한다
2. 핵심 API 응답 시간, 오류율 수집

#### 클라우드와 옵저빌리티
- CloudWatch는 도구일 뿐 결국엔 "서비스를 안정적으로 서빙해야한다"
  - 옵저빌리티가 높아져야한다.

---

#### 💡 정리
- CloudWatch: AWS 리소스와 애플리케이션의 상태를 모니터링하고 대응하는 서비스
- Metrics: CPU, 요청 수, 오류율 등의 숫자 지표
- Logs: 오류와 이벤트 등의 상세 기록
- Alarms: 임계값 초과 시 알림을 보내거나 자동으로 대응하는 기능 
- Dashboard: 여러 지표를 한 화면에서 확인하는 기능 
- Observability: 메트릭, 로그, 트레이스를 종합해 시스템 상태와 원인을 파악하는 능력 
- CloudWatch Agent: EC2의 메모리, 디스크, 로그 등을 수집하는 에이전트 
- CloudTrail: AWS 작업 이력과 API 호출 기록을 저장하는 서비스
