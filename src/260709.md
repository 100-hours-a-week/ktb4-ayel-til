# 260709

| 키워드 | 정의 | 사용하는 이유 |
| --- | --- | --- |
| CI | 여러 개발자의 코드 변경 사항을 자주 통합하고, 빌드와 테스트를 자동으로 수행하는 개발 프로세스 | 코드 통합 과정에서 발생하는 충돌, 빌드 오류, 테스트 실패 등의 문제를 빠르게 발견하고 코드 품질을 지속적으로 유지하기 위해 |
| Test Code | 프로그램의 기능이 예상한 대로 동작하는지 자동으로 검증하는 코드 | 기능 추가나 코드 변경으로 기존 기능에 문제가 발생했는지 확인하고 예상하지 못한 오류를 조기에 발견하기 위해 |
| Test Coverage | 전체 코드 중 테스트를 통해 실행된 코드의 범위를 정량적으로 나타내는 지표 | 테스트가 부족한 영역을 파악하고 테스트의 충분성을 판단하는 참고 자료로 활용하기 위해 |
| TDD | 실제 구현 코드를 작성하기 전에 테스트 코드를 먼저 작성하고, 테스트를 통과하도록 구현 코드를 작성하는 개발 방법론 | 구현 전에 요구사항과 예상 동작을 명확하게 정의하고 작은 단위로 개발하여 설계의 문제를 조기에 발견하기 위해 |
| Given-When-Then | 테스트 코드를 Given(준비), When(실행), Then(검증)의 세 단계로 구분하여 작성하는 테스트 표현 방식 | 테스트의 상황, 실행 대상, 예상 결과를 명확하게 표현하여 테스트 코드의 가독성을 높이고 테스트의 목적을 쉽게 이해할 수 있도록 하기 위해 |
| CD | CI를 통해 검증된 결과물을 실제 운영 환경에 안전하고 반복 가능하게 배포하는 프로세스 | 반복적인 배포 작업을 자동화하여 수동 배포 과정의 실수를 줄이고 빠르고 일관된 배포와 장애 발생 시 복구를 가능하게 하기 위해 |
| GitHub Actions | GitHub 저장소에서 발생하는 이벤트를 기준으로 빌드, 테스트, 배포 등의 작업을 자동화하는 CI/CD 플랫폼 | 코드 변경 시 빌드, 테스트, 배포 작업을 자동으로 실행하여 개발 생산성과 코드 품질을 높이기 위해 |
| GitHub Actions Workflow | `.github/workflows/*.yml` 파일에 정의하는 GitHub Actions의 전체 자동화 실행 흐름 | 빌드, 테스트, 이미지 생성, 배포 등의 CI/CD 과정을 코드로 정의하여 동일한 작업을 일관되고 반복 가능하게 실행하기 위해 |
| GitHub Actions Runner | Workflow에 정의된 Job이 실제로 실행되는 컴퓨터 또는 가상 머신 환경 | Workflow에 정의된 빌드, 테스트, 배포 등의 명령을 실제 환경에서 실행하기 위해 |
| GitHub Actions Job | 하나의 Workflow 안에서 실행되는 독립적인 작업 단위 | 빌드, 테스트, 배포 등의 작업을 목적에 따라 분리하고 병렬 실행하거나 실행 순서를 제어하기 위해 |
| GitHub Actions Artifact | Workflow 실행 중 생성된 빌드 결과물, 테스트 결과, 리포트 등의 파일을 저장하고 전달하는 기능 | 서로 다른 Job 사이에서 결과물을 전달하거나 빌드 결과와 테스트 리포트를 일정 기간 보관하고 확인하기 위해 |
| Zero-downtime Deployment | 사용자의 입장에서 서비스 중단 없이 애플리케이션을 업데이트하거나 배포하는 방식 | 서비스 이용자에게 중단 없이 안정적인 기능 업데이트를 제공하기 위해 |
| Blue/Green Deployment | 두 개의 독립된 환경(블루, 그린)을 운영하며, 트래픽을 새로운 버전으로 전환해 서비스 중단 없이 배포와 롤백이 가능한 배포 방식 | 두 개의 완전 분리된 환경에서 새 버전을 검증한 뒤 트래픽 스위치만으로 즉시 롤아웃·롤백할 수 있어 무중단 배포 과정을 단순화하여 배포하기 위해
|
| Rolling Deployment | 기존 인스턴스를 하나씩 새로운 버전으로 순차 교체하며 전체 서비스를 점진적으로 업데이트하는 배포 방식 | 인프라를 두 배로 준비하지 않더라도 배포 중 서비스의 처리 용량을 유지하기 위해서 사용 |
| Canary Deployment | 새 버전을 전체에 적용하기 전에 일부 사용자나 트래픽에만 점진적으로 배포하여 안정성을 검증한 후 전면 배포하는 방식 | 새 버전의 안정성을 실사용 환경에서 미리 검증하여 전체 배포로 인한 장애를 사전에 방지하기 위해서 |
| AWS ECR | Docker 이미지를 AWS 안에 안전하게 저장하고, ECS/EKS/EC2 같은 실행 환경에서 가져다 쓸 수 있 게 해주는 컨테이너 이미지 저장소 | 컨테이너 이미지를 AWS 환경 안에서 안전하게 저장하고, AWS 서비스가 빠르게 가져와 실행할 수 있도록 하기 위해  |
| Registry | 컨테이너 이미지를 저장하고 배포하기 위한 중앙 저장소 | 컨테이너 이미지를 중앙에서 관리하여 배포의 일관성을 유지하기 위해 |
| Repository | 특정 이미지를 이름을 기준으로 버전을 모아두는 공간 | 특정 애플리케이션의 컨테이너 이미지와 버전을 구분하여 관리하고, 배포 시 필요한 이미지 버전을 명확하게 선택하기 위해 |
| AWS CodeDeploy | AWS에서 제공하는 자동화된 애플리케이션 배포 서비스 | 배포 과정을 자동화하여 수동 작업에서 발생할 수 있는 실수를 줄이고, 안정적인 배포와 빠른 복구를 지원하기 위해 |
