## 2. VPC (Virtual Private Cloud)
> 공용 클라우드 환경에서 사용자에게 독립된 가상 네트워크를 제공하는 서비스

- AWS 안에 나만의 논리적으로 분리된 가상 네트워크(IP 대역, 서브넷, 라우팅, 보안규칙)

### 사용 이유
> 서버와 데이터베이스를 무작정 인터넷에 연결하지 않고, 서비스별 통신 경로와 접근 범위를 통제하기 위해 사용
- VPC가 없으면 웹 서버, 디비, 캐시 서버들이 외부 인터넷에 노출된다
- VPC를 사용해서 서비스별로 네트워크를 나누고, 트래픽이 지나가는 경로를 제어할 수 있다
  
### 구성 요소
#### 1. VPC	
- 클라우드 환경에서 논리적으로 격리된 가상 네트워크
- VPC 만들 때 가장 먼저 지정하는 값이 보통은 IPv4 CIDR 블록
- 설정: CIDR 블록, DNS 옵션, 테넌시
- ex) 사내 전체 네트워크 환경

#### 2. 서브넷 (Subnet)	
- VPC 내의 IP 주소 범위를 나눠 생성한 논리적 네트워크 단위
- 분리할 때는 용도에 맞춰서 서브넷을 분리하여 더 작게 나눌 수 있다
- ex) LAN의 하위 네트워크 (세그먼트)

##### AZ (Availability Zone)
- 전세계적으로 퍼져있는 데이터센터를 갖고 있으면서 컴퓨팅 자원을 가상화해서 대여하는 서비스
- 데이터센터가 여러개 지어져 있다
- 보통 서브넷을 나눌 때는 최소한 한 두 개 이상의 AZ에 분배되도록 구성한다
  - 고가용성이 필요한 운영환경에서는 AWS에서도 권유한다
    - 서브넷을 나눠서 AZ를 분리한 구성으로 만들면 단점이 비용이 2배

#### ⭐️ 3. 퍼블릭 서브넷	
- 인터넷과 연결되어 외부 접근이 가능한 서브넷 (보안성 ↓)
- 인터넷 게이트웨이(IGW)로 가는 경로가 있다
- ex) 인터넷 접근 가능한 DMZ 또는 외부망

#### ⭐️ 4. 프라이빗 서브넷	
- 인터넷과 직접 연결되지 않고, 내부 통신만 가능한 서브넷 (보안성 ↑)
- 인터넷 게이트웨이로 직접 가는 경로가 없다
- ex) 사내의 인터넷 접근이 제한된 내부망

#### 5. 라우팅 테이블	
- 서브넷 간 또는 인터넷과의 데이터 흐름을 결정하는 라우팅 규칙 목록 (네트워크 경로표)
- ex) 네트워크 라우터의 라우팅 테이블

#### 6. 인터넷 게이트웨이(IGW)	
- VPC와 인터넷 간의 연결을 지원하는 게이트웨이 장치
- 인터넷 게이트웨이 VPC에 연결한 뒤에, 퍼블릭 서브넷 라우팅 테이블에 경로 추가하면서 사용
- 퍼블릭 서브넷은 IGW 경로가 설정되어 있으며, EC2가 인터넷과 통신할 수 있다.
- 프라이빗 서브넷은 IGW로 직접 통신할 수 없으며 NAT Gateway를 통해 인터넷에 접근한다.
- ex) LAN과 WAN 사이의 인터넷 연결 라우터

#### 7. NAT Gateway
- 프라이빗 서브넷의 인터넷 연결을 지원하는 장치
- 외부 인터넷으로의 아웃바운드 통신은 허용하고, 외부에서 먼저 들어오는 연결은 차단한다.
- 프라이빗 서브넷 → NAT Gateway → 인터넷 방식으로 통신한다.
- ex) 내부망에서 외부 인터넷 연결 시 사용하는 NAT 장비

#### 8. 보안 그룹	
- 인스턴스 수준에서 트래픽 접근을 제어하는 상태 저장형 방화벽
- ex) 개별 서버에 설정된 방화벽 규칙

#### 9. 네트워크 ACL	
- 서브넷 전체의 트래픽을 제어하는 상태 비저장형 접근제어 규칙 집합
- 서브넷 전체에 적용된 방화벽 규칙

---

#### ‼️ VPC 구성 시 주의 사항
1. 퍼블릭 IP
- 사용하지 않는 퍼블릭 IP는 과금될 수 있으므로 주의
2. 내부 서비스 공개
- RDS, ElastiCache 등 내부 서비스에 퍼블릭 IP 할당 주의
3. SSH 보안
- SSH를 0.0.0.0/0으로 개방하지 않는다.
4. 네트워크 설계
- WAS, DB, Cache 등의 배치 위치를 사전에 설계한다.
5. NAT Gateway
- 네트워크 사용량에 따라 비용이 증가하므로 주의한다.

---

#### 💡정리
- VPC는 AWS 리소스를 사용하기 위한 네트워크 설계도
- 어떤 IP 대역을 사용할지, 어떤 서버를 외부에 공개할지, 어떤 서버를 내부용으로 사용할지 결정한다.
- 인터넷 트래픽 경로와 서버·DB 간 통신 범위를 제어한다.
- EC2, RDS 등 AWS 리소스의 통신 구조를 결정하는 기반이다.
- 서버, DB, 캐시 등의 리소스를 안전하게 배치하고 통신 경로를 설계하는 나만의 가상 네트워크이다.

## 3. IAM (Identity and Access Management)
> AWS 리소스에 대한 사용자 인증과 권한 관리를 제공하는 서비스

- AWS 리소스에 누가 접근할 수 있고, 어떤걸 할 수 있나
- IAM이 다루는 두 가지
  1. 인증: 사용자, 역할, 로그인 방식, MFA 확인
  2. 인가: AWS 서비스. 리소스·API별 권한 확인

### 사용 이유
> 사용자와 리소스에 대한 세밀한 권한 제어를 통해 보안성을 강화하고 운영을 안전하게 관리하기 위해
- 모두가 권한을 갖고 있으면 상당한 보안적 위험이 생긴다

### IAM 권한 배분 원칙
1. 최소 권한 원칙
- 필요한 작업을 수행할 때, 필요한 최소한의 권한만 부여하는 보안 원칙
- 권한을 넓게 열고, 나중에 줄이는 것보다 처음에 최소한으로 할당하고 나중에 필요하면 확장 시켜주는 것이 안전하다

### IAM 구성 요소
1. Root User: AWS 계정을 처음 만들 때 생성되는 최고 관리자
2. User: AWS에 접근하는 개별 사용자
3. Group: 여러 사용자에게 공통 권한을 부여하는 묶음
4. Role: 특정 사용자나 AWS 서비스가 임시로 맡는 권한
5. Policy: 허용, 거부할 작업을 작성한 권한 규칙 
6. MFA: 로그인 시 비밀번호 외에 추가 인증 요구

#### Group
- 여러 IAM 사용자에게 동일한 권한을 한 번에 부여하기 위한 사용자 그룹

##### 기본 사용하는 그룹
- Developers: 개발 계정의 EC2, CloudWatch, S3 일부 접근
- Operators: 배포, 모니터링 장애 대응 권한
- ReadOnlyAuditors: 리소스 조회만 허용
- BillingAdmins: 비용, 결제 관련 설정 접근

#### Policy
- AWS 에서 어떤 작업을 허용할지, 거부할 지정하는 규칙
- IAM 정책은 보통 4가지를 정의 
  - Effect: 허용할지(Allow) 거부할지(Deny)
  - Action: 어떤 AWS API 작업을 허용·거부할지
  - Resource: 어떤 AWS 리소스에 적용할지
  - Condition: 어떤 조건에서만 허용·거부할지

#### Role
- IAM 사용자나 AWS 서비스가 특정 권한을 임시로 사용할 수 있게 하는 권한 묶음
- IAM 유저에게 여러가지 권한을 미리 묶어놓고, 이걸 사용하게 할 수 있다
  - AWS EC2 에 대한 "생성" 권한을 가진 Role을 미리 만들어서 특정 서비스가 잠시동안 이 Role 을 가지고 생성할 수 있게 한다
- 요약: 누가 이 권한을 갖고 사용하느냐

#### MFA
- 멀티 팩터 인증
- 비밀번호 외에, 인증 수단들로 로그인할 때 사용하는 인증 수단

---

#### 💡정리
- IAM : AWS 사용자, 서비스, 도구 등에 권한을 부여하고 통제하는 서비스

1. Root User
- 계정의 최고 권한자
- MFA 적용 후 일상 사용 금지
2. User
- 개별 사용자 계정
3. Group
- 여러 사용자에게 공통 권한 부여
4. Policy
- 어떤 작업을 허용·거부할지 작성한 규칙
5. Role
- 사람 또는 AWS 서비스가 임시로 맡는 권한
- 서버, 서비스 간 접근에서는 Role 우선
6. MFA
- 비밀번호 유출 위험을 줄이는 추가 인증

## 4. 보안 그룹 (Security group)
> 클라우드 환경에서 인스턴스에 대한 네트워크 트래픽을 제어하는 가상 방화벽
- AWS 리소스에 들어오고 나가는 네트워크 트래픽을 허용 규칙으로 제어하는 상태 저장형 가상 방화벽
- 누가, 어떤 포트로 이 리소스에 접근할 수 있는지 관리한다.
- EC2, RDS, ALB 등의 접근 가능 여부를 제어하며 인바운드·아웃바운드 트래픽을 관리한다.
  
### 보안그룹의 적용 범위
- 보안 그룹은 EC2 인스턴스 자체에 붙는게 아니라 ENI(네트워크 인터페이스)에 적용된다

### 사용 이유
> 인스턴스에 대한 트래픽을 필터링하여 보안을 강화하기 위해서
- 서버를 인터넷에 무작정 노출하지 않고 필요한 대상에게만 통신을 허용한다.
- 인바운드 규칙이 없으면 모든 인바운드 트래픽은 기본적으로 차단된다.

#### 인바운드 트래픽
- 외부 또는 다른 리소스에서 내 리소스로 들어오는 트래픽

#### 아웃바운드 트래픽
- 내부에서 외부로 나가는 트래픽

### 특징
1. 상태 저장형 방화벽
- 한 번 허용된 요청의 응답은 반대 방향 규칙을 별도로 작성하지 않아도 자동으로 허용

2. Allow는 가능하지만, Deny 안된다.
- 보안 그룹은 명시적으로 허용(Allow)한 트래픽만 통과시킨다
- 허용 규칙이 없으면 기본적으로 차단된다
- Deny 규칙은 지원하지 않으며, 특정 IP나 국가 단위 차단은 NACL, WAF, Network Firewall 등을 사용한다

3. 여러개 보안 그룹을 하나의 리소스 연결할 수 있다
- 여러 보안 그룹을 조합하여 사용할 수 있다.
- 보안 그룹이 많다고 보안이 강해지는 것은 아니며 Allow 범위가 넓어질 수 있다.

### 보안 그룹의 구성
- Type: 서비스 유형 (SSH, HTTP, HTTPS, MySQL)
- Protocol: 통신 규약 (TCP, UDP, ICMP)
- Port Range: 허용할 포트의 범위 
- Source: 인바운드 출발지
- Destination: 아웃바운드 목적지
- Description: 규칙 목적 설명 

### AWS 보안 그룹 참조
- IP 대역 또는 다른 보안 그룹을 소스로 지정할 수 있다.
- 보안 그룹 참조를 사용하면 서버 수가 늘어나거나 줄어들어도 관리가 편하다.

---

#### 💡 정리
- 보안 그룹은 인바운드와 아웃바운드 트래픽을 제어한다.
- 보안 그룹은 상태 저장형 방화벽이며, 허용된 요청의 응답은 자동 허용된다.
- 보안 그룹은 Allow 규칙만 작성할 수 있으며, 규칙이 없으면 기본적으로 차단된다.
- CIDR 또는 다른 보안 그룹을 기준으로 접근을 제어할 수 있다.
- 실무에서는 역할별(ALB, App, DB, Redis)로 분리하고, 내부 서비스 통신은 보안 그룹 참조를 사용한다.

## 5. Route 53
> 사람이 읽는 도메인 주소를 서버나 AWS 서비스의 주소로 연결하고 트래픽을 라우팅하는 DNS 서비스

### 사용이유
- 도메인과 AWS 서비스를 연결하고 DNS를 관리하기 위해 사용
- AWS 서비스와 유기적으로 연동되며, 위치 기반 라우팅과 트래픽 분산을 지원한다.

#### 도메인 등록 / DNS 관리는 다르다
- 도메인 등록 : 도메인 구매 및 소유
- DNS 관리 : 도메인 연결 정보 관리
- 도메인 구매처와 DNS 관리 서비스는 서로 다를 수 있다.

#### Hosted Zone
- 특정 도메인 및 서브도메인에 대한 DNS 레코드를 보관하고 관리하는 공간

#### Public Hosted Zone
- 인터넷 전체에서 조회 가능
- 외부 DNS 조회 가능

#### Private Hosted Zone
- VPC 내부에서만 조회 가능
- 내부 DB, 사내 API 등에 사용
- 외부 DNS에서는 조회할 수 없다
- 내부 리소스를 IP 대신 도메인으로 관리할 수 있다

---

#### NS 레코드
- 이 도메인의 DNS 설정을 어디에서 관리하는지 알려주는 레코드

#### SOA (Start of Authority)
- DNS 영역의 대표 네임서버와 관리 정보를 담는 레코드

#### DNS 레코드
- 도메인을 어떤 대상에 연결할지 정의하는 설정

#### A 레코드
- 도메인 → IPv4(ElasticIP) 주소로 연결

#### CNAME
- 도메인 → 다른 도메인 이름으로 연결

#### Alias 레코드
- AWS 리소스를 도메인에 직접 연결하기 위한 Route53 전용 기능

#### TXT 레코드
- 텍스트 정보를 저장하는 레코드
- 도메인 소유권 확인, 이메일 보안 정책 등에 사용

### Route53 라우팅 정책
- DNS 응답을 제어하여 부하 분산, 장애 조치, 카나리 배포 등을 수행한다.

#### 1. Simple Routing
- 하나의 도메인을 하나의 대상으로 연결

#### 2. Weighted Routing
- 여러 대상에 트래픽을 비율대로 분산
- 무중단 배포, 카나리 배포에 사용

#### 3. Failover Routing
- 주 서버 장애 시 대기 서버로 전환

#### 4. Latency Routing
- 가장 지연 시간이 낮은 리전으로 연결

#### 5. Geolocation Routing
- 사용자 위치 기반으로 리전에 연결

---

#### 실무에서 사용하는 방식
1. 도메인 → ALB 연결
- ALB는 고정 IP를 보장하지 않으므로 도메인으로 연결
2. CloudFront + S3
- 정적 웹사이트 및 프론트엔드 배포에 사용

## 6. Elastic Compute Cloud (EC2)

### 하이퍼바이저
> 물리 서버 한 대에 CPU, 메모리, 디스크, 네트워크 등의 자원을 여러 개 "가상 컴퓨터" 가 나눠서 사용하고 서로를 격리 해주는 소프트웨어 계층
- 물리 서버를 한 사용자만 사용하면 남는 자원을 다른 사용자가 활용할 수 없다.
- 하이퍼바이저는 서버를 여러 개의 가상 머신으로 분리하여 자원을 효율적으로 사용하게 한다.
- 각 가상 머신은 독립된 OS를 가진 것처럼 동작한다.

### 가상화
> 하나의 물리 컴퓨터를 여러 개의 “독립된” 가상 컴퓨터를 실행하는 기술
- 각 가상 머신은 서로 독립적으로 동작한다.
- 가상 머신은 자신만의 컴퓨터처럼 인식한다.
- EC2의 인스턴스는 하이퍼바이저가 분리한 가상 머신 단위이다.

#### 하이퍼 바이저의 역할
1. CPU 분배: 어떤 EC2가 언제 CPU를 사용할지 조정
2. 메모리 분리: 각 EC2가 자기 메모리만 사용하는 것처럼 보이게 함
3. 가상 장치 제공: 가상 디스크, 가상 네트워크 카드 등을 제공
4. 격리:	다른 고객 EC2의 메모리·프로세스·디스크에 접근하지 못하게 차단

‼️ 하이퍼바이저로 만들어진 가상 OS 는 자기가 가상인지 모른다.

#### CPU는 어떻게 나눠 쓰는지?
- 하이퍼바이저가 가상 머신마다 CPU 실행 시간을 분배한다.
- AWS에서는 물리 CPU보다 vCPU와 할당된 컴퓨팅 자원을 기준으로 사용한다.

#### 가상화 방식
- 도커
- 하이퍼바이저
  - 물리 서버를 여러 가상 머신으로 분리
  - OS 레벨까지 격리
- 컨테이너
  - OS 하드웨어 사용하고 Application 레벨만 격리
- Namespace 
  - 리눅스의 자원 분리 명령어

#### EC2 왜 배우냐
- AWS에서 가장 기초적이고 범용적인 자원
- 백엔드, 게임 서버, 크롤러, VPN 서버 등 다양한 서비스에 활용된다.
- 서버를 직접 다루기 때문에 운영체제, 네트워크, 보안, 스토리지 등을 함께 학습할 수 있다.
- 많은 AWS 서비스가 EC2를 기반으로 발전한 형태이다.
- 가장 기본적이고 저렴한 컴퓨팅 서비스이다.

#### 온프레미스와 차이
- 서버를 직접 구매하고 운영체제, 네트워크 등을 직접 구성해야 한다.
- 초기 구축 비용이 크고 증설에도 많은 비용이 발생한다.
- 장애가 발생하면 직접 대응해야 한다.
- 반면 장기간 대규모 인프라를 운영할 경우 클라우드보다 저렴할 수 있다.

### 핵심 요소

#### 1. AMI
- 서버를 만드는 템플릿
- 운영체제와 초기 소프트웨어 구성이 포함된 서버 이미지
- AMI를 기반으로 EC2 인스턴스를 생성한다.

##### 실무에서 AMI
- 자주 사용하는 서버 환경을 미리 AMI로 만들어 둔다.
- Custom AMI를 사용해 반복 배포와 오토 스케일링을 구성할 수 있다.

#### 2. 인스턴스 타입
- CPU와 메모리 성능 조합을 정의한 EC2 사양

##### 인스턴스 계열
- T: 일반적인 개발 및 소규모 서비스
- M: CPU·메모리 균형형
- C: CPU 집약적 작업
- R: 메모리 집약적 작업
- G/P: GPU 기반 작업
- I/D: 고성능 스토리지 작업

###### 인스턴스 선택
- 서비스 특성과 트래픽 패턴에 따라 선택한다.
- 실무에서는 부하 테스트와 모니터링 결과를 기반으로 결정한다.

#### 3. EBS (Elastic Block Store)
- EC2에 연결되는 영구 블록 스토리지
- EC2의 데이터를 저장하는 가상 하드디스크
- EC2와 분리되어 있으며 다른 EC2에도 연결할 수 있다.

##### EC2 인스턴스 상태에 따라 EBS
- EC2가 중지되어도 EBS는 유지된다.
- EC2 재시작 시 기존 EBS를 계속 사용할 수 있다.
- 인스턴스 종료 시 EBS는 삭제 정책에 따라 유지 또는 삭제된다.
- 스냅샷을 통해 EBS 데이터를 백업할 수 있다.

#### 4. 네트워크
- AWS의 대부분의 리소스는 네트워크를 통해 접근한다.
- EC2는 반드시 VPC의 서브넷 안에 배치된다.

- 퍼블릭 서브넷의 EC2 접근 조건
  - 퍼블릭 IP가 할당되어 있어야 하고, 서브넷이 IGW와 연결되어 있어야 한다. 그리고 보안 그룹에서 외부 요청을 허용해야 한다.

#### 5. 보안그룹

#### 실무에서 EC2 를 잘 사용하는 방법
1. 태그를 강제
- 리소스를 쉽게 관리하기 위해 태그를 일관되게 사용한다.
2. EC2 에는 중요한 파일을 저장하지 않는다.
- EC2는 삭제될 수 있으므로 중요한 파일은 S3 등에 저장한다.
3. 서버에서 직접 “SSH” 로 파일을 수정하지 마세요.
- 수동 수정 대신 배포 자동화를 통해 관리한다.
4. 장애를 전제로 구성한다. ⭐️
- EC2는 장애가 발생할 수 있으므로 모니터링과 장애 대응 체계를 갖춘다.
