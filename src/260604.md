## 파일 처리
1. 문제 정의
- 목표: 커뮤니티에 이미지 파일 사용하기
- 필요 기능: 접근, 업로드

2. 개략적 설계하기
- 파일 업로드와 파일 접근을 위해 어떤 것이 필요하나
- 서버 환경
  - 로컬 서버 환경 기준 설계
    - express 에서 프론트엔드 서빙
    - Spring 에서 백엔드 서빙
  - 향후 클라우드 배포 고려
    - 현재는 로컬 기준이지만 확장성만 고려

3. 구현하기

### 데이터 저장 방식
- 스토리지(로컬 또는 클라우드)에 파일 저장
- 파일에 대한 정보는 RDB 에 저장함 (Image 테이블 저장)
  - 저장하는 정보는 아래와 같음
    1. 스토리지 접근 경로
    2. 썸네일 접근 경로 (Optional)
    3. 생성일
    4. 활성 여부 (isActive)

### 파일 형태
- 고용량 파일 양식 및 기타 이미지 형식은 지원 X
- 미지원 이미지 파일 형식 처리 방식
  - 지원하지 않는 이미지 파일 형식은 접근을 deny 하는 것으로 설정
  - 향후 미지원 이미지 파일은 서버 안정성을 위해 포맷 변환 기능 제공
- 파일 크기 제한은 10MB 이하

#### 파일 업로드 시
1. 클라이언트 파일 업로드 시도
2. WAS에서 파일 저장 처리
  - 파일 관련 추가 처리 진행
  - 스프링 정적 리소스 저장
  - 파일 접근 정보 RDB 저장

#### 파일 접근 시
1. 클라이언트 파일 접근 시도
2. WAS 정적 리소스 서빙

### 파일 업로드 시 백엔드에서 필요한 작업들
- 파일 검증
- 포맷 확인 및 처리
- 압축 처리
- 파일 업로드 처리
- 파일 정보 저장

### FileService
- 파일 기능은 단순하지만 스토리지에 의존적이지 않아야 함
- 향후 클라우드 확장 가능성을 고려

### LocalFileService
- FileService 인터페이스 구현체
- MultipartFile 로 파일 전달 받음
- 로컬에 파일 저장하는 기능 제공

### FileUploadRequestDTO
- 이미지 요청 처리할 DTO 작성
- 파일 관련 처리에서 공통으로 사용
  - 요청 값 검증도 가능
- 파일 크기 관련 설정은 스프링 설정 파일로도 가능함
  - application.yml/properties

## 예외처리

1. 백엔드 서비스 try-catch
- 서비스마다,컨트롤러마다
  - 중복되는 코드
  - 가독성 저하
  - 유지보수 어려움
  - 예외 처리 흐름 불명확

2. BasicErrorController
- 스프링의 기본 예외 처리 컨트롤러
- 별도 예외 처리 설정이 없을 때 동작
- 예외 발생 시 호출되며, 에러 요청을 다시 WAS에 전달하여 처리
- timestamp, status, error 등의 기본 JSON 응답 반환
- 클라이언트에 유의미한 에러 정보를 전달하기 어려움

3. @ResponseStatus
- 에러 HTTP 상태를 변경하는 어노테이션
- Exception 클래스, 메소드에서 @ExceptionHandler, 클래스에서 @RestConrollerAdvice 사용 가능

- ResponseStatusException
  - 스프링에서 추가된 예외 응답
  - HttpStatus와 함께 선택적으로 reason,cause 추가
  - Unchecked Exception 상속
    - 명시적인 에러 처리 안해도 사용 가능

- 장점
  - 예외처리 빠르게 적용 가능
  - HttpStatus 설정으로 예외 클래스 결합도 낮음
  - 불필요하게 많은 예외 클래스 안만듬

- 한계점
  - 직접 예외 처리 프로그래밍 함 
    - 일관된 예외 처리 어려움
  - 예외 처리 코드 중복 발생

4. @ExceptionHandler (실무에서 많이 씀)
- 매우 유연하게 에러 처리 가능
- 상태 코드, 메시지, 응답 구조를 자유롭게 정의 가능
- 다음에서 어노테이션 추가로 에러 처리 가능
  - 컨트롤러 메서드
  - @ControllerAdvice
  - RestControllerAdvice가 있는 클래스의 메서드들

- 컨트롤러에서 구현
  - 특정 컨트롤러에서만 발생하는 예외 처리
  - 컨트롤러에 예외 처리 코드 섞임
  - 예외 처리 코드가 중복
  
-> 이를 해결하기 위해 @ControllerAdvice, @RestControllerAdvice를 사용한 전역 예외 처리

5. @ControllerAdvice, @RestControllerAdvice 
- 자바 빈으로 등록되어 스프링 전역으로 @ExceptionHandler 적용
- 여러 컨트롤러에서 @ExceptionHandler 사용 가능
- 두 개의 차이는 @ResponseBody 포함 여부
  - @RestControllerAdvice는 @ResponseBody가 포함되어 JSON 응답 처리

- 이점
  - 하나의 클래스로 모든 컨트롤러 전역 예외 처리
  - 직접 정의한 에러 응답을 일관성 있게 전달
  - 별도의 try-catch 없이 코드 가독성 높음

- 주의
  - 프로젝트당 하나의 ControllerAdvice 관리
  - 직접 구현한 Exception 클래스는 한 곳에서 관리

---

### Advice 적용하기
- 클라이언트한테 보내줄 에러 코드 정의하기
   - 이름, 상태 메시지 등
   - 응답할 에러 규격을 클래스로 만들기
- ErrorCode 인터페이스 구현하기
- 서비스 전역에서 사용되는 CommonErrorCode
- 특정 도메인에서 사용하는 UserErrorCode

- 에러 응답 클래스를 정의할 수 있음
  - ErrorResponse 클래스 

- 전역 에러 처리해주는 예외 처리 클래스 선언
  - @RestControllerAdvice 어노테이션
- 우리가 만들었던 RestApiException 처리 위임
- 그 외 스프링에서 만들어둔 예외들도 처리 가능

- 에러 응답 만드는 건 반복되는 코드 (ErrorResponse) 만드는 팩토리 추가
- 에러 케이스들 Enum 으로 미리 정의 해도 OK

## 필터와 인터셉터

### 필터란?
- 서블릿 컨테이너가 디스패처 서블릿 요청 전달 전/후 URL 패턴에 맞는 모든 요청에 대한 부가 처리
1. 관리 컨테이너 - 서블릿 컨테이너
2. 스프링 예외 - X
3. Req, Res 객체 조작 - O

### 용도
1. 공통 보안, 인증/인가 작업
2. 모든 요청에 대한 로깅, 감사
3. 이미지 데이터 압축 및 문자열 인코딩
4. 스프링과 분리되어야 하는 기능

## 필터 메서드
1. init
  - 필터 객체 초기화
  - 웹 컨테이너가 1회 호출함
  - 필터 객체를 초기화한다.

2. doFilter
  - URL 패턴에 맞는 모든 요청이 디스패처 서블릿에 전달되기 전 실행
  - 파라미터에 FilterChain 이 있음.
  - 필터 체인에 doFilter 로 다음 대상으로 요청 전달

3. destroy
  - 필터 객체를 서비스에서 제거하기
  - 필터에서 사용했던 자원을 반환하는 등 동작 정의
  - 웹 컨테이너에 의해 1번 호출, 더 이상 doFilter 에 의해 처리 X

### 필터 체인
- 서블릿 컨테이너가 관리하는 필터들의 연결고리
- 디스패처 서블릿 도착 전, 필요한 여러 필터를 순차적으로 거치도록
- 필터 등록 순서에 따라 순차 처리 순서 설정
- 각 필터에서 doFilter() 호출로 다음 필터 호출

## 인터셉터란?
- 디스패처 서블릿이 컨트롤러 호출 전/후 호출되는 기능
1. 관리 컨테이너 - 스프링 컨테이너
2. 스프링 예외 - O
3. Req, Res 객체 조작 - X

### 특징
- 스프링이 제공하는 기술
- 요청과 응답을 참조, 가공하는 기능
- 스프링 컨텍스트에서 동작 제공

### 용도
- 세부적인 보안, 인증/인가 작업
- API 호출에 대한 로깅 또는 감사
- 컨트롤러로 넘겨주는 정보 가공

### 인터셉터 메소드
1. preHandle
  - 컨트롤러 호출 전 실행
  - 컨트롤러 이전에 처리해야하는 전처리
  - 요청 정보를 가공, 추가하는 경우
  - 반환 타입은 boolean
    - true: 다음 인터셉터 혹은 컨트롤러
    - false: 작업 중지

2. postHandle
  - 컨트롤러 호출 후 실행
  - 컨트롤러 이후 처리 해야하는 후처리
  - 컨트롤러 반환 값 타입 정보 제공
  - 컨트롤러 하위에서 예외 발생 시 호출되지 않음

3. afterCompletion
  - 모든 작업이 완료된 후 실행
  - 요청 처리 중 사용한 리소스 반환 등
  - 요청 중, 예외 발생 되더라도 반드시 afterCompletion 은 호출

---

- 필터: 전역 로직 처리 (인코딩,XSS 필터링 등)
- 인터셉터: 컨트롤러 관련 로직 (요청별 공통 데이터 주입 등)
- AOP: 스프링 빈 메서드 관련 로직 처리 (트랜잭션)
