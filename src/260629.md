## 1.DevOps
> 개발과 운영의 협업을 통해 소프트웨어 배포 속도와 안정성을 높이는 문화 및 방법론

### 등장 이유
- 기존 방식의 문제: 개발/운영 분리
  - 개발 팀: 기획부터 설계, 코드 작성, 테스트 및 배포 준비 단계까지의 전 과정을 수행하는 영역
  - 운영 팀: 개발된 소프트웨어를 실제 서비스 환경에 배포하여 사용자에게 제공하고, 안정적으로 운영 및 관리하는 역할
  
#### 문제
1. 배포 지연
- 배포의 덩어리가 커지고, 서버가 안정적이지 않다
- 테스트하고 안정화 시키기 어렵다

2. 수동 작업
- 개발 팀은 운영 서버에 접속 못한다

3. 환경 차이
- 개발 서버 <-> 운영 서버

4. 책임 차이
- 서버 문제인지 코드 문제인지?

**‼️️️ 개발, 운영이 서로 분리 되어 있으면 소통 지연, 배포 지연, 수작업 문제를 줄이기 위해서 만들어졌다**

### 핵심 목표
> 더 자주 배포 하는 것 자체가 목표가 아니라, 작은 변경을 더 빠르게 검증하고, 안전하게 배포하고, 문제가 생기면 복구할 수 있는 환경이 목표

#### 추구하는 것
1. 빠른 전달
2. 안정적인 배포
3. 자동화
4. 공동 책임
5. 빠른 피드백
6. 지속적 개선

### 사용 이유
> 개발-운영 간 소통 지연, 책임 분산, 수작업 등으로 발생하는 시간과 자원 낭비를 없애 배포를 빠르고 안정적으로 하기 위해서 사용함

---

### DevSecOps
> 개발, 보안, 운영을 통합해 소프트웨어의 개발부터 배포까지 모든 단계에서 보안을 적용하는 방법론

### 보안 영역
소프트웨어 개발 및 배포 과정에서 발생 가능한 보안 위협을 미리 탐지하고 예방하며, 운영 과정에서 지속적으로 관리하여 보안 리스크를 최소화하는 역할

### 차이점 
- DevOps: 개발과 운영 단계 후, 최종 단계나 배포 이후에 보안 점검이 별도의 독립적인 절차로 진행됨
- DevSecOps: 개발 단계부터 운영까지 모든 과정에 보안을 통합하여, 보안 문제를 초기에 발견하고 즉시 해결함

### 사용 이유
> 배포 속도와 안정성을 유지하면서 보안 문제를 초기에 발견하고 빠르게 해결하기 위해서 사용함

### DevSecOps 주요 보안 활동 설명
1. 정적 코드 분석 (SAST): 소스 코드를 실행하지 않고 코드 자체를 분석하여 잠재적인 보안 취약점을 미리 발견하는 기법
2. 의존성 점검 (Dependency Check): 애플리케이션에서 사용하는 오픈소스 라이브러리나 외부 패키지의 보안 취약점 여부를 검사하여 안전한 버전 사용을 권장하는 과정
3. 동적 애플리케이션 테스트 (DAST): 애플리케이션을 실제 실행한 상태에서 보안 취약점을 찾아내는 기법으로, 실행 중 발생 가능한 보안 문제를 점검
4. 보안 컴플라이언스 (Compliance): 소프트웨어 및 인프라가 조직의 보안 표준이나 법적 요구사항을 준수하는지 확인하고 관리하는 활동

## 2. Docker
> 애플리케이션이 실행되는 데 필요한 모든 요소(코드, 라이브러리, 설정 등)를 하나로 묶어, 어떤 컴퓨터에서든 동일하게 실행되도록 도와주는 도구

### 도커 이전 발생 문제
- 코드는 git으로 공유 됐지만, 실행하는 사람마다 환경이 달랐다
- 로컬에서는 직접 수동으로 환경을 설정했다

### 기존 해결 방식 - 가상머신 (VM)
하이퍼바이저, 서비스마다 독립적인 OS 제공

#### 장점
- 서비스별로 강하게 분리 -> 운영체제를 다르게 사용할 수 있다
- VM의 장애가 다른 VM으로 잘 전파되지 않는다

#### 단점
- VM 하나의 애플리케이션을 실행하기 위해서는 항상 전체 OS를 실행해야한다
- 안정적인 격리에는 좋으나, 서비스가 많아지면 자원 사용량 + 관리 비용이 커진다

### 도커 - 앱 분리
> 도커는 운영체제 전체를 여러 개 만드는 대신, 하나의 운영체제 위에서 애플리케이션 실행 환경만 분리한다

운영체제 복사하지말고 앱 + 파일, 라이브러리 정도만 묶어서 실행하자

### 사용이유
1. 컨테이너화로 인한 일관된 환경 제공
2. 빠른 배포 및 확장 
3. 이식성 
4. 격리 및 보안

---

### 구성 요소
> 도커는 실행 환경을 "이미지" 로 표준화하고, 컨테이너로 실행하고, 레지스트리로 배포한다.

#### DockerFile
> 실행 환경 설명서
도커파일에서는 애플리케이션을 실행하기 위해 필요한 작업을 "코드" 로 작성한 파일

#### Docker Image
- 애플리케이션을 실행할 수 있도록 준비된 결과물
- 실행 환경까지 포함된 배포 패키지, 도커 파일은 도커 이미지라는 결과물을 만든다
- 도커 이미지만 있으면 언제 어디서든 똑같은 환경으로 재사용 가능

#### Docker Container
> 템플릿으로 만들어진 프로세스, 이미지를 실제로 실행한 상태

- 도커 이미지 = 붕어빵 틀
- 컨테이너 = 구워진 붕어빵

### 컨테이너가 어떻게 서로 분리되어 있는지?
- 하나의 컴퓨터를 사용하지만 실제로는 서로 격리되어 있는 거처럼 보인다
- ec2 사용하면 실제로는 하드웨어 장비를 공유 받는 것
- 컨테이너는 하나의 호스트 OS를 나눠 사용하지만 실제로는 서로가 서로에 대해서 격리되어 있다

---

### ⭐️ 도커는 어떻게 서로 격리하는 환경을 만드나?
> 컨테이너는 별도의 컴퓨터가 아니라, 하나의 컴퓨터에서 보이는 환경", "사용 가능한 자원" 을 제한한 프로세스

### 구성요소
1. 커널: 애플리케이션이 CPU, 메모리, 디스크, 네트워크를 쓰도록 실제로 처리해주는 운영체제의 핵심
2. Namespace: 컨테이너마다 서로 다른 프로세스, 네트워크 파일시스템이 있는 것처럼 보이게 함
3. cgroups: 컨테이너별로 CPU, 메모리, 프로세스 수 등을 얼마나 사용할지 제한하고 측정함

### 1. 커널
- 실제 하드웨어 자원을 관리하는 역할
- 하드웨어 <-> 하드웨어 사이에서 CPU, 메모리, 네트워크, Disk 자원을 관리하는 운영체제의 핵심 프로그램
- 애플리케이션 직접 디스크에 접근하지 못하기에 반드시 커널에게 요청 -> 시스템 콜

#### 도커 컨테이너에는 "커널"이 없다
- 호스트 OS 커널을 공유해서 사용하기 때문에 도커 컨테이너 안에는 "커널" 직접적으로 있지 않다
- Guest OS 전체 부팅하는 VM에 비해서 도커 컨테이너 방식이 훨씬 더 가볍다.

### 2. Namespace
> 네임스페이스는 컨테이너마다 "프로세스, 네트워크, 파일시스템" 독립적으로 존재하는 것처럼 보이게 만드는 Linux 의 커널 기능

- 하나의 전역 자원을 분리된 자원처럼 사용할 수 있다
- 같은 서버에서 실행되도 다른 네임스페이스에서 실행되면 분리할 수 있다.
  - 분리 레벨, 프로세스, 네트워크, 파일시스템

- 모든 프로세스가 같은 서버 자원을 본다
  - 프로세스 목록
  - 네트워크 인터페이스
  - 파일 시스템 구조
  - hostname
  - 사용자 체계

#### PID Namespace
- 컨테이너가 자기 컨테이너 안에 있는 프로세스만 보도록 분리하는 것
- 프로세스를 분리하면, 장애 영향이 덜 간다

#### Network Namespace
- 컨테이너마다 독립적인 IP, 포트, 라우팅 테이블, 네트워크 인터페이스도 분리한다

#### Mount Namespace
- 파일시스템을 분리하는 것

### 3. Cgroups
> 여러 프로세스를 하나의 그룹으로 묶고, 그 그룹의 CPU, 메모리, I/O, 프로세스 수 사용량을 제한하고 측정하는 Linux 커널 기능

- Namespace - 다른 컨테이너, 프로세스 파일 네트워크를 보이지 않게 했음
- 호스트 OS의 CPU, 메모리 등의 자원 사용량을 컨테이너별로 제한하고 관리하는 기능

---

### 실무에서의 도커 활용
- 애플리케이션 -> 도커파일 -> Dockerfile로 Image로 만든다
- 이미지 -> Registry 저장
- 서버에서 레지스트리에 이미지를 다운 받아 컨테이너로 띄워서 사용한다

1. 로컬 개발 환경 통일할 때
- 컨테이너로 환경을 통일 시킨다

2. 초기 프로젝트에서 단일 EC2 서버에서 사용
- EC2 하나에 다양한 서비스 띄울 때

3. 배포 과정에서 컨테이너 사용
- 소스 코드를 복사하지 않는다
- 빌드된 도커 이미지를 서버에게 전달해서 사용한다

4. 컨테이너를 여러개 사용할 때, "Docker Compose"
- 애플리케이션이 하나면 docker run

---

### ⭐️ 지켜야하는 원칙
1. 이미지에는 비밀번호를 넣지 않는다
- 도커 이미지만 습득할 수 있으면 보안은 아무런 소용이 없다
- 비밀번호, API Key, .env 파일은 AWS Secrets Manager에 비밀번호를 직접 넣고 변수 적용

2. 태그 중에 latest만 사용하지 않는다
- 도커 이미지는 버저닝이 가능하다
- 일반적으로 배포할 때는 최신 버전을 가지고 한다. 
  - latest <- 마지막 버전 가져옴
- 실제로 어떤 버전을 사용하는지 디버깅할 때 모른다
- 운영 배포할 때는 버전 명시를 꼭 해줘야한다

3. 컨테이너 안에 데이터를 영구 저장하지 않는다
- 컨테이너는 데이터의 영속성을 보장하지 않는다
- 컨테이너 실행 -> 내부 저장 -> 컨테이너 종료
  - 삭제되는게 기본 설정
- Docker + Docker Volume
  - 데이터 영속이 필요하면 볼륨과 함께 사용해야한다

4. 하나의 컨테이너에 하나의 핵심 역할만 둔다
- 배포 할 때, 확장, 장애 분석하기가 어려워진다
- 컨테이너 = Namespace + cgroups + Kernel 분리한 영역
  - 프로세스가 여러 개 들어가도 문제는 없다
- 관리 + 책임 분리 원칙

5. 운영 환경에서 로그를 컨테이너 밖에서도 볼 수 있게 해야한다
- EC2 -> 컨테이너 -> 프로세스
- 로그는 프로세스에서 발생한다
  - 컨테이너에 접속해야만 로그를 볼 수 있다
- 옵저빌리티
- 운영 로그를 컨테이너 내부 파일에서만 보는게 아니라 외부로 로그를 모아주는 것을 설정하는게 좋다

#### 💡 정리
- 도커가 나온 이유
  - 환경 차이의 문제를 좁히기 위해서 만들어졌다
- 도커가 해결하는 방법
  - 코드 + 자바, 라이브러리 등등 실행에 필요한 모든걸 다 묶어서 "이미지" 라는걸로 전달한다.
- Dockerfile
  - 애플리케이션 실행 환경을 만드는 코드 설명서
- Image
  - 애플리케이션을 실행할 수 있도록 만들어진 배포 패키지
- Container
  - 이미지를 실제 실행한 격리된 프로세스
- Namespace
  - 프로세스, 네트워크, 파일 시스템 등을 분리된 것 처럼 보이게하는 커널 명령어
- Cgroups
  - 컨테이너별 CPU, RAM 같은 자원 사용량을 제한하고 모니터링할 수 있는 커널 명령어
- 도커 = 기술인가?
  - Container라는 기술을 사용하기 쉽게 만든 "서비스" 이름이다

## 3. DockerFile
> 도커 이미지를 생성하기 위한 명령어 및 설정이 담긴 텍스트 기반의 스크립트 파일

- 애플리케이션 실행 환경을 코드로 정의한다.
- 누구나 같은 방법으로 동일한 도커 이미지를 만들 수 있다.
- 배포 설계서
- 그냥 도커만 써도 환경차이가 없어지지 않는가?
  - 도커만 사용한다 = 컨테이너 만들 때, 매번 환경 변수를 직접 기입하는 식
  - 수동으로 만드는 과정 -> 파일에 적어놓는다.

#### 예시
- Dockerfile = 붕어빵을 만드는 레시피
  - -> 실행 환경을 만드는 코드
- Image = 완성된 붕어빵 틀
  - -> 실행 환경이 포함된 읽기 전용 배포 결과물
- Container= 실제로 만들어진 붕어빵
  - -> 이미지 기반으로 실행되는 격리된 프로세스

### 도커 파일은 어디에 위치할까?
보통 도커파일은 프로젝트 최상위 경로에 두는게 일반적이다.

### 핵심 명령어
1. FROM
- 이 이미지는 어디에서 시작할 것인가?
- 도커 이미지는 보통 다른 사람이 만들어 둔 이미지를 기반으로 시작한다.
- 어떤 OS와 런타임 환경에서 시작할지 정하는 명령어

- FROM은 1번만 사용하는 것이 아니다.
  - 멀티 스테이지 빌드
    - 빌드용 이미지와 실행용 이미지를 분리해서 사용
    - JDK: 자바 프로그램을 빌드할 때 사용
    - JRE: 자바 프로그램을 실행할 때 사용
      - 빌드 이미지 → FROM JDK
      - 실행 이미지 → FROM JRE

2. WORKDIR
- 컨테이너 안에서 작업할 기본 디렉터리를 지정한다

3. COPY
- 내 프로젝트 파일을 Image 안으로 넣는다

4. RUN
- 이미지를 만드는 과정에서 명령어를 실행한다
- 컨테이너가 실행될 때가 아니라, 이미지를 빌드하는 과정에서 실행된다

- 이 차이 구분해야 한다.
  - RUN = 이미지를 만들 때 사용하는 명령어
  - CMD / ENTRYPOINT = 컨테이너가 시작될 때 실행하는 명령어

5. EXPOSE
- 이 앱이 사용하는 포트를 표시한다
- EXPOSE 8080은 호스트의 8080 포트를 열어주지 않는다

6. CMD + ENTRYPOINT
- 컨테이너가 시작되면 뭘 실행할까?
- CMD: 기본 명령 또는 기본 인자 지정
- ENTRYPOINT: 컨테이너가 기본적으로 실행할 프로그램 지정

---

#### CMD, ENTRYPOINT 둘 다 꼭 써야 하나?
- 둘 다 써야 하는 것은 아니다.
- 구분 기준: 무엇을 고정하고, 무엇을 실행할 때 바꿀 것인가

#### ENTRYPOINT
- 컨테이너가 반드시 실행할 주 프로그램
- 컨테이너 내부 프로그램의 실행 명령어 (java -jar app.jar)
- "이 이미지는 이 프로그램을 실행한다." 를 고정
- `--entrypoint` 옵션으로 변경 가능

#### CMD
- 주 프로그램에 전달할 기본 명령, 기본 옵션
- docker run 실행 시 변경 가능
- "기본 동작은 이렇게 하는데, 필요하면 실행할 때 변경해서 사용."

#### 언제 사용하는가?
##### 1. ENTRYPOINT, CMD만 사용하는 경우
- 실행 명령어가 단순한 경우
- 옵션을 바꿔야 한다

##### 2. ENTRYPOINT + CMD를 함께 사용하는 경우 (실무)
- 실행할 프로그램은 고정
- 실행 옵션은 쉽게 변경

---

#### ENTRYPOINT
- 이 컨테이너는 이 명령어를 무조건 실행한다.
- 주 실행 명령
- 항상 실행해야 하는 프로그램 명령어

#### CMD
- 기본 플래그, 기본 인자
- 기본 값인데, 실행 시 바꿀 수 있는 옵션

#### CMD만 사용하는 경우
- ENTRYPOINT를 굳이 사용하지 않는 것
- 항상 실행할 명령어를 고정하지 않겠다.
- 실행 시 완전히 다른 명령어를 실행하고 싶을 때 사용

---

### ⭐️ 도커 파일과 이미지 레이어
- 도커 이미지는 여러 개의 레이어로 구성된다
- 이전 빌드에서 변경되지 읺는 레이어는 재사용한다
- Update Frequency는 자주 변경될수록 레이어를 상단으로 배치
- 각 레이어 단계를 나눈다
  - 자바 레이어
  - 라이브러리 레이어
  - JAR 레이어
  - 환경 변수 레이어

- 이미지를 다시 빌드할 때 변경되지 않은 레이어는 그대로 재사용한다
- Dockerfile을 작성할 때도 레이어 구조를 고민해야 한다
  - COPY . . 이후 소스 코드가 하나라도 변경되면 해당 레이어와 이후 레이어를 다시 빌드한다

---

### 도커파일 레이어
> 도커 이미지는 하나의 거대한 파일이 아니라, 베이스 이미지에사 시작해서 이전 상태에서 바뀐 파일만 한 겹씩 쌓아 만든 실행환경이다
- 레이어는 파일의 변경분이다
- 투명필름
- 1번 필름
  - -> 기본 적인 Node.js 파일, 리눅스 파일
- 2번 필름
  - -> 라이브러리 파일
- 3번 필름
  - -> npm install 로 설치한 패키지들
- 4번 필름
  - -> 우리가 작성한 js 코드

- 이 투명필름을 한 번에 겹쳐서 보면 -> 완성된 코드가 보인다
- 이러한 특징이 있다면, 우리의 도커 파일의 명령어 순서는 중요해진다
  - 변경되지 않은 레이어는 재사용하고, 변경된 레이어부터 다시 빌드하기 때문이다.

### .dockerignore
- docker build 할 때, 전달하지 않을 파일들

  - .git -> git 커밋 이력
  - .gradle -> 내부 의존성 파일, 의존성 설치하면 다시 설치된다.
  - build 
  - node_modules
  - *. log -> 과거 로그가 들어간다.
  - .env-> 비밀번호나 API Key 들어갈 수 있어서
  - .env.*

#### 💡정리
- 도커 필요 이유
  - 실행환경을 수동 작업이 아니라 코드로 정의하기 위해서
- 도커파일 무엇을 만드나?
  - Docker Image
- Image
  - 애플리케이션 + 실행 환경이 담긴 배포 패키지
- 도커 파일을 얻은 장점
  - 실행 환경 코드 = 표준화가된다. 재현성 높아진다.
  - 협업성이 높아진다. 모든 개발자가 다 같은 환경
    - 환경이 코드로 정의되기 때문에
    - CI/CD 연결

## 4. Docker Image
> 애플리케이션 실행에 필요한 바이너리, 설정, 라이브러리 등을 미리 포함한 읽기전용(Read-only) 스냅샷
- 도커 파일 
  - 도커가 읽고 빌드하는 내용
- Layer가 쌓인 하나의 이미지가 만들어진다
- 컨테이너는 그 이미지를 기반으로 실행된다

- 레이어로 만들어서 전체 파일을 매번 새로 복사하지 않고 이전 상태에서 바뀐 파일만 새로운 레이어에 기록한다

### 레이어
> Layer는 전체 파일시스템 복사본이 아니라, 이전 레이어와 비교해 추가, 수정, 삭제된 파일의 차이(dift)를 저장한 단위다
- 이전 빌드에서 만든 결과물 레이어를 캐싱하기 좋다

### 레이어는 폴더가 아니다
레이어에는 이전 상태에서 새롭게 추가되거나 바뀐 파일만 기록된다

### 사용 이융
애플리케이션 실행에 필요한 모든 환경을 미리 구성해 어디서든 동일하게 실행될 수 있도록 하기 위해서

### OverlayFS
> 여러 개의 읽기 전용 Image Layer를 겹쳐, 애플리케이션이 하나의 완성된 파일시스템처럼 사용할 수 있게 하는 Linux 파일시스템 기능이다.

## 5. Container
> Docker Image를 바탕으로 실제 애플리케이션 프로세스를 실행한 격리된 실행 단위

- 도커파일 - 이미지를 어떻게 만들지 정의
- 도커 이미지 - 애플리케이션 + 실행환경이 담긴 읽기 전용 결과물
- 컨테이너 - 이미지를 기반으로 실제로 실행된 격리 실행 단위
  - 호스트 운영체제 커널 위에서 실행되는 격리된 프로세스다

### 필요한 이유
- 도커 이미지는 공통 "실행환경"을 제공한다.
- 컨테이너에서는 실제 실행환경에 맞는 값을 적용해서 사용한다
  - 이미지 공통 패키지 만들기 결과물
  - 컨테이너는 그걸 기반으로 특정 변수를 넣어 실행한 프로세스다

### 도커 컨테이너 실행
```

docker run nginx
// 1. 새 컨테이너를 생성
// 2. 생성한 컨테이너를 실행한다.

docker create ~~
docker start ~~

// docker run  실행하면
// 1. registry <- 이미지 저장소, 여기에서 해당 이미지 확인
// 2. 외부 저장소에서 이미지를 가져오는걸 시도 (docker pull)
// 3. 컨테이너를 만든다.
// 4. 실제 실행 변수
docker run -d \
  --name nginx-web \
  -p 8080:80 \
  
// 5. 메인 프로세스, 
// 6. 실행 상태 유지 -d 
// 7. 프로세스 종료
// 8. 컨테이너 "중지" 한다.
```

### 컨테이너는 메인 프로세스가 끝나면, 중지 된다
- 컨테이너 내부에 메인 프로세스가 살아 있는 동안만 유지된다
- 서버 프로세스다 -> -d
- 서버 프로그램-d 옵션과 함께 사용한다

#### 컨테이너의 생명 주기
- 도커는 종료되어도 삭제되지 않는다
  - 컨테이너 + 볼륨 + 이미지
  - ec2에서 컨테이너
    - 이미지가 남아 있다.

#### 중지랑 삭제는 다르다
- docker stop: Container를 멈춘다
- docker start: 멈춘 기존 Container를 다시 실행한다
- docker rm: Container 자체를 삭제한다
- docker run: 새 Container를 생성하고 실행한다
- docker rmi: 기존에 이미지를 삭제한다.

### 컨테이너 - 이미지 차이
- Image: 실행 환경을 담은 템플릿
- Container: Image를 실제로 실행한 단위

#### 컨테이너 내부 명령어
- 우분투 계열에서
  - sh는 기본 제공
  - bash는 제공하지 않을 수 있다
- 네트워크 명령어
- 컨테이너는 기본적으로 경랑화하려고 한다

### 실무적으로 컨테이너 다루기
1. 컨테이너는 이름을 붙여야한다
- 컨테이너는 수가 상당히 많을 수 있다
  - 내가 관리하는 서버가 많거나 서버 내부에 컨테이너가 많을 수 있다

2. Docker run 반복해서 쓰지말자
- 도커 런은 기존 컨테이너를 찾아서 실행 명령어가 아님
- 매번 새로운 컨테이너를 만든다
- 항상 docker ps -a로 확인
- 없으면 명렁어를 분리해서 사용하자
  - docker create & start = run
  - 만들고나서, 확인하고 스타트를 하는게 안전하다.

3. 운영 컨테이너는 직접 수정하지 않는다
- 변경이 필요하면 이미지를 수정해라
  - 새로운 이미지 빌드
  - 그걸로 컨테이너를 만든다
- Why? Thin laywer에 수정하고 있다

4. 컨테이너는 실행 중이라 해서, 정상 상태가 아니다
- docker ps -> RUNNING 상태 확인
  - 프로세스 실행 중 -> 서비스가 정상이다 X
- docker ps-a +
  - docker logs -f nginx 
  - docker stats

5. 운영 재시작 정책을 고려
- 서버는 항상 "재부팅"이 될 수 있다
- 프로세스들이 재시작되면 어떻게 행동해야하나?
  - 도커도 서비스로 등록되어 있어서 자동 재실행 되는데
  - 이때 어떻게 컨테이너가 수행해야하는지를 미리 기재하는게 좋다

---

#### 💡 정리
- 컨테이너는 이미지를 실제로 실행한 격리 프로세스 단위
- 컨테이너는 생명주기
  - Created
  - RUNNING
  - Exited
  - Remove (삭제 X)
- 운영에서는 컨테이너 내부에 들어가서 수정하면 안된다
- Thin R/W layer

## 6. Registry
> 컨테이너 이미지를 저장하고 배포하기 위한 중앙 저장소
- 버전 관리 기능을 통해 이미지의 변경 이력을 추적할 수 있다
- Private 또는 Public으로 설정해 조직 내 또는 외부 사용자와 컨테이너 이미지를 공유할 수 있다

### 사용 이유
> 컨테이너 이미지를 중앙에서 관리하여 배포의 일관성을 유지하기 위해서
