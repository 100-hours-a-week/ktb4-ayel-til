## 1. ElastiCache
> Redis나 Memcached 같은 인메모리 캐시 서버를 직접 EC2에 설치하고 운영하지 않아도, AWS에서 간편하게 생성하고 사용할 수 있도록 제공하는 관리형 캐시 서비스

#### 데이터베이스만으로 서비스 할 때 문제점
- 처음에는 RDS(MySQL)만으로도 충분하지만 사용자 수가 증가하면 조회 요청이 DB에 집중된다
- MySQL의 CPU, Memory, DISK I/O 사용량이 증가한다
- 데이터베이스는 일반적으로 병목 구간이 되기 쉽고, 응답 속도가 저하될 수 있다

### 캐시
- 캐시는 원본 데이터를 매번 다시 조회하지 않도록, 자주 사용하는 데이터들을 빠르게 꺼낼 수 있게 임시로 저장하는 기술
- 데이터가 있으면 Cache Hit 응답
- 데이터가 없으면 Cache Miss, RDS 조회 및 Cache를 저장

### ElastiCache
> AWS 관리해주는 인메모리 캐시 서비스
- "분산형" 인메모리 데이터 저장소

#### 캐시를 메모리에 저장하는 이유는? 
- 캐시는 자주 접근, 변경, 빠른 속도가 중요하기 때문에 RAM(In-Memory)에 저장된다
- RDS를 사용하면서 + ElastiCache 를 같이 사용한다.

### 사용 이유 
1. 애플리케이션 성능 향상
2. 데이터베이스 부하 감소
3. 확장성과 고가용성 제공
4. 분산 캐시 아키텍처 지원
5. AWS 에코시스템과의 통합

### 캐시 사용 패턴
#### 1. Cache-Aside 패턴
- Cache-Aside는 애플리케이션이 먼저 캐시를 조회하고, 캐시에 없을 때만 DB를 조회한 뒤 캐시에 저장하는 방식

#### Cache Hit
- 캐시에 데이터가 있는 경우
#### Cache miss
- 캐시에 요청한 데이터가 없는 경우

#### TTL (Time To Live)
- 캐시 데이터가 자동으로 만료되기까지의 시간
- 캐시에 데이터가 오래 남아 있는걸 방지하기 위해서 사용
  - 캐시는 메모리 자원을 사용하여 제한적이다
  - 캐시 데이터가 항상 유효하지 않기 때문에 정합성을 보장하지 않는다
    - 최신의 데이터로 변경해야하는데, 비즈니스 로직상 자연스럽게 캐시가 갱신이 된다.

- **짧아야 좋은가?**
  - 캐시 미스가 많이 생긴다.
  - RDBMS 에서 조회 캐시 효과가 줄어들어서, 데이터의 정합성을 올릴 수 있다
- **TTL 너무 길면?**
  -  오래된 데이터를 보여줄 수 있고 데이터 변경이 반영이 안될 수도 있기에 사용자 경험이 깨질 수도 있다
- **TTL은 어떤 값을 캐싱하냐에 따라서 설정해야한다. ⭐️**
  - 자주 바뀌는 데이터 → 짧은 TTL 검토 
  - 거의 바뀌지 않는 데이터 → 긴 TTL 검토 
  - 즉시 최신 값이 필요한 데이터 → TTL만 믿지 말고 캐시 삭제 또는 갱신 필요

#### 캐시 무효화 전략
원본 데이터가 변경됐을 때 기존 캐시 값을 삭제하거나 수정하는 작업

### ElastiCache에서 사용할 수 있는 엔진
#### Redis, ValueKey, Memcached
- Valuekey : Redis OSS 호환 계열의 인메모리 저장소 (캐시, 세션, 랭킹, Pub/Sub)
- Redis OSS : 다양한 자료구조를 제공하는 인메모리 저장소 (캐시, 세션, 분산 락, 실시간 기능)
- Memcached : 단순하고 가벼운 분산 Key-Value 캐시 (단순 조회 캐시)

### ElastiCache 고가용성 구성
#### Replica 구성 
Primary 데이터를 복제하여 고가용성과 읽기 확장 제공
-> 읽기 요청을 분산하고 장애 복구에 활용
#### Multi AZ
캐시 노드 장애 시 Replica 승격으로 가용성 향상
-> 서로 다른 AZ에 배치
#### Shard
데이터를 여러 노드에 분산 저장하여 저장 용량 및 처리 성능 확장
-> 데이터를 나누어 저장하는 방식

#### ⭐️ 캐시를 사용할 때, 알아야하는 문제
1. 캐시는 원본 데이터가 아니다
- 캐시는 인메모리에 저장했기에 휘발성 데이터, Redis(RAM)가 꺼지면 사라진다
- TTL이 끝나거나, 장애로 제거될 수 있다
- 비즈니스 로직에서 간혹 캐시에서만 데이터를 조회하는 의존도 높은 시스템을 구성할 수 있다.
- 복구 정책이 필요하여, 캐시가 히트 안 됐을 때 영구 저장소를 항상 조회하는 로직(finally)을 추가해야함

2. 캐시 스탬피드
- TTL이 만료되는 순간 10,000개의 Key가 동시에 Cache Miss가 발생한다
- 갑자기 많은 요청이 RDBMS로 몰리게 된다
- 응답 지연이 발생한다
- 다른 서비스에도 영향을 줄 수 있다
- Timeout이 발생하면서 서비스 안정성이 떨어질 수 있다
- 실무에서는 캐시의 TTL 설정할 때 항상 임의 값을 추가한다

3. 메모리 부족 현상
- 캐시는 메모리 동작, 메모리는 한정된 자원
- 캐시 메모리가 가득 차면 새롭게 캐시가 생성되지 않고, 새 쓰기가 계속 실패한다
- Eviction 정책은 캐시 메모리가 부족한 경우에 오래 되거나 덜 사용된 키를 제거하는 정책이다

---

#### 💡 정리
- ElastiCache : AWS 관리형 인메모리 캐시 서비스
- 주요 엔진 : Valkey, Redis OSS, Memcached
- 핵심 목적 : 반복 조회를 빠르게 처리하고 RDS 부하 감소
- 저장 위치 : 메모리(RAM)
- 대표 패턴 : Cache-Aside
- Cache Hit : 캐시에 데이터가 있어 빠르게 응답
- Cache Miss : DB에서 조회한 후 캐시에 저장
- TTL : 캐시 데이터 자동 만료 시간
- 캐시 무효화 : 원본 데이터 변경 시 기존 캐시 삭제 또는 갱신
- 주요 활용 : 게시글 캐시, 세션, 인증번호, 랭킹, Rate Limiting
- Multi-AZ : 캐시 노드 장애 시 Replica 승격으로 가용성 향상
- Replica : Primary 데이터를 복제하여 고가용성과 읽기 확장 제공
- Shard : 데이터를 여러 노드에 분산 저장하여 저장 용량 및 처리 성능 확장

## 2. ELB (Elastic Load Balancer)
> 여러 대의 서버로 들어오는 네트워크 트래픽을 자동으로 분산해 주는 서비스

### 왜 Load Balancer 가 필요한가?
- EC2 서비스 전달
- 웹 서비스는 처음 만들 때, 서버 한 대에서 시작함
- 서버 한 대로 운영하면 아래의 문제들이 생긴다.
- 서비스를 안정화하기 위해서 서버를 여러 개 추가하더라도, 안정화 되는 건 아니다.
  - 여러 서버를 사용한다 하더라도 사용자 요청이 특정 서버에만 몰리거나 장애난 서버로 계속 요청 전달 되면 서비스 품질이 떨어진다.

### 사용 이유
1. 트래픽 관리 및 부하 분산
2. 고가용성 및 자동 장애 조치
3. 확장성 및 비용 효율성
4. 보안 강화 및 SSL 관리
5. 모니터링 및 관리 용이성

### ELB가 해결하는 방식
- 사용자는 ELB로 접속을 요청
- ELB는 연결되어 있는 리소스들 중에 “건강하고” 트래픽도 얼마 없는 요청을 분리해서 줄 수 있다.

**‼️요청 분산으로 전반적인 처리 성능 높이기**

### 역할
1. 요청 분산
2. 장애 서버 제외
3. 단일 진입점 제공
4. 서버 확장 지원
5. HTTPS 처리
6. 요청 분리

### 장애 대응 방식
- 서버를 여러대 도는 이유는 고가용성, 내결합성
- 서버를 안정적으로 유지되기 위해서

### 헬스 체크
- 로드 밸런서가 서버의 상태를 주기적으로 확인하는 기능
- 정상 서버에게만 요청을 보내기 위한 상태 확인

### 구조
#### 1. Load Balancer
- 사용자가 접속하는 입구
- 사용자는 LB 경로만 알면 요청 할 수 있다.

#### 2. Listener
- ELB가 특정 포트에서 요청을 기다리는 입구
- 사용자는 요청을 HTTPS로 안전하게 전달하고 ALB는 서버 내부에 HTTP 요청을 전달하게 된다
- Listener에서 HTTP, HTTPS 요청을 받아주게 된다

#### 3. Rule
- 이 요청을 어디로 보낼거냐란 규칙

#### 4. Target Group
- 타겟 그룹은 실제 요청을 처리할 서버들의 묶음
- 타겟 그룹을 설정할 때는 이런 설정
  - 대상 유형
  - 프로토콜
  - 포트
  - Health Check 경로
  - 성공 코드
  - 등록 대상
- 타겟 그룹은 지정한 프로토콜 + 포트로 등록된 대상에게 요청을 전달하게 된다

#### 종류
- ELB에는 여러가지 로드 밸런서를 포함하고 있다
- 기준
  - 웹서비스 + REST API -> ALB
  - TCP, UDP처럼 HTTP가 아니면 -> NLB

#### ALB
- HTTP, HTTPS 요청을 이해한다
- L7 레이어 - 응용 계층 레이어
- 이 것들을 기준응로 요청을 분기할 수 있다

### 구성 방법
#### 1. 보안 그룹 구성
- ELB를 구성할 때는 애플리케이션 서버를 인터넷에 노출하지 않는다

##### ALB 보안 그룹
- Inbound-80
- Inbound-443
- Outbound-8080

##### 애플리케이션 보안 그룹 
- Inbound-8080
- Inbound-22
- Outbound-3306

⚠️ 8080 포트를 0.0.0.0/0으로 열지 않기

#### 2. HTTPS 처리
- 현업에서는 HTTPS 처리
  - 요청의 HTTPS - SSL을 제거하는 처리
  - 응답에 HTTPS를 붙이는 처리
- 애플리케이션 서버에서 하지 않고, ALB에서 처리한다
  - ALB에 인증서를 붙여야 하고, ACM를 통해서 인증서 발급 받으면 된다.

##### 장점
1. 인증서 중앙 관리
2. 서버 확장 편리
3. 자동 갱신 활용
4. 애플리케이션 단순화

---

#### 💡 정리
- ELB: 여러 서버에 요청을 분산하는 AWS 서비스
- ALB: HTTP/HTTPS 웹 서비스에 주로 사용하는 로드 밸런서
- Listener: ELB가 요청을 받는 포트와 프로토콜
- Rule: 요청을 어디로 보낼지 결정하는 규칙
- Target Group: 실제 요청을 처리하는 서버 묶음
- Health Check: 정상 서버에게만 요청을 보내기 위한 상태 확인

## 3. Cloudfront
> 전 세계에 분산된 서버 네트워크(CDN)를 통해 사용자에게 콘텐츠를 빠르고 안전하게 전달하는 서비스

### 필요한 이유
- 웹서비스를 운영 하면 사용자가 요청하는 파일, API 응답은 원본 서버에 만들어짐
  - 정적 웹 페이지 파일 : S3
  - 이미지, 영상 : S3
  - 백엔드 API: ALB -> EC2
- 처음 이 구조만으로 동작을 잘하지만 사용자가 많아지거나, 서버의 거리가 멀어지면 문제가 생긴다

#### 문제
1. 페이징 로딩이 느림
2. 이미지 요청이 원본 서버에 집중
3. 갑작스러운 트래픽 증가
4. 서버 비용 증가
5. 원본 S3 또는 서버 직접 노출

#### CDN 역할
- 클라우드프론트 <- CDN
  - 사용자 <-> 원본 서버 사이에 캐시 계층
  - 전 세계 분산되어 있는 CDN을 둬서 원본을 요청하지 않더라도, CDN 에 데이터를 가져올 수 있게 한다.

#### CDN이란?
- 여러 지역에 컨텐츠 전달 서버를 분산 배치, 사용자랑 가까운 서버에서 콘텐츠를 내려 받도록 하는 방식
- CloudFront는 AWS에서 제공하는 CDN이다

#### 엣지 로케이션
- AWS CloudFront가 콘텐츠를 캐시하고 사용자에게 더 빠르게 전달하기 위해 전 세계에 분산된 데이터 센터
- 엣지 로케이션에는 원본 데이터 들어있는데, 영구적으로 저장하지는 않고 자주 요청되는 콘텐츠의 복사본을 잠시 들고 있는 서버

### 사용이유
1. 전송 속도 최적화
2. 트래픽 관리 및 안정성
3. 보안 기능 통합
4. 다양한 AWS 서비스와의 통합성
5. 비용 효율성

### Cloudfront 구성요소
1. Distribution : CloudFront 배포 단위, 어떤 원본과 캐시 정책을 사용할지 정의 
2. Viewer : CloudFront에 요청하는 사용자 또는 브라우저 
3. Edge Location : 사용자 가까이에서 캐시된 콘텐츠를 전달하는 위치 
4. Origin : 원본 콘텐츠가 실제 저장된 위치 
5. Cache Behavior : 어떤 경로를 어떤 원본으로 보내고, 어떻게 캐시할지 정하는 규칙 
6. Cache Policy : 캐시 키와 TTL 등 캐시 동작을 결정하는 정책 
7. OAC : S3 원본에 CloudFront만 접근하도록 제한하는 기능

#### Cache Behavior
- URL 경로에 따라서 어떤 원본으로 캐시를 어떻게 적용할지 정하는 규칙
- 웹 정적 페이지를 HTML 같은 파일
  - Cloudfront 캐싱을 한다
  - HTML 파일은 변경되는 주기가 뚜렷하다(배포할 때)
  - 배포 스크립트에다가 캐시 무효화 코드를 같이 넣는다

#### 어떤 컨텐츠를 캐시해야하나?
모든 요청을 다 비슷하게 캐시하면 안되고, 콘텐츠 특성에 따라서 캐시 전략을 설정해야한다

### CloudFront vs ELB
- 모두 사용자 요청 앞단에 위치하지만 해결하려고 하는 문제가 다르다
- CloudFront: 콘텐츠 캐싱과 글로벌 전송 가속
- ELB: 여러 서버에 요청 분산

---

#### 💡정리
- CloudFront: AWS의 CDN 서비스
- CDN: 사용자 가까운 위치에서 콘텐츠를 전달하는 분산 네트워크
- Origin: 콘텐츠 원본 위치
- Edge Location: 콘텐츠를 캐시하고 사용자에게 전달하는 위치
- Cache Behavior: URL 경로별 Origin·캐시 규칙

> CloudFront 는 “파일을 저장하는 것” 이 아니라 원본 콘텐츠를 사용자 가까이에서 빠르게 전달할 때 원본 서버에 반복 요청을 줄일 때 사용한다.
