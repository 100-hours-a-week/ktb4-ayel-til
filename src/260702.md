## 1. Docker Compose
> 여러 컨테이너로 구성된 애플리케이션을 YAML 형식의 파일로 명확하게 정의하고, 단일 명령어로 동시에 실행 및 관리할 수 있도록 지원하는 Docker의 공식 오픈소스 도구

### 나온 이유
#### Docker 명령어로만 구성했을 때 어려움
- 여러 개의 서비스를 실행, 네트워크 생성, 볼륨 설정, 명령어 직접 작성
- 처음에는 실행 할 수 있지만,
  - 서비스가 늘어가거나 
  - 운영 중 수시로 껐다 키거나
  - 명령어 수정되거나 
  - 다른 개발자가 사용할 때
- 실행 순서 기억
  - 백엔드는 db 생성 후 생성되는데 데이터베이스 컨테이너는 만드는데 시간이 오래걸린다

**‼️ 도커 컴포즈는 컨테이너 여러 개를 하나의 애플리케이션으로 관리하기 어려우니 해결하려고 함**

```
애플리케이션 구성
├── 어떤 이미지로 실행할지
├── 어떤 Dockerfile로 빌드할지
├── 어떤 포트를 열지
├── 어떤 환경 변수를 넣을지
├── 어떤 네트워크에 연결할지
├── 어떤 볼륨을 연결할지
├── 어떤 서비스에 의존하는지
└── 장애 시 재시작할지
```
**💡 docker compose 파일에 적어두고 사용한다**

### 핵심 개념
#### 1. Project
- 도커 컴포즈 실행어 -> `docker compose up -d`
- memo-app Stack or Project

#### 2. Service
실행해야 하는 컨테이너의 역할

```
services:
  backend:
    image: my-backend:1.0.0

  mysql:
    image: mysql:8.0

  nginx:
    image: nginx:stable-alpine
```

- backend, mysql, nginx <- 서비스의 이름
- 서비스는 컨테이너의 이름이 아니라, 애플리케이션 내부에서 사용하는 **논리적인 역할 이름**
- 하나의 서비스는 여러 개의 컨테이너로 확장 가능

```
docker compose up -d --scale backend=3
# memo-app-backend-1
# memo-app-backend-2
# memo-app-backend-3
# docker compose 에서 container_name 지정 # container 이름은 식별자,
# 포트는 어떻게 사용하나요?
# scale 이 필요하면 포트 공개도 하면 안된다.
ports:
- 8080: 8080
```

#### 3. Network
- compose 를 사용하면 별도로 네트워크를 만들지 않아도, 기본 네트워크 자동 생성

``` 
services:
  backend:
    image: my-backend:1.0.0

  mysql:
    image: mysql:8.0
    
  nginx:
	  image: nginx:sts
``` 

#### 4. Volume
- 컨테이너 삭제되면 내부 데이터가 날라감
- 볼륨으로 호스트 저장소 사용 할 수 있다

#### 5. 환경변수
- 환경 변수 -> 컨테이너마다 다른 값을 넣는다
- 환경 변수 -> 추가되거나 변경되는 경우도 있다

- API key, PW <- yaml에 적지 않는다
- docket-compose.yaml <- 깃허브로 공유되어야 하는 파일
- .env or Secret 관리해주는 서비스로 주입 받는다

#### 6. depend_on
- 서비스 간 생성 ,시작 순서, 의존성을 선언
- 컨테이너의 생성 시작 순서를 조정할 수 있는데 실제 요청 준비 순서를 보장하지는 않는다
- 컨테이너 실행 순서
- 내부에서 설계 프로세스가 준비되는 순서는 일치하지 않는다

#### 1. Nginx + WAS + DB
특히 개발 서버를 만들 때 많이 사용한다

**운영 서버**
- 서비스 별로 보통 컨테이너들이 분리되어 구성이 많다.
  - EC2 → BE EC2 [ BE Container]
  - EC2 → FE EC2 [ FE Container]
- 사이드카 패턴 = 메인 컨테이너 옆에 보조 컨테이너를 붙이는 패턴

**개발 서버**
- 하나의 서버를 운영하는 경우가 많다.
- 개발자들이 본인이 만든 기능을 테스트 해보는게 주 목적이다.
  - 하나의 EC2 여러가지 컨테이너 둬야함

**로컬 서버**

### 주의 해야하는 상황
1. latest 태그 피하기
- 실제로 어떤 버전 배포하는지 모름

## 2. IaC (Infrastructure as Code)
- 처음에는 콘솔이 제일 직관적이다.
- 하지만 운영이 시작되면 "같은 작업을 다시 해야하는 상황"이 많아진다
- 그때는 기능이 아니라 관리 방식이 문제다

> 운영이 시작되면 처음 만든 사람의 기억에 의존하기 시작한다 -> 기억 기반 인프라.

기억은 문서가 아니고, 문서는 자동으로 갱신되지 않는다

#### 문제
1. 인프라를 기억에 의존하면서 문제 발생
2. 긴급 대응 후 기록 X
3. 같은 환경을 다시 만들 수 없음
4. 여러 리소스를 동시에 수정해야한다
5. 사람마다 설정 방식이 다른다
6. 리뷰 없이 콘솔 수정은 바로 운영 반영
7. 퇴사자 인프라 / 좀비 리소스

❓ 코드는 Git으로 관리하는데, 인프라에도 Git이 필요하지 않을까? -> IaC
- 문서 대신 코드 (기억 대신 코드)
- 수동 반복 대신 코드
- 즉시 반영 대신 리뷰
- 감으로 복구 대신 재현
- IaC는 인프라 운영의 Git화

---

### 선언형 IaC와 코드형 IaC
- Console: 눈으로 보면서 이해
- CLI: 명령어로 빠르게 조작 
- 선언형 IaC: 원하는 상태를 파일로 관리 
- 코드형 IaC: 반복되는 패턴을 언어로 추상화

#### 선언형 IaC - 무엇이 있어야 하는가
- 원하는 최종 상태를 적음
- 도구가 순서와 의존성을 계산
- Terraform, CloudFormation
  - 리소스와 설정을 적고 도구가 생성 순서를 계산한다

#### 장점
- 인프라 구조가 비교적 눈에 잘 보인다
- Plan / Change Set으로 변경 전 확인할 수 있다
- 코드 리뷰와 버전 관리가 쉽다
- 작은 실습과 기본 인프라에 적합하다

#### 단점 
- 환경이 많아지면 파일이 길어질 수 있다
- 조건, 반복, 재사용 표현이 제한적으로 느껴질 수 있다
- 복잡한 조직 표준을 매번 직접 적기 어렵다
- 모듈 설계가 없으면 복붙 인프라가 된다

---

#### 코드형 IaC - 인프라를 함수로 만든다
- 일반 프로그래밍 언어로 작성
- 조건문, 반복문, 클래스 사용
- AWS CDK, Pulumi
  - typeScript, Python 사용

#### 필요한 순간
- 모든 서비스에 같은 태그 정책 적용
- 서비스마다 ALB + Target Group + SG 생성
- 환경별 dev/stage/prod 설정 분리
- 보안 표준을 Construct로 감싸기

#### 장점
- 조건문, 반복문으로 환경별 구성 표현
- 함수, 클래스, 패키지로 표준 재사용
- 테스트 코드와 정적 분석 적용 가능

#### 단점
- 실제 리소스가 추상화 뒤에 숨을 수 있음
- 코드가 복잡해지면 리뷰가 어려움
- 프로그래밍 경험이 약하면 학습 부담이 큼

---

### 실무에서 어떻게 쓰는가
- 초반에는 리소스가 보이는 방식이 좋고, 조직 규모가 커지면 추상화가 필요하다
- 권장 순서: Console- Terraform/CloudFormation- Module - CDK/Pulumi

### 핵심 개념
- State: 코드와 실제 AWS 리소스를 연결하는 기록 ⭐️
- Plan: 적용 전에 변경 내용 미리보기 ⭐️ 
- Apply: 실제 인프라에 변경 사항을 적용

### 장점
- 누가 바꿨는지 Git에 남는다.
- 왜 바꿨는지 PR에 남는다
- 위험한 보안 변경을 리뷰에서 잡을 수 있다
