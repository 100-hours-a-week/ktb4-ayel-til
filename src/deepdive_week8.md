## **Registry**

**레지스트리(Registry)**란 **Docker 이미지를 중앙에서 저장하고 관리하는 저장소**다. 사용자는 이미지를 **업로드**(Push)하거나 **다운로드**(Pull)하여 필요한 환경에서 동일한 이미지를 사용할 수 있다. Docker 호스트는 레지스트리에서 이미지를 내려받아(Pull) 이를 기반으로 컨테이너를 생성하고 실행한다.

레지스트리를 사용하면 개발 환경에서 생성한 이미지를 서버나 다른 개발자와 쉽게 공유할 수 있다. 동일한 이미지를 기반으로 컨테이너를 실행하여 개발, 테스트 및 운영 환경에서 일관된 실행 환경을 유지할 수 있으며, 이를 통해 **환경 차이로 인해 발생하는 문제를 줄일 수 있다**.

![](./images/registry.png)

레지스트리는 이미지를 단순한 하나의 파일로 저장하는 것이 아니라 **Repository, Tag, Layer, Manifest 등의 구조와 정보를 기반으로 이미지를 저장하고 관리한다.**

**Repository**는 관련된 이미지들을 하나의 단위로 모아 관리하는 공간이며, **Tag**는 저장된 이미지의 버전이나 배포 단계를 구분하기 위한 식별자 역할을 한다. 태그를 통해 하나의 Repository에서 여러 버전의 이미지를 구분하고 관리할 수 있다.

Docker 이미지는 여러 개의 **Layer**로 구성되며, 레지스트리는 이러한 Layer를 저장하고 관리한다. 여러 이미지에서 동일한 Layer가 사용되는 경우 중복되는 Layer를 다시 저장하거나 전송하지 않고 재사용할 수 있어 저장 공간과 네트워크 사용량을 줄일 수 있다.

**Manifest**는 특정 이미지가 어떤 Layer로 구성되어 있는지와 해당 이미지의 구성 정보를 나타내는 메타데이터다. 레지스트리는 Manifest를 통해 이미지의 구성을 식별하고, 사용자가 이미지를 Pull할 때 필요한 Layer를 확인하여 제공한다.

따라서 레지스트리는 단순히 이미지를 보관하는 저장 공간이 아니라, 이미지를 중앙에서 저장하고 공유하며 여러 버전을 체계적으로 관리하고 배포할 수 있도록 지원하는 시스템이다.

레지스트리는 접근 방식과 운영 목적에 따라 **Public Registry**와 **Private Registry**로 구분할 수 있다.

## **Public Registry**

**Public Registry**는 인터넷을 통해 접근할 수 있는 공개 컨테이너 이미지 저장소다. 대표적으로 Docker Hub가 있으며, 사용자는 공개된 이미지를 내려받아 사용하거나 자신이 만든 이미지를 저장하고 다른 사용자와 공유할 수 있다.

Public Registry의 대표적인 특징은 **높은 접근성과 이미지 공유의 편리성**이다. 사용자는 별도의 레지스트리 서버를 직접 구축하고 관리하지 않아도 되며, 인터넷에 연결된 환경이라면 필요한 이미지를 쉽게 내려받아 사용할 수 있다.

대표적인 Public Registry인 Docker Hub는 일반 사용자가 공개한 이미지뿐만 아니라 **Docker Official Images**, **Verified Publisher 이미지** 등 이미지의 출처와 신뢰성을 구분할 수 있는 체계를 제공한다. 따라서 사용자는 다양한 소프트웨어의 이미지를 직접 처음부터 구성하지 않고 필요한 이미지를 활용할 수 있다.

---

#### **장점**

Public Registry의 첫 번째 장점은 **비용과 운영 부담이 적다는 것**이다. 자체 레지스트리를 구축하려면 서버와 스토리지 등의 인프라가 필요하며, 지속적인 관리와 유지보수도 필요하다. Public Registry는 별도의 인프라를 직접 구축하지 않고 사용할 수 있어 초기 비용과 관리 부담을 줄일 수 있다.

두 번째 장점은 **접근성과 공유의 편리성**이다. 인터넷을 통해 다양한 환경에서 필요한 이미지를 쉽게 Pull할 수 있으며, 자신이 만든 이미지를 다른 개발자와 공유할 수도 있다. 또한 공식 이미지와 검증된 게시자의 이미지를 활용할 수 있어 필요한 실행 환경을 빠르게 구성할 수 있다.

---

#### **단점**

Public Registry는 인터넷을 기반으로 여러 사용자가 이미지를 공유하는 환경이기 때문에 **보안과 이미지 신뢰성 측면에서 주의가 필요하다.**

다양한 사용자가 이미지를 공개할 수 있으므로 이미지의 출처를 확인하지 않고 사용할 경우 악성 코드가 포함된 이미지나 정상적인 이미지와 유사한 이름으로 배포된 이미지를 사용할 위험이 있다. 그리고 신뢰할 수 있는 이미지라 하더라도 이미지 내부의 운영체제 패키지나 라이브러리에 알려진 보안 취약점이 포함되어 있을 가능성이 있다.

기업 내부에서 사용하는 애플리케이션 이미지는 외부에 공개되어서는 안 되는 코드나 내부 시스템과 관련된 정보를 포함할 가능성이 있으므로 이미지의 공개 범위와 접근 권한을 신중하게 관리해야 한다.

특히 조직 내부 이미지에 대한 세밀한 접근 제어나 독립적인 보안 정책이 필요한 환경에서는 Public Registry만으로 요구사항을 충족하기 어려울 수 있다.

또한 Public Registry는 외부 네트워크를 통해 이미지를 Push하고 Pull하기 때문에 **인터넷 연결 상태와 외부 서비스의 가용성에 영향**을 받을 수 있다. 특히 대규모 이미지를 전송하거나 여러 서버가 동시에 이미지를 Pull하는 경우 네트워크 지연이나 서비스의 요청 제한 정책이 배포 속도에 영향을 줄 수 있다.

---

#### **한계의 보완**

Public Registry의 공개적인 특성에서 발생할 수 있는 위험을 줄이기 위해서는 **이미지 출처 검증과 취약점 분석**이 필요하다.

**Docker Content Trust(DCT)** 는 디지털 서명을 기반으로 이미지의 무결성과 게시자를 검증하는 방식이다. 이를 통해 사용자가 내려받은 이미지의 출처와 배포 과정에서의 변조 여부를 확인할 수 있다.

**그리고 Docker Scout**와 같은 이미지 분석 도구를 활용하면 이미지에 포함된 소프트웨어 구성 요소를 분석하고, 알려진 취약점 정보와 비교하여 보안 취약점을 확인할 수 있다.

이러한 방법은 이미지 자체의 신뢰성과 안전성을 검증하기 위한 것이며, 조직 내부 이미지에 대한 접근 자체를 통제하는 것과는 차이가 있다. 따라서 강력한 접근 제어와 인증, 내부망 운영 및 독립적인 보안 정책이 필요한 환경에서는 **Private Registry**를 고려할 수 있다.

## **Private Registry**

**Private Registry**는 조직이나 사용자가 직접 구축하여 운영하는 비공개 컨테이너 이미지 저장소다. Public Registry를 거치지 않고 자체 서버나 사내 인프라에 레지스트리를 구축하여 이미지를 저장하고 배포할 수 있으며, 인증과 접근 제어를 통해 허가된 사용자와 시스템만 접근하도록 제한할 수 있다.

대표적인 구축 방법으로는 **Docker Registry**를 직접 컨테이너로 실행하는 방식과 **Harbor**와 같은 레지스트리 플랫폼을 구축하는 방식이 있다.

Docker Registry는 이미지 저장과 Push/Pull을 위한 기본적인 레지스트리 기능을 제공하며, 비교적 단순한 구조로 자체 이미지 저장소를 구축할 수 있다.

Harbor는 레지스트리 기능을 기반으로 사용자 및 프로젝트 관리, 역할 기반 접근 제어(RBAC), 이미지 취약점 분석 등 조직 환경에서 필요한 다양한 관리 기능을 제공한다.

자체 Private Registry는 사내 네트워크나 접근이 제한된 네트워크 환경에서 운영할 수 있다. **인증**과 **접근 제어**를 적용하여 허가된 사용자나 시스템만 이미지를 Push하거나 Pull할 수 있도록 구성할 수 있다. 이를 통해 기업 내부에서 사용하는 이미지를 외부 Public Registry에 노출하지 않고 조직의 보안 정책에 따라 관리할 수 있다.

자체 Registry를 컨테이너로 운영할 경우에는 **이미지 데이터의 영속성**을 고려해야 한다. 컨테이너가 삭제되거나 재생성되어도 이미지 데이터를 유지할 수 있도록 `/var/lib/registry`를 **Docker Volume 또는 외부 스토리지와 연결**하여 데이터를 별도로 관리해야 한다.

그리고 Registry와 클라이언트 간의 안전한 이미지 Push/Pull을 위해 **TLS를 적용하여 통신을 암호화**해야 한다. 이를 통해 Registry 서버의 신원을 확인하고 이미지 전송 과정에서 발생할 수 있는 보안 위험을 줄일 수 있다.

이처럼 자체 Private Registry는 이미지의 저장 위치와 접근 권한뿐만 아니라 데이터 영속성과 통신 보안까지 조직이 직접 통제할 수 있다는 특징이 있다.

---

#### **장점**

자체 Private Registry의 첫 번째 장점은 **보안과 기밀성 확보**다. 기업 내부 이미지를 자체 인프라에서 관리하고, 인증과 접근 제어를 통해 허가된 사용자와 시스템만 접근하도록 제한할 수 있다.

두 번째 장점은 **빠르고 안정적인 이미지 배포**다. Registry와 배포 서버가 동일한 내부 네트워크에 위치하면 외부 인터넷을 거치지 않고 이미지를 전송할 수 있다. 따라서 네트워크 지연과 외부 Registry의 장애 및 Pull 요청 제한에 대한 영향을 줄일 수 있다.

세 번째 장점은 **높은 통제권**이다. 이미지 저장 용량과 보관 정책을 직접 결정할 수 있으며, Registry 플랫폼에 따라 RBAC, LDAP, SSO 등의 인증 체계와 연동하여 사용자와 프로젝트별 권한을 세밀하게 관리할 수 있다.

---

#### **단점**

자체 Private Registry의 가장 큰 단점은 **구축 비용과 운영 부담**이다. Registry 서버, 스토리지, 네트워크 및 백업 환경을 직접 구성하고 지속적으로 관리해야 한다.

그리고 이미지가 계속 쌓이면 **스토리지 용량 관리 문제**가 발생할 수 있으므로, 사용하지 않는 이미지와 오래된 버전을 정리하고 이미지 보관 및 삭제 정책을 관리해야 한다.

마지막으로 Private Registry를 구축했다고 해서 보안이 자동으로 보장되는 것은 아니다. **TLS 인증서, 사용자 인증, 접근 권한 및 보안 업데이트** 등을 지속적으로 관리해야 하며, 잘못된 설정은 외부 노출이나 무단 접근으로 이어질 수 있다.

따라서 자체 Private Registry는 높은 보안성과 통제권, 안정적인 내부 배포 환경을 제공하지만 이를 운영하기 위한 인프라 비용과 관리 역량이 필요하다.

## **장단점 비교**

#### **장점 비교**

| Public Registry | 자체 Private Registry |
| --- | --- |
| 초기 구축 비용과 운영 부담이 적음 | 내부 이미지를 외부에 노출하지 않고 관리 가능 |
| 높은 접근성과 이미지 공유의 편의성 | 인증과 접근 제어를 조직 정책에 맞게 구성 가능 |
| 공식 이미지와 검증된 게시자의 이미지 활용 가능 | 내부 네트워크를 활용한 빠르고 안정적인 이미지 배포 가능 |
| 별도의 서버와 스토리지 관리 부담이 적음 | 저장 정책과 사용자 권한 등을 직접 통제 가능 |

#### **단점 비교**

| Public Registry | 자체 Private Registry |
| --- | --- |
| 이미지의 출처와 신뢰성 검증 필요 | 초기 인프라 구축 비용 발생 |
| 악성 이미지 및 알려진 취약점 사용 위험 | 지속적인 유지보수와 운영 인력 필요 |
| 외부 네트워크와 서비스 가용성에 의존 | 이미지 증가에 따른 스토리지 관리 필요 |
| 사용량 및 Pull 요청 제한의 영향을 받을 수 있음 | TLS, 인증 및 접근 권한 등을 직접 관리해야 함 |

## **보안, 비용, 배포 속도 관점**

#### **1. 보안**

| Public Registry | 자체 Private Registry |
| --- | --- |
| 인터넷을 통한 접근 | 내부망 또는 제한된 네트워크에서 운영 가능 |
| 서비스 제공자의 보안 정책에 의존 | 조직의 보안 정책을 직접 적용 가능 |
| 공개 이미지의 출처와 신뢰성 확인 필요 | 허가된 사용자와 시스템 중심으로 접근 제한 |
| 이미지 노출 및 악성 이미지 사용 위험 | 인증과 접근 제어를 통한 내부 이미지 보호 |
| 이미지 서명 검증 및 취약점 분석 필요 | 자체 인증, 접근 제어 및 보안 정책 구성 가능 |

보안 측면에서는 자체 Private Registry가 높은 통제권을 제공한다. Public Registry는 인터넷을 통해 접근할 수 있고 다양한 사용자가 이미지를 공유하므로, 외부 이미지를 사용할 때 이미지의 출처와 취약점을 검증하는 과정이 중요하다.

자체 Private Registry에서는 내부망이나 제한된 네트워크 환경에서 운영할 수 있고, 인증과 접근 제어를 적용하여 허가된 사용자와 시스템만 이미지에 접근하도록 구성할 수 있다. 따라서 기업 내부 이미지를 외부에 공개하지 않고 자체 보안 정책에 따라 관리해야 하는 환경에 적합하다.

그러나 Private Registry를 사용한다고 해서 보안이 자동으로 보장되는 것은 아니다. TLS 인증서, 사용자 인증, 접근 권한, 이미지 취약점 관리 등을 조직이 직접 구성하고 지속적으로 관리해야 하므로 잘못된 설정이나 관리 부족이 새로운 보안 위험으로 이어질 수 있다.

---

#### **2. 비용**

| Public Registry | 자체 Private Registry |
| --- | --- |
| 초기 구축 비용이 낮음 | 초기 인프라 구축 비용 발생 |
| 무료 또는 구독형 서비스 이용 가능 | 서버, 스토리지, 네트워크 비용 발생 |
| 서비스 제공자가 인프라 관리 | 조직이 직접 유지보수 |
| 운영 인력 부담이 적음 | 전문 운영 인력 필요 |
| 사용량 증가 시 요금제 비용 증가 가능 | 규모에 따라 인프라 확장 비용 발생 |

비용 측면에서는 초기 규모가 작은 환경에서 Public Registry가 유리하다. 자체 서버와 스토리지를 구축할 필요가 없고 레지스트리 시스템의 유지보수를 서비스 제공자가 담당하기 때문에 초기 비용과 운영 부담을 줄일 수 있다.

자체 Private Registry에서는 서버, 스토리지, 네트워크, 백업 등의 인프라를 직접 구축해야 하며 이를 운영할 인력도 필요하다. 따라서 초기 구축 비용과 지속적인 운영 비용이 발생한다.

그러나 조직의 규모가 커지고 저장하는 이미지와 배포 대상 서버가 증가하면 단순히 서비스 이용 요금만 비교해서는 안 된다. 자체 Private Registry는 기존 인프라를 활용하고 저장 용량과 이미지 보관 정책을 조직이 직접 결정할 수 있으므로, 대규모 환경에서는 보안 요구사항과 운영 규모를 포함한 전체 비용을 기준으로 판단해야 한다.

---

#### **3. 배포 속도**

| Public Registry | 자체 Private Registry |
| --- | --- |
| 외부 인터넷 네트워크에 의존 | 내부 네트워크를 통한 전송 가능 |
| 네트워크 상태와 외부 서비스의 영향을 받음 | 네트워크 환경을 조직이 직접 통제 가능 |
| 요청 제한 정책의 영향을 받을 수 있음 | 자체 정책에 따라 요청 처리 가능 |
| 대규모 동시 Pull 시 외부 네트워크 부하 가능 | 내부의 반복적·대규모 배포에 유리 |

Public Registry에서 이미지를 Pull하려면 일반적으로 외부 네트워크를 거쳐야 하므로 인터넷 연결 상태, 이미지 크기, 외부 서비스 상태 등에 따라 전송 시간이 영향을 받을 수 있다. 특히 여러 배포 서버가 동시에 큰 이미지를 Pull하는 경우 네트워크 병목이나 외부 서비스의 요청 제한 정책이 배포 과정에 영향을 줄 수 있다.

자체 Private Registry를 배포 서버와 동일한 내부 네트워크 또는 가까운 네트워크 환경에 구축하면 외부 인터넷을 거치지 않고 이미지를 전송할 수 있다. 따라서 여러 서버에 동일한 이미지를 반복적으로 배포하는 대규모 환경에서는 네트워크 지연을 줄이고 안정적인 배포 환경을 구성하는 데 유리하다.

하지만 Private Registry라고 해서 항상 Public Registry보다 빠른 것은 아니다. Registry 서버의 성능, 스토리지 I/O, 네트워크 대역폭이 부족하면 자체 Registry가 오히려 병목 지점이 될 수 있으므로 배포 규모에 맞는 인프라 설계가 필요하다.

---

### **💡 결론 - 스타트업과 대기업 환경에서는 어떤 선택이 합리적인가?**

#### **스타트업 환경**

스타트업은 일반적으로 초기 인프라 비용과 운영 인력을 최소화하면서 서비스를 빠르게 개발하고 배포하는 것이 중요하다. 자체 Private Registry를 구축하면 서버와 스토리지뿐만 아니라 인증, TLS, 백업, 모니터링 및 보안 업데이트 등을 직접 관리해야 하므로 규모가 작은 조직에서는 운영 부담이 커질 수 있다.

따라서 초기 단계의 스타트업에서는 **Public Registry를 활용하는 것이 상대적으로 합리적**이다. 별도의 레지스트리 인프라를 구축하지 않고 빠르게 개발 환경을 구성할 수 있으며, 초기 비용과 관리 부담을 줄여 개발과 서비스 개선에 자원을 집중할 수 있기 때문이다.

그러나 스타트업이라고 해서 항상 공개 저장소만 사용해야 하는 것은 아니다. 기업 내부 이미지의 기밀성이 중요하거나 보안 요구사항이 높은 서비스를 운영한다면 비공개 저장 기능이나 관리형 Private Registry를 선택하는 것이 더 적절할 수 있다. 따라서 스타트업에서는 조직 규모만이 아니라 보안 요구 수준과 운영 역량을 함께 고려해야 한다.


#### **대기업 환경**

대기업은 다수의 개발팀과 서비스가 존재하고, 많은 이미지와 배포 서버를 관리하는 경우가 많다. 또한 기업 내부 보안 정책, 사용자별 권한 관리, 감사 및 규정 준수와 같은 요구사항이 중요하므로 이미지 저장과 배포 환경에 대한 높은 수준의 통제권이 필요하다.

이러한 환경에서는 **자체 Private Registry가 합리적 선택이 될 수 있다.** 내부망을 기반으로 레지스트리를 운영하고 인증과 접근 제어를 적용하여 사용자, 팀 또는 프로젝트 단위로 이미지 접근 권한을 관리할 수 있기 때문이다. 또한 내부 네트워크를 활용하면 많은 서버가 반복적으로 이미지를 Pull하는 대규모 배포 환경에서 외부 네트워크에 대한 의존도를 줄일 수 있다.

대기업은 자체 인프라와 전문 운영 인력을 확보한 경우가 많으므로 Private Registry의 구축과 유지보수에 필요한 비용을 감당하면서 보안성, 통제권 및 배포 효율성을 확보할 수 있다.

하지만 기업 규모만으로 Registry의 종류를 결정하는 것은 적절하지 않다. 실제 선택에서는 이미지의 기밀성, 보안 요구 수준, 배포 규모, 운영 인력 및 전체 비용을 함께 고려해야 한다. 따라서 **운영 부담과 초기 비용 절감이 중요한 환경에서는 Public Registry가 유리하며, 강력한 접근 통제와 독립적인 운영 환경, 대규모 내부 배포가 중요한 환경에서는 자체 Private Registry가 유리하다.**
