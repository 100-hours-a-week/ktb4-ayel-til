## 1. 공유 자원
> 여러 사용자나 프로세스, 스레드가 동시에 접근하거나 사용하는 시스템 내의 자원을 의미

### 사용이유
- 운영체제에서는 CPU, 메모리, 파일, 네트워크 <- 자원들이 무한하지 않다
- 운영체제에서는 하나의 자원을 여러 작업이 같이 수행할 수 있는 공유 자원
- 리소스 낭비를 방지하고 메모리 사용 효율성을 극대화하기 위해 사용함

1. 리소스 낭비 방지
- 자원을 독점적으로 사용하면 시스템 리소스가 낭비될 가능성이 높음
- 공유 자원을 통해 여러 사용자나 프로세스가 동일한 자원을 활용하여 시스템 효율성을 향상시킬 수 있음
2. 데이터 일관성 유지
- 공유 데이터를 사용하면 데이터를 일관적으로 유지
3. 협업 가능성 증대
- 데이터를 공유함으로써 여러 사용자가 동시에 협력 작업을 수행할 수 있음
- ex) 파일 공유, 데이터베이스에서 공동 작업

### 문제점
1. 동시에 공유자원을 수정
2. 경쟁 상태
- 여러 작업들이 공유 자원에 동시 접근
- 실행 순서에 따라 결과 달라질 수 있다
  
---

## 2. 임계 영역
> 공유 자원에 접근하는 프로그램 코드의 일부분으로, 동시에 여러 프로세스나 스레드가 접근하면 문제가 생길 수 있는 구간

### 사용 이유
1. 데이터 무결성 유지: 여러 스레드가 동시에 같은 데이터를 수정해도 데이터가 깨지지 않도록 하기 위해
2. 경합 조건 방지: 실행 순서에 따라 결과가 달라지는 문제를 막기 위해
3. 예측 가능한 프로그램 실행: 같은 입력에 대해 항상 같은 결과가 나오도록 만들기 위해
4. 시스템 안정성 확보: 멀티스레드 환경에서 데이터 손상, 중복 처리, 누락 처리를 줄이기 위해

### 문제점
1. 경합 조건 (Race Condition)
- 여러 스레드가 동시에 공유 자원에 접근할 때, 실행 순서에 따라 결과가 달라지는 문제
- 임계 영역의 실행 순서에 따라 결과 값이 달라질 수 있다. (Lost Update)

2. 데이터 무결성
- 데이터가 논리적으로 맞지 않는 상태가 되는 문제
- ex) 재고 1개인데 동시에 주문이 들어와 주문은 2건 생성
- 즉시 발견되지 않아 재현과 추적이 어려울 수 있다.

3. 교착 상태 (Deadlock)
- 여러 스레드가 서로가 가진 자원을 기다리며 영원히 진행하지 못하는 상태
- 잘못된 락 획득 순서로 인해 발생할 수 있다.

## 3. 동기화
> 여러 스레드가 데이터를 안전하게 읽고, 쓸 수 있도록 접근 순서를 제어하는 기술 (데이터 변경 X)

### 임계영역 해결법
1. 동시에 들어가지 못하게 한다: 한 스레드가 임계 영역에 있으면 다른 스레드는 기다리게 한다
2. 작업이 끝나면 반드시 나온다: 락을 잡은 스레드는 작업 후 반드시 락을 해제해야 한다
3. 무한정 기다리지 않게 한다: 특정 스레드가 계속 밀려나지 않도록 보장해야 한다
4. 필요한 구간만 보호한다: 임계 영역을 너무 넓게 잡으면 성능이 떨어진다

### 임계 영역을 해결하는 3가지 조건
1. 상호 배제: 한 프로세스가 임계 영역에 있으면 다른 프로세스는 들어갈 수 없음
2. 진행: 임계 영역이 비어 있고 들어가려는 프로세스가 있으면 누군가는 들어가야 함
3. 유한 대기: 특정 프로세스가 무한히 기다리지 않아야 함

---

### 동작 방식

**1. Lock(락) / Mutex(뮤텍스)**
- 락
  - 공유 자원에 들어가기 전에 “잠금” 을 획득하고,
  - 작업 후에 “잠금” 을 해제
  - 락 사용 시 finally 꼭 사용

- 뮤텍스(Mutual Exclusion)
  - 한 번에 하나의 스레드만 임계 영역에 들어가도록 하는 락

**동작 흐름**
1. Thread 1이 lock 획득
2. Thread 1이 임계 영역 실행
3. Thread 2는 lock이 풀릴 때까지 대기
4. Thread 1이 unlock
5. Thread 2가 lock 획득 후 임계 영역 실행

---

**2. 세마포어**
- 락 <- 임계 영역에 한 명만 들어갈 수 있는 것
- 세마 포어 <- 임계 영역에 들어갈 수 있는 입장권의 개수가 정해져 있다

1. 요청이 들어옴 → permit 1개 획득
2. DB 작업 수행
3. 작업 완료 → permit 반환

---

**3. Atomic 연산**
- 읽기, 수정, 저장을 하나의 쪼갤 수 없는 연산처럼 처리하는 방식
  - CompareAndSet(CAS) 연산을 사용한다.
  -"내가 읽은 값이 아직 그대로일 때만 수정한다"를 보장

**아토믹은 모든 걸 해결하나?**
- 단일 연산은 안전하게 처리할 수 있다.
- 하지만 여러 작업을 하나의 비즈니스 로직으로 묶는 것은 한계가 있다.
- 복잡한 작업에서는 여전히 동시성 문제가 발생할 수 있다.

---

**4. 트랜잭션**
- 내부적으로 락, MVCC, Isolation  Level

---

**5. 임계 영역을 작게 유지도 해줘야한다. + 성능**
- 임계 영역은 공유 자원을 안전하게 사용하기 위해 보호해야 한다.
- 하지만 너무 넓게 잡으면 성능이 저하될 수 있다.
- 락을 획득한 스레드가 오래 머무를수록 다른 스레드들은 기다려야 한다.
- 결과적으로 처리량이 감소하고 성능이 떨어질 수 있다.

---
**백엔드 개발자 관점**
- 운영체제 레벨의 락을 직접 다루는 경우는 드물다.
- 트랜잭션, Redis Lock, 메시지 큐 등을 통해 동기화를 사용한다.

**인프라 엔지니어 관점**
- 커널, 파일 시스템, 데이터베이스, 쿠버네티스 등에서 공유 리소스의 경합을 관리한다.

---
**헷갈릴만한 것들**

1. 공유 자원 = 임계영역 같지 않다
- 공유 자원은 공유된 자원
- 임계 영역은 그 공유자원을 수정하는 코드 블럭

2. 모든 공유 자원에 접근하는 것은 다 임계 영역이 아니다
- 접근 했는데, 읽기만한다 -> 임계 아닐 가능성

3. 락을 많이 걸면 안전해지나요?
- 그렇긴한데, 성능이 나빠질 수 있어, 락의 범위를 제한해야한다

4. 락을 쓰면 다 해결되지 않는다
- 데드락, 성능저하, 기아상태, 락 누락, 락 범위 오류

**TIP**
1. 임계 영역 작게 잡아야 한다
2. 락은 잡으면 무조건 해제해라 finally
3. 순서를 통일해야한다
4. 데이터베이스에서 Unique, Transaction ← 이거 적극적으로 활용해라
5. 분산 환경에서는 로컬 락으로는 부족하다
- 서버가 여러 대일 때 DB Lock, Redis 기반으로 분산 락, 직렬화

## 4. 락
> 공유 자원 앞에 걸어두는 자물쇠
- 하나의 스레드나 프로세스가 자원을 점유할 경우 다른 스레드/프로세스가 해당 자원에 접근하지 못하도록 제어하는 기법
- 공유자원 <- 여러 프로세스 스레드 접근
  - 읽기 -> 안전
  - 쓰기 -> 결과 꼬일 수 있음

### 사용이유
- 락은 공유 자원 안전하게 쓰려고 사용

1. 데이터 무결성 유지: 여러 스레드가 동시에 데이터를 수정해 잘못된 값이 저장되는 것을 막는다
2. 경합 조건 방지: 실행 순서에 따라 결과가 달라지는 문제를 방지한다
3. 원자성 보장: 특정 작업 단위가 중간에 끊기지 않고 끝까지 실행되도록 보호한다
4. 동기화 제공: 여러 스레드가 공유 자원에 접근하는 순서를 제어한다

**공유자원, 임계영역, 락 어떤 관계인지?**
1. 공유 자원: 여러 스레드나 프로세스가 함께 사용하는 대상
2. 임계 영역: 공유 자원에 접근하는 위험한 코드 구간
3. 락: 임계 영역에 한 번에 하나의 스레드만 들어가게 만드는 도구

### 락의 동작
1. 락 요청: 스레드가 공유 자원에 접근하기 전에 락을 요청한다
2. 락 획득: 락이 비어 있으면 해당 스레드가 락을 획득한다
3. 임계 영역 실행: 락을 가진 스레드만 공유 자원을 사용한다
4. 다른 스레드 대기: 다른 스레드는 락이 해제될 때까지 기다린다
5. 락 해제: 작업이 끝난 스레드가 락을 해제한다
6. 다음 스레드 진입: 대기 중인 다른 스레드가 락을 획득하고 작업한다

---

### 락의 종류

**1. 스핀 락**
- 락이 풀릴 때까지 계속 확인하면서 기다리는 락이다
  - 락을 얻지 못할 때, 스레드가 잠들지 않고 계속해서 반복 확인한다

장점
1. 락이 아주 빨리 풀리면 빠르게 진입 가능
2. 컨텍스트 스위칭 비용이 적음 
3. 커널 내부나 짧은 임계 영역에 적합
  
단점
1. 기다리는 동안 CPU를 계속 사용 
2. 락 대기 시간이 길면 비효율적
3. 단일 CPU 환경에서는 특히 비효율적

**스핀 락 쓰이는 경우**
- 임계영역 상당히 짧고, 스레드 다시 깨우는 비용이 더 클 때
- 백엔드 개발에서는 쓸 일이 없다
  - 운영체제 커널, 런타임, 저수준 라이브러리

---

**2. 낙관적 락**
- 충돌이 거의 없다고 "가정"
- 작업은 먼저하고, 마지막에 충돌 여부를 검사하는 방식


- 기본 가정: 충돌이 자주 발생하지 않을 것이다
- 동작 방식: 먼저 읽고 수정한 뒤, 저장 시점에 버전이나 값이 바뀌었는지 검사
- 충돌 발생 시: 롤백하거나 재시도
- 적합한 상황: 읽기가 많고 쓰기가 적은 시스템
- 대표 예시: DB version 컬럼, CAS, 분산 환경의 상태 갱신

---

**3. 뮤텍스**
> 한 번에 하나의 스레드만 자원에 접근하게 하는 대표적인 락

- Mutual Exclusion -> 상호 배제

**요약**
> “공유 자원 한 번에 하나의 스레드만 들어가게하는 잠금 장치”

**핵심 3가지**
1. 상호 배제: 한 번에 하나의 스레드만 임계 영역에 들어갈 수 있다.
2. 소유권: 락을 획득한 스레드가 “현재 소유자”가 된다.
3. 해제 권한: 일반적으로 락을 획득한 스레드만 락을 해제할 수 있다.

**뮤텍스 내부**
- Lock State: 현재 잠금 상태
- Owner Thread: 현재 락 소유자
- Wait Queue: 대기 중인 스레드 목록
- Policy: 대기 스레드 처리 방식

**방식**
- FIFO: 먼저 기다린 스레드 우선
- Priority: 우선순위가 높은 스레드 우선
- Fair Lock: 대기 순서를 비교적 엄격하게 보장
- Non-fair Lock: 새로 온 스레드가 먼저 획득 가능

---

**장점**
1. 데이터 무결성 보장: 한 번에 하나의 스레드만 공유 자원에 접근하게 하므로 값이 깨지는 것을 막을 수 있다
2. 사용 방식이 직관적: lock → 작업 → unlock 구조라 이해하기 쉽다
3. 운영체제/언어 지원: 대부분의 운영체제와 언어에서 기본적으로 제공한다
4. CPU 낭비 감소: 스핀락과 달리 오래 기다릴 때 스레드를 잠들게 할 수 있다
5. 임계 영역 보호에 적합: 공유 변수, 큐, 파일, 버퍼 같은 자원을 보호하기 좋다

**단점**
1. 병렬성 감소: 한 번에 하나만 들어가므로 동시에 처리할 수 있는 양이 줄어든다
2. 컨텍스트 스위칭 오버헤드: 대기 스레드를 재우고 깨우는 과정에서 비용이 든다
3. 데드락 위험: 여러 뮤텍스를 잘못된 순서로 잡으면 서로 기다리며 멈출 수 있다
4. 락 미해제 위험: unlock()을 호출하지 않으면 다른 스레드가 계속 대기한다
5. 우선순위 역전 가능성: 낮은 우선순위 스레드가 락을 쥐고 있어 높은 우선순위 스레드가 기다릴 수 있다
6. 락 경합 성능 저하: 많은 스레드가 하나의 뮤텍스를 두고 경쟁하면 성능 병목이 된다

**해결하기 어려운 경우**
- 뮤텍스는 "한 번에 하나만 접근" 문제를 해결한다.
- 특정 조건을 만족할 때까지 기다려야 하는 경우에는 조건 변수(Condition Variable)를 함께 사용한다.

> 뮤텍스에서 가장 중요한 개념은 소유권 
> 뮤텍스는 락을 획득한 스레드가 소유자가 되고, 일반적으로 그 소유자만 락을 해제할 수 있다.

**뮤텍스** = 공유 자원 접근 권한 관리
**조건 변수** = 특정 조건 충족 여부 관리

**4. 리드 라이트 락**
> 리드-라이트 락은 읽기는 여러 명이 동시에 허용하고, 쓰기는 한 명만 허용하는 락

**상황 허용 여부**
- Reader + Reader: 가능
- Reader + Writer: 불가능
- Writer + Writer: 불가능

**장점**
1. 높은 동시성: 여러 Reader가 동시에 접근할 수 있어 읽기 중심 작업에서 성능이 좋아진다
2. 데이터 무결성 보장: Writer는 독점적으로 접근하므로 수정 중 데이터가 깨지는 것을 막을 수 있다
3. 뮤텍스보다 효율적일 수 있음: 읽기가 많고 쓰기가 적은 환경에서는 뮤텍스보다 대기 시간이 줄어든다
4. 공유 자원 활용도 증가: 읽기 작업을 병렬로 처리할 수 있어 CPU 활용도가 좋아질 수 있다

**단점**
1. 구현이 복잡함: Reader 수, Writer 상태, 대기 큐, 정책을 함께 관리해야 한다
2. Writer 기아 가능성: Reader가 계속 들어오면 Writer가 오래 기다릴 수 있다
3. Reader 기아 가능성: Writer 우선 정책에서는 Reader가 오래 기다릴 수 있다
4. 오버헤드 존재: 단순 뮤텍스보다 관리해야 할 상태가 많다
5. 쓰기가 많으면 성능 이점 감소: Writer가 자주 들어오면 결국 대부분 독점 락처럼 동작한다
6. 업그레이드 문제: Read Lock을 잡은 상태에서 Write Lock으로 바꾸려다 데드락이 생길 수 있다

**예시**
- 캐시 조회: 읽기는 많고 갱신은 적은 경우
- 설정 정보 조회: 대부분 읽고 가끔 수정하는 경우
- 파일 시스템 메타데이터: 조회는 많고 변경은 제한적인 경우
- 인메모리 데이터 구조: 읽기 중심 자료구조 보호

**Reader 우선 정책과 Writer 우선 정책에 따라 기아(Starvation)가 발생할 수 있다.**
