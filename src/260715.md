## 1. Service
> 파드(Pod) 집합에 대한 네트워크 엔드포인트를 생성하고, 클러스터 내부 또는 외부에서 해당 파드들에 안정적으로 접근할 수 있도록 지원하는 쿠버네티스 리소스

- 파드는 항상 IP가 변경되고, 실행되고 있는 노드도 완벽하게 예측 불가능
- 파드는 언제든지 생성, 삭제된다 -> 새로운 파드 생성 = 새로운 IP
  - 클라이언트, 내부 서비스에서 특정 파드의 IP로 접근이 불가능하다 -> 안정적 X
- 서비스는 이런 파드 앞에서 오랫동안 유지되는 가상의 IP, DNS 이름 제공 

#### 파드의 IP 문제
- 파드마다 IP가 있지만, 파드는 영구적이지 않고 지속적으로 만들어지고 없어진다

### 서비스로 내부 연결을 해결하는 방법
```
frontend (user brower)
└── Ingress (https://api.domain.com/users/me) (LB, RP)
   └── backend-service (내가 요청을 전달해야하는 파드들)
              │
              ├── 10.244.1.10
              ├── 10.244.2.15
              └── 10.244.2.16
```
- 파드가 교체된다 하더라도 `backend-service:8080` 이것만 부르면 된다
- 백엔드에서 -> 데이터베이스 파드
  - backend → db connection
  - database-service:3306
- 쿠버네티스에서는 서비스가 일관된 DNS 이름을 갖고 있어서
  - 클러스터 내부에서 트래픽 전달을 IP 주소를 쓰지 않고, Service 이름으로 접근해서 처리한다
 
### 서비스는 기본적으로 내부 연결을 해결함
#### 서비스의 기본 역할
- 외부에 공개하는 엔드포인트가 아니라 클러스터 내부에서 변경되는 파드들에게 안정적으로 접근하게 하는 것이 서비스의 역할
- 외부 요청 -> 처리하는 걸로 생각하기 쉬운데 그렇지 않다
`클러스터 내부의 Pod가 다른 Pod 집합에 안정적으로 접근하는 방법

```
frontend Pod (내부 파드)
    ↓
backend Pod (동일한 클러스터에 백엔드 파드)
    ↓
database Pod (동일한 클러스터에 데이터베이스 파드)

이럴 때 사용하는게 서비스다 (Cluster IP Service). 
```

```
frontend Pod
     │
     │ backend-service (http://backend-service:8080)
     ▼
ClusterIP Service
     │
     ├── backend Pod A
     └── backend Pod B
```

#### 비유
- 서비스를 고객센터 대표 번호 <- 외부에서 내부로 요청하는 것을 설명 

#### 회사 전화 체계
- 사내 내선번호
  - 개발팀 대표 번호 -> 사원 1, 2, 3
- 사원이 퇴사하고 입사할 때마다 번호가 새롭게 갱신되면, 우리가 개발팀에 요청하기 힘드니 개발팀 대표번호로 전화한다

### 핵심 역할
#### 1. 안정적인 접근 주소 제공
- 일반적으로 사용하는 서비스 타입이 `ClusterIP Service`를 사용
- 클러내스터 내부에서 사용할 수 있는 가상의 IP가 만들어진다
- 실제로는 IP 사용하지는 않고, 대부분 주소를 사용해서 연결
- 네임스페이스 <- 분리되어 있는 가상의 공간
  - 클러스터 내부에서도 이렇게 가상의 공간처럼 나눠놓는다
```

# 같은 네임스페이스에서는 이런식으로 호출

# 다른 네임스페이스에 있다.
http://backend-service.default:8080
```
- 서비스의 DNS 구조
```
- [서비스명].[네임스페이스].svc.cluster.local
```

    - 서비스 대상에서 제외된다

#### 4. 여러 파드로 트래픽을 전달할 수 있다
- 자연스럽게 Load Balancing이 된다
```

   │
   │ backend-service
   ▼

```
- L4 수준 - 네트워크 레이어 수준에서의 로드밸런싱이 가능함
  - 엄청 복잡한 로드밸런싱 로직이 돌아가지는 않는다
  - L7 레이어 수준의 로드밸런싱 규칙이 필요하다? -> Service X
    - API Gateway, Ingress L7 레이어에 있는 리소스에서 구분해야함
- 정확하게 1:1:1 이런식으로 트래픽 간다라고 보면 안된다
  - 트래픽 정책
  - 세션 설정
  - 운영 환경에 문제가 생기거나

#### 서비스는 L4 수준 리소스
- 서비스는 기본적으로 IP 주소 + 포트를 기준으로 트래픽을 전달
  - IP, Port, TCP, UDP
- HTTP 요청 경로같은걸 보고 트래픽을 분산하지는 못한다

### Service 동작 구조
1. Pod에 Label을 붙임
2. Service에 Selector를 작성함
3. Selector와 일치하는 Pod를 찾음
4. 해당 Pod의 IP를 EndpointSlice에 기록함
5. Service로 들어온 트래픽을 backend Pod로 전달함

#### Pod의 Label
```
metadata:
  labels:
    app: community
    tier: backend
```
#### Service의 Selector
```
spec:
  selector:
    app: community
    tier: backend
```

#### EndpointSlice?
- 서비스가 현재 연결할 수 있는 실제 파드 IP 목록을 저장하는 리소스
- 서비스는 만들어지면 서비스 자체에 IP가 부여가 된다
- 엔드포인트 슬라이스는 서비스 뒤에 **어떤 파드들이 연결되어야 하는지, 연결 대상인 파드들의 IP 리스트를 들고 있는 실제 리소스**

```
Service: backend-service (10.99.101.3)

EndpointSlice:
- 10.244.1.10
- 10.244.2.15
- 10.244.2.16
```

#### Endpoint <-> EndpointSlices
- 버전 차이
- 예전 버전에서는 Endpoint
- 1.3x -> ENdpointSlices

```

```

```
   │

   ▼
Service
port: 80
   │
   │ targetPort: 3000
   ▼
Pod
containerPort: 3000
```

### Service 타입
- 쿠버네티스 서비스 타입 중에서 대표적인 타입
1. ClusterIP: 클러스터 내부 접근, 내부 애플리케이션 간 통신에 사용
2. NodePort: Node의 IP와 포트를 통해 외부 접근, 실습 또는 제한된 외부 노출에 사용
3. LoadBalancer: 외부 Load Balancer를 통해 접근, 클라우드 환경의 외부 서비스에 사용

---

### 1. ClusterIP
- 클러스터 내부에서만 접근할 수 있는 기본 Service 타입
    - 서비스 선언 할 때, 타입을 적지 않으면 자동으로 클러스터 IP형
```
apiVersion: v1
kind: Service
metadata:
  name: backend-service
spec:
  type: ClusterIP
  selector:
    app: community
    tier: backend
  ports:
    - port: 8080
      targetPort: 3000
```
- Cluster IP -> 클러스터 내부에서 IP를 서비스를 통해서 노출함
  - 내부에 있는 파드들에게 요청을 전달했음
- ClusterIP형 서비스만 만들어두면 외부에서 접근이 불가능하다

---

### 2. NodePort
- 각 노드들에 특정 포트를 열어서 클러스터 외부에서 → Service 로 접근할 수 있게 하는 타입
```
apiVersion: v1
kind: Service
metadata:
  name: community-nodeport
spec:
  type: NodePort
  selector:
    app: community
    tier: backend
  ports:
    - port: 80
      targetPort: 3000
      nodePort: 31000
```

NodePort Service는 각 Node에서 같은 포트를 노출하고 있고 NodeIP:Port 번호 형식으로 외부에서 접근할 수 있게 하는 방식

#### 노드 포트 사용하는 사례
- 실습, 간단한 테스트 환경, 내부 네트워크에 임시 접근

#### 왜 노드 포트를 자주 사용하지 않을까?
- 모든 유저한테 우리 퍼블릭 IP + 포트 번호
- 관리 측면 및 보안 측면 x

### 서비스가 하지 않는 일

#### 1. 서비스는 파드를 생성하지 않는다
- 파드에 연결하는 역할, 서비스는 파드를 직접 생성하지 않는다
    - deployment, replicaset ← 리소스
    - kubelet
- 서비스는 만들어진 파드 중에서 조건에 맞는 파드에게 트래픽을 전달하는 역할만 가짐

#### 2. 서비스가 URL 경로로 라우팅 하지 않는다

```
/api -> backend-service
/admin -> admin-service
/images -> image-service

# 이렇게 처리하는건 L7 에 있는 다른 리소스가 처리 해야함
# API Gateway, Ingress

요청이 오면
backend-service -> pod A , B 
여기로 전달하는 역할만 한다.
```

#### 실무팁

#### 1. 서비스가 동작하지 않으면, 엔드포인트 → DNS 문제를 확인하기
- 서비스는 그냥 고정되는 이름 제공 하는 역할
    - 가상 IP, 주소 밖에 없음
- 실제로 서비스가 연결이 안되는 문제를 서비스에서 찾으면 찾기 힘들다 -> Endpointslices 확인
- CoreDNS, LocalDNS 확인
  - backend-service-10.401.123123.
    - Node A → backend pod A 가 있음, node A → LocalDNS, CoreDNS 가 문제가 없음
    - Node B → backend pod 가 없음
    - Node C → backend pod 가 있는데 LocalDNS 가 고장나 있음
    - 요청이 50% 확률로 실패

#### 2. Service Target Port ↔ Pod Container port
- service targetPort: 3000
- pod containerPort: 8080 
포트가 다르면 요청이 실패함

#### 4. NodePort 는 실습 위주로만, 운영 환경에서는 x
- 노드 포트가 구조가 단순해서 학습하기는 좋은데,
    - Node IP, 포트의 제한적인 범위, 보안 그룹, TLS, 퍼져 있는 외부 진입점, 여러 서비스의 포트 충돌
- 이런 것들을 고려해서 보통은 Ingress, API Gateway 같은 구조를 운영 환경에서는 선호함

## 2. Probe
> 컨테이너의 상태를 주기적으로 진단하는 메커니즘

Probe는 kubelet이 컨테이너 안의 애플리케이션 상태를 주기적으로 검사하고, 검사 결과에 따라 컨테이너를 재시작하거나 Service 트래픽에서 제외하는 기능
- Probe 설정하면 애플리케이션의 상태를 주기적으로 점검
- 필요한 조치를 자동으로 수행해서 안정성 + 가용성을 보장하는 핵심 요소

---

### 필요한 이유
- 컨테이너는 “실행” 한다는 것이 정상처리를 할 수 있는게 아니다
 - 컨테이너가 Running -> 애플리케이션에서 처리를 못할 수 있다
    - 데드락, 내부 스레드 멈춤 , 무한 루프, 데이터베이스 설정이 끊김, 과부하가 있어서 Thread Pool 소진
- 그렇기 때문에 쿠버네티스에서 파드에게 물어봐야하는 질문이 3가지
  - 시작 상태, 생존 상태, 준비 상태

---

### Probe 종류

#### Startup Probe
- 애플리케이션이 초기화 과정이 완료 되었는지 확인
- 초기화 시간이 긴 애플리케이션이 있음
 - 스프링, 데이터베이스

#### Liveness Probe
- 앱 정상적으로 실행 중인지 “지속적으로” 확인하는 프로브
- 비정상 상태로 확인되면 자동 복구 트리거를 실행함

#### Readiness Probe
- 앱이 사용자 요청을 처리할 준비가 되어 있는지 점검
- 준비되지 않은 상태 -> 트래픽이 유입되지 않게 방지

---

### 프로브는 진단 방법
- 프로브 모두 다 세 가지 방법 중에 하나를 사용함

#### 1. httpGet (가장 흔함)
- 특정 URL 경로로 HTTP 요청을 보냄
- 응답 2xx (200~299) 이러면 정상으로 판단

#### 2. tcpSocket
- 특정 포트에 TCP 연결 시도
- 성공적으로 연결되면 정상으로 판단
    - WAS, 소켓 연결이 필요한 파드
  
#### 3. exec
- 컨테이너 내부에 “특정” 명령어를 실행함
- 명령어 종료 코드가 0 이면 정상으로 판단

---

### 사용 이유
- 앱의 상태를 지속적 감지, 안정성 가용성
- 컨테이너 환경에서는 제대로 동작하는지 확인하려면 API 콜, 내부 로그를 보거나, 모니터링 시스템
    - 수동적인 작업 -> 대응 속도가 느리다
- 프로브는 이런 수동 작업을 자동화

#### 프로브 역할
1. 상태 점검
- 앱 상태 감지, 이상하면 kubelet이 재시작을 함
2. 트래픽 제어
- 준비가 안된 앱에 트래픽 주지 않는다
3. 자동 복구
- 비정상 상태 → 자동으로 복구하거나 재시작

---

### Kubelet , Probe
- 프로브는 컨테이너 안에 설치된 별도 프로그램이 아님
- 워커 노드에 상주하는 kubelet 이 주기적으로 컨테이너에 문을 두드려 보는걸 → probe
    - 프로브의 요청을 kueblet → pod 로 요청을 해봄
    - 컨테이너가 응답 하거나 못하거나
- 프로브가 실패한걸 kubelet 이 듣고
    - kubelet → 이 컨테이너가 정상이 아닌데? 라고 판단
    - 재시작 명령 → kuebelet 이 내림

---

### Probe 사용방법
> spec.containers.readinessProbe, livenessPorbe, startupProbe 필드에 프로브를 정의하여 컨테이너 상태를 주기적으로 검사하도록 설정

###  1. Liveness Probe
- 컨테이너 생존 확인
- 설정 방식으로 라이브니스 프로브가 실패
  - 컨테이너가 죽으면 큐블렛이 해당 컨테이너를 재시작 시도
- 라이브니스 프로브 -> 죽은 앱을 감지하고, 다시 살려준다

#### 핵심 역할
- `데드락 탐지`
- 라이니스 프로브의 진정한 가치
    - 프로그램이 겉으로는 살아 있는데 사실은 멈춰 있을 때 
- 문제 상황
    - 앱이 무한 루프, 데드락
    - CPU 는 열심히 씀, API 요청에는 응답하지 않음
    - 이 때 CPU Usage 같은걸 보면, 이상함 탐지
- 라이브니스 프로브
    - API 호출 → 응답 돌아오는지 확인
    - 응답 없으면 → 재시작
- 라이브니스 프로브 → 앱이 “무응답” 상태를 감지하는 방법

---

### 동작 방식
#### 1. 헬스 체크
- Liveness Probe 는 애플리케이션의 특정 엔드포인트를 정기적 호출하거나, 명령어 또는 TCP 소켓으로 상태를 점검함
- 일반적인 HTTP 요청을 통해 상태 확인하고, HTTP 응답 코드로 결과 판단 (200 정상, 500 에러)

#### 2. 설정 요소
- 초기 지연 시간 - 컨테이너 시작 후 첫 번째 상태 점검을 수행하기 까지 대기하는 시간
- 주기 - 상태 점검 사이의 간격
- 타임 아웃 - 응답을 기다리는 시간
- 실패 임계값 - 특정 횟수 이상 상태 점검 실패하면, 컨테이너 재시작

#### 3. 장애 발생 시 처리 과정
- 특정 엔드포인트가 정상적인 상태 코드를 반환 못하면, 쿠버네티스는 장애로 인식
- 설정된 횟수만큼 연속 점검 실패하면, 쿠버네티스는 컨테이너 재시작
   
---

### 구현 예시
```
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
  failureThreshold: 3
```

- **`httpGet`:** `/health` 경로로 Health check API를 호출해 상태를 점검
- **`initialDelaySeconds`:** 컨테이너 시작 후 5초 동안 대기한 뒤 점검을 시작
- **`periodSeconds`:** 이후 10초마다 점검을 수행
- **`failureThreshold`:** 상태 점검에 3회 연속 실패하면 컨테이너를 재시작

#### ‼️구현 시 주의 사항
#### 1. 로직 단순화
- 라이브니스 프로브 → 주기적으로 요청
- 로직이 복잡 ->  점검 자체가 리소스 낭비
- 라이브니스 프로브에서 엔드포인트 경량화 하도록 설계
  - DB 쿼리 날리거나, 특정 값을 계산. 단순하게 200 OK를 리턴
  
#### 2. 일시적 장애를 고려 (Flapping 고려하기)
- periodSeconds, failureThreshold 잘 설계
- Probe 주기를 너무 짧게 설정 하면
    - 앱이 잠깐 바빠서 응답이 느렸는데 정상 아니라고 죽임
    - 죽였다가 살렸다를 Flapping
    - Flapping 발생하면, 가용성 + 처리량이 상당히 안좋아진다.
---

#### 실무적으로 튜닝
##### 1. initailDelaySconds
- 앱 부팅 시간보다 여유있게, 특히 StartUpProbe 가 없으면 좀 더 길게 하는게 좋음
##### 2. failureThreashold
- 보통은 3~5 번정도를 기준으로 잡는다 (1~2번은 플래핑 발생할 수 있음)
##### 3. period
- 주기를 조금 길게하는 게 좋음 (10~30초 정도)
##### 4. timeout
- 일시적으로 트래픽이 몰리면 응답 시간 지연이 가능하기 때문에 응답시간을 여유롭게 가져가는게 좋다
- API 평균 응답시간, p95 시간 을 보는게 좋음
  - p95 시간 1000ms
  - avg 시간 200ms
  - p95 x 3~5 = 3000ms ~ 5000ms

### 2. Readiness Probe
- 레디니스 프로브는 컨테이너가 요청을 받을 준비가 되어 있는지 판단
- 준비가 되어 있지 않다라고 판단하면 해당 Pod를 Service 에서 제거한다
- 애플리케이션이 살아 있는데 아직 초기화 중이거나 일시적으로 요청을 못받는 상태다
    - 일시적으로 외부 요청을 못받도록 처리하는 것
        - 서비스에서 제외 시킨다
        - 엔드포인트슬라이를 수정
- 레디니스 프로브를 통과 해야지만 해당 파드의 IP 주소를 service의 Endpointslices 목록에 추가
    - Probe 실패하면 → EPS에서 제거
- 결론적으로 Readiness Probe 가 없으면 무중단 배포를 못한다
  - 새로운 버전의 파드가 “준비” 상태가 되어야 한다
  - Auto scaling 할 때도 readiness probe가 있고
  - 새롭게 추가된 파드가 준비가 된 이후에 서비스에 올라가야 처리량을 제대로 받아주는데 
  - 그래야 유저한테 에러를 겪게 하지 않는다

### 주요 특징
#### 주기적 점검
- 정의된 주기와 방식에 따라 컨테이너 상태 점검

#### 준비 상태 제어
- 컨테이너 준비 안됐으면, Pod 의 IP 를 서비스 엔드포인트로 간주 X
- 외부 트래픽 유입 안되도록 함

#### 다양한 점검 방식 지원
- HTTP GET, 명령 실행, TCP 소켓 등 지원

---

#### Readiness Probe가 구분하는 상태
- 컨테이너가 준비 상태로 전환되기 전까지 서비스는 해당 파드를 엔드포인트로 안씀
- Ready 상태 -> 컨테이너가 외부 요청 처리할 준비 된 상태
- NotReady 상태 -> 컨테이너가 외부 요청 처리할 준비가 되지 않은 상태

---

#### Liveness Probe vs Readiness Probe

| **구분** | **Liveness Probe** | **Readiness Probe** |
| --- | --- | --- |
| **목적** | **지속적인 생존 확인** (Is the app healthy?) | **트래픽 처리 준비 확인** (Is the app ready for traffic?) |
| **실패 시 행동** | **컨테이너를 재시작 (Restart)** | **서비스 목록에서 제외 (Stop Traffic)** |
| **사용 사례** | **데드락** (Deadlock, 무한 루프) 발생 시 | **롤링 업데이트** 또는 **DB 연결 대기** 중 |
| **비유** | **심장 박동 확인** (멈추면 심폐소생술) | **영업 준비 완료 확인** (안 되면 문 닫음) |
- 두 가지를 보통은 같이 사용한다
  - WAS에 필요함 -> 재시작을 해야하는 데드락, 롤링 업데이트, 일시적으로 스레드 풀이 가득차는 경우

---

### 3. Startup Probe
- 초기화가 오래걸리는 컨테이너한테 사용
- 실무적으로는 라이브니스의 오작동 막는 용도로도 사용
    - 애플리케이션 중에서 초기화 까지 오래걸리는 경우 (스프링, Mysql)
- 스프링부트 프로젝트가 커지면 실행 초기 시간 2~3분 걸리는 경우가 생김
    - 라이브니스 프로브는 기본적으로 10초 단위로 실행
        - 3분동안 초기화를 해야하는 스프링
        - 라이브니스 프로브 -> 설정값이 10초마다 체크, 3번 실패하면 재시동
    - 재시작을 무한 반복 할 수 있다  (False failure)
- 스타트업 프로브
    - 앱이 초기화 될 때까지 라이브니스 프로브를 멈춤
    - 초기화 시간이 긴 앱들에서 많이 사용함

---

#### 💡정리
#### 1. 스타트업 프로브
- 부팅되는 시간동안 라이브니스가 못건드리게 지킴
#### 2. 라이브니스 프로브
- 앱이 응답을 못하는 상태를 감지하고, 데드락 감지
- 응답 못하면 재시작
#### 3. 레디니스 프로브
- 앱이 트래픽을 일시적으로 못받으면 잠시동안 외부 트래픽을 못받도록 함

#### Web 서비스에서 선택하는 표준

| **파드 종류** | **Startup** | **Liveness (생존)** | **Readiness (준비)** | **핵심 전략** |
| --- | --- | --- | --- | --- |
| **Frontend** | X | **HTTP** (`/`) | **HTTP** (`/`) | 단순하게 (켜지면 바로 투입) |
| **Backend** | **O** (느리다면) | **HTTP** (`/live`)
*(DB 체크 금지)* | **HTTP** (`/ready`)
*(DB 체크 필수)* | **이원화** (살아있는 것과 일할 준비된 것을 구분) |
| **Database** | O | **TCP** / **CMD**
*(보수적 설정)* | **CMD** (`SELECT 1`) | **신중하게** (재시작은 최후의 수단) |

## 3. QoS classes
> Pod의 CPU•메모리 requests 와 limits 설정을 기준으로 Kubernetes가 Pod를 분류하고, 노드 자원이 부족할 때 어떤 Pod를 우선 보호하거나 퇴출할지 판단하는 기준

- 쿠버네티스는 파드를 세 가지 Qos Class 중 하나로 자동 분류한다
  - Guaranteed: 필요한 자원을 명확하게 확보하고 가장 강하게 보호받는 Pod
  - Burstable: 최소 자원은 요청하지만, 여유가 있다면 추가 자원을 사용할 수 있는 Pod
  - BestEffort: 자원을 요청하지 않고 노드의 남는 자원을 사용하는 Pod
- QoS Class 사용자가 직접 "이름으로 설정하는게 아님"
- Pod 작성한 CPU, Memory 설정을 보고 쿠버네티스가 자동으로 결정

---

### Qos Class 사용 이유
- 하나의 워커 노드에서 여러 파드가 CPU, Memory, 디스크, 네트워크 등등 자원을 함께 사용함
- 노드에 자원이 충분하면 별문제 없음
- 자원이 부족하면, 실행되고 있는 모든 파드를 계속해서 실행하지 못하는 상황이 생김
- 노드 상태에서 메모리가 부족해지면, 쿠버네티스는 어떤 파드를 먼저 종료해야할까?
- 모든 파드를 무작위 종료 -> 비즈니스 로직적으로 중요한 파드가 먼저 중지될 수 있다

#### Qos Class
- 중요한 파드들은 상대적으로 보호
- 자원을 많이 사용하는 파드를 식별
- 노드 전체가 멈추기 전에 일부 파드를 퇴출 -> 내구성 높임
- CPU, Memory 자원 사용량을 예측 가능하도록 관리
- 하나의 파드가 노드의 자원을 과도하게 사용하는 문제도 방지
- Qos Class <- 서비스의 중요도를 나타내지는 않고 리소스 설정에 따라서 파드의 보호 수준을 결정하는 분류 체계

---

### Requests, Limits

### Requests
> Pod 를 실행하기 위해서, 쿠버네티스에게 요청하는 "최소한의" 자원
```
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
```
- 스케줄러가 파드를 어느 노드에 배치할 지 판단할 때 사용
- 적어도 requests에 적혀 있는 자원량 이상이 있는 파드에게 배치
- 해당 자원을 수용할 수 있는 노드를 찾아서 거기에 배치
- CPU 250m <- CPU 코어에서 25% 를 의미

### Limits
> 컨테이너가 사용할 수 있는 최대한의 자원 한도
- 배치가 된 파드가 노드의 자원을 사용할 때 사용할 수 있는 최대치를 CPU와 Memory Limit 동작이 다름 
  - CPU: 컨테이너를 종료하지 않고 CPU 사용을 제한함
  - Memory: 메모리를 더 사용할 수 없으면 컨테이너가 OOM Kill될 수 있음
- CPU는 요청을 나눠서 조금 덜 할 수 있는데, 메모리는 할당된 이후 해제하기 어렵다
- CPU는 최소 배분이 가능하고,메모리는 컨테이너가 사용할 수 있는 상한선으로 동작

---

### Qos Class 종류

### 1. Guarateed
- 컨테이너의 CPU, Memory의 Request, Limit를 동일하게 설정한 파드
#### 분류 조건
- 파드 안에 모든 컨테이너가 아래 조건 맞춰야함
  - CPU, Memory
  - Request 설정
  - Limit 설정
  - Request = limit
  
```
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
spec:
  containers:
    - name: app
      image: nginx:1.27
      resources:
        requests:
          cpu: "500m"
          memory: "512Mi"
        limits:
          cpu: "500m"
          memory: "512Mi"
```

#### 특징
- 스케줄러는 요청한 자원을 확보할 수 있는 노드에만 파드를 배치 - Request - Mem 512MB
- 동시에 해당 파드가 사용할 자원도 Limit = Mem 512MB
- 실행 중에 요청량보다 더 많은 자원을 애초에 사용할 수가 없음
- 노드 자원 부족 상황에서 상대적으로 가장 강하게 보호됨
- 중요한 시스템, 안정적인 성능이 필요한 파드들을 배치한다

#### 언제 사용할까?
- 결제, 인증 <- 서비스들은 처리량보다 안정성
- 안정적인 처리가 우선되는 시스템
- 급격한 처리량 변화를 파드의 자원 할당으로 처리하는 시스템은 어울리지 않는다
  - 실시간 랭킹 -> 동시에 수많은 사람들이 랭킹 집계 전에 많은 요청
- 예상 자원 사용량이 비교적으로 명확한 앱
- 장애 발생 -> 비즈니스 로직에 심각한 문제가 생기는 경우

#### 주의 사항
- 개런티드 QOS ← 절대 네버 종료가 안되는건 아님
  - 컨테이너가 애초에 메모리가 부족한 경우
    - 노드 장애가 생기는 경우
    - 노드가 종료되는 경우
    - 관리자가 파드 지우는 경우
    - 더 낮은 우선순위를 갖고 있는 파드를 제거해도, 필요한 자원량 확보되지 않는 경우
- 하나의 노드에 모든 파드가 전부다 개런티드 → 보통 이렇게 안되게 affinity 라는걸 설정
    - QoS Class 만 가지고는 퇴출 순서를 못정한다.

---

### 2. Burstable
> 일부 자원은 보장을 받는데, 노드에 여유가 있으면 요청량보다 더 많은 자원을 사용할 수 있는 파드

#### 분류 조건
- 최소 하나의 컨테이너에 CPU 또는 메모리에 개런티드 조건이 맞지 않으면서 Request or Limit이 설정
```
apiVersion: v1
kind: Pod
metadata:
  name: burstable-pod
spec:
  containers:
    - name: app
      image: nginx:1.27
      resources:
        requests:
          cpu: "250m"
          memory: "256Mi"
        limits:
          cpu: "1000m"
          memory: "1Gi"
```
- 평상시에는 request 기준으로 실행하고 노드에 여유 있으면 Limit 까지 가져와서 사용함
- 버스터블 클래스는 일부만 설정해도 버스터블 클래스로 봄
```
    resources:
      requests:
        memory: "256Mi"
```

- Limit이 없어도 버스터블
  - memory request 256 MB
    - 요청량이 늘어나면 버스터블 클래스처럼 노드의 자원 여유가 있으면 더 가져다 사용

---

#### 특징 
- Requests 설정하면, 기준으로 스케줄링
- 여유 자원 있으면 리퀘스트보다 많이 씀
- 개런티드 보다는 자원 활용이 여유로움, 유연함
- BestEffort 보다는 상대적으로 보호받음
- 일반적인 WAS 버스터블 클래스로 설정함

#### 언제 사용? 
- WAS, Spring
- Node.js API
- request 를 설정하고, limit 안잡음
- 노드의 최소 자원량은 보장 받되, 리미트는 조금 더 여유롭게 설정하거나 아니면 설정하지 않거나.
    - Spring 돌리기 위해서 필요한 최소 자원
    - Spring Container ← 요청량이 많으면 자원을 더 필요로 함
- WAS ← 일반적으로 위의 특징을 가짐
- 트래픽에 따라서 자원 사용량이 높아지는 서비스들

---

### 3. BestEffort
> CPU, 메모리 - Request, limit 설정하지 않음 노드에 남는 자원으로만 사용하는 파드

#### 분류 조건
- 아무것도 설정 안하면 끝
```
apiVersion: v1
kind: Pod
metadata:
  name: best-effort-pod
spec:
  containers:
    - name: app
      image: nginx:1.27
```

---

#### 특징
- 스케줄러 요청 사항이 없음
- 노드의 남은 자원을 자유롭게 쓴다
- 다른 파드가 Qos Class 높다. 우선 보호된다
    - 가장 먼저 퇴출 된다
- 메모리 부족할 때, OOM 발생 가능성이 큼

### 언제 사용?
- 실패해도 문제없는 파드들
    - 테스트 파드, 일회성 파드, 디버깅 파드
- 개발 환경
- 보조 작업
  - 중간에 실패해도 다시 시도하면 같은 결과가 나오는 경우
    - 통계성 작업

---

###  Pod 는 언제 퇴출되는지?

#### Eviction
- 노드를 안정적으로 유지하기 위해서 kubelet 이 실행 중인 파드를 노드에서 종료
- 워커노드 자원이 부족하면 전체 파드 문제 생김
    - 전체 파드가 죽기전에 미리 자원확보
  
```
노드 자원 부족 감지
        ↓
불필요한 이미지와 종료된 컨테이너 정리
        ↓
자원 부족이 계속됨
        ↓
퇴출 대상 Pod 선정
        ↓
Pod 종료
        ↓
노드 자원 확보
        ↓
API Server 보고
        ↓
종료된 파드가 다시 실행되어야 하면?
        ↓
다시 스케줄링
        ↓
다른 노드로 배치
```

### 뭐가 부족하면 퇴출?
1. 메모리
2. 디스크 공간 부족
   - 노드 파일 시스템, 컨테이너 이미지 저장, 컨테이너 로그
3. PID
    1. 노드에서 생성할 수 있는 프로세스 ID 가 부족한 경우
    2. 앱에서 너무 많은 프로세스 만들면 (스레드)
    3. PID 할당
    4. 노드별로 할당할 수 잇는 PID 가 정해져 있음

---

#### 💡정리
- QoS Class: CPU·메모리 Requests와 Limits를 기준으로 Pod를 자동 분류
- Guaranteed: 모든 컨테이너의 CPU·메모리 Request와 Limit이 동일
- Burstable: 일부 자원을 설정했지만 Guaranteed 조건은 충족하지 않음
- BestEffort: CPU·메모리 Requests와 Limits가 모두 없음
- 주요 목적: 노드 자원 부족 상황에서 Pod 보호와 퇴출 판단
- 실제 퇴출 판단: Request 초과 여부 → Pod Priority → Request 대비 사용량
