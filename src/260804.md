# 260804 

## 1. 부하테스트
> 부하 테스트는 실제와 유사한 사용자와 요청을 시스템에 발생시키고,  
처리량, 지연 시간, 오류, 리소스 포화도를 측정하여 목표 성능을 만족하는지와 병목이 어디인지 확인하는 테스트

- 서버에게 많은 요청은 보낸다 X
- 특정 목표를 정하고 그 기준을 통과하는지, 못한다면 어떤 이유로 못하는지?
- 분석 -> 개선하는 작업
- 단순히 부하를 많이 넣는게 아님
  - 서비스가 목표 트래픽을 처리할 수 있는지?
  - 사용자가 느끼는 서비스의 응답 속도가 목표 안에 들어오는지?
  - 부하가 증가되는데 어디에서부터 성능이 저하되는가?
  - HPA, CA가 어느정도 속도로 늘어나고 줄어드는가 등등

성능 테스트
- 시스템의 속도, 안정석, 확장성 <- 테스트 전체
- 부하테스트는 성능 테스트의 한 종류
  - 사용자가 인위적으로 부하를 발생시키는 시스템의 동작
    
---

### 왜 부하테스트를 하는가? 
#### 1. 목표 성능 검증
- 비즈니스 요구 사항 충족
  - 초당 300개 처리, 오류율 1% 미만
- 실제 유저가 사용하면서 저런 상황을 만들어주지 않으면 우리가 알 수 없음
  - 만약 유저가 해당 상황을 겪었는데 처리를 못하면? -> 서비스의 문제

#### 2. 병목 구간 탐지
- 병목 구간이 탐지된다
- 서비스가 느려졌다 -> 어디에서, 왜, 어떻게?
- 병목에는
    - Pod Limit
    - HPA 확장 속도 못 따라옴
    - N+1, Write back, Disk IO, Connection Pool 등의 문제가 있음
- 일단 서비스가 동작은 하나, 트래픽이 급격하게 오거나 특정 요청만 반복적으로 있을 때 문제가 가시화 된다

#### 3. 시스템의 한계 지점 알기
#### 4. 시스템 변경, 구조 변경 성능 비교

---

### 핵심 용어
#### 1. Workload
- 테스트 중 시스템에 발생시키는 사용자 행동, 요청의 전체 패턴 
- 단순히 요청이 몇 개다
  - 어떤 API 호출
  - API 호출 바율
  - 사용자는 호출 사이에서 얼마나 기다리나
  - 이런 것들을 합친게 워크로드
 
---

#### 2. VUser (Virtual User)
- 가상 사용자 
- 테스트 도구 안에서 실제 사용자의 행동을 흉내내는 가상의 실행 주체
- 하나의 VU가 로그인, 게시글 목록 조회, 게시글에서 특정 게시글 접근, 댓글 작성, 3초 대기

---

#### 3. 처리량 Throughput
> 시스템이 일정 시간동안 처리한 작업의 양
- HTTP 시스템
    - RPS = Requests Per Seconds
    - TPS = Transactions  Per Seconds
    - QPS = Queries  Per Seconds
- 아무리 다른 구간이 빨라도 가장 느린 구간의 처리량 = 최대 처리량 -> 병목 구간
- 병목 구간 개선 -> 병목 구간 이동한다
- 병목이 아닌 곳을 개선하면, 처리량이 늘지 않는다
  - -동시 처리량을 늘린다
    - 병목 구간 파악
    - -> 부하테스트를 해보면 안다
  - 보통 시스템 구성에서 병목 구간이 노출되는 경우가 많음

##### 요청과 처리량 구분
- 부하기가 초당 1000개를 요청 보냄
- 그 중 300건 실패 -> 처리량 700개

---

#### 4. 응답시간 Latency
> 요청을 보낸 시점 - 전체 응답을 받을 때까지 걸린 시간
- HTTP 요청은 시간 나눈다면
  - TCP
  - TLS 교환
  - 요청 전송
  - 서버 처리 -> 응답 대기
  - 응답 데이터 수신
  - 응답 데이터 수신 끝나는 시간까지를 응답 시간
- 요청 전송 - 대기 - 응답 받고 - 요청이 마무리 될 때까지의 시간을 응답 시간
- 응답 시간은 시스템이 요청 받고 응답할 때까지의 시간
- 어떤 부분을 개선해도 총 시스템 응답 시간에 영향이 있음

---

#### 5. 동시성
- 같은 시간대에 진행 중인 요청이나 사용자 작업의 수
- VUser가 1000명 -> RPS는 1000일까?
- 사용자의 행동 -> 페이지 읽음 (Get), 입력, 다음 버튼(Post), 다음 화면 이동 (Get)

---

#### 7. 오류율
- 전체 요청 중에 실패한 요청이 차지하는 비율
- 시나리오 상 응답 자체 500대 기대, 400대를 기대한 요청 -> 오류율에 포함하지 않는다

### 부하테스트의 종류
#### 1. Smoke Test
> 최소한의 부하를 발생시켜 테스트 스크립트와 시스템이 기본적으로 정상 동작하는지 확인하는 테스트
- 테스트 스크립트에 오류가 없는가?
- 인증과 데이터 설정이 정상인가?
- URL과 환경 변수가 올바른가?
- 기본 응답이 정상인가?
- 최소 부하에서도 비정상적으로 느리지는 않은가?

#### 2. Load Test (Average Load Test)
> 서비스가 평상시에 받는 트래픽을 “재현” 해서 정상적인 운영 상태를 확인하는 테스트
- 평상시 RPS를 안정적으로 처리하는가?
- p95, p99 응답 시간이 목표 안에 있는가?
- 오류율이 허용 범위 안에 있는가?
- CPU, 메모리, DB 커넥션이 안정적인가?
- HPA가 불필요하게 반복 동작하지 않는가?

#### 3. Stress Test
- 피크 시간의 트래픽을 처리할 수 있는가?
- 부하가 높아질 때 성능이 어떻게 저하되는가?
- HPA가 필요한 속도로 Pod을 추가하는가?
- 부하가 줄어들었을 때 정상 상태로 복구되는가?
- 보호 장치가 정상 작동하는가?
- 스트레스 테스트라고 해서 항상 2배의 트래픽을 만들지는 않음
    - 과거 최대 트래픽
     
#### 4. Spike Test
- 쿠폰, 티켓 예매, 라이브 방송 시작, 푸시 알림 발송, 수강 신청
- 확인하는 사항
  - 갑작스러운 요청을 큐가 흡수 하는지?
  - 커넥션 풀이 고갈될 떼ㅐ 어떻게 다음 처리를 하는지?
  - 스케일아웃하기 전에 기존 파드가 버티나?
  - 부하가 줄어들면 어떻게 대응하나?
  - 스파이크 마지막에 들어온 요청은 언제 완료 처리되나
  
#### 5. Soak Test (Endurance Test)
- 메모리 사용량이 지속적으로 증가하는가?
- DB 커넥션이 반환되지 않는가?
- 파일 디스크립터가 누적되는가?
- 로그 파일이 디스크를 채우는가?
- 캐시가 비정상적으로 증가하는가?
- 장시간 이후 응답 시간이 느려지는가?

#### 6. Breakpoint Test
> 부하를 점진적으로 증가 시키고 시스템이 더이상 버티지 못하는 지점을 찾는 테스트
- 어느 지점부터 오류가 증가하는가?
- 최대 정상 처리량은 얼마인가?
- 가장 먼저 포화되는 자원은 무엇인가?
- 시스템이 점진적으로 느려지는가, 갑자기 무너지는가?

### 부하테스트를 설계하는 방법
#### 1. 테스트 목표 설정
- 서버가 얼마나 버티는지 확인 <- 목표가 없음
- 테스트의 목표를 설정

#### 2. 테스트 범위
##### 2-1. 단일 API 테스트
`GET /posts/{randomId}`
- 특정 API 병목 찾기 편함
- 결과 해석 단순
- 실제 사용자 흐름이랑은 다르게 움직일 수 있음

##### 2-2. 사용자 시나리오 테스트
- 실제 서비스 사용패턴 가깝게 테스트
- 여러 시스템이 연결된 상태를 검증할 수 있음
- 단점
    - 병목 원인을 분리하기가 어려움
    - 테스트 설계가 조금 복잡함

#### 3. 실제 트래픽 비율 고려
- 사용자가 실제로 어떻게 움직이는지를 참고해서 트래픽 비율을 정해야함
    - 운영 로그
    - PLG 지표를 확인하면서 API Call Ratio

#### 4. 테스트 데이터를 준비해야함
- 요청의 회수
- 데이터의 크기 + 분포도 가 중요함
- 테스트를 할 때는 실제 사용자 환경이랑 유사하거나 아니면 더 가혹 환경을 만들어서 테스트 하기
    - 현재 데이터가 100만 건 -> 500만건 데이터를 밀어 넣고 테스트를하는게 더 장기적으로 안정성이 높음

#### 5. 부하 증가 단계를 구분해서 만들기
- 부하를 특정 단계로 끊어서 나눠서 전달해야함
- 맨 처음 부하 요청할 때는 아주 적은 수의 부하만 주고 -> 시나리오에 문제가 없네?
    - 작은 부하부터 큰 부하, 스파이크, 스트레스 등등의 부하로 부하 증가 단계를 나눠서 하는게 좋음

### 부하 모델의 차이
- 크게 VU 방식, RPS 방식

#### Closed Model
> 사용자가 요청을 끝내야 다음 요청을 보내는 방식
- 가상 사용자 (VU) 수를 기준으로 부하를 만든다
- VU 100명 -> 100명 사용자가 각자 응답을 기다렸다 다음 행동을 수행
- 특징
    - 서버가 느려지면 각 사용자가 응답을 기다리는 시간도 길어져서 다음 요청도 늦음
- 서버가 느려질수록, 부하기가 보내는 RPS 도 자연스럽게 감소
- 실제 사용자가 웹사이트에서 응답을 기다리고 나서 행동하는 거처럼, 이런 사용자 시나리오 기준의 부하 테스트에서는 VU 기준으로 우리가 테스트를 진행함

#### Open Model
> 이전 요청이 끝났는지 관계 없이, 정해진 속도로 새 요청을 보내는 방식
- 매초 100개 요청 시작
- 서버 응답 100ms, 500ms, 1000ms
    - 초당 100개 작업을 계속 요청
- 서버가 느려지면, 요청이 줄지 않고 그냥 처리 중인 요청, 대기 중인 요청이 쌓이는 형식
- 예를 들어서
    - 초당 300건의 요청
    - 주문이 매 초 100건 식 밀려 들때 
    - 이벤트 시작하고 나서 일정 트래픽이 계속 유입될 때
- API 부하 테스트 <- 단일 부하테스트 할 때는
- 선택하는 기준
    - 동시에 500명이 사용하는 서비스를 가정한다 -> Closed Model
    - 초당 300건 요청 밀어넣기 -> Open Model

### 부하테스트 결과 해석하기
#### 1. 트래픽
- 목표 RPS
- 실제 RPS
- 성공 RPS
- 동시 사용자 수
- iteration, API 별 요청
- 내가 요청한 대로 트래픽이 전달됐는지?

#### 2. Latency
- 사용자가 응답을 받기 위해서 얼마나 기다렸는가?
- p50, p95, p99 값을 보통은 많이 사용함
- 평균, p50 값을 중점으로 보지 않음
    - p95, p99 값이 확 튀는 API
    - 평상시에는 괜찮은데, 트래픽이 조금 몰리면 바로 문제가 생기는 API

#### 3. Error Rate
- 요청 중에서 얼마나 많은 작업이 실패했는지
- HTTP 4xx, 5xx 값이 중요한게 아님
- 의도하지 않은 에러가 어디에서 얼마나 나왔느냐

#### 4. H/W, Application PLG Stack
- 대시보드를 잘 만들어놔야 부하테스트를 했을 때 의미가 생김

### 부하테스트 중요한 점?
부하테스트의 목표가 최대 RPS 숫자를 찍어내는게 아니다

목표한 트래픽에서 사용자 성능 만족하는지 성능이 무너지는 시점과 그 원인을 파악하는 것

이게 부하테스의 목적이자 목표
