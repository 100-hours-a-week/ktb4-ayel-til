## 서블릿 (Servlet)
- 동적인 컨텐츠를 전달하기 위해서 클라이언트의 요청을 해석하고 
- 요청, 응답 흐름을 서블릿 메서드로 제공
- 서블릿을 통해서 개발자는 HTTP 요청보다 비즈니스 로직에 집중할 수 있음
- 서블릿 핸들러의 공통 로직이 반복
- 스프링 컨테이너에서 Dispatcher Servlet으로 의존성 주입
- HTTP 요청, 응답을 전달, 생성해주는 것

## MVC

### MVC 패턴이 뭐냐
- 소프트웨어를 만들면 디자인, 데이터, 통신제어 영억을 3개로 찢어서 개발하는 디자인 아키텍처
- Model, View, Controller을 나누어서 코드의 책임을 분리하기 위해 사용하는 패턴

### 구성
1. Model
- 데이터와 비즈니스 로직을 담당
- 처리 결과를 Controller/View에 전달
- 시스템이나 데이터의 구조와 동작을 이해, 설계, 표현하기 위해 현실을 단순화해 나타낸 추상적 표현 또는 구조

2. View
- 사용자에게 보여지는 결과물을 담당한다
  - HTML <-
  - Thymeleaf <-
  - JSP <- 동적으로 화면을 그리는
  - JSON <-
- 현대에 들어와서 클라이언트와 서버가 나뉘었다
  - 클라이언트는 화면만 그리고
  - 서버는 로직만 처리
  - 현대 웹에서
    - 서버가 전달하는 결과물 데이터만 갖고 있으면
    - 클라이언트가 그 결과물을 가지고 화면을 그림
- Model의 데이터를 사용자에게 시각적으로 표현하고 사용자 입력을 수신하는 사용자 인터페이스 컴포넌트

3. Controller
- 클라이언트의 요청을 해석해서, 필요한 모델을 부른다
- 사용자 입력을 받아 Model과 View 간 데이터 흐름을 제어하고 비즈니스 로직을 조율하는 중개자 컴포넌트

### 사용이유
- 역할과 책임을 명확히 분리해 변경 범위를 통제하고, 
화면, 로직, 데이터의 독립적 개발과 유지보수를 가능하게 하기 때문에 사용한다

### MVC가 없이 웹 요청을 처리할 땐 어떤 문제가 있었나?
- 스프링 mvc 없이 웹 요청을 처리하려면
- 유저가 요청하면, 그 요청을 받는 전문 상담사 배정했다
  - post를 알고 싶다 -> post 상담사
  - user를 알고 싶다 -> user 상담사
    - 서블릿은 클라이언트 요청을 해석, 데이터 파싱, 응답을 생성해서 다시 전달하는 역할을 갖고 있다
  - 유저의 요청이 두개면, 서블릿도 두개
- 전문 리셉션 데스크를 만들자
  - DispatcherServlet -> 안내 전문 데스크 매니저
    - 모든 외부 요청을 혼자 다 받는다
    - 일을 직접 처리하지 않는다
    - 요청을 확인하고, 처리할 수 있는 부서로 연결해 줄지 결정
  - Controller (담당 부서 직원)
    - 안내 데스크 요청을 전달 받아보니
    - 우리 팀 맞다 user 팀 컨트롤러
      - 비지니스 로직이 2가지
        - 유저 생성
        - 유저 조회
        - 유저 삭제
      - 요청 [유저 생성해주세요]
  - Model -> 담당 부서가 일을 처리하는 것 + 결과 데이터도 담아두는 상자
  - View -> 고객이 요청한 결과물
    - 고객이 나는 로그인 페이지를 주세요 -> HTML 페이지
    - 고객이 나는 로그인 시도를 했고, 생공했는지 알려주세요 -> JSON
    - 고객이 쵸청한 결과물
    - 고객이 요청한 결과물의 형태가 요청 마다 다르기 때문에
      - 요청 마다 다른 결과물을 만들어주기 위해서 -> ViewResolver
      - 고객이 HTML 주세요 하면 HTML로 만들어주고
      - 고객이 JSON 주세요 하면 JSON

## 스프링 MVC
- 웹 애플리케이션을 구현하기 위한 프레임워크
- 코드의 책임 분리
- 패턴: MVC 패턴
- Model -> 데이터/비지니스 로직 
- 실제 필요한 비지니스 로직과 데이터
- View -> 사용자가 보는 화면
- Controller -> 요청 처이, 모델과 뷰 연결 
사용자 요청을 URL 단위로 받고 Model과 View를 연결
- 코드의 복잡성을 줄이고 유지보수를 높임

### 왜 알아야하나
- 디버깅, 성능개선 + 면접

### 스프링 MVC 내부 흐름
- 클라이언트 요청 -> URL로 우리 서버에 요청을 한다 GET/posts
- DispatcherServlet 수신 -> 이 요청 제가 먼저 수신
- HandlerMapping(지도) 조회 -> 이 요청은 어떤 컨트롤러 담당이지?
- HandlerAdapter -> 컨트롤러 중에서 user 핸들러 불러라
- Controller 실행 -> 비지니스 로직 어떤걸 해야하지
- Model 실행 -> 비지니스 로직 수행
- View Resolver -> 유저가 요청한 결과 값이 어떤 형태냐
- DispatcherServlet에게 결과물을 전달
  - DispatcherServlet은 프론트 컨트롤러 역할 수행

### 알아야 하는 이유
- Spring Boot에서 웹 요청 처리 흐름의 기준을 이해해, 
구조를 일관되게 설계하고 유지보수 가능한 애플리케이션을 만들기 위해서 알아야 한다

## HTTPS
- 인터넷으로 점점 할 수 있는게 다양해지고, 보안이 중요해지면서 HTTP에 보안을 추가함
- HTTP + SECURE = HTTPS

### 특징
#### 1. 암호화
데이터를 읽을 수 없는 형태로 함

1. 대칭키
- 암호화, 복호화를 1개로
- 장점: 데이터 전달이 빠름
- 단점: 키를 전달하기 어려움

2. 비대칭키
- 암호화는 공개키로만 복호화는 비공개 개인키로만
- 장점: 키 교환 안전함
- 단점: 대칭키보다 처리가 느림

#### 2. 인증
- 통신하는 상대방이 누군지 신원 확인
- 인증서를 통해 서버의 신뢰성을 검증

### HTTPS로 통신하는 방법
- HTTPS는 비대칭키로 대칭키를 안전하게 교환하고,
실제 데이터 통신은 빠른 대칭키 방식으로 수행한다.


1. 서버는 CA로부터 SSL/TLS 인증서를 발급받는다.
- 인증서에는 서버의 공개키와 서버 정보가 포함된다.

2. 클라이언트가 HTTPS 요청을 보내면,
서버는 자신의 인증서를 클라이언트에게 전달한다.

3. 클라이언트(브라우저)는 CA의 공개키를 사용해 인증서를 검증한다.
- 인증서가 신뢰 가능한지 확인
- 서버의 공개키를 안전하게 획득

4. 클라이언트는 대칭키를 생성 후 암호화하여 서버에 전달한다.

5. 서버는 자신의 개인키로 대칭키를 복호화한다.

- 이후 클라이언트와 서버는 같은 대칭키를 사용해 암호화 통신을 진행한다.
  - 실제 데이터 통신은 대칭키 방식 사용
  - 비대칭키 방식은 상대적으로 느리기 때문이다
