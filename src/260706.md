## 1. Continuous Integration (CI)
> 개발자가 작성한 코드를 자동으로 **통합** 및 **테스트**하여 **코드의 품질을 지속적으로 유지하는 개발 프로세스**

- CI는 "여러 개발자의 코드 변경"을 자주, 하나의 기준 코드에 통합하는 것을 의미한다
  - 개발 방법론
  - 매 통합 시점마다, 자동 빌드 + 테스트

#### 단계
1. 개발 (Develop)
2. 소스 관리 (Source Control)
3. 빌드 (Build)
4. 테스트 (Test)
5. 리포트 (Report)

### 사용 이유
> 코드 통합 과정에서 발생하는 문제를 빠르게 찾고 빌드 및 테스트를 자동화하기 위해서
- 변경 사항을 너무 오랫동안 개인 로컬 브랜치에 쌓아두지 않고 자주 공유하고 있는 코드 베이스(GitHub)에 통합
- 통합 결과를 자동으로 검증하고 실패했을 때 빠르게 수정 한다
- 팀의 개발 방식 + 자동 체계 = CI

---

### CI가 왜 필요한가?
#### CI가 없을 때 생기는 문제
- 개발자들이 각자 기능을 오랫동안 개발하고 마지막에 한 번에 합친다
- 각자 개인의 로컬에서는 잘 동작하지만, 이 코드를 며칠 뒤에 한번에 합치면 문제 발생
  - ex) 같은 파일의 같은 부분을 수정했거나, 의존성 문제가 생기거나
- 문제를 해결하는 것도 어렵지만, **"언제"**, **"누구의 커밋"** 때문에 **"어떻게"** 문제가 발생하는지 추적하기 힘들다

#### CI를 통해서 한다면?
- 개발자는 PR (Pull Request)를 요청하면 아래 피드백을 받는다
  - 컴파일이 되나
  - 테스트를 통과하나
  - 의존성 문제 없나
  - 빌드가 되나
- 운영 서버에 문제가 반영되기 전에 GitHub 같은 저장소 안에서 먼저 실패한다

---
  | 문제 | CI가 해결하는 방식 |
  | --- | --- |
  | 개발자가 로컬에서만 테스트함 | 공통된 Runner 환경에서 자동 검증 |
  | 병합 후 빌드 실패 발견 | PR 또는 main 병합 직후 자동 빌드 |
  | 테스트를 빼먹음 | 테스트 실행을 병합 조건으로 설정 |
  | 코드 리뷰만으로 오류를 찾으려 함 | 자동 테스트와 정적 분석을 함께 실행 |
  | 누가 언제 깨뜨렸는지 모름 | 커밋·PR 단위의 실행 로그와 결과 제공 |
  | 배포 직전에 여러 문제를 한꺼번에 발견 | 작은 변경 단위로 빠르게 실패 발견 |
---

#### CI (지속적인 코드의 통합)
- 코드의 통합을 자동화 시키고
  - 자동화 되었으니, 개발자들이 더 자주 통합
  - 더 작은단위로 문제를 해결 
- "자동화"
  - 코드 품질
  - 빌드 테스트
  - 정적 테스트
- CI는 여러 개발자의 코드를 자주 하나의 기준에 통합
  - 통합 시점마다 자동 빌드 + 테스트
  - 문제를 빠르게 발견하고 해결하는 개발 방식
- CI 사용하여 PR 올리는 순간 자동화 되어 있는 CI를 통해서 컴파일, 테스트 통과 등등 알 수 있다

### 구성 원칙
CI를 제대로 운영하려면 아래의 규칙을 따르는게 좋다

#### 1. 하나의 코드 기준 베이스
브랜치 전략을 나눈다 `main-dev`, `main-dev-staing-feature`

```
main -> 항상 배포가 가능한 상태를 목표로 하는 "기준이 되는 브랜치"

dev -> 개발자들이 작업을 수행하는 브랜치

feature -> 특정 기능 개발하는 브랜치

---

main -> dev 로 브랜치를 하나 만듭니다.

dev 에서 
a -> feature/login
b -> feature/payment
c -> feature/coupon

dev 에 합치는 과정으로 수행한다.
```

- 메인 브랜치 -> 기준이 되는 브랜치
  - 팀이 신뢰하는 항상 동작하고 배포 가능한 브랜치

---

#### 2. 변경 사항을 "자주" 통합 ⭐️
- 지속적으로 코드가 계속해서 통합되어야 한다
- 개발자가 너무 오랫동안 다른 사람의 코드랑 분리된 상태로 작업하지 않아야한다
  - 작은 단위의 변경 사항이 자주 통합되어야 한다
- 큰 기능을 만들고 한번에 합치려고 하면 변경이 커서 CI 과정이 복잡해진다
  - 통합 자동화를 돌기 위해서
    - 테스트 코드
    - 빌드
    - 의존성
  - CI의 비용이 커진다
    - 개발자들은 본능적으로 CI를 피하게 된다 (기능 완성을 우선함)

##### 최대한 짧게 하는게 좋다 - 변경 단위 기준
- 로그인 API 형식이 수정됐다 -> 통합
- 특정 예외처리 -> 통합
- Dockerfile 게시 -> 통합

##### 보통 우리가 하는 (피해야하는) 변경 단위 기준
- 인증, 결제, 주문, 쿠폰 기능을 하나의 PR 에 다 때려 넣고, -> 이거 CI 하자
- 리팩토링 + 기능 추가랑 같이 PR 넣기
  - 리팩토링 보통 전역에 영향을 미치고, 기능 추가는 특정 도메인에만 영역을 가진다
- 많은 파일을 수정하고 변경을 통합하는건 좋지 않다.

---

#### 3. 재현 가능한 빌드
- 개발자 노트북에서는 빌드가 된다.
- CI 서버에서는 빌드되지 않는 경우가 흔하다
- Secret 관리 문제가 생기거나 테스트 코드가 멱등성을 가지고 있지 않다던지, 의존성이 로컬에 있는 의존성을 사용하거나
---
| 항목                                  | 역할 |
|-------------------------------------| --- |
| `pom.xml`, `build.gradle`           | Java 의존성과 빌드 설정 |
| `package.json`, `package-lock.json` | Node.js 의존성과 버전 고정 |
| `Dockerfile`                        | 컨테이너 실행 환경 정의 |
| `docker-compose.yml`                | 여러 컨테이너 구성 정의 |
| `.github/workflows/*.yml`           | GitHub Actions 자동화 정의 |
| 테스트 코드                              | 기대 동작 정의 |
| 환경 예시 파일                            | `.env.example` 등 설정 구조 공유 |
---

#### 4. 자동으로 테스트를 돌려야한다
- CI는 빌드만 되는 것이 아니라, 빌드가 돌아야하고, 테스트 코드도 동작해야한다
- "자동"으로 이뤄져야 한다
- 개발자들은 통합을 미룬다

### CI를 왜 PR에서도 하고, Main에서 하는지
- Pull Request 생성, 수정 시 - 병합 전 위험한 변경을 발견
- main 병합 후 - 실제로 통합된 코드 상태를 다시 검증
- 배포 직접 - 배포할 결과물이 정상인지 최종 확인

#### GitHub Actions
GitHub Actions는 GitHub 저장소에서 이벤트가 발생했을 때 빌드, 테스트, 배포 같은 작업을 자동으로 실행하는 CI/CD 플랫폼
- EC2 or ECS 같은 VM, Container 기반의 배포에서는 일반적으로 Github Actions 를 사용하는 경우가 많다.

#### CI 품질 게이트를 설정해야한다 ⭐️
##### 목적
- 코드를 자주 병합하여 변경사항 지속적으로 병합
- 항상 배포될 수 있는 코드 상태를 유지
- 자동화에 대한 "기준점"이 필요하다
- 어디까지 통과해야 CI가 성공했냐라는 기준이 필요하다
- 초기 프로젝트에는 이런 기준을 잡는게 좋다
---
| 단계 | 필수 여부 | 이유 |
| --- | --- | --- |
| 컴파일·빌드 성공 | 필수 | 실행 불가능한 코드는 병합하면 안 됨 |
| 단위 테스트 통과 | 필수 | 핵심 로직 회귀 방지 |
| 통합 테스트 통과 | 가능하면 필수 | DB·Redis·외부 연동 오류 확인 |
| PR 리뷰 승인 | 팀 상황에 따라 | 설계·가독성·의도 검토 |
| 정적 분석 | 점진적 도입 | 코드 규칙과 잠재 문제 탐지 |
| 보안 검사 | 점진적 도입 | 알려진 취약점 탐지 |
| E2E 테스트 | 핵심 기능만 | 느린 테스트의 비용 관리 |

### 실무적으로 CI 잘하기
#### 1. CI는 "빠르고 + 신뢰할 수 있어야 한다"
- CI를 수행 -> 결과까지 30분이 걸린다
- CI가 실패 -> 실패를 늦게 발견
  - 늦게 발견
    - 다른 개발자 + CI 실행시킨 개발자 -> 다른 작업을 한다
    - 이미 실패한 CI 위에 다른 커밋이 쌓인다
  - PR 병합이 느려지고 실행 CI까지의 커밋 + 다른 작업을 병합
  - 해당 CI를 무시하거나 우회한다
- CI는 이벤트 별로 설정하는게 좋다

#### 2. 깨진 테스트는 방치하지 않는다
코드는 그대로인데, 외부 환경에 따라 테스트 결과가 달라지는 테스트

- 원인
  1. 데이터를 의존적으로 사용하는 경우
    - 테스트 실행 시 , 이미 어떤 데이터가 있다고 가정하는 경우
  - 현재 시간에 의존하는 경우
    - Local Time Stamp <- 특정 값에 동작하는 경우
  - 외부 API 에 의존하는 경우
  - 테스트가 병렬적으로 실행될 때, 데이터가 충돌되는 경우
  2. 핵심 기능이 아니라고 자기 합리화한다
  - 테스트의 정합성을 챙기기 힘들다
  - 그래서 퀄리티 게이트 목록에서 제거한다

#### 3. Secret + 권한을 최소화
- CI는 저장소에 있는 코드를 실행하는 환경에서 (CI runner) 에서 실행
  - CI 러너는 CI를 실행하는 서버> 보통 외부 환경에 있다.
     - Github Actions Runner- Github 서버에 있다.
     - 내 환경에 있는 비밀 정보를 저기에 넣어야 한다.
- 권한 + Secret 을 과하게 주면 위험하다.
  - PR 테스트
  - SSH 키 (.pem 키 올리지 않기)
  - AWS 배포 권한

#### ❓ CI에 대한 오해
1. 테스트가 있으면 CI다?
- 개발팀이 같이 공유하는 "자주 통합하는 개발 규칙"이 필요
- 자동 빌드
- 자동 테스트

2. CI 통과했는데, 왜 오류나는지?
- CI 를 통과해도 버그는 사라지지 않는다
- 테스트코드 -> 내가 실패할걸 예상한 실패한 코드를 막는 코드

---

#### ⭐️ 4. 정리
- CI란? : 여러 개발자의 변경 사항을 자주 통합하고 자동 빌드 테스트로 문제를 빠르게 발견하는 개발 방식
- 왜 필요한가? : 각자 로컬에서는 정상이어도, 코드를 합치면 충돌, 컴파일 오류, 환경 차이, 테스트 누락 문제가 생길 수 있기 때문
- 핵심 흐름 : Push / PR -> 빌드 -> 테스트 -> 결과 확인 성공 시 병합
- CI의 목적 : 오류를 없애는 것이 아니라, 운영 배포 전에 오류를 발견하는 것
- 테스트 원칙 : 중요한 비즈니스 규칙을 검증하고, 테스트끼리 독립적이며, 같은 코드에서는 항상 같은 결과가 나와야 함
- 테스트 우선순위 : 단위 테스트를 가장 많이 두고, DB, Redis 등은 통합 테스트로, E2E는 핵심 사용자 흐름에 제한적으로 사용
- GitHub Actions : GitHub의 Push, Pull Request 같은 이벤트를 기준으로 CI 작업을 자동 실행하는 도구

‼️ **CI가 실패한다 -> CD가 실패한다 -> 운영이 안정적이지 않다 -> 옵저빌리티가 안나온다 -> 서비스 퀄리티가 떨어진다**

## 2. 알아햐 하는 지식 - 빌드와 테스트
#### 빌드 (Build)
- 소스 코드를 실행 가능한 결과물로 만드는 과정
- 빌드 과정에서는 보통 자바 코드 컴파일, 의존성 다운로드, JAR 파일 생성

#### 테스트 (Test)
기대하는 동작이 실제로 실행되는가? 이를 코드로 검증하는 과정
- 테스트 코드는 명확하게 동작이 명시되어야 해서 한글로 적는다

- 테스트 코드를 작성해놔야 한다
    - 테스트 코드 다 적어야 하나? -> NO
        - TDD (Test Driven Development)

### 테스트 코드
#### 역할
1. 기능 검증
2. 회귀 방지
3. 요구사항 문서
4. 변경 안정성 확보
5. 설계 피드백

#### 좋은 테스트 코드 작성법
1. 동작을 검증한다
2. 하나의 중요한 동작만을 검증한다
- 테스트에는 하나의 기능만 테스트하는게 좋다
3. 테스트는 서로 독립적이어야 한다 ⭐️
- 각 테스트는 필요한 데이터를 직접 준비한다.
- 각 테스트는 실행 후 다른 테스트에 영향을 남기지 않는다.
- 테스트 순서가 바뀌어도 결과가 같다.
- 좋은 테스트는 실행 순서랑 상관없이 항상 같은 결과를 만들어야 한다
- CI에서 실행 순서 바뀌면, 병렬 실행 -> 결과 달라진다

#### 테스트 작성 방법
테스트 코드를 읽기 쉽게 하기 위해서 구분해놓은 것
- Given : 테스트 준비 (어떤 상황인지?)
- When : 실행 (무엇을 실행하는지?)
- Then : 검증 (무엇이 일어나야 하는지?)

#### 테스트 대상 선정법
- 모든 코드를 다 테스트 할 수 없다
- 중요한 코드 우선순위로
  1. 핵심 비즈니스 규칙, 장애 시 피해가 큰 로직
  2. 입력 검증과 예외 처리, 복잡한 조건문과 계산 로직
  3. 외부 시스템 연동
  4. 단순한 DTO, Getter, Setter, 프레임워크 자동 설정

---

### TDD(Test Driven Development )
구현 코드를 작성하기 전에, **테스트 코드를 먼저 작성하고**, 테스트 코드를 통과하는 구현 코드를 작성하는 개발 방법론

##### 장점
1. 요구사항을 먼저 코드로 작성
2. 작은 단위 개발
- 테스트 코드는 작은 테스트부터 짜는게 좋다
- 한 번에 큰 기능을 만들지 않고 작은 기능을 만들어서 조립하는 방식 개발이 자연스럽게 된다

##### 단점
1. 내가 실패할 것 같은 사항을 예측 가능한지
2. 코드가 안전하다고 착각한다
3. 테스트를 "통과"만 하는 코드를 작성

#### 테스트 코드의 커버리지
- 실패 후 수정
    - 해당 부분에 대한 테스트 코드를 상당히 자세하게 작성한다
    - 이걸 반복하면 알아서 테스트 코드 커버리지가 넓어진다
    - 목적이 테스트 코드 커버리지를 넓히는걸 목적으로 삼으면 안된다

---

#### 💡테스트 코드 정리
- 테스트 코드는 커버리지를 올리기 위한 숫자가 아니라 앞으로 변경이 되어도 고장나지 않아야하는 기능에 대한 검증을 하는 코드
- 좋은 테스트 코드
  - 중요한 비즈니스에 대한 동작을 검증
  - 테스트끼리 독립적
  - 같은 코드면 항상 같은 결과가 나와야한다.
- 테스트를 코드를 작성하는 방법은 Given-When-Then 으로 작성한다.

---

## 3. Continuous Delivery / Continuous Deployment (CD)
> 코드가 자동화된 테스트를 통과하면 운영 환경까지 자동으로 배포되는 소프트웨어 배포 프로세스

- CI가 이 코드가 정상적으로 작동하는가에 대해서 확인한다면
- CD는 확인한 코드를 실제 서버나 사용자에게 어떻게 전달할건지

### 사용 이유
>  코드가 준비되는 즉시 사람의 승인 없이 자동으로 운영 환경에 반영하여, 배포 속도를 최대화하고 배포 과정에서 발생하는 지연·수동 작업을 제거하기 위해서 사용

#### CI가 끝나고 나서 뭐가 남는지?
- 테스트가 성공했다고 해서 이 기능이 사용자에게 자동으로 제공되는건 아니다
- "배포" 과정이 남아있다
- 매번 사람이 직접 수정했다
  - 실수하기가 상당히 좋은 구조, 느림

#### CD
- CI 이후의 "배포 과정"을 자동화하는 것
- 배포 결과를 검증도 한다
- 실패하면 이전 버전으로 복구하는 것까지가 CD다
  
### CD가 없으면?
- 수동 배포
  - 개발자가 기능 개발 -> 서버에 접속
  - 작은 프로젝트에서는 괜찮지만 조금만 규모가 커지면 문제 발생
    - 배포 절차가 사람마다 다름
    - 운영 서버를 잘못 조작
    - 환경 설정 누락

#### 수동 배포의 문제점
```
진행하는 사람마다 배포 결과가 달라질 가능성이 존재한다
-> 변수가 발생할 수 있다
```

- CD를 통해서 배포하는 과정을 "코드"로 만들어서 자동화 시킨다
- 누가 배포하더라도 같은 결과가 나온다

### CD를 통해 해결하는 것들
1. 반복적인 배포 작업
2. 사람이 하는 실수
3. 배포 버전 추적 어려움
4. 환경별 설정 혼동
5. 배포 후 장애 발견
6. 장애 시 복구 지연
7. 동시 배포로 인한 충돌

⭐️ CD는 단순히 배포를 빠르게 하는 것이 아니라 **배포를 예측 가능하게, 복구 가능하게 하는 것이 목적**

### CD의 흐름
- CI: 코드 품질 검증
- Artifact 생성 : 배포 가능한 결과물 생성
- Registry 저장 : 결과물을 저장하고 배포 대상에 전달
- Deploy : 서버 또는 플랫폼에 새 버전 반영
- Health Check : 새 버전이 실제로 정상 동작하는지 확인
- Monitoring : 배포 이후 장애 여부 확인
- Rollback : 문제가 발생하면 이전 안정 버전으로 복구

### Artifact
> CI가 통과하고 나서 실제로 배포할 수 있는 결과물

- 왜 아티팩트로 별도로 보관하려고 하는가
1. 운영 서버에서 빌드하지 않기 위해서
2. GitHub actions에 문제

### CD의 두 가지 의미
CD는 문맥이나 팀에 따라서 두 가지로 해석된다
1. Continuous Delivery
2. Continuous Deployment
- CI 이후 배포하는 과정
  - 운영 환경에서 배포할 때 약간 차이가 난다
  - 사람이 중간에 개입을 하냐마냐에 대한 차이

#### Continuous Delivery
- 운영 배포 직전까지만 자동
- 최종 배포는 사람이 승인

#### Continuous Deployment
- 테스트 + 자동 배포 조건 확인

### Health Check, Rollback 왜 필요하냐?
- 도커 컨테이너가 동작한다 하더라도 내부에서 문제가 발생한다
- 항상 백엔드에 헬스체크
- 롤백은 "자동화"

---

#### 💡 정리
- CD: CI에서 검증한 결과물을 운영 환경에 안전하고 반복 가능하게 반영하는 프로세스
- CI와의 차이: CI는 코드 품질 검증, CD는 검증된 결과물의 배포와 운영 반영
- CD가 필요한 이유: 수동 배포의 실수, 배포 지연, 환경 차이, 복구 어려움을 줄이기 위해
- Continuous Delivery: 운영 배포 직전까지 자동화하고, 최종 배포는 승인 후 진행
- Continuous Deployment: 테스트와 조건을 통과하면 운영 환경까지 자동 배포 
- Artifact: 배포 가능한 결과물. Docker 환경에서는 Docker 이미지 
- Health Check: 컨테이너 실행 여부가 아니라 서비스가 실제로 정상 동작하는지 확인 
- Rollback: 새 버전 장애 시 이전 안정 버전으로 되돌리는 작업

---

## 4. Github Actions
> GitHub 내에서 코드 빌드, 테스트, 배포 등의 워크플로우를 자동화하는 CI/CD 도구

### 사용 이유
> 코드 변경 시 빌드, 테스트, 배포를 GitHub 내에서 자동화하여 개발 생산성과 코드 품질을 높이기 위해서

1. GitHub와의 통합성
2. 쉬운 워크플로우 관리
3. 코드 중심의 접근법
4. 커뮤니티 및 생태계 활용

---

```
1. GitHub에 코드 Push
2. 로컬 또는 서버에서 최신 코드 Pull
3. 의존성 설치
4. 테스트 실행
5. 빌드
6. Docker 이미지 생성
7. Docker Hub 또는 ECR에 Push
8. EC2 또는 ECS에 배포
9. 배포 결과 확인
```

- 작업 누락, 환경 차이, 속도 저하
- 깃헙 액션즈
    - 저장소안에서 특정 이벤트
    - 코드 변경, PR, 이슈 만들어졌거나, 릴리즈 생겼거나
    - 저장소의 발생한 이벤트를 트리거로 CI/CD 작업 실행할 수 있다.


### CI/CD + Github Actions
- Github Actions -> CI/CD 실제로 수행하는 도구

### 핵심 구성
- Event : 워크플로우를 시작시키는 GitHub 이벤트
- Workflow : 자동화 전체 흐름을 정의한 YAML 파일
- Job : 워크플로우 안의 독립 실행 작업 단위
- Step : Job 안에서 순서대로 실행되는 한 단계
- Action : 특정 기능을 재사용하기 위해 만든 자동화 코드 조각
- Runner : Job이 실제로 실행되는 컴퓨터 또는 가상 머신

---

### Github Actions 1. Event
어떤 일이 발생했을 때, 자동화를 시작하나?

#### 자주 사용하는 이벤트
- push : main 브랜치 병합 후 배포
- pull_request : PR 생성 시 테스트, 린트, 빌드 검증
- workflow_dispatch : GitHub 화면에서 수동 실행
- schedule : 매일 새벽 보안 검사, 정기 배치 작업
- release : 릴리스 생성 시 패키지 배포
- issues : 이슈 생성 시 Slack 또는 Discord 알림

---

### Github Actions 2. Workflows
Github Actions가 수행할 전체 자동화 절차

#### 워크플로우 규칙
- 루트폴더
- 코드로 작성한다
  - 변경 이력 조회, 누가 실행해도 같은 결과 나온다.

---

### Github Actions 3. Runner
Job이 실제로 실행되는 환경
- 이 워크플로우는 저 환경에서 실행된다
  - Github에서 제공하는 우분투 가상머신에서 Job을 실행한다

#### 유형
- GitHub-hosted Runner: GitHub가 관리하는 임시 실행 환경
- Self-hosted Runner: 회사 또는 개인이 직접 설치, 운영하는 Runner

---

#### GitHub-hosted Runner
- Job 마다 깨끗하게 비어있는 실행환경을 새롭게 만들어서 동작
- 이전 실행, 설치한 의존성, 코드, 생성한 파일
- 다음 Job이 받아서 수행하지 않는다
- 의존성 캐시, 아티팩트 전달
- 내 EC2에서 실행되는거 아니다
  - 깃헙에서 관리하는 서버에서 가상화시켜서 실행하는 것
  - 깃헙 러너 -> EC2에 접근하려면

---

### Github Actions 4. Job
워크 플로우 안에서 실행되는 독립 자원

#### 핵심 특징
1. 기본 실행 방식 : Job들은 기본적으로 병렬 실행 가능
2. 실행 환경 : 각 Job은 별도 Runner에서 실행
3. 파일 공유 : Job 간 파일은 자동 공유되지 않음
4. 실행 순서 제어 : `needs :` 를 사용
5. 실패 처리 : 선행 Job이 실패하면 후속 Job은 기본적으로 실행되지 않음 

#### 주의사항
1. Job을 너무 잘게 쪼개지 말기
- 각각 병렬로 각기 다른 "Runner"
- 각 잡들은 서로 다른 결과 파일을 공유하려면 별도 설정

---

### Github Actions 5. Step
Step은 Job 내부에서 순차적으로 실행되는 "한 단계"

---

### Github Actions 6. Actions
반복 기능을 재사용하는 자동화 코드
- Action 내부에서 자주 사용되는 것들을 미리 github actions에서 정의해둠
  - 외부에 있는 다른 집단들도 actions 등록할 수 있음

### Job 간 데이터 공유
- Job, 독립적인 실행 환경
- Cache: 속도 향상, 다음 Job 전달 가능하지만 목적이 다르다
- Artifact: 결과물 전달 및 보관, 다음 Job 전달 가능

#### 💡 Github Actions 정리
- GitHub Actions : GitHub 이벤트를 기준으로 개발.운영 작업을 자동화하는 CI/CD 플랫폼
- Workflow : `.github/workflows/*.yml` 에 정의하는 자동화 전체 흐름
- Event : 워크플로우 실행 조건
- Job : 독립된 실행 작업 단위
- Step : Job 안에서 순서대로 실행되는 단계
- Action : 재사용 가능한 자동화 코드
- Runner : Job이 실제로 실행되는 환경
- run : 쉘 명령어 직접 실행
- Action 호출 : Job 실행 순서 제어
- Cache : 의존성 다운로드 속도를 높이는 기능 
- Artifact : 빌드 결과물 또는 리포트를 전달•보관하는 기능
