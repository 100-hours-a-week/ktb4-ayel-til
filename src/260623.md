## 1. EFS
> AWS에서 제공하는 사용자가 스토리지를 직접 설정하거나 용량을 관리하지 않아도 자동으로 확장, 축소되고 운영이 자동화된 "네트워크 파일 시스템"

#### 문제 상황
- EC2가 한 대라면, 서버 디스크에 파일을 저장해도 문제는 안 되지만, 두 대 이상이면 문제 발생 가능성 ↑
- .env 파일은 깃으로 관리 못하고 서버에 로컬 파일로 존재하여, ec2 접속하여 항상 별도로 만들어야 한다

#### EFS
- 여러 EC2가 하나의 파일 시스템을 공유할 수 있는 관리형 공유 파일 시스템
- 한 EC2가 저장한 파일을 다른 EC2도 동일하게 접근할 수 있다
- 다중 EC2 환경에서 업로드 파일을 공유하기 위해 사용한다

#### 마운트란?
> 외부 파일 시스템을 서버의 특정 디렉토리에 연결해서, 로컬 폴더처럼 사용하는 작업
- EFS는 서버 밖에 있는 네트워크 저장소이다
- EFS를 마운트하면 서버의 특정 경로를 통해 로컬 디렉토리처럼 사용할 수 있다

### 사용 이유
1. 동시 액세스 및 데이터 공유
2. 자동 확장 및 유연성
3. 고가용성 및 내구성 보장
4. 관리 부담 감소 및 운영 효율성 향상
5. 보안 및 통합 기능

### 언제 사용하는지?
1. 여러 서버가 같은 파일을 공유해야할 때
- 여러 웹 서버가 동일한 업로드 파일을 제공해야 하는 경우
- 여러 EC2에서 동일한 환경변수 (.env, key)를 사용해야 하는 경우
- 컨테이너에서 여러개가 같은 영속 볼륨을 사용해야 하는 경우

2. 용량을 예상할 수 없을 때
- EBS는 생성할 때 디스크 용량을 정한다
- 파일 업로드가 많은 서비스는 필요한 저장 공간을 예측하기 어렵다
- EFS는 사용량에 따라 자동으로 확장, 축소된다

3. 여러 가용영역(AZ)애서도 공유해야 할 때
- Regional EFS는 같은 리전 안에 여러 가용 영역에 데이터를 중복 저장하는 방식이다
- 가용성이 상당히 높아진다

### 구성 요소
1. 파일 시스템
- 파일을 저장하고 폴더를 만드는 공간

2. Mount Targer
- VPC 안에서 EC2가 EFS에 접속하기 위한 네트워크 진입점
- EFS는 VPC 내부에서 접근해야 한다
- EC2가 EFS에 접속하려면 각 AZ의 Mount Target으로 접속한다

3. Security Group
- EFS는 퍼블릭 인터넷에 공개되는 서비스가 아니다
- VPC 내부에서 통신하기 위해 보안 그룹 설정이 필요하다
- EC2 <-> EFS가 서로 통신할 수 있도록 허용해야 한다

#### EFS, EBS, S3
EBS = 서버 한 대의 디스크
EFS = 여러 서버가 공유하는 파일 시스템
S3 = 객체 저장소

##### 언제 어떤 걸 선택할지?
- 여러 서버가 같은 파일을 사용 → EFS
- EC2에 연결할 고성능 "디스크" 필요한 파일시스템 → EBS
- 이미지, 영상, 로그 저장 → S3

#### EFS ← 성능, 비용 관점
네트워크 통신 기반이라 네트워크 딜레이 발생 가능과 네트워크 사용량에 따른 과금 발생

##### 1. 성능 모드
EFS는 기본 설정으로 시작하고 실제 사용하면서 지표를 확인한 뒤 성능과 비용을 고려해 최적화하는 것이 좋다.

- General Purpose
  - 낮은 지연 시간 중심
  - 일반 웹 서비스, CMS, 홈 디렉터리

- Max I/O
  - 높은 병렬 처리 중심
  - 아주 많은 클라이언트가 동시에 접근하는 환경

-> 보통은 General Purpose 추천됨

##### 2. Throughput Mode
- Elastic: 사용량에 따라 처리량을 자동으로 늘리고 줄임 
- Bursting: 파일 시스템 크기와 버스트 크레딧 특성을 활용 
- Provisioned: 필요한 처리량을 직접 지정 
- EFS 도입 초기에는 Elastic

##### 3. Lifecycle Management
- 스토리지, 파일 시스템에 저장된 것들 중에서
- 클라우드 서비스는 접근 속도가 빠를 수록 돈이 비싸다
  - RAM > SSD > Disk
- 오랫동안 접근하지 않는 파일은 항상 저렴한 스토리지로 이동시키는 걸 고려해야한다.

---

### 실무 적용 시 고려 사항
1. EFS ← 모든 저장소로 사용하지 않는다.
- 비용이 상대적으로 비싸다
- 공유 파일 시스템이 꼭 필요할 때만 선택

2. DB 디렉토리는 사용하지 않는게 좋다.
- EFS는 네트워크 파일 시스템
- MySQL, PostgreSQL은 보통 EBS 사용을 권장한다.

3. NFS Port 2049 ← 인터넷에 열면 안된다.

4. 백업에 대해서 설계를 해야한다.
- EFS도 결국 파일 시스템
- 중요한 파일은 별도로 백업하는 것이 좋다.
- AWS의 많은 서비스는 기본 백업 기능을 제공한다.

---

#### 💡정리
- EFS: 여러 서버가 공유하는 관리형 파일 시스템
- 핵심 목적: 여러 EC2가 같은 파일을 동시에 읽고 쓰기
- 접근 방식: Linux에서 NFS로 마운트
- 대표 포트: TCP 2049
- 주요 구성: File System, Mount Target, Security Group, Access Point 
- 장점: 자동 확장, 공유 파일 시스템, 다중 EC2 접근 
- 적합한 사례: 공유 업로드 파일, CMS, 컨테이너 공유 볼륨, 배치 파일 공유 
- 부적합한 사례: DB 데이터 디렉터리, CDN용 대규모 정적 콘텐츠 
- EBS와 차이: EBS는 서버 한 대의 디스크에 가깝고, EFS는 여러 서버 공유 파일 시스템

## 2. S3 (Simple Storage Service)
> S3는 이미지, 동영상, 백업 파일, 로그처럼 많은 파일을 객체(Object) 단위로 저장하고 인터넷 또는 AWS 서비스에서 접근할 수 있게 해주는 객체 스토리지 서비스

#### 서버 디스크 (EBS) 저장하면 생기는 문제점
- 사용자 파일이나 이미지를 EBS에 직접 저장
- EFS로 공유할 수도 있지만 항상 적합한 것은 아니다.
    - 이미지 파일은 외부에서 바로 볼 수도 있어야 한다.
    - EFS는 공유 네트워크 파일 시스템으로 주로 VPC 내부에서 사용한다
    - 정적 파일 서빙에는 S3를 많이 사용한다.

#### S3
- 파일을 “객체 단위로” 저장하는 관리형 객체 스토리지 서비스
- 서버 디스크처럼 마운트해서 사용하는 서비스는 아니다.
- 파일을 업로드하면 객체(Object)로 저장된다.
- HTTP, AWS SDK를 통해 접근한다.

#### 객체 스토리지가 뭔지?
- 객체는 S3에 저장되는 실제 데이터 단위
  - 이미지, 동영상, PDF 등 모든 파일을 객체로 저장할 수 있다.

- S3의 객체는 파일 데이터와 함께 추가 정보를 저장한다.
  - Bucket : 객체가 저장되는 공간
  - Key : 객체의 경로 및 이름
  - Value : 실제 파일 데이터
  - Metadata : 파일의 부가 정보
  - Version ID : 객체 버전 정보

#### 차이
- EBS, EFS
  - 파일 시스템
  - 마운트, mkdir 등의 파일 시스템 명령 사용 가능

- S3
  - 객체 스토리지
  - 객체 단위로 저장 및 관리

### 구성 요소
1. Bucket
- S3 객체를 담는 “최상위” 저장 공간 (폴더랑 비슷한 개념)
- 버킷 이름 특징
  - AWS 내에서 고유해야 한다.
  - 소문자, 숫자, 하이픈(-) 사용
  - 다른 사람이 사용 중인 이름은 사용할 수 없다.
  - 특정 리전에 생성된다.
- 실제 폴더가 아니라 객체를 저장하는 논리적인 저장 공간

2. Object
- 실제로 저장되는 데이터 단위
  - Bucket : 객체가 저장되는 버킷
  - Key : 객체의 고유한 경로 이름
  - Value : 실제 파일 데이터
  - Metadata : 파일의 부가 정보
  - Version ID : 객체 버전 정보

3. Key
- 버킷 안에서 객체를 구분하는 고유한 이름
- S3 콘솔에서는 계층형 폴더처럼 보이지만 실제 디렉토리 구조를 관리하는 파일 시스템 X
- 하나의 Key로 저장되는 객체 스토리지

### 사용 이유
1. 제한 없이 확장 가능
- EBS는 용량이 부족하면 직접 증설해야 한다.
- S3는 저장할 객체가 늘어나도 별도 디스크 증설 X

2. 서버가 바뀌어도 파일이 유지
- EC2는 언제든 교체될 수 있다
- S3에 저장된 파일은 새로운 EC2에서도 그대로 사용할 수 있다

3. 내구성 + 가용성 높다.
- S3 Standard 연간 내구성 제공 

### S3 ↔ EC2 를 사용하는 방식
1. 백엔드가 업로드를 처리하는 방식
- 사용자가 업로드한 파일을 일관적으로 관리해야 할 때 사용
  - 파일 포맷 검증
  - 파일 크기 제한
  - 리사이징, 압축 처리
- 보안적으로 더 안전하다.
- S3는 파일 저장과 조회만 담당한다.


2. Presigned URL 구조
- 일정 시간 동안 특정 S3 객체에 접근할 수 있도록 만든 서명된 URL
- 클라이언트가 S3에 직접 업로드 또는 다운로드한다.
- 장점
  - 백엔드 서버가 큰 파일 데이터를 직접 안받아도 된다.
  - EC2의 네트워크 자원을 덜 쓰게 된다 = 저렴하다.
  - 업로드 가능한 시간, 파일 경로, 권한을 제한
- 단점
  - 파일 검증을 클라이언트에 의존한다.
  - 클라이언트는 변조될 수 있다.
  - 압축, 리사이징, 파일 변환 처리가 어렵다.
      
### 주요기능
1. Versioning
- 같은 key(.png) 파일을 다시 올려도, 이전 버전을 보관하는 기능
- 여러 버전 보존 가능
- 실수로 삭제, 덮어쓰기 한 경우에도 복구할 수 있다.
- 버저닝을 키면, 보관도 늘어난다.
- Lifecycle 이랑 같이 설계

2. Lifecycle Rule
- 오래된 객체를 더 저렴한 스토리지 (더 느린 스토리지) 옮기는 기능

3. 스토리지 클래스 설정 (성능)
- 접근 속도, 복구 속도에 따라서 필요한 스토리지 클래스를 사용

#### 사용처
1. 사용자 이미지 처리
2. 정적 웹사이트 배포

---

#### 💡정리
- S3: AWS의 객체 스토리지 서비스
- 저장 대상: 이미지, 동영상, 백업 파일, 로그, 정적 파일 등
- 저장 단위: Object
- 최상위 저장 공간: Bucket
- 객체 식별자: Key
- 접근 방식: AWS SDK, CLI, REST API, HTTP
- 파일 시스템: X
- EBS와 차이: EBS는 EC2 디스크, S3는 객체 저장소
- EFS와 차이: EFS는 마운트 가능한 공유 파일 시스템

## 3. RDS (Relational Database Service)
> 클라우드에서 관계형 데이터베이스를 손쉽게 생성·운영·확장할 수 있도록 제공하는 완전관리형 서비스

RDS 자체가 데이터베이스 프로그램이 아니라 데이터베이스를 운영하기 위한 AWS 관리 서비스

#### RDS - 직접 설치
- EC2 + MySQL : 저렴하지만 직접 관리
- RDS : 비싸지만 운영이 편함

- 운영은 편하지만 비용이 더 높다.
- 서비스 규모와 상황에 따라 선택한다.

#### 일반적인 RDS의 구성
- 사용자는 RDS 직접 접속 X
- 애플리케이션 서버만 접속

- 운영 환경에서는 RDS를 Private Subnet에 둔다.
- 외부 인터넷(HTTPS, SSH)에서는 직접 접근할 수 없다.

### RDS 구성 요소
1. DB Engine: 실제 데이터를 저장하는 SQL 처리하는 데이터베이스 엔진
2. DB Instance: 실제 DB 엔진이 실행되는 서버 자원
   - EC2 인스턴스 선택하듯이 RDS 에서도 DB 인스턴스 클래스 설정
   - CPU + 메모리 + Network
3. Storage
- RDS 에 저장되는 데이터들은 단순히 데이터베이스 로우들만 저장되지 않는다.
- 스토리지 용량뿐만 아니라 성능도 함께 고려해야 한다.

#### IOPS
- Input / Output Operations Per Second
- 디스크가 1초 동안 처리할 수 있는 작업 횟수
- 조회, 수정, 삭제가 많은 서비스에서 중요하다.
- PK, 인덱스 기반 조회나 Update가 많은 경우 영향을 많이 받는다.

#### Throughput
- 디스크가 1초에 읽고 쓸 수 있는 데이터 양
- 배치 작업, 백업, 리포트 생성, 데이터 마이그레이션 등 대용량 처리에서 중요하다.

4. Endpoint: 엔드포인트는 애플리케이션 RDS 에서 접속할 수 있는 지점
5. Security Group: 어떤 서버가 데이터베이스에 접근할 수 있는지

### 자동백업과 스냅샷
1. 자동 백업 (Automated Backup)
- RDS가 주기적으로 수행하는 관리형 백업
- 지정된 백업 보관 기간 동안 유지된다.
- 특정 시점으로 복구할 수 있다.

2. Manual Snapshot
- 사용자가 원하는 시점에 직접 생성하는 DB 스냅샷
- 스키마 변경, 엔진 업데이트, 마이그레이션, 대규모 배포 전에 주로 생성한다.
- 큰 작업 전 현재 상태를 보관하기 위해 사용한다.

### 실무 구성 방법
#### 1. Multi AZ 구성
- 다른 AZ에 대기 DB를 유지하는 구성 방식
- DB 장애 시 서비스 중단을 줄이기 위한 고가용성 구성

#### 2. Read Replica 구성
- 보통 웹서비스가 읽기가 훨씬 많기 때문에

### 실무적인 적용 방식
#### 1. RDS 백업 기능을 신뢰하지말기
- 자동 백업이 제공되더라도 실제 복구가 가능한지 검증해야 한다.
- 장애 발생 시 복구 절차도 함께 고려해야 한다.

#### 2. DB 연결수를 무한정 늘리지말기
- DB 커넥션 수에는 제한이 있다.
- 커넥션이 많아질수록 CPU, RAM 사용량도 증가한다.
- 커넥션 풀(HikariCP 등)을 적절히 튜닝해야 한다.

---

#### 💡 정리
- RDS: AWS의 관리형 관계형 데이터베이스 서비스
- DB Engine: MySQL, PostgreSQL 같은 실제 DB 제품
- DB Instance: DB 엔진이 실행되는 관리형 서버 자원
- Endpoint: 애플리케이션이 DB에 연결하는 주소
- DB Subnet Group: RDS를 배치할 VPC Subnet 묶음
- Security Group: 어떤 서버가 DB 포트에 접근할지 제어
- Automated Backup: 자동 백업과 특정 시점 복구 지원
- Multi-AZ: 장애 대응과 고가용성 목적
- Read Replica: 읽기 성능 확장 목적
