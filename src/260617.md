## 1. Proxy
> 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치

- 보통 네트워크 통신은 Client -> Server
- 실무에서는 중간에 다른 서버 하나 더 두는 경우가 많다
  - Client -> Proxy -> Server
- Proxy = 대리인
- 네트워크에서는 클라이언트 서버 사이에서 요청과 응답을 중계하는 장치 or 소프트웨어

#### Client -> Server
- 클라이언트가 직접 서버에게 요청
- 서버도 직접 클라이언트한테 응답
- 장점
  - 구조가 단순
- 단점
  - 보안, 로컬, 캐싱, 접근 제어 등
  - 중간에서 처리하기 힘들다

#### 프록시가 있으면?
1. 클라이언트가 Proxy에게 요청
2. Proxy가 서버에게 대신 요청
3. 서버가 Proxy에게 응답
4. Proxy가 클라이언트에게 응답 전달

### 사용 이유
1. 보안 강화
2. 트래픽 최적화
3. 접근 제어
4. 로깅/감시
5. 익명성
6. 정책 적용

### 프록시 종류
- 프록시를 이해할 때 중요한 질문
- "이 프록시는 누구를 대신하냐?" 프록시는 크게 두 가지로 나뉜다.

1. Forward Proxy: 클라이언트의 대리자 - 클라이언트 보호, 우회, 익명성, 사내 정책 적용
2. Reverse Proxy: 서버의 대리자 - 서버 보호, 로드 밸런싱, SSL 처리, 캐싱

#### Forward Proxy (우회)
> 클라이언트 대신 외부 서버에 요청을 보내는 프록시
- 포워드 프록시는 클라이언트에게 가까이 있는 프록시 서버
- 클라이언트가 외부 서버에 직접 요청하지 않고
    - 요청을 포워드 프록시에게 전달
    - 포워드 프록시가 그 요청을 실제로 보낸다.
    - 응답도 포워드 프록시가 받아 클라이언트에게 전달하는 방식

##### 사용예시
1. 회사 인터넷 프록시: 직원들의 외부 사이트 접근을 통제하고 로그 기록
2. 학교 네트워크 프록시:	특정 사이트 접근 제한
3. 캐싱 프록시: 자주 요청하는 파일이나 페이지를 저장해 속도 개선
4. 익명 프록시: 클라이언트의 실제 IP를 숨김
5. 제한 우회: 특정 네트워크 제한을 우회하는 데 사용될 수 있음

#### Reverse Proxy (보호 및 감시)
> 서버 대신 클라이언트 요청을 먼저 받아 처리하는 프록시
- 클라이언트는 실제 서버에 직접 접근하지 않으며, Reverse Proxy를 통해 서버와 통신한다.
  
##### 사용예시
1. NginX: Spring, Node.js 같은 애플리케이션 서버 앞에서 요청 중계
2. Apache HTTPD: 웹 서버 겸 Reverse Proxy
3. Envoy: 마이크로서비스, 서비스 메시에서 자주 사용
4. HAProxy: 고성능 로드밸런싱 프록시
5. CloudFront: CDN 역할과 Reverse Proxy 성격
6. API Gateway: API 요청을 받아 백엔드 서비스로 라우팅

**클라우드 개발자 입장에서는 Reverse Proxy 가 훨씬 중요하다**

#### 💡 정리
- 한줄 정리: 클라이언트와 서버 사이의 중계자 “역할” 
- 핵심 역할: 요청과 응답을 대신 전달
- 주요 목적: 보안, 최적화, 접근 제어, 캐싱, 로깅, 익명
- Forward Proxy: 클라이언트의 대리자
- Reverse Proxy: 서버의 대리자
- 실무 예시: Nginx, HAProxy, Envoy, API Gateway, CDN
- 주의점: 병목, 장애점, 헤더 처리, 타임아웃, 로그 해석

## 2. VPN
- 우리는 여러 네트워크 장비를 거쳐서 통신을 한다
  - 기본적으로 "공용 네트워크"를 거친다
  - 카페, 공항, 호텔 와이파이 사용한다
  - 보안성이 약할 수 있다

- 인터넷에서 지나가는 여러 라우터, 공유기 등을 지나갈 때
  - 마치 터널을 만든거처럼 나와 서버가 통신하는 데이터를 한 번 더 암호화하여 전송한다

> 공용 인터넷 위에 암호화된 가상 터널을 만들어, 멀리 떨어진 사용자나 네트워크를 사설망처럼 안전하게 연결하는 기술

### 사용 이유
1. 원격지 안전하게 내부망을 사용해야할 때
2. 보안성 강화
3. 떨어진 사설망들을 하나의 사설망 처럼 묶을 때

### 핵심 구성 요소
1. VPN Client: 사용자의 PC나 스마트폰에서 VPN 연결을 시작하는 프로그램
2. VPN Server: VPN 접속을 받아 인증하고 터널을 만들어주는 서버
3. VPN Tunnel: 클라이언트와 서버 사이의 암호화된 가상 통로
4. 인증 정보: 계정, 비밀번호, 인증서, MFA 등 사용자 확인 수단
5. 암호화 키: 데이터를 암호화하고 복호화하기 위한 키
6. 가상 IP: VPN 연결 후 클라이언트에게 할당되는 내부망용 IP
7. 라우팅 정책: 어떤 트래픽을 VPN으로 보낼지 결정하는 설정

### 동작 흐름
1. VPN Client 실행
2. VPN Server로 연결 요청
3. 사용자 인증
4. 암호화 키 협상
5. VPN 터널 생성
6. 가상 IP 할당
7. 라우팅 테이블 변경
8. 트래픽 암호화 후 터널로 전송
9. VPN Server가 복호화 후 목적지로 전달
10. 응답도 다시 암호화되어 Client로 반환

### 터널링이란?
- 원본 패킷을 다른 프로토콜로 감싸서 보내는 방식
- 전용 통로를 만드는 것과 유사한 개념
- 기존 네트워크 위에 가상의 네트워크 경로를 생성
- 터널 내부에서 암호화된 통신 수행

### 연결 방식
1. Full Tunnel
- 모든 트래픽을 항상 VPN 으로 보내는 방식
2. Split Tunnel
- 사내망에 가야하는 트래픽만 VPN 가고
- 나머지는 일반 인터넷으로 내보내는 방식

### 사용예시
1. 재택 근무자가 사내 Git 접속
2. 공용망에서 통신 암호화 하기 (익명성)

#### 실무적인 관점
1. Bastion Server, Jump Server
    - 운영 DB 접속
    - Private Network 접근

2. 사내 API 테스트

3. 어드민 페이지 외부 접속

4. IDC - Public Cloud Server (AWS)
    - LAN ↔ LAN 연결

#### 💡 정리
- 한 줄 정리: 공용 인터넷 위에 암호화된 가상 사설 통로를 만드는 기술
- 핵심 목적: 원격 사용자나 떨어진 네트워크를 안전하게 연결
- 주요 원리: 인증, 터널링, 암호화, 가상 IP, 라우팅
- 대표 유형: Remote Access VPN, Site-to-Site VPN
- 주요 예시: 재택근무, 사내망 접속, 본사-지사 연결, 클라우드 VPC 연결
- 장점: 안전한 원격 접속, 비용 효율, 공용망 보호
- 한계: 속도 저하, 계정 탈취 위험, 과도한 내부망 접근 위험
- 실무 포인트: MFA, 최소 권한, 로그, 라우팅, DNS, Kill Switch 설계

## 3. NAT(Network Address Translation)
> 사설 IP 주소를 공인 IP 주소로 변환하여 인터넷 통신을 가능하게 하는 기술

### IPv4 주소 한계
- 40억개 정도 IPv4
- 늘어나는 인터넷 연결 장치들

### 사용 이유
1. IPv4 주소 절약
2. 보안 강화
3. 네트워크 관리

### 사설 IP 와 NAT 등장
- 공개 IP: 인터넷에 등록되어야 하는 IP, 40억개로 제한됨, 비쌈
- 사설 IP: 공개되지 않는 IP, 제한 거의 없음, 비용 없음
- NAT: 사설 IP 와 공개 IP 를 변환하는 기술 (라우터가 수행해줌)

---
### 주소변환 방식

### Symmetric NAT
> 동일한 내부 IP와 포트를 사용해도 외부 대상에 따라 서로 다른 매핑된 IP와 포트를 생성하며, 비대칭적 통신을 제한하는 네트워크 주소 변환 방식

#### 특징
1. 매핑 독립성: 내부, 목적지 별로 독립적인 매핑 테이블
2. 보안 강화: 외부에서 내부로 임의 접근 어려움
3. P2P 연결 제약: 비대칭 통신 제한
4. 리소스 사용: 목적지별 매핑 생성, NAT 테이블 크기 증가

#### 사용이유와 사용처
- 외부 네트워크로 부터 내부 네트워크 보호
- IP 주소 절약
- 네트워크 관리 효율성
- 비대칭 통신 차단
- 기업 보안망, 정부 기관, 보안 강화 내부망 (P2P, WebRTC 등 직접 연결 기반에서는 어려움)

---

### Cone NAT
> 내부 네트워크의 장치와 외부 네트워크 간의 통신에서, 특정 조건에 따라 외부에서 내부로의 접근을 허용하는 네트워크 주소 변환 방식

---

#### Full Cone NAT
- 송신 데이터 기반으로 NAT 테이블 생성 
- 내부 클라이언트가 아웃바운드 요청을 한 번이라도 수행하면 매핑 생성
- 어떤 외부 IP나 포트에서든 매핑된 외부 IP와 포트를 통해 내부 네트워크의 해당 클라이언트로 패킷을 전송 가능 
- NAT 방식 중 가장 개방적인 형태

##### 특징
  - NAT 매핑 정보만 있으면, 외부 모든 장치가 내부 장치로 패킷 전송 가능
  - 내부 클라이언트는 한 번만 아웃바운드 요청하면 외부와 자유로운 통신
  - P2P 통신, 온라인 게임, 화상 통화 등 실시간 연결 요구되는 환경에 효과적

##### 보안
  - 허용 범위가 넓어 보안에 취약
  - 비인가 접근 가능성
  - NAT 장치가 외부 요청을 별도 필터링 하지 않음

---

#### Restricted Cone NAT
- Full Cone NAT 의 보안 문제를 개선한 방식
- 내부 클라이언트가 아웃 바운드 요청을 보낸 외부 IP에만 접근 허용
- 외부의 무작위 접근을 방지하면서도, 연결 효율성을 유지하는 방식

##### 특징
- 외부 IP 기반으로 접근을 제한, 송신 기록이 없는 외부 장치 요청 차단
- 동일한 외부 IP 라면, 포트 번호 관계 없이 통신 가능
- 보안 강화하면서도 Full Cone NAT 보다 정밀하게 접근 제어
- 제한적인 P2P 연결, 화상 통화 등

##### 보안
- Full Cone NAT 에 비해 보안성이 높음.
- 여전히 동일한 외부 IP 라면 포트 관계 없이 접근 가능, 일부 보안 취약점 존재

---

#### Port Restricted Cone NAT
- Restriceted Cone NAT 의 접근 조건을 더욱 엄격히 제한
- 외부 IP + 포트 번호까지 매칭 조건으로 추가함
- 내부 클라이언트가 아웃바운드 요청을 보낸 외부 IP 와 포트가 정확히 일치해야 접근 허용
- Cone NAT 방식 중 가장 보안성이 높음

##### 특징
- 외부 IP + Port 까지 매칭 조건, 동일한 IP 라도 포트가 다르면 접근 불가능
- 가장 엄격한 형태의 Cone NAT, 보안을 중시할 때 적합
- 금융 거래 서버, 기업 네트워크 등

##### 보안
- 외부 네트워크로부터 무작위 접근 가능성 최소화
- 허용 조건이 엄격, 외부에서 내부로 임의 접근 가능성 차단
- P2P 통신, 일부 실시간 통신에서 추가적인 설정 필요

## 4. 네트워크 모델

### 네트워크 프로토콜 (Network Protocol)
- 네트워크 상에서 데이터를 주고 받는 규칙과 절차를 정의하는 체계
- 데이터를 안전하고 신뢰성 있게 전송
- 모든 장치가 통신의 약속을 지키고
- 이로 인해 통신이 원활하게 이뤄지도록

> 네트워크 장치들 간 약속,데이터 전송을 원활하고 안전하게 하기 위해 사용

#### 주요 네트워크 프로토콜
1. TCP
- 신뢰성 있는 데이터 전송 보장
- 패킷 전송, 오류 검출 및 복구 흐름 제어
- 연결 기반 통신
- 데이터 순차 처리

2. UDP
- 비연결성 프로토콜
- 데이터 전송 시 신뢰성 보장 안함
- 빠른 전송 속도 제공
- 스트리밍, 온라인 게임 등 사용

3. ICMP
- 네트워크 진단, 오류 메시지 전송 용도
- 네트워크 상태 확인
- 오류 발생 시 알림 발생
- Ping 명령어 등으로 사용

4. ARP
- IP 주소 기반, MAC 주소를 찾는 프로토콜
- 네트워크 내 IP 주소를 가진 장치에게
- MAC 주소를 얻기 위해 사용함

#### 응용 계층 프로토콜
1. HTTP, HTTPS
- 웹브라우저 - 서버 간 사용
- 웹페이지 텍스트, 이미지, 비디오 전송
- HTTPS 는 보안 기능을 추가

2. FTP
- 서버-클라이언트 간 파일 전송 프로토콜
- 파일 업로드 및 다운로드 기능
- 파일 서버에서 사용

3. SSH
- 안전한 원격 접속 제공 프로토콜 
- 원격 서버에 안전하게 접속 
- 암호화를 통한 기밀성 보장

4. SMTP
- 이메일 전송을 위한 프로토콜
- 이메일 서버 간 메시지 전달
- 클라이언트-서버 메일 전송 시에도 사용

### 패킷
- 데이터를 한 번에 스트림으로 보내려고 하면, 전송 시 다른 통신이 기다려야 하는 문제가 발생
- 데이터를 스트림이 아닌 패킷으로 나누어 전송
- 여러 통신이 네트워크를 효율적으로 공유 가능하지만 복잡해진 네트워크 데이터

### TCP/IP (Transmission Control Protocol)(Internet Protocol)
- 인터넷에서 컴퓨터 간 통신을 위한 표준 프로토콜 스택 
- 대부분의 현대 네트워크 통신 사용
- TCP/IP 를 중심으로 4계층 구조 사용

#### 사용이유
- 복잡한 네트워크 과정, 특정 역할을 담당하도록 분리 
- 체계적인 데이터 전송 보장

#### TCP/IP 계층화
- 네트워크 통신의 복잡성을 나눠 관리
- 각 계층은 독립적으로 작동
- 다른 계층과 상호작용으로 통신 완성

#### 응용 계층 (HTTPS 등)
- 애플리케이션 (Spring 등) 에서 이미지 데이터 생성
- 데이터를 생성하고, 이를 메세지 라고 부름
- 메시지에 데이터를 담고 전송 계층으로 전달

#### 전송 계층 (TCP 등)
- TCP: 신뢰성 있는 전송 담당
- 전달 받은 메시지 데이터를 세그먼트로 자름
- MSS 단위: 한 번에 보낼 수 있는 패킷 양
- 자른 뒤 각 자른 데이터에 전송에 필요한 헤더를 붙임
- 메세지 데이터 -> 세그먼트 분리
- MSS 크기를 기준으로 데이터를 분할

> 전달 받은 데이터 세그먼트 단위로 나눔

#### 인터넷 계층 (IP)
- 전송 계층에서 전달 받은 세그먼트에 IP 헤더 추가
- 네트워크 간 경로 설정에 필요한 정보
- 데이터 목적지 IP, 출발지 IP 같은 정보 헤더에 추가
- 라우터를 통해 목적지까지 전달

#### 네트워크 인터페이스 계층
- 전기, 광, 전파 등 전송 신호로 변환

#### 캡슐화
- 수신 측에서는 각 계층의 헤더를 제거하며 응용 계층까지 데이터를 전달
- TCP/IP 계층을 통해 계층적으로 캡슐화 = Encapsulation
- 캡슐화된 데이터를 원래 형태로 복원  = Decapsulation

#### TCP/IP 계층 사용 이유
1. 통신 표준화: 서로 다른 장치가 데이터 주고 받는 규칙 
2. 확장성: 다양한 네트워크 기술과 호환 
3. 신뢰성: 신뢰성 있는 데이터 전송 
4. 인터넷 기반: 인터넷의 근간 프로토콜, 전 세계 통용

### TCP- UDP의 차이
- TCP
  - 연결 지향
  - 신뢰성 보장
  - 순서 보장
  - 흐름 제어, 혼잡 제어 지원
  - 상대적으로 느림

- UDP
  - 비연결 지향
  - 신뢰성 보장 안함
  - 순서 보장 안함
  - 오버헤드가 적음
  - 상대적으로 빠름

## 5. CIDR
> 라우팅할 때 트래픽 경로를 명확하게 지정하기 위해 네트워크 범위를 구분하는 주소 표준

### IP 주소의 구성
- 겉으로 보면 숫자 4개지만
- 각 숫자는 0~255 가질 수 있고
- 한 칸을 "옥텟"이라고 부른다
  - 그냥 IP 주소를 장치마다 하나씩 주면 되는거 아닌지?
  - 네트워크 영역 - 호스트 영역

### IP 주소는 두 가지 정보가 필요하다
1. 네트워크 영역: 이 IP가 어느 네트워크에 속해 있는지 
2. 호스트 영역: 그 네트워크 안에서 몇 번 장치인지 

#### 나누지 않으면?
- 단순하고 직관적으로 보이는데 
- 인터넷은 전세계의 장치들이 서로 연결되어 있는 환경
  - 모든 라우터는 모든 경로에 대해서 하나하나 위치를 알아야한다
  - 라우팅 테이블이 너무 커진다
  - 모든 주소지를 다 외우는게 아니라
    - 동네 단위로 길을 찾는거처럼 찾는다

#### 그래서 IP 주소는 네트워크 영역 + 호스트 영역으로 나눠져 있다
[네트워크 영역] + [호스트 영역]
- 192.168.1.10/24
- 네트워크: 192.168.1
- 호스트: 10

#### 어디까지를 네트워크 영역으로 봐야하나요?
192.168.1.10 <- 어디까지가 네트워크 영역이냐?

- 192 까지 네트워크
- 192.168
- 192.168.1

- 그래서 필요한게 서브넷 마스크 또는 프리픽스의 길이
- 192.168.1.10 / 24 <- 24

### 네트워크를 나누는 방식
#### 클래스 방식
- 초기 IP 주소 체계에서는 네트워크를 단순하게 나누고 싶었다.
- IP 주소를 A, B, C 클래스라는 고정된 크기로 나눴다.

#### 문제
- 너무 크거나, 너무 작다

### CIDR
- 서브넷마스크를 클래스에 고정하지 말고
- 필요한 크기만큼 알아서 네트워크 영역을 정하자

#### 💡 정리
- 한 줄 정리: IP 주소 뒤에 /숫자를 붙여 네트워크 범위를 표현하는 방식
- 핵심 목적: IP 주소를 네트워크 영역과 호스트 영역으로 구분
- 등장 배경: 클래스 기반 주소 체계의 비효율성 해결
- 주요 원리: 네트워크 비트와 호스트 비트를 유연하게 분할
- 대표 표기: /8, /16, /24, /32
- CIDR 숫자가 클수록: 네트워크 영역 증가, 호스트 영역 감소
- 호스트 수 계산: 2^(호스트 비트 수) - 2
- 제외되는 주소: 네트워크 주소 1개, 브로드캐스트 주소 1개
- 장점: IP 주소 효율적 사용, 라우팅 테이블 축소, 유연한 네트워크 설계
- 실무 포인트: 서브넷 마스크와 함께 네트워크 범위를 계산할 수 있어야 함
