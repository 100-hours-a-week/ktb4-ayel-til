## 1. Zero-downtime Deployment (무중단 배포)
> 사용자의 입장에서 서비스 중단 없이 애플리케이션을 업데이트하거나 배포하는 방식

### 중단 배포가 문제가 될 수 있는 경우
#### 기본적인 배포 
`기존 서버 종료 -> 새 코드 배포 -> 새 서버 실행`

#### 문제
기존 컨테이너 종료 -> 새 버전 실행 및 기동 완료 
- 서비스가 요청을 처리하지 못하는 시간이 생기고 이 시간을 **다운 타임**이라고 부른다

#### 다운 타임
서비스가 정상적으로 요청을 처리하지 못하는 시간

#### 중단 배포
기존 버전을 종료하고 새 버전을 실핼하는 방식

#### 무중단 배포
서비스 요청을 계속 처리하면서 새 버전으로 전환하는 배포 방식

---

### 무중단 배포
- 사용자가 서비스를 계속 이용할 수 있도록 유지하면서, 애플리케이션 버전을 새 버전으로 교체하는 배포 전략
- "무중단 배포"는 서버를 멈추지 않는다라고 이해하면 안된다
  - 배포 전략에 따라서 서버나 혹은 컨테이너가 중단될 수 있다
    - 그런데 그 중단이 서비스의 요청을 중단시키지 않는 형태를 띄는 경우
    - 기존 서버가 종료되기 전에 새 서버가 배포되어 있고 사용자 요청은 계속해서 처리된다

> 새 버전을 먼저 준비하고, 준비가 완료된 뒤 트래픽을 전환한다. 그리고 정상 작동하면 기존 버전을 종료한다

### 무중단 배포가 꼭 필요할까?
- 요즘 서비스들은 대부분 항상 동작하는걸 기본으로 전제한다
- 요즘에는 대부분의 서비스가 트래픽을 전국이 아닌 글로벌이 트래픽을 받으려고 한다
  - 보통은 서비스를 만들고 KR로 만들어서 -> EN, JP, CN 등등 언어로 번역한다
    - 글로벌 서비스를 하기 위해서는 서비스가 계속 돌아야한다
- 중단 배포를 하는 대표적 예시
  - 게임 서버, 은행
- ‼️ 무중단 배포가 필요한 서비스는 지속적으로 유저가 들어와야 하는 서비스들
  - 커머스, Saas, API 서비스, 실시간 서비스
- 무조건 무중단하는 건 아니고 중단이 필요한 경우에는 중단을 선택할 수 있다
  - 한 번에 크게 변경이 필요한 서비스 
    - -> 게임 ->  많은 양을 한 번에 업데이트
      - 서버를 채널 같은 개념을 둬서 하나의 채널에만 배포
  - 혹은 변경에 검증을 꼭 해야하는 서비스들 
    - -> 은행 -> 메이저 버전을 변경할 때
    - 은행에서는 패치, 마이너 버전은 무중단으로 하는 경우

### 사용 이유
> 서비스 이용자에게 중단 없이 안정적인 기능 업데이트를 제공하기 위해서
- 무중단 배포는 빠르게 배포한다 뿐만 아니라 안정적으로 전환, 빠르게 복구, 지속적 관측
- 요구사항
  - 가용성
  - 안정성
  - 롤백 가능성
  - 관측 가능성
  - 자동화
  - 재현성

### 구성 요소
- 다중 인스턴스 또는 다중 컨테이너: 기존 버전과 새 버전을 동시에 실행
- 로드밸런서 / 리버스 프록시: 사용자 요청을 정상 서버로 분산
- 헬스 체크: 새 버전이 실제 요청을 받을 준비가 되었는지 확인
- 트래픽 전환 정책: 기존 버전과 새 버전 사이의 요청 비율을 조절
- 롤백 전략: 새 버전에 문제가 생기면 이전 버전으로 복귀
- 모니터링: 배포 후 오류율, 응답 시간, 리소스 상태 확인
- CI/CD 파이프라인: 빌드 테스트 배포 과정을 자동화

### 기존 요청은 어떻게 되나?
- 새 버전으로 트래픽을 전환하면 기존 서버 종료
- 만약에 기존 서버가 긴 요청을 처리하고 있다면? (파일 업로드, 결제 요청, 웹소켓)
- 이 때 필요한 개념이 Connection Draining or Graceful Shutdown
- 기존 서버에는 새 요청이 가지는 않는다
- 그런데 이미 처리 중인 요청을 마무리할 시간을 주는 방식
- 디폴트로 설정되어 있는 경우
  - ECS, EKS 같은 사용하면 AWS에서 Graceful Shutdown 300초 정도 설정 해둔다
- 무중단 배포를 하기위해서 단순히 "새 서버가 돌아가네?" 하고 기존 서버를 죽이면 안된다

```
1. 새 버전 실행
2. 새 버전 헬스 체크 통과
3. 새 버전에 트래픽 전달 시작
4. 기존 버전에는 새 요청 전달 중단
5. 기존 요청 완료 대기
6. 기존 버전 종료
```

---

### 무중단 배포 종류
| 전략 | 핵심 개념 | 특징 |
| --- | --- | --- |
| **Blue/Green** | 두 환경을 준비하고 트래픽을 한 번에 전환 | 빠른 전환·빠른 롤백 |
| **Rolling** | 기존 인스턴스를 순차적으로 새 버전으로 교체 | 구조가 비교적 단순 |
| **Canary** | 일부 사용자에게만 새 버전을 먼저 제공 | 실사용 환경에서 위험 최소화 |

---

### 무중단 배포 시 고려해야 하는 사항
#### 1. 애플리케이션은 가능하면 Stateless하게 설계해야 한다
서버 메모리에 사용자 상태 저장하면 서버 교체에 문제가 될 수 있다
- 서버에 메모리 
  - 랭킹, 쿼리 캐싱, 사용자 로그인
- 실무에서는 무중단 배포를 해야한다
- 상태 값들을 외부 저장소에 저장하려고 한다

---
| 상태 데이터 | 일반적인 저장 위치 |
| --- | --- |
| 사용자 로그인 세션 | Redis |
| 사용자 데이터 | MySQL, PostgreSQL 등 DB |
| 업로드 파일 | S3, EFS, Object Storage |
| 캐시 | Redis, Memcached |
| 메시지 | Kafka, RabbitMQ, SQS |
---

#### 2. 데이터베이스 변경은 무중단이어도 문제가 발생한다
- 애플리케이션 -> Blue/Green, Rolling 등등
- DB 스키마 변경을 조심해야 한다
- 무중단 배포를 하면
  - V1, V2가 동시에 실행 중이어야 한다
  - 둘 다 사용자의 요청을 정상적으로 처리해야 한다
  
```
1. display_name 컬럼 추가
2. V2가 nickname, display_name 모두 처리하도록 개발
3. 데이터 마이그레이션
4. 모든 서버를 V2로 전환 + V2 가 안정적이다.
5. nickname 컬럼 제거

'+' 하는건 괜찮은데, '-'는 하지마라
```

- 디비를 컬럼을 날리고 prod 컬럼을 날렸다
- display_name 컬럼에는 아직 nickname 이 전달이 안됐다
- 이 전 날의 데이터베이스 스냅샷을 봐야하고 이걸 보고 복구 시켰다
- 스냅샷 -> 복구 시점 의 그동안 데이터는?

---

#### 3. 롤백 "배포 실패시" 가 아니라 "지표가 불안정"
- 새 버전이 실행됐다 -> 헬스체크 성공했다 -> 배포가 성공했다?
- 디비 날리고 기존 버전 컨테이너도 날린다
- v2 에서 500 에러 rate -> 10% 찍는다. -> 복구 어려움
---
| 관측 항목 | 확인 이유 |
| --- | --- |
| HTTP 5xx 비율 | 서버 오류 증가 여부 |
| 응답 시간 p95, p99 | 일부 사용자 요청 지연 여부 |
| CPU / 메모리 | 리소스 부족 여부 |
| DB 커넥션 수 | DB 과부하 여부 |
| 컨테이너 재시작 횟수 | 애플리케이션 비정상 종료 여부 |
| 핵심 비즈니스 지표 | 결제, 주문, 로그인 등의 성공률 확인 |
---

#### 4. 무중단 배포는 실행보다 롤백 계획이 더 중요하다.
- 무중단으로 배포하는거 안 어렵다 
- 그거보다 "롤백"을 어떻게 안정적으로 할거냐 ⭐️
- "무중단" <- blue green, rolling 배포방식 에 꽂히는데
- Devops, Infra, Backend - 인프라를 만지면 무조건
  - "안정성"
  - "관측성"

---

#### 💡정리
- 무중단 배포: 사용자가 서비스를 이용하는 동안 새 버전으로 전환하는 배포 방식
- 해결하려는 문제: 배포 중 발생하는 다운타임, 요청 실패, 사용자 불편
- 핵심 원칙: 새 버전을 먼저 준비하고, 정상 확인 후 트래픽을 전환
- 필수 요소: 다중 인스턴스, 로드밸런서, 프록시, 헬스 체크, 롤백, 모니터링
- 기존 요청 처리: Connection Draining, Graceful Shutdown으로 완료 대기 
- 대표 전략: Blue/Green, Rolling, Canary

## 2. Blue/Green deployment (블루/그린 배포)
> 두 개의 독립된 환경(블루, 그린)을 운영하며, 트래픽을 새로운 버전으로 전환해 서비스 중단 없이 배포와 롤백이 가능한 배포 방식
- Blue / Green 이 두 개의 환경을 동시에 실행하는 방식
  - 다운타임 줄이고 + 배포 위험 줄인다.
  
#### Blue, Green 이 항상 기존버전, 새버전? ❌
```
Blue = 이전버전
Green= 새버전

# 현재
app-blue # 1.0.1

# 여기에서 배포를 시작한다.
app-green # 1.0.2
# 이 앱을 만들어서 대기 -> green 으로 옮기고

app-blue #1.0.3
```
- Blue, Green 버전 번호나 이전 버전을 고정시키는게 아니라 
  - 트래픽을 받고 있는 환경
  - 대기 중인 환경 
- 이 두개의 환경을 동시에 운영하면서 분리하는 것이 핵심

---

#### 구성 요소
- Blue 환경: 현재 서비스 중인 운영 환경으로, 사용자가 실제로 접근하고 있는 버전
- Green 환경: 새로운 애플리케이션 버전이 배포되는 대기 중인 환경이며, 전환 준비가 완료되면 서비스 대상이 된다
- 트래픽 전환 도구: Nginx, AWS ALB, 로드 밸런서 등, Blue에서 Green으로 사용자의 요청을 즉시 전환할 수 있도록 설정을 변경하는 구성 요소
- 헬스 체크 및 모니터링: Green 환경이 정상적으로 동작하는지 사전 검증하는 절차로, 전환 후에도 안정성을 확보할 수 있다
- 롤백 메커니즘: Green 전환 이후 문제가 생겼을 때, 빠르게 Blue로 복귀할 수 있도록 설계된 자동 혹은 수동 복원 절차

### 장점
#### 1. 롤백
- 롤백이 상당히 편하다
- 새 버전이 문제가 생기면 어차피 대기하고 있던 이전 버전으로 바로 롤백하면 된다
- 롤백도 뭐 특별한 코드를 친다? ❌ 
- RP -> app 프록시 패시를 green -> blue 옮기기만 하면 끝
- nginx -s reload

#### 2. 배포 구조가 간단하다
- 현재 환경 <-> 신규 환경이 분리
- 배포하는 과정이 다른 무중단 배포에 비해서 상당히 간단

#### 3. 장애 영향 최소화
- 사전에 검증 + 롤백이 용이
- 서비스의 영향을 적게 줄 수 있다

### 블루 그린이 유리한 서비스, 상황
- 결제, 주문처럼 장애 영향이 큰 서비스
- API 변경 위험이 큰 배포
- 신규 기능을 릴리즈
- 대규모 리팩터링
- 인프라 설정 변경
- 공통적으로 롤백이 필요할 수 있고, 한다면 빠르게 해야하는 상황

---

### 단점
#### 1. 리소스 비용이 상당히 크게 들 수 있다
- Blue의 구성 요소를 그대로 Green으로 이중화를 먼저 한다
  - Blue가 EC2 10대라면 Green도 EC2 10대 필요
  - 지금 우리 서비스가 트래픽이 처리하기 위해 필요한 양이 10대
  - 배포하는 시점에 20대

#### 2. 이중 운영 위험
- Blue, Green 둘 다 어느정도 시간동안 유지
  - Blue도 기존 버전을 유지해야하고
  - Green도 계속 유지를 해야한다
- 배포 스크립트에서 문제가 생기면 
  - 이미 Green 배포가 완료
  - 안정화도 완료됐다라고 판단
- Blue을 없애야하는데 이 작업을 하지 않으면 이중으로 리소스 계속 사용 + 복잡도 증가

#### 3. DB 변경하기 힘들다
- 블루 그린이 만족하는 데이터베이스 스키마를 제공

### 블루그린 할 때, 실무에서 실수하는 포인트
#### 1. Green이 실행되자마자 트래픽 전환
- 헬스체크를 해야한다
- 그린이 실행된 게 그린이 정상작동은 아니다

#### 2. 트래픽 전환 후 블루를 바로 종료하기
- 새 버전은 안정성이 확인되기 전까지 지표가 정상적으로 나오는지 확인

#### 3. 롤백을 먼저 고려하기
- 블루그린에선 어떤 상황에, 어떤 지표가, 어떤 수치에 닿으면, 어떻게, 어떤 거를 롤백한건지?
- 미리 정의하고, 코드로 작성
- Http Response 500 -> 5%
  - 기준점을 설정해야한다
  - 기준점은 지표마다 다르게 설정

#### 4. 블루그린이 서로 다른 설정
- 환경 변수
- 리소스 설정 
  - 도커 네트워크 
  - CPU
- 권한
  - IAM, Role

---

#### 💡정리
- Blue: 현재 운영 중이거나 롤백 가능한 안정 환경
- Green: 새 버전을 배포하고 검증하는 환경
- 핵심 원리: 새 버전을 먼저 준비한 뒤 트래픽만 전환
- 핵심 정점: 빠른 롤백, 낮은 다운타임, 분리된 사전 검증
- 핵심 단점: 배포 중 이중 리소스 비용, DB 호환성 문제

---

## 3. Rolling Deployment
> 서비스를 구성하는 여러 인스턴스를 한 번에 종료하지 않고, 일부씩 새 버전으로 교체하여 서비스 가용 성을 유지하는 배포 전략입

### 사용 이유
> 인프라를 두 배로 준비하지 않더라도 배포 중 서비스의 처리 용량을 유지하기 위해서 사용

- Blue/Green 각각 10대, 총 20대
- 롤링은 v1 10 -> 9, v2 0 -> 1

### 롤링 배포의 난이도
- 롤링 배포를 하기 위해서 V1에 배포되어 있는 인스턴스 중 하나를 Nginx -> RP에서 제거
- V1 인스턴스 죽이고 V2 인스턴스 등록 -> 정상 동작 -> Nginx에 등록
- AWS ECS, k8s, EKS 관리형 서비스에서 기능으로 제공되는걸 사용하는 경우가 일반적

### 롤릴 배포의 방식
- In-place 방식(교체 실행 방식): 기존 인스턴스를 하나씩 종료한 뒤 같은 자리에서 새 버전 실행, 추가 자원이 적게 듦
- Side-by-side 방식(동시 실행 방식): 새 인스턴스를 먼저 추가한 뒤 기존 인스턴스를 제거, 처리 용량 유지에 유리

- 둘 중에 어떤걸 사용해야할까?
  - 트래픽 유형
    - 스파이크 형
    - 스트레스 형
  - 서비스의 상황
  - 업데이트 시간

---
  | 비교 항목 | In-place | Side-by-side |
  | --- | --- | --- |
  | 새 버전 실행 시점 | 기존 서버를 제거한 뒤 실행 | 새 서버를 먼저 추가 |
  | 추가 리소스 | 거의 필요 없음 | 일시적으로 필요 |
  | 배포 중 처리 용량 | 감소할 수 있음 | 비교적 유지 가능 |
  | 배포 안정성 | 상대적으로 낮음 | 상대적으로 높음 |
  | 롤백 속도 | 이전 버전을 재배포할 수 있음 | 기존 버전이 남아 있을 수 있음 |
  | 적합한 환경 | 소규모·리소스 제한 환경 | 트래픽이 많고 안정성이 중요한 환경 |
---

### 장점
#### 1. 인프라 비용 절감
- 블루그린에 비해 동시에 유지해야하는 리소스가 적다

#### 2. 점진적 배포
- v1 10 -> 9 -> 8
- 변경 영향을 점진적으로 전달한다
- 변경 영향으로 서버가 문제 -> 일부 인스턴스만 문제가 생긴다

---

### 단점
#### 1. 배포 시간이 길다
- 교체해야하는 인스턴스가 1000대라면?

#### 2. V1, V2가 동사애 존재
- V1, V2 가 동시에 계속 요청을 처리 해줘야한다.
- 요청이 혼재된다.
- 클라이언트는 V2 가 필요한데
- 요청을 보냈더니? V1 에서 응답을 줄 수 있다. 
  - → API Docs versioning 
    - /api/v1/users/me
    - /api/v2/users/me

#### 3. 롤백 속도가 많이 느리다
- V2 이미 10대 중에 8대가 v2
- 롤백을 결정한다.
- V1을 이미 날렸다.
  - 8대의 V1 을 다시 만들어야한다

---

### Blue/Green vs Rolling Deployment
| 비교 항목 | Blue/Green | Rolling Deployment |
| --- | --- | --- |
| 배포 방식 | 환경을 두 개 준비 후 트래픽 전환 | 기존 인스턴스를 순차 교체 |
| 트래픽 전환 | 보통 한 번에 전환 | 인스턴스 교체 과정에서 자연스럽게 분산 |
| 추가 리소스 | 배포 중 상당히 필요 | 설정에 따라 일부만 필요 |
| 배포 속도 | 전환 자체는 빠름 | 전체 완료까지 시간이 걸릴 수 있음 |
| 롤백 속도 | 매우 빠름 | 이전 버전 재배포가 필요할 수 있음 |
| V1·V2 혼재 | 전환 전후로 비교적 분리 가능 | 배포 중 혼재 상태가 일반적 |

---

#### 💡정리

- Rolling Deployment: 기존 인스턴스를 일부씩 새 버전으로 교체하는 배포 방식
- 핵심 목표: 배포 중에도 일정 수 이상의 서버가 요청을 처리하도록 유지
- 핵심 흐름: V1 일부 제외 → V2 실행 → Health Check → V2 등록 → 다음 V1 교체
- In-place 방식: 기존 서버를 하나씩 새 버전으로 교체, 추가 리소스가 적음
- Side-by-side 방식: 새 서버를 먼저 추가한 뒤 기존 서버 제거, 용량 유지에 유리
- 롤백: 이전 버전을 다시 순차 배포하는 방식이 일반적

---

## 4. Canary Deployment
> 새 버전을 전체에 적용하기 전에 일부 사용자나 트래픽에만 점진적으로 배포하여 안정성을 검증한 후 전면 배포하는 방식

### 사용 이유
> 새 버전의 안정성을 실사용 환경에서 미리 검증하여 전체 배포로 인한 장애를 사전에 방지하기 위해서

### 카나리 vs 롤리
- 목적이 다르다
- 롤링 배포는 인프라 교체 전략
- 카나리 배포는 사용자 영향 범위를 제어하는 전략
  - 위험을 줄이면서도 빠르게 릴리스할 수 있는 전략

---
| 구분 | Rolling Deployment | Canary Deployment |
| --- | --- | --- |
| 핵심 목적 | 서버·Pod를 순차적으로 새 버전으로 교체 | 새 버전의 위험을 작은 사용자 집단에서 먼저 검증 |
| 기준 | 인스턴스 교체 순서 | **트래픽 비율 또는 사용자 그룹** |
| 새 버전 노출 | 새 인스턴스가 준비되면 자연스럽게 요청을 받음 | 의도적으로 일부 요청만 전달 |
| 배포 판단 | 새 인스턴스가 정상인지 확인 | 오류율·응답 시간·핵심 기능 지표를 보고 확산 여부 판단 |
| 대표 질문 | “몇 대씩 교체할까?” | “처음에 몇 %에게 노출할까?” |
---

### 트래픽 비율 제어
- v1 90%, v2 10%
- 이런식으로 그냥 트래픽 비율만 제어한다?
  - 이렇게하면 무슨 일이 생기나?
    - 90% 확률로 v1
    - 10% 확률로 v2
  - 클라이언트 프로그램
    - 특정 버전끼리 호환되는 경우
    - 유저가 내가 원하는 버전을 사용하도록 "강제"할 수가 없다
    - 웹 브라우저는 강제할 수 있는데
    - 설치하는 프로그램(앱, 컴퓨터 프로그램)
- 유저 그룹
  - 클라이언트 트래킹 태그
- 이렇게 유저를 고정시키고 특정 유저한테만 새로운 버전
- 혹은 다른 버전을 보여주는 방식
  - A/B Test라고 한다

### Bake Time
- 카나리 트래픽을 유지하면서
- 새버전의 실제 운영 지표를 관찰하는 시간
