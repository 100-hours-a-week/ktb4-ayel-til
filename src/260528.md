## NoSQL
- SQL만을 사용하지 않는 여러 유형의 데이터베이스

### 알아야 하는 이유
- 데이터의 다양성, 대규모 데이터 처리, 수평 확장 및 유연한 설계 요구에 대한 필요성이 점점 증가함
- 기존 스키마들은 너무 규칙이 강하고 사용자가 늘어나면 빠르게 확장해야함
  - RDB의 규칙성이 높으면 확장성이 내려감

### 특징
- 빠른 읽기/쓰기 처리 속도
- 유연성
- 동시 처리성
- 확장성

---

## 동작방식
## 1. Key-value Store

### 특징
- 단순한 key-value의 한쌍으로 데이터를 저장
- 각 키에 하나의 값이 매핑되는 가장 단순한 형태의 데이터 저장 방식

### 장점
- 매우 빠른 읽기/쓰기 속도
  - 인메모리 구조
  - 해시 테이블 기반
- 구조 단순/수평 확장 용이

### 단점
- 데이터 구조가 단순해서 복잡한 쿼리(관계 처리)나 검색이 어려움
- value 내부 구조를 DB가 이해하지 못함

### 주 사용처
- 세션, 캐시, 토큰, 사용자 설정 같은 곳
- 많이 써야하고, 많이 읽혀지는 곳 (속도에 민감한 곳들)
- 예: Redis, DynamoDB.

### in-memory 쓰는 이유란?
- key랑 value만 저장 -> 데이터가 작음
- 자주 접근하는 데이터라서 속도가 매우 중요
- 저장하는 값들이 사라져도 문제 안됨
  - 날아가도 서비스에 영향을 안주는

### 실시간성 + 데이터 영속성 + 큰 용량이 클 때
- ex) Aerospike
- 비교적 고속 읽기/쓰기 성능
- 고가용성과 확장성
- 강한 일관성

- 실시간 채팅에 사용됨

---

## 2. Documents Store / Document Oriented Databases

### 특징
- JSON, XML 같은 문서 단위로 데이터 저장

### 장점
- 구조가 자유로워 스키마 변경이 유연
- 문서 단위로, 조회, 수정 가능
- 쿼리 검색 유연

### 단점
- JOIN이 어려움 -> 복잡한 관계 데이터는 비효율적
- 데이터 중복 허용
- 데이터 간 관계성이 약함

### 주 사용처
- 콘텐츠 관리, 블로그, 게시판, 카탈로그
- 속성의 수정이 많거나, 관계성이 낮은 데이터
- 예: MongoDB, CouchDB.

- 실시간 채팅에 사용됨

---

## 3. Column-Oriented Store / Column-based Databases

### 특징
- 테이블 구조처럼 컬럼 단위 데이터 저장, 동일 행 내 컬럼 그룹 관리
- 대량의 데이터를 빠르게 조회하고 분석

### 장점
- 대용량 데이터, 빅데이터 처리 적합
- 컬럼 단위 조회 최적화 -> 읽기 성능 좋음

### 단점
- 설계가 복잡함, 스키마 잘못 설계하면 비효율
- 단순 조회/저장 외 복잡 쿼리는 어려움

### 주 사용처
- 로그 수집, 분석, 시계열 데이터, 추천 시스템
- 예: Cassandra, HBase.

---

## 4. Graph Store / Graph Databases

### 특징
- 노드와 엣지 구조로 데이터 저장 -> 관계 중심
- 객체 간의 관계를 중심으로 데이터를 저장하고 조회

### 장점
- 관계 기반 조회 최적화
- 소셜 네트워크, 추천 시스템에서 효율적

### 단점
- 트랜잭션/대용량 처리 복잡
- 수평 확장이 어려움 (관계를 유지해야함)

### 주 사용처
- 소셜 그래프, 추천 엔진, 지식 그래프
- 예: Neo4j, Amazon Neptune

## 데이터베이스 확장
- 데이터베이스를 물리적 또는 논리적으로 분산시키는 기술

### 사용이유
- 데이터베이스의 처리 가능 양과 속도를 늘리기 위해

---

## 확장 방식
## 1. 파티셔닝
- 기존 테이블을 파트로 나누자
  - 수직 파티셔닝 (Vertical Partitioning)
  - 수평 파티셔닝 (Horizontal Partitioning)

---

## 수직 파티셔닝 (Vertical Partitioning)
- 하나의 테이블의 컬럼을 나누자
- 자주 조회되는 컬럼 / 아닌 컬럼 분리하자

### 장점
- 조회가 잦은 데이터에 대한 I/O 감소
- 테이블 잠금, 캐싱 효율 증가

### 단점
- 조인 필요도가 늘어서 쿼리 복잡도 증가
- 2개 테이블 동시 적용 트랜잭션 시 관리

---

## 수평 파티셔닝 (Horizontal Partitioning)
- 하나의 스키마(데이터구조)를 여러 테이블로 저장하자
- 테이블 스키마는 같지만, 범위에 따라서 저장하자

- ex) 범위, 리스트, 해시
- 범위: 날짜별
- 리스트: 지역별
- 해시: id로 균등하게 분배하기

### 장점
- 많이 작성되는 경우, 쓰기 성능 증가
- 특정 파티션 별로 처리하기 좋음
- 아카이빙, 백업이 쉬움

### 단점
- 인덱스 관리 힘듬
- 데이터 불균형
- 파티션간 쿼리 검색이 어려움
- 트랜잭션 어려움

---

## 2. 복제 (Replication)
- 똑같은 데이터를 복제하자

1. Primary/Master (주 노드)
- 데이터 변경 작업을 담당하는 노드

2. Replica/Slave (복제 노드)
- Master의 데이터를 복제하여 유지하는 노드

### 장점
- 읽기 부하를 분산
- 장애 발생 시 빠른 복구
- 가용성을 높임

### 주의사항
- 성능 및 운영 최적화
- 데이터 일관성 
- 장애 처리
- 복제 지연 가능성

---

## 서버 캐시
- 웹 서버가 데이터를 빠르게 제공하기 위해 자주 조회되는 데이터 임시로 저장하는 장소

## 사용이유 
- 웹 사이트의 속도를 높이고 서버 부하를 줄여 사용자 경험을 개선할 수 있음

---

## 1. Local Cache
- 각 서버 인스턴스에 독립적으로 존재
- 서버의 리소스를 사용하여 데이터를 캐싱함
- 해당 서버 내에서만 사용되고 서버 간에는 공유되지 않음

### 장점
- 데이터 접근 속도 빠름
- 추가적인 네트워크 지연 없음

### 단점
- 스케일 아웃 시, 일관성 유지 힘듬
- 각 서버 캐시가 독립적으로 작동하여 데이터 중복

### 예시
- 단일 서버 세션 정보
- 임시 계산 결과
- 인기글

> 로컬 캐시는 빠른 속도와 낮은 비용으로 자주 사용하는 데이터를 처리하기 위해 사용한다.

---

## 2. Global Cache
- 여러 인스턴스에서 공유하는 캐시

### 장점
- 데이터 일관성과 공유
- 여러 서버 인스턴스가 동일한 캐시 데이터 사용

### 단점
- 네트워크 지연 가능성
- 로컬에 비해 상대적으로 느림

### 예시
- 멀티 서버 세션 정보
- 상품 정보, 가격 등 공유 정보

> 글로벌 캐시는 여러 서버가 동일한 데이터를 공유하고 일관성을 유지하기 위해 사용한다.

---

### 사용되는곳
1. DB
   - DB 엔진 메모리
   - 데이터 페이지, 쿼리 결과
2. 스토리지
   - 정적 리소스
   - CDN에 저장
3. 브라우저
   - 로컬 브라우저
   - 정적 리소스 (HTML, CSS, JS) 등 저장
4. 프록시
   - HTTP 응답 캐싱
   - WAS 전에 정적 응답 캐싱
