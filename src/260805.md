## Resilience와 장애 전파 방지 

### 장애 전파 방지
> 장애 전파 방지는 장애를 완전히 없애는 기술이 아니라, 장애가 발생해도 전체 시스템으로 퍼지지 않도록 장애의 시간과 범위를 제한하는 설계
- 장애가 발생한 부분을 감지
- 장애가 발견한 부분에 추가적인 요청 보내지 않기
- 하나의 장애가 다른 시스템의 자원을 소진하지 않기 위해

---

### Resilience
- 회복 탄력성
- 시스템의 일부가 느려지거나 장애가 발생하더라도
  - 정상적 기능 제공
  - 중요한 기능 보호
  - 장애 회복되면 점진적으로 정상 상태로 돌아가고
  - 일부 기능 제한하거나 간소화시킴
- Resilience 목표를 달성하려고 함
  - 회복 탄력성 <- 모든 요청을 반드시 성공시키는게 아님
  - 전체 시스템이 무너지지 않게 일부 요청을 빠르게 실패하거나 일부 요청을 의도적으로 제외 시킨다
  - Spring 에서는 특히 resilience4j 라는 라이브러리가 있음

---

### 왜 장애 전파 방지가 필요한가?
- MSA 환경에서 적용하는 경우가 많음
- mono repo <- 여기에서도 차용되는 개념이 많음
- 기준 = MSA 환경
  - 분산 시스템을 기준
  - 분산 시스템에서는 하나의 요청이 여러 서비스를 거쳐서 완성
- 하나의 장애가 전체 장애로 번지는 현상을 Cascading Failure

---

### 해결 방식
#### 1. 기다리는 시간 제한하기
- 응답하지 않는 서비스 <- 그대로 기다리고 있으면 스레드, 커넥션 점유
  - 기다리지 않는 것 특정 시간이상 <- timeout

#### 2. 들어오는 요청량 제한하기
- 시스템이 처리할 수 있는 요청보다 많은 요청이 들어오면 거절할 수 있음
- Rate Limiter: 요청이 들어오는 자체를 제한
- Load Shedding: 들어온 요청이 너무 많으면 버림

#### 3. 실패한 요청 무조건 반복하지 않기
Retry
- 실패를 했다하더라도 일시적인 경우
- 너무 많이 사용하면, 시스템에 부하를 만듬
- Retry 회수랑, 대상을 제한

#### 4. 반복해서 실패하면 해당 대상 잠시 호출하지 않기
- 어떤 서비스만 계속 실패함
- 이 서비스는 이미 장애 상태라고 판단
- 그 서비스는 요청을 잠깐 하지 않고 대기하기 <- Circuit Breaker

#### 5. 자원을 나눠서 사용하기
- 하나의 외부 서비스가 느려졌다고해서 모든 커넥션, 모든 스레드 풀이 전부다 이걸 기다리거나 모든 자원이 서비스에 종속되면 안된다
- Bulkhead

#### 6. 완전한 성공이 안 되면, 제한된 기능 제공하기
- 제품 리스트, 추천 제품(에러), 광고 제품 -> 제품 리스트, 광고 제품만 제공
- Fallback, Graceful Degradation

---

### 인프라와 백엔드의 역할 구분
- 장애 전파 방지는 인프라, 백엔드 둘 중 하나만 처리하는게 아님
- 각 계층이 알고 있는 정보가 달라서 둘 다 같이 함께 처리를 해야함

- 인프라: 트래픽 + 연결 보호
- 애플리케이션: 비즈니스 로직 + 실제 재시도 처리

```
요청 

1. 요청이 너무 많은거 아닌지? -> Rate Limiter
2. 너무 오래 기다리는거 아닌가? -? timeout
3. 일시적인 실패인가? -> Retry
4. 계속 실패하는 거 아닌가? -> Circuit breaker
5. 특정 기능, 서비스 자원을 독점하는거 아닌가? -> Bulkhead
6. 정상 결과를 줄 수 없으면? -> Fallback
```
- 이 패턴들이 서로를 대체하는 관계가 아님
- 각기 다른 문제를 해결함
- 일반적으로는 <- 비즈니스의 형태
  - 인프라 구성에 따라서 위의 내용을 조합해서 사용함
  
---

### 1. Rate Limiter
> 시스템이 감당할 수 있는 범위까지만 요청을 받아들이는 장치
- 해결하는 문제
    - 서비스 최대 처리량 (RPS) 1000 RPS
        - 실제로 들어온 요청이 2000RPS
        - 문제가 생김
            - 요청 큐 증가, 응답 시간 증가, 메모리 사용량 증가, 스레드와 DB 커넥션 고갈, Timeout 증가, 클라이언트 Retry 증가, 전체 시스템 장애
- 처리 용량보다 많은 요청 결국에 장애를 만듬
- 일정 수준을 넘으면 그냥 요청을 빠르게 거절하는게 시스템 안정성에 도움이 된다

#### 인프라에서의 Rate Limit
- Nginx, Ingress
- 요청을 제한
```
limit_req_zone $binary_remote_addr
    zone=api_rate_limit:10m
    rate=30r/s;

server {
    location /api/ {
        limit_req zone=api_per_ip burst=30 nodelay;
        limit_req_status 429;

        proxy_pass http://backend;
    }
}
```
- 일반적으로는 요청이 시스템 내로 들어오는거 자체가 문제
    - 일반적으로는 시스템 입구에서 거절하는 방식으로 구현이 되어 있음

#### 백엔드 Rate Limit
- 비즈니스 기준으로 제한해야할 때
- 예를 들어
    - 사용자당 이메일 인증을 1분에 5회로 제한한다
    - 사용자당 결제 시도를 1분에 10회로 제한한다
- 서비스별로 RPS 가 많이 차이나면?
    - 제일 느린 RPS 를 기준으로 인프라 레벨에서 Rate Limit 을 걸면 다른 서비스들을 상대적으로 널널한 요청을 받음 -> 자원 효율성이 안나옴
- 서비스 별로 RPS 를 걸 수 있다
    - 인프라 구성을 분산을 많이 해놓고 파드에 Nginx Pod 를 앞에다 두는 경우
---
#### Rate Limit ≠ 동시 요청 수
- Rate Limit = 초당 몇 개의 요청을 허용할거냐
- Concurrency = 동시에 몇 개를 처리할 거냐
- 초당 100개의 요청을 받을 수 있음 <- Rate Limit = 100 RPS
  - 이 요청이 처리에 10초가 걸린다면?
  - 시스템에서 처리하고 있는 동시 요청 수는 몇 개? -> 1000개
- Rate Limiter 가지고는 느린 요청에 대한 자원 고갈을 막기가 힘듬 -> Bulkhead, Timeout
---

### 2. Timeout
> 응답하지 않는 작업을 무한정 기다리지 않도록 기다리는 시간에 상한을 두는 장치
- 어떤 문제 해결 하는지?
    - 타임아웃이 없을 때 외부 서비스가 응답 X
    - 자원 점유
        - 요청 처리 스레드, HTTP 커넥션, 디비 커넥션, 메모리, 요청 큐
- 요청 하나가 기다리는거 자체는 큰 문제는 아님
- 동시에 수백, 수천개 요청이 계속 기다리고 있으면 자원 고갈

#### 인프라 Timeout
- Nginx timeout
```
location /api/ {
    proxy_connect_timeout 500ms;
    proxy_send_timeout    2s;
    proxy_read_timeout    2s;

    proxy_pass http://backend;
}
```

#### 백엔드 Timeout
- 비즈니스 로직에 따라서 일관적인 타임아웃이 아닌 로직에 따라서 다르게 타임아웃을 적용해야할 수 있음
---
#### Timeout <- 작업을 중단하는걸 의미하지는 않음
- 요청이 처리되고 있는데 Timeout 남
    - 일반적으로는 종료되는게 맞음
- 분산 시스템, 외부 요청 시스템 (결제, 주문)
    1. 결제 서비스가 결제를 완료
    2. 주문 서비스를 호출
    3. 주문 서비스에서 타임아웃
        1. 주문 서비스가 Retry
        2. 결제 서비스가 주문 서비스의 완료를 기다리지 않을 수도 있음
- 타임아웃이 하나의 비즈니스 로직 중간에 나는 경우
    - 전체 로직이 한 번에 취소가 되면 되는데, 전체 로직이 여러개의 서비스
      - 여러 개의 데이터베이스에 들어가는 경우 요청에 대해 데이터가 변화하는게 일관성이 없을 수 있음
      - 결제 OK -> 주문이 생성 X or 주문이 두 번 들어간다
    - Timeout 설정을 할 때는 Retry 정책, 멱등성
---
#### 너무 짧은 타임아웃
- 정상 요청 -> 타임아웃
- Retry가 너무 많이 증가
- 사용자 오류율 증가
- 1회 → 1번 API Call
    - 5 API Call
- p95, p99 값이 얼마나 나오는지?
    - 어디까지 허용할건지?
    - 서비스 별로 측정하고 나서 타임아웃 설정을 해야함

---

### 3. Retry
> 일시적인 실패일 가능성이 있을 때 요청을 제한된 횟수만큼 다시 시도하는 방법

#### 어떤 문제 해결 하는지
- 분산 시스템 <- 일시적인 실패 가능성이 항상 존재
    - 네트워크
    - 파드 재생성
    - 노드의 재생성, 초기화
- 이런 오류들은 요청이나 처리에 문제가 아님 -> 재시도를 하려고 함

#### 재시도 하면 안되는 문제들
- 다시 요청해도, 결과가 달라지지 않는 오류는 재시도 하지 않음
    - 잘못된 요청 → 회원 가입인데, 요청 값이 잘못되는 경우
    - 인증 실패 → 인증은 재시도를 해도 계속 실패
    - 권한 부족
    - 비즈니스 규칙 위반 → 애플리이션 로직이 실패 → 재시도 실패
---
#### 인프라 Retry
- Nginx
```
location /api/ {
    proxy_next_upstream
        error
        timeout
        http_502
        http_503
        http_504;

    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 1s;

    proxy_pass http://backend;
}
```

#### 백엔드 Retry
- Resilience4j 설정
```
# resilience4j 설정
retry:
	instances:
		payment:
			max-attempts: 3
			wait-duration: 200ms
		order:
			max-attempts: 2
```
---
#### Retry storm
- 재시도가 폭풍처럼 후두두 많아지는 것을 의미하는데 재시도를 할 때는 몇 가지 제약

#### Exponential Backoff
- 재시도 할 수록 대기 시간을 증가
    - 1차 재시도 -> 100ms
    - 2차 재시도 -> 200ms

#### Jitter
- 재시도 대기 시간을 무작위 값으로 추가함
    - 1차 → 85ms
    - 2차 → 405ms
    - 3차 → 200ms
- 재시도 회수에 대한 제한
---
#### 여러 계층에서의 재시도 요청
- 하나의 요청
    - Nginx
    - 주문 서비스
    - 결제 서비스
        - 결제 SDK
    - DB Clien
- 재시도
    - Nginx
    - 주문
    - 결제
        - 결제 SDK
    - DB Client
- 요청 하나에는 하나의 계층에서만 재시도를 시도한다

#### 재시도 정책 설정 할 때
- 성공률을 관찰해야함
- Retry <-
    - 최초 요청 성공
    - Retry 요청 성공 <- 회수 별로 언제 요청이 성공하는지
  - 전체 Retry 회수
  - Retry 로 추가된 트래픽 - 일반 트래픽을 분리해서 관측
- 재시도 정책 잡고 시행
    - 재시도 성공률이 떨어진다-> 재시도 정책을 고치는게 아니라 애플리케이션 로직의 문제 확인하기
- Retry 
    - 장애를 복구하는게 아님
    - 실패하면 다시 시도하는 역할, 부하를 증폭 하는 역할만 될 수 있음

### 4. Bulkhead
> 하나의 기능이나 의존성이 전체 자원을 사용하지 못하도록 자원을 분리하는 방법

- 선박의 격벽에서 나온 개념
    - 배의 한 구역에 물이 들어와 격벽이 있으면 배 전체가 침몰하지 않음
---
#### 해결하는 문제
주문 서비스 
- 결제 서비스
- 재고 서비스
- 알림 서비스

모든 호출이 같은 스레드 풀을 사용하면 알림 서비스의 장애 -> 전체 요청의 장애

---

### 백엔드 영역 -> bulkhead
#### Semaphore Bulkhead
- 동시에 실행할 수 있는 요청 수 제한
  - 결제 서비스 호출 개수 -> 최대 20개
  - 주문 서비스 호출 개수 -> 최대 10개
- 서비스 별로 사용할 수 있는 자원에 대해서 최대 수량을 정해두는 방식
- 허용된 요청 수 넘으면 거절

#### ThreadPool Bulkhead
- 의존성 별로 Thread pool + Queue 분리
  - 결제 전용 스레드 풀
  - 재고 전용 스레드 풀
  - 알림 전용 스레드 풀
---
#### 인프라 Bulkhead
- Nginx 설정
```
upstream backend {
    server backend-1:8080 max_conns=100;
    server backend-2:8080 max_conns=100;
}
```

- K8s
    - Pod Anti-affninty
    - Topology Spread
    - 특정 서비스에 Node 를 몰아둔다던지

### 5. Circuit Breaker
> 계속 실패하는 서비스에 요청을 보내지 않고 빠르게 실패시키는 장치

서킷 브레이커는 외부 서비스가 계속 실패하거나, 느리게 호출될 때 잠시 호출을 차단하는 역할 (ex. 누전 감지기)
- 장애가 현재 서비스까지 전파되지 않게 하는 역할

- 주문 서비스 -> 결제 서비스 호출
1. 결제 서비스 응답 지연
2. 주문 서비스에 스레드 응답 대기
3. 실패하면 - 서킷브레이커 오픈
   1. 타임 아웃 증가
   2. Retry 증가
   3. 내부 트래픽 폭증
4. 바로 요청을 중간에 실패 처리
- 외부 서비스 실패율 높거나, 응답 시간이 지연된다
  - 실제 호출을 중단 시킴
  - 요청을 Fallback 시킴
---
### 서킷브레이커 상태
#### Closed
- 정상 상태
- 호출 허용하면 최근 호출 결과 기록
  - 성공한 요청 몇 개고, 실패한 요청 몇 개고, 느린 요청 몇 개고
- 임계치 설정한 값에 다다르면 Open으로 전환

#### Open
- 장애가 감지된 상태
- 외부 서비스를 실제로 호출하지 않음
- 대신에 Fallback 반환 -> 실패 결과 반환
- 캐시 데이터 반환
- 기능을 임시적으로 비활성화
- 작업을 Pending 상태로 전환
  - 큐에 작업을 쌓아 놓을 수도 있음

#### Half-Open
- 외부 서비스가 회복됐는지 확인하는 상태 
- 모든 요청이 한 번에 허용되지 않음
- 설정한 개수만 테스트 요청으로 허용함
- 테스트 요청에 실패율 + 느린 호출 비율 비교해서 
  - 정상이면 -> Close
  - OPEN 으로 둔다
---
### 서킷브레이커가 열리면 운영자 대응

#### 1. 지표 확인
- 현재 상태
- 실패율
- 느린 호출 비율

#### 2. 원인 파악
- 왜 서킷브레이커가 열렸나
- 코드 레벨
- 로키 로그를 파악
- 디비 커넥션

#### 3. 서킷을 바로 강제로 닫지 않음
- 외부 서비스가 복구 <- 디버깅
- 서킷을 강제로 닫으면 안됨
- 대기 중인 요청이 한 번 다 유입될 수 있음
- HALF-OPEN
    - 소량 테스트 요청

---

### 6. Fallback
> 정상적인 결과를 제공할 수 없을 때, 전체 실패 대신 제한된 결과를 제공하는 방법

- 추천 서비스 장애
    - 개인화 상품 추천 안됨
    - 제품 목록 조회는 오케이 -> 제품 목록 조회 기능만 제공
- 백엔드 코드에서 이러한 대응을 해두는 것

#### Fallback 하면 안되는 경우
- 일부 서비스가, 그 비즈니스 로직의 상당한 영향을 끼치는 경우
    - 결제 서비스, 송금, 주문
- 안전하게 제공 가능한 대체 결과가 있을 때만 사용하는 기술

---

#### 💡 패턴별 역할 정리
| 패턴 | 해결하려는 문제 | 핵심 동작 |
| --- | --- | --- |
| Rate Limiter | 처리 용량보다 많은 요청 | 일부 요청 거절 |
| Timeout | 끝없이 기다리는 요청 | 대기 시간 제한 |
| Retry | 일시적인 실패 | 제한적으로 다시 시도 |
| Circuit Breaker | 지속적으로 실패하는 의존성 | 호출 자체를 일시 차단 |
| Bulkhead | 하나의 장애가 모든 자원을 사용 | 자원과 동시성 격리 |
| Fallback | 정상 결과 제공 불가 | 제한된 대체 결과 제공 |

---
1. Rate Limiter: 처리 가능한 요청만 받아들인다
2. Bulkhead: 해당 기능이 사용할 수 있는 동시 실행 수를 제한한다
3. Timeout: 한 번의 호출이 기다릴 수 있는 시간을 제한한다
4. Retry: 일시적인 실패만 제한적으로 다시 시도한다
5. Circuit Breaker: 실패가 반복되면 실제 호출을 차단한다
6. Fallback: 안전한 대체 결과가 있다면 제한된 기능을 제공한다
---
#### 💡  정리
장애 전파 방지는 실패를 숨기는 것이 아니라, 실패를 빠르게 감지하고 제한된 영역 안에서 끝내는 것이다
