## 1. Job / CronJob
> Job은 한 번 실행하고 정상적으로 끝나야 하는 작업을 관리하는 컨트롤러

- Deployment
  - 애플리케이션을 계속 "실행" 상태로 유지
  - 업데이트 같은 것들 처리
- Job
  - 작업을 한 번 성공하는걸 목표로 함
  - 애플리케이션 한 번 실행되고 "종료"
- 한 번 apply하면 되는거 아닌지?

### Job 사용 이유
- 일회성 작업
- 일반 파드로 실행하면 문제가 생김
  - 작업이 실패 -> 다시 실행하면 문제가 생김
    - 작업이 실패한걸 파드 로그를 쳐다보고 있어야 함
      - 파드가 300대면 301번 파드에 일회성 작업을 새롭게 해야한다
  - 일회성 작업이 데이터 베이스 마이그레이션 (mysql -> mongo db)
    - 파드 하나로 작업하기에는 너무 시간이 오래걸린다
      - 처리량에 비해 데이터가 너무 많다
      - 처리를 하고 있는데, 처리 속도보다 신규 데이터 작성 속도가 빠르면?
        - 영원히 계속 작업을 해야함
  - 병렬로 처리함
    - 파드 하나 띄우지 않음
    - 파드 20 개 띄우고 → 2분 내에 작업한다.

#### Job
- 작업이 성공할 떄까지 해당 작업에 사용되는 파드를 관리
- 파드들의 성공 회수를 관리
- 성공 회수가 특정 지정한 회수가 되면, 작업이 성공했다고 판단

Job은 일회성 작업을 안정적으로 자동화된 방식으로 처리 할 수 있다

---

### 동작 방식

```
Job 생성 -> Pod 생성 -> 컨테이너에서 작업 실행 -> 종료 코드 확인 -> 0 -> 성공 (exit 0)
try-catch 
try {

}
catch (Execption e) {
// 에러를 만들놔야 한다
}

-> 0이 아님 -> 실패 및 재시도
```
```
apiVersion: batch/v1
kind: Job
metadata:
  name: example-job
spec:
  completions: 3            # 총 작업 완료 수 (3개의 Pod 실행 필요)
  parallelism: 2            # 동시에 실행할 Pod 수 (병렬 실행)
  template:
    metadata:
      name: example-pod
    spec:
      containers:
      - name: example-container
        image: busybox
        command: ["sh", "-c", "echo Hello World! && sleep 30"]
      restartPolicy: OnFailure  # 실패 시 재시도
```

---

### 핵심 설정

#### 1. Completions
전체 작업이 완료되기 위해 필요한 성공 회수

#### 2. parallelism
동시에 실행할 수 있는 파드 수

#### 3. restartPolicy
재시도 할지 말지 정하는 정책
- OnFailure 실패하면 재시도
  - backoffLimit <- 몇 번 재시도 할지?
- Never -> 실패하면 중지

---

#### 실무적으로 사용하는 예시
- 데이터베이스 초기화
- 데이터베이스 스키마 마이그레이션
- 일회성 데이터 변환
- 대량 파일 처리
- 테스트 데이터 생성
- 배포 전 사전 작업

## CronJob
> CronJob은 정해진 시간마다 Job을 생성하는 컨트롤러
```
CronJob -> 정해진 시간 Job 생성 -> Pod 생성 -> 작업 실행
```

### 사용이유
- 서버에서는 운영하다보면 반복적으로 처리해야하는 작업
  - 매일 데이터베이스 백업
  - 매시간 임시 데이터 정리 (Image)
  - 매일 통계 생성
  - 매주 보고서 생성

```
# * * * * *
# 분 시간 날짜 월 요일

schedule: "*/5 * * * *"
5분 마다 하겠다
```

### concurrencyProxy
이전 Job이 끝나지 않았는데, 다음 실행 시간 됐을 때 처리 방식
- Allow: 이전 Job이 실행 중이어도 새 Job 실행
- Forbid: 이전 Job이 실행 중이면 이번 실행을 건너뜀
- Replace: 이전 Job을 종료하고 새로운 Job 실행

## 2. Networking
> 클러스터 안의 Pod와 Service가 서로 통신하고, 필요에 따라 클러스터 외부와도 연결될 수 있도록 네트워크 경로를 구성하고 관리하는 체계

### 필요한 이유
`Frontend Pod -> Backend Pod -> Database Pod`

- 파드는 확장성 때문에 메인 비즈니스 로직이 하나가 있는 컨테이너를 담음
- 파드 여러개에 나눠져서 컨테이너들이 배치
- 파드는 주기적으로 생성, 파괴 -> 그때마다 IP가 달라짐
- Frontend Pod → Backend Pod
  - 백엔드 Pod IP 모름
- Backend Pod → Redis
- Backend Pod -> 외부 결제 API
  - 백엔드 파드는 워커노드 배치 -> 어떤 노드의 몇 번 포트 열어야 하는지?
- 외부 사용자 Frontend 애플리케이션 
  - 프론트엔드 파드 IP 모른다
- 운영자 - Kubernetes API Server

⭐️ 쿠버네티스 단순히 컨테이너 실행하는 것을 넘어서 파드들이 서로 통신하는 경로를 잘 잡아주는게 아주 중요하다

---

### 네트워크 동작 방식에 따른 구조
1. 같은 Pod 내부의 컨테이너 간 통신
2. Pod와 Pod 간 통신
3. Pod와 Service 간 통신
4. 클러스터 내부와 외부 네트워크 간 통신

---

#### 1. 같은 파드 내부 컨테이너간 통신
같은 파드에서는 네트워크 공간을 공유한다 
- localhost 쓰는거랑 같다 -> 포트가 겹치면 안 된다

#### 장점
- 통신 속도가 엄청 빠르다

#### 단점
- 포트 공유 문제

---

#### 2. Pod와 Pod 간 통신
파드는 모두 고유한 IP를 가지고 있다
- 파드가 서로 같은 노드
- 파드가 서로 다른 노드

#### 2-1. 같은 노드에 있는 파드끼리 통신
```
Worker Node A

Pod A (10.244.1.10) -> Pod B (10.244.1.11)
```
- 내부 브릿지 네트워크로 통신한다

#### 2-2. 서로 다른 노드에 있는 파드 간 통신
- TCP 프로토콜을 UDP 프로토콜로 감싸서 통신
    - UDP를 통해 노드 간 통신
    - TCP를 통해 파드 간 통신
- 서로 다른 노드의 파드 간 통신을 위해서는
    - 목적지 Pod가 어느 노드에 있는지 확인
    - 목적지 Pod 네트워크로 전달
    - 노드 간 패킷 전달 방식 사용 (VXLAN, IP in IP, BGP, eBPF)
- 실제 네트워크 구성은 CNI 플러그인이 담당
    - Flannel, Calico, Cilium
- 쿠버네티스는 자체적으로 패킷을 전달하지 않음
- CNI 플러그인이 구현한 네트워크 구성을 사용
- 쿠버네티스는 오케스트레이션 프로그램이지, 네트워크 프로그램은 아님

---

#### 3. Pod와 Service 간 통신

- 파드의 가변성 (IP, 노드 변경)
- Service라는 대표 주소를 제공 -> Service로 요청하면 내부 Pod로 전달
- kube-proxy -> 리눅스 커널(iptables)의 Routing Table 관리
---

#### kube-proxy
- Service는 특정 네트워크 인터페이스에 직접 연결되어 있지 않음
- Service는 가상의 리소스
- 실제로 존재하는 리소스: 파드, 노드, 네트워크 인터페이스 실제로 존재 (가상으로 있기도 함)
- 가상 리소스(Service)에게 요청을 보내려고 하면 실제 존재(Pod)에게 전달하기 위한 중간 대리자
`Pod -> Service ClusterIP -> kube-proxy가 구성한 네트워크 규칙 -> Backend Pod`

#### kube-proxy가 무엇인지?

> 각 노드에서 Service와 EndpointSlice 정보를 감시하고, Service로 들어온 트래픽이 실제 Pod로 전달되도록 노드의 네트워크 전달 규칙을 구성하는 컴포넌트

- 모든 요청이 kube-proxy를 통해서 지나가나? X
- 네트워크 규칙을 설정하는 컴포넌트
- Linux 안에 라우팅 규칙 설정
- kube-proxy는 모든 노드에 배치
    - 워커 노드 → 파드
    - 마스터 노드 → 파드
- 파드의 위치를 예측하기 힘들다
    - 어떤 파드가 어떤 서비스를 호출할지 모름
    - 서비스에 대한 목적지를 무조건 설정할 수 있어야 함
    - 그래서 모든 노드에 kube-proxy가 배치된다

```
Control Plane Node
- kube-proxy Pod

Worker Node A
─ kube-proxy Pod

Worker Node B
─ kube-proxy Pod

kubectl get pods -n kube-system -o wide
```

#### kube-proxy 의 동작 방식
- 기본적으로 API Server 에게 아래 정보를 감시함
- Service
- EndpointSlices

1. API Server에서 Service 정보를 감시한다
2. API Server에서 EndpointSlice 정보를 감시한다
3. 사용할 수 있는 Backend Pod 목록을 확인한다
4. 노드에 패킷 전달 규칙을 구성한다
5. Service 트래픽이 들어오면 커널이 규칙에 따라 Backend를 선택한다
6. 패킷의 목적지를 Service IP에서 Pod IP로 변경한다.

- 실제 통신 흐름

```
kube-proxy -> 커널에 규칙 설치

Frontend Pod -> Linux 커널 네트워크 규칙 -> Backend Pod
```
---

#### kube-proxy 의 동작 모드
- iptables
- IPVS
- nftables

iptables 동작

`Service ClusterIP:Port -> iptables 규칙 -> Endpoint PodIP:Port`

```
10.96.20.30:80으로 온 요청 (Service IP Port)
->
10.244.1.10:8080 또는 (Endpoint IP Port)
10.244.2.15:8080으로 DNAT
```
- iptables -save | grep KUBE-SVC

---

#### kube-proxy 역할 정리
> service 주소 -> Pod 주소로 연결
- Service 감시
- EndpointSlice 감시
- ClusterIP 규칙 구성
- NodePort 규칙 구성
- Backend Endpoint 선택
- Service IP를 Pod IP로 DNAT

```
Frontend Pod
->
Backend Service 10.96.20.30:80
->
kube-proxy가 구성한 규칙
->
Backend Pod 10.244.2.15:8080
->
CNI가 구성한 네트워크 경로
->
실제 Backend Pod 도착
```

- kube-proxy는 Service의 주소를 실제 EndpointSlice의 Pod IP:Port로 연결하는 네트워크 규칙을 각 노드에 설정한다
- Service를 호출하더라도 실제로는 Linux 커널의 `iptables`에 저장된 라우팅 규칙을 따라 Backend Pod로 전달된다

- kubeadm :  쓰기 어렵고 클라우드랑 연결 설정해야함

#### 3. Ingress 를 통해서 접근
- 웹서비스가 여러 개

    - URL, Path를 기준으로 요청 전달
- 담당하는 Service로 요청 전달
- HTTP 레벨의 로드밸런서가 필요
    - → L7 Load Balancer
  
```

```

- Ingress Controller

### Network Policy
기본적으로 파드 네트워크는 파드간의 통신 경로 제공
```
Frontend -> Backend 허용
Backend -> Database 허용
Frontend -> Database 차단
```
- Network Policy 사용한다

#### 쿠버네티스 네트워크
> 파드에 네트워크 연결, 서비스로 안정적으로 연결 지점 제공

내부, 외부 사이의 트래픽이 올바른 대상까지 전달되도록 만든 통신 구조를 k8s networking

---

#### 💡  정리
#### 1. Pod IP
- 각 파드에 할당되는 파드 IP
- 결국 모든 요청은 다 Pod IP 로 전달 된다

#### 2. Service IP
- 네트워크 인터페이스 직접 연결되지 않는 IP (가상의 IP)
- 여러 파드에 접근할 수 있는 엔드포인트 제공

#### 3. Node IP
- 워커 노드, 마스터 노드 IP
- Ec2 주소, 물리 장비 IP

#### 4. CNI
- Pod 네트워크를 실제 구성하는 구현체
- CNI ← 네트워크 규칙
- CNI 플러그인 → 실제로 그 규칙을 구현한 구현체
    - Pod 네트워크 인터페이스 구성
    - Pod IP 할당
    - Pod 네트워크 연결
    - 노드 간 Pod 통신 경로 제공

#### 5. kube-proxy
서비스 트래픽을 특정 파드로 전달하는 네트워크 규칙을 구성하는 컴포넌트

- Service
    - 변경될 수 있는 Pod 앞에서
    - 안정적으로 접근 지점을 제공
- CoreDNS
    - Service Domain → Service IP로 변환
    - `backend-service` → `10.244.10.33`
- Ingress / NodePort / LoadBalancer
    - 외부 트래픽을 내부 클러스터로 전달

#### 전체 통신 흐름
`외부 사용자 → NodePort 또는 Ingress → Frontend Service (kube-proxy) → Frontend Pod → Backend Service (kube-proxy) → Backend Pod → 외부 또는 내부 Database`

## 3. CNI
> Pod가 생성되거나 삭제될 때 네트워크 인터페이스, IP 주소, 라우팅 등을 설정하고 정리하기 위한 표준 규격

#### Networking에서 배운 것
1. 파드는 각가 고유한 IP를 갖고
2. 같은 노드 - 다른 노드도 통신 할 수 있어야함
3. 파드는 계속 만들어지고 삭제되기 때문에, 네트워크 설정이 자동으로 처리 되어야함

파드가 생성되고 삭제될 때, IP 할당하고, 네트워크 인터페이스에 연결하는 역할을 수행하는게 CNI 플러그인

### CNI란
CNI 에서 정의되어 있는 것들
- 네트워크 설정 파일의 형식
- 컨테이너 런타임이 플러그인을 호출하는 방법
- 플러그인을 순서대로 실행하는 방법
- 플러그인이 실행 결과를 반환하는 형식
- 여러 플러그인이 기능을 나누어 처리하는 방법

컨테이너 런타임 <-> 네트워크 플러그인이 서로 통신할 때 사용할 약속

#### CNI ↔ CNI 플러그인 관계
- CNI: 네트워크 플러그인이 따라야 하는 표준 규격
- CNI 플러그인: CNI 규격에 따라 실제 네트워크를 구성하는 구현체
- 네트워크 기능: 플러그인이 실제로 제공하는 기능

### 사용 이유
1. 네트워크 설정 자동화
2. 표준화
3. 플러그인 선택 가능
4. Pod ID 관리
5. 노드 간 통신 구성
6. 환경 확장

---

#### CNI는 어디에 있는가
- 모든 노드에 CNI 플러그인이 동작
    - Pod는 노드에서 생성
    - 생성된 Pod는 네트워크에 등록되어야 함
    - 네트워크 등록은 CNI Plugin이 담당
        - IP 할당, 네트워크 인터페이스 연결
- `kubectl get pods -A -o wide`
    - CNI 관련 Pod 중 하나라도 Ready가 아니면 통신이 안 될 수 있음


### CNI 플러그인 종류
#### 1. Flannel
단순한 구조 파드 간 네트워크 연결에 집중하는 CNI 플러그인
- 플라넬에서 이 파드 네트워크 대역폭을 노드별로 나눠서 사용
- 다른 노드들 끼리 통신할 때 네트워크 경로를 구성

#### 2. Calico
- Pod 네트워크 구성
- NetworkPolicy 지원
- 다양한 네트워크 구성 방식 지원
    - BGP
    - IP in IP
    - VXLAN
- 실무에서는 Calico를 많이 사용
- 구성 방식
    - 기본: Native Routing(BGP)
    - Overlay Network(IP in IP, VXLAN)
- 환경에 따라 선택
    - 실습 -> VXLAN
    - 실무 -> BGP

#### 3. Cilium
- eBPF

### CNI 랑 kube-proxy 차이
| 구분 | CNI 플러그인 | kube-proxy |
| --- | --- | --- |
| 주요 대상 | Pod 네트워크 | Service 네트워크 |
| 주요 역할 | Pod에 IP를 부여하고 통신 경로 구성 | Service IP로 온 요청을 실제 Pod Endpoint로 전달 |
| 동작 시점 | 주로 Pod 생성·삭제 시 네트워크 설정 | Service와 EndpointSlice 변경을 감지해 전달 규칙 구성 |
| 예시 | Flannel, Calico, Cilium | iptables, IPVS, nftables 등의 구현 모드 |

- 우리는 통신 자체는 서비스로 호출
    - backend-svc:8080
        - → kube-proxy
            - api server → etcd → service리스트
                - endpointslice
        - 워커 노드 iptables 라우팅 경로를 적어둠
        - 10.244.2.5 → backend-svc-endpoint
    - 10.244.2.5 →
        - VXLAN CNI
        - 192.165.10.4 캡슐화
        - 노드 B로 통신을 보낸다.
```
Service 요청
->
kube-proxy가 만든 전달 규칙
->
대상 Pod IP 선택
->
CNI가 구성한 Pod 네트워크 경로로 전달
```

- 통신 = 교통
    - CNI
        - 파드가 실제 도로를 사용할 수 있도록 도로 설치 하는 교통공사
    - kube-proxy
        - 실제 좌표 값을 → 도로명 주소로 바꿔주고 패킷에게 가는 길을 알려주는 역할

#### VXLAN과 IP in IP
- VXLAN
    - 요청을 TCP → UDP로 감싸서 전송
- IP in IP
    - IP 레이어에서 새로운 IP 헤더를 추가
- 동작 자체는 거의 유사
- 차이점: 어디에서 캡슐화하느냐
- 캡슐레이션 → 디캡슐레이션
    - IP 헤더를 추가할지, UDP 패킷을 추가할지
- IP in IP
    - IP 헤더만 추가
    - 구조가 비교적 간단
- VXLAN → UDP 로 쏨
```
원래 Pod 패킷
      ↓
노드 간 전달용 외부 헤더 추가
      ↓
실제 노드 네트워크로 전송
      ↓
목적지 노드에서 외부 헤더 제거
```

### BGP
> 어떤 IP 대역에 도달하려면 어느 이웃으로 보내야 하는지를 네트워크 장비 사이에서 교환하는 라우팅 프로토콜

- 주변 Node에게 Prefix만 광고
- Pod IP 하나하나가 아니라 Pod CIDR을 광고

#### BGP 상세 동작
```
Node A
Node IP: 192.168.10.11
Pod CIDR: 10.244.1.0/24

Node B
Node IP: 192.168.10.12
Pod CIDR: 10.244.2.0/24
```

1. BGP 이웃(Neighbor) 관계 형성
    - Node A ↔ Node B
    - TCP 연결
    - TCP 179 포트 사용

2. 서로 보유한 경로(Pod CIDR) 광고
```
# Node A -> B 
NLRI:
10.244.1.0/24
# 10.244.1.0 대역도 가려면 나를 거처야해

Next Hop:
192.168.10.11

# Node B -> A 
NLRI:
10.244.2.0/24 
# 10.244.2.0 으로 가려면 나한테 와야해 
# Node B 도 광고
Next Hop:
192.168.10.12
```

3. 수신한 경로를 라우팅 테이블에 반영
    1. Node A 가 Node B 의 광고
        `10.244.2.0/24 via 192.168.10.12 `

    2. Node B 라우팅 테이블
        `10.244.1.0/24 via 192.168.10.11`

4. 실제 파드 패킷 전달

    ```
    # Pod A -> Pod B
    10.244.1.10 -> 10.244.2.20
    
    # Node A 라우팅 테이블 확인
    10.244.2.0/24 via 192.168.10.12
    
    # Native Routing 사용
    출발지: 10.244.1.10
    목적지: 10.244.2.20
    경유지: 192.168.10.12
    ```

---

### BGP 실제로 패킷 전달까지 하나? X
- 실제로 BGP 는 그냥 패킷을 운반 하지 않고 BGP 라우팅 테이블을 만드는 경로만 작성

`BGP -> 라우팅 정보 교환 -> Linux Routing Table 갱신 -> Linux Kernel이 실제 패킷 전달`

- BGP는 컨트롤 플레인, 실제 패킷 전달은 데이터 플레인
- BGP는 길을 알려주고 리눅스 커널로 운반한다

### BGP 방식

### Full Mesh

- 노드가 3대 ↔

    ```
    Node A
    Node B
    Node C
    
    A ↔ B
    A ↔ C
    B ↔ C
    ```

- 모든 노드가 서로 BPG 를 맺게 된다
- 각 노드가 자신의 파드 대역대를 직접 광고
- 만약에 노드가 많아지면? (100대)
    - 노드가 많지 않을 때 Full Mesh 방식을 사용함
    - BPG 의 연결 = BGP Peer
        - 노드 수 N
        - BGP Peer = N * (N-1) / 2

### BGP Reflector
- 각 노드들끼리 서로가 peer를 만들지 않고 Route Reflector를 만들어서 거기에 경로를 저장하는 방식

```
  Route Reflector
  /      |      \
Node A  Node B  Node C
```

### BGP 패킷 전달 2가지 방식
#### 1. Native Routing
- `10.244.1.10 → 10.244.2.20`
  - 캡슐화 없이 라우팅 테이블을 보고 전달
  - 물리 네트워크가 Pod CIDR을 라우팅할 수 있는 환경(VM)에서 사용

##### IP in IP 랑 같이 사용할 수 있다
```
BGP:
10.244.2.0/24가 Node B 뒤에 있다는 경로를 학습

IP-in-IP:
실제 Pod 패킷을 Node B까지 캡슐화해서 운반
```

#### 2. Calico
- VXLAN
  - 헤더 추가 많다
  - 패킷이 정보양 / 헤더양
- IP in IP
    - IP 헤더만 추가
- BGP
    - Native Routing 사용

### VXLAN

```
Pod A
  ↓ 원본 Ethernet Frame
Node A VTEP
  ↓ UDP + VXLAN으로 캡슐화
Underlay Network
  ↓ Node IP 기반 전달
Node B VTEP
  ↓ 디캡슐화
Pod B
```

### IP-in-IP

```
Pod A
  ↓ 원본 IP Packet
Node A
  ↓ Outer IP Header 추가
Underlay Network
  ↓ Node IP 기반 전달
Node B
  ↓ Outer IP Header 제거
Pod B
```

### BGP 직접 라우팅

```
Pod A
  ↓ 원본 IP Packet
Node A
  ↓ BGP로 학습한 경로 조회
Underlay Network
  ↓ Pod IP 패킷 그대로 전달
Node B
  ↓ 로컬 Pod 경로 조회
Pod B
```

### 언제 어떤 걸 선택하는 게 좋을까
#### VXLAN

- 언더레이 네트워크(물리 네트워크)를 수정하기 어려운 클라우드 환경에 적합
- UDP 트래픽을 사용할 수 있는 환경
    - 구현이 단순
    - 호환성이 좋음
- 단점
    - 캡슐화 헤더가 큼
    - MTU 조정 필요

#### IP in IP가 적합할 때

- Layer 3(IP) 기반 전송
- VXLAN보다 단순한 캡슐화
- 언더레이 네트워크가 IP in IP(IP Protocol 4)를 허용할 때
- VXLAN보다 캡슐화 오버헤드를 줄이고 싶을 때

#### BGP가 적합할 때

- 언더레이 네트워크 장비에 Pod CIDR 경로를 설치할 수 있을 때
- 캡슐화 오버헤드를 줄이고 싶을 때
- 성능을 최대한 활용하고 싶을 때
- 대규모 환경
- 네트워크 팀이 BGP를 직접 운영할 수 있을 때
- 단점
    - 네트워크 구성 복잡
    - 운영 난이도가 높음

## 네트워크 구성
VXLAN
- Ethernet Frame을 UDP 안에 캡슐화
- Layer 2 over Layer 3
- VTEP와 VNI 사용
- 호환성이 좋지만 헤더 오버헤드가 큼

IP-in-IP
- IP Packet을 새로운 IP Packet 안에 캡슐화
- Layer 3 over Layer 3
- 구조가 단순하고 오버헤드가 상대적으로 작음

BGP
- 캡슐화 기술이 아님
- 도달 가능한 IP Prefix와 Next Hop을 교환
- 실제 패킷 전달은 Linux 라우팅이 수행
