## 1. 데이터베이스 동시성 제어
- 여러 사용자가 동시에 데이터베이스에 접근할 때 발생할 수 있는 문제를 방지하고, 
데이터의 일관성과 무결성을 유지하기 위한 기술

### 사용이유
- 데이터의 일관성과 무결성을 유지하며, 
- 동시에 여러 사용자가 데이터에 접근하더라도 신뢰성을 보장하기 위해

1. Serial Schedule - 일반적인 경우
  - 트랜잭션 순차 처리
  - 일관성 보장
  - 동시성 낮음
2. Non Serial Schedule - 트랜잭션이 겹치는 경우
  - 트랜잭션 비순차 처리
  - 일관성 보장 낮음
  - 동시성 높음
- 일관성과 동시성은 반비례 관계 (트레이드오프)

### Conflict
- 세 가지 조건을 모두 만족하면 Conflict
1. 서로 다른 트랜잭션 소속
2. 같은 데이터에 접근
3. 최소 하나는 Write

- 수행 결과가 달라지면 충돌 발생 시 직렬화 필요함

---

### 락킹 (Locking)
- 데이터를 안전하게 관리하고, 
다중 사용자가 동시에 데이터에 접근할 때 발생할 수 있는 충돌을 방지하기 위한 기술

1. 비관적 락 (Pessimistic Lock)
- 충돌 가능성을 미리 가정하고 데이터를 사용할 때 락을 걸어 다른 사용자의 접근을 차단.

2. 낙관적 락 (Optimistic Lock)
-  충돌 가능성을 낮게 가정하고 데이터를 먼저 사용한 뒤, 최종적으로 업데이트 시 충돌 여부를 검사.

---

### 1. 비관적 락 
- 충돌이 일어날 가능성을 가정함
- 데이터를 사용하기 전에 락을 걸어 다른 사용자의 접근을 제어
- 일반적으로 RDBMS에서 사용함
- 데이터베이스 자원에 대한 동시 접근 방지
- 작업 수행 전, 작업할 자원에 접근을 먼저 제어함
- 정확성과 일관성이 무엇보다 중요한 데이터에 적용

### 장점
- 높은 무결성, 일관성
- 충돌 사전 방지
- 데이터 손상 방지
- 신뢰성 제공
- 정합성이 중요한 작업에 적합

### 단점
- 성능 저하 및 데드락 발생 가능성
- 트랜잭션 대기 시간
- 자원 사용 효율성 낮음
- 과도한 락으로 인한 병목
- 동시성 저하

---

### 교착상태(데드락)란?
- 데드락은 여러 트랜잭션이 서로가 가진 락을 기다리며 순환 대기 상태에 빠질 때 발생
- 일반적인 원인은 서로 다른 자원을 서로 다른 순서로 잠그는 경우 발생

### 교착상태를 방지 하는 법
- 트랜잭션을 자주 COMMIT
- 정해진 순서로 테이블에 접근
- 읽기 잠금 획득(SELECT ~ FOR UPDATE)의 사용을 지양

---

### 2. 낙관적 락
- 충돌이 일어나지 않을거라 가정함
- 데이터를 먼저 사용한 뒤, 최종 업데이트 시에 충돌 검사
- 주로 NoSQL에서 사용
- 데이터 작업 수행
  - 데이터 변경 후 작업 완료
- 최신 버전 확인 
  - 데이터 업데이트 전, 버전 체크
    - 버전이 똑같네, 그럼 업데이트
    - 어라 버전이 달라졌네?
      - 충돌 여부 검사하기
      - 충돌 발생되면, 작업 롤백

### 장점
- 높은 동시성
- 성능 향상
- 분산 시스템 적합
- 빠른 읽기 속도
- 락 대기 없음

### 단점
- 무결성 수준이 낮음
- 충돌 발생 시 복잡한 예외 처리
- 버전 관리, 추가 구현 비용
- 충돌 발생 시 재시도 비용 증가

## 2. OAuth
- 제 3자 어플리케이션이 사용자리소스에 대한 접근 권환을 얻을 수 있게 해주는 프로토콜
- 인증과 인가를 분리한 것

### 사용이유
- 인증과 인가를 분리함으로 외부 서비스에 정보를 제공하기 위해
- 인증은 유저가 직접하고 인가는 우리 어플리케이션이 받고
- 사용자 비밀번호를 노출하지 않고도, 애플리케이션이 사용자의 데이터에 안전하게 접근할 수 있도록 도와줌

### 동작방식 
1. 사용자 로그인 요청
2. 클라이언트가 인증 요청을 인증 서버로 전송
3. 로그인 페이지 제공
4. 사용자의 ID/PW 입력 및 제출
5. Authorization Code 발급
6. 클라이언트로의 리다이렉션
7. Authorization Code와 Access Token 교환
8. Access Token (및 필요시 Refresh Token) 발급
9. 로그인 성공
10. Access Token으로 리소스 서버에 리소스 요청
11. 리소스 서버의 토큰 검증
12. 리소스 제공
13. 클라이언트에서 데이터 활용

### 용어 정리
- Resource Owner: 유저
- Client: 커뮤니티 서비스
- Authorization Server, Resource Server: 카카오톡

### 인증 코드가 브라우저에 전달되는 이유는?
- 웹의 stateless한 특성으로 인가 시에 해당 유저인지 확인하는 용도 + 보안성

### PKCE
- Authorization Code 탈취 공격을 방지하기 위한 보안 기술
