## 락(Locking)

락은 하나의 스레드가 프로세스의 공유 자원을 점유할 경우 다른 스레드가 **동시에 접근하지 못하도록 제어하는 기법**이다.

락은 공유 자원을 안전하게 사용하기 위해 사용된다. 여러 스레드가 동일한 자원에 동시에 접근하면 데이터 손상이나 예상치 못한 결과가 발생할 수 있기 때문이다.

이를 방지하기 위해 스레드는 공유 자원에 접근하기 전에 **락을 획득**하고, 작업이 끝난 후 **락을 해제**한다. 락이 설정된 동안에는 다른 스레드의 접근이 제한되므로 공유 자원을 안전하게 보호할 수 있다.

락은 **원자성**을 보장하여 하나의 작업 단위가 중간에 다른 스레드의 간섭 없이 수행될 수 있도록 하며, 이를 통해 데이터의 안정성과 일관성을 유지할 수 있다.

락을 구현하기 위한 대표적인 기법으로는 **뮤텍스, 스핀락, 세마포어**가 있다.

뮤텍스는 **상호 배제**를 보장하는 동기화 기법으로, 한 번에 하나의 스레드만 임계 영역에 접근할 수 있도록 한다.

뮤텍스는 **소유권** 개념을 가지며, **락을 획득한 스레드가 해당 락의 소유자가 된다**. 그러므로 락을 해제할 수 있는 것은 락을 획득한 스레드뿐이다. 이를 통해 **데이터 무결성을 유지**할 수 있다.

하지만 스레드가 하나의 뮤텍스를 두고 경쟁할 경우 대기 시간이 증가하여 성능 저하가 발생할 수 있다.

```
Thread 1이 lock 획득
Thread 1이 임계 영역 실행

Thread 2는 lock이 풀릴 때까지 대기
Thread 1이 unlock
Thread 2가 lock 획득 후 임계 영역 실행
```

스핀락은 락을 획득하지 못했을 때 스레드를 대기 상태로 전환하지 않고 **락이 해제될 때까지 반복적으로 확인하며 기다리는 방식**이다.

스핀락은 구현이 비교적 단순하며, 스레드를 잠들게 했다가 다시 깨우는 과정이 없기 때문에 **컨텍스트 스위칭이 발생하지 않는다.** 또한 락이 매우 짧은 시간 안에 해제되는 경우 빠르게 락을 획득할 수 있다는 장점이 있다.

하지만 대기 시간이 길어질 경우 CPU를 계속 사용하므로 비효율적일 수 있으며, 특히 단일 CPU 환경에서는 성능 저하를 유발할 수 있다. 임계 영역이 매우 짧은 환경에서 주로 사용된다.

```
Thread A: lock 획득

Thread B:
while(lock 사용 중)
    계속 확인

Thread A: unlock
Thread B: lock 획득
```

세마포어는 공유 자원에 접근할 수 있는 **허가권**(Permit)의 개수를 관리하는 동기화 기법이다.

뮤텍스가 단일 자원에 대한 접근을 제어하지만, 세마포어는 내부 카운터를 사용하여 여러 개의 **자원에 대한 접근 수를 관리**할 수 있다.

여러 개의 허가권을 통해 동시에 접근 가능한 스레드 수를 제한할 수 있으며, 허가권이 모두 사용되면 다른 스레드는 대기하게 된다.

뮤텍스와 달리 세마포어는 소유권 개념이 없기 때문에 일반적으로 **허가권을 획득한 스레드가 아니더라도 허가권을 반환**할 수 있다.

```
Semaphore = 2

Thread A: Permit 획득
Thread B: Permit 획득
Thread C: Permit 요청 → 대기

Thread A: Permit 반납
Thread C: Permit 획득
```

## 멀티스레드

멀티스레드는 하나의 프로세스 내에서 여러 개의 스레드가 **동시에 실행되거나 동시에 실행되는 것처럼 동작하는 방식**이다.

각 스레드는 독립적인 실행 흐름을 가지지만, 같은 프로세스의 메모리와 자원을 공유한다. 멀티스레드는 프로그램의 응답성과 자원 활용 효율을 높이기 위해 사용된다.

멀티스레드 환경에서는 **동시성**이 중요하다.

동시성이란 **CPU가 작업을 빠르게 전환**하여 ****여러 작업이 동시에 수행되는 것처럼 보이도록 처리하는 방식이다. 하나의 CPU를 여러 스레드가 번갈아 사용하기 때문에 실제로는 순차적으로 실행되지만, 사용자는 여러 작업이 동시에 수행되는 것처럼 볼 수 있다.

이 과정에서 운영체제는 **스케줄러**를 이용하여 실행할 스레드를 선택한다. 스케줄러는 프로세스와 스레드의 실행 순서를 **관리**하는 구성 요소이며, **스케줄링**은 CPU를 어떤 작업에 할당할지 **결정**하는 정책을 의미한다. 운영체제는 **스케줄링**을 통해 특정 스레드가 CPU를 독점하지 않도록 조정하며, CPU 이용률 향상, 처리량 증가, 응답 시간 단축, 공정성 확보하려고 한다.

스레드 전환 과정에서는 **컨텍스트 스위칭**이 발생한다. 컨텍스트 스위칭은 현재 실행 중인 스레드의 상태를 저장하고 다른 스레드의 상태를 복원하는 과정이다. 이를 통해 여러 스레드가 번갈아 실행될 수 있지만, 상태 저장 및 복원 과정에서 **추가적인 CPU 비용이 발생**한다.

```
Thread A 실행
↓
CPU 사용 시간 종료
↓
Thread A 상태 저장
↓
Thread B 상태 복원
↓
Thread B 실행
```

컨텍스트 스위칭은 멀티스레드 환경을 가능하게 하는 핵심 기술이지만, 지나치게 자주 발생할 경우 CPU가 실제 작업보다 상태 전환에 더 많은 시간을 사용하게 되어 성능 저하의 원인이 될 수 있다.

멀티스레드는 높은 성능과 응답성을 제공하지만, 여러 스레드가 동일한 자원을 공유하기 때문에 경쟁 상태와 같은 동기화 문제가 발생할 수 있다. 따라서 운영체제는 락킹과 같은 동기화 기법을 이용하여 공유 자원을 안전하게 관리한다.

## 공유 자원

공유 자원은 여러 스레드나 프로세스가 동시에 접근하거나 사용하는 시스템 내의 자원을 의미한다. 멀티스레드 환경에서는 스레드들이 동일한 메모리 공간을 공유하기 때문에 변수, 객체, 파일, 버퍼와 같은 자원이 공유 자원이 될 수 있다.

여러 스레드가 동일한 공유 자원에 동시에 접근할 경우 **데이터가 예상과 다르게 변경되거나 일관성이 깨질 수 있다**. 따라서 운영체제와 프로그래밍 언어는 공유 자원을 안전하게 사용하기 위한 다양한 제어 기법을 제공한다.

공유 자원을 보호하기 위한 대표적인 개념으로는 **임계 영역**과 **동기화**가 있다.

임계 영역은 **공유 자원**에 접근하는 **프로그램 코드의 일부분**을 의미한다.

여러 스레드가 동시에 임계 영역을 실행하면 데이터 충돌이나 **경쟁 상태**가 발생할 수 있으므로, 일반적으로 한 번에 하나의 스레드만 접근할 수 있도록 제어한다.

이를 통해 **공유 자원의 무결성과 일관성을 유지할 수 있다.**

동기화는 여러 스레드가 **공유 자원에 동시에 접근할 때 발생할 수 있는 충돌이나 데이터 무결성 문제를 방지**하고, **올바른 순서와 조정**을 보장하는 기법이다.

운영체제는 뮤텍스, 세마포어와 같은 동기화 도구를 제공하여 공유 자원을 안전하게 관리할 수 있도록 지원한다. 이를 통해 여러 스레드가 동일한 자원에 접근하더라도 **정해진 순서와 규칙에 따라 작업을 수행**할 수 있다.

동기화가 이루어지지 않을 경우 **데이터 충돌**이나 **경쟁 상태**와 같은 문제가 발생할 수 있고, 잘못된 동기화는 **데드락을** 유발할 수 있다.

따라서 공유 자원은 멀티스레드 환경에서 반드시 관리되어야 하는 대상이며, 임계 영역과 동기화는 공유 자원을 안전하게 보호하기 위한 핵심 개념이다.

## 경쟁 상태(Race Condition)

경쟁 상태는 둘 이상의 스레드가 공유 자원에 동시에 접근하여 작업을 수행할 때, **실행 순서에 따라 결과가 달라지는 현상**을 의미한다.

이것은 공유 자원에 대한 **접근 순서가 보장되지 않을 때 발생**한다. 동일한 코드라도 스레드의 실행 순서에 따라 결과가 달라질 수 있으며, 이는 예측하기 어려운 오류의 원인이 된다.

대표적으로 **Lost Update**가 있다.

두 개의 스레드가 동일한 데이터를 동시에 읽고 수정한 뒤 저장하는 경우, 먼저 수행된 작업의 결과가 나중에 수행된 작업에 의해 덮어써질 수 있다. 이로 인해 **일부 데이터 변경 사항이 사라지는 문제**가 발생한다.

```objectivec
balance = 1000

Thread A: balance 읽음 → 1000
Thread B: balance 읽음 → 1000

Thread A: +100 후 저장 → 1100
Thread B: +100 후 저장 → 1100

예상 결과: 1200
실제 결과: 1100

Thread A의 갱신 결과가 사라짐 (Lost Update)
```

또한, **데이터 불일치**를 유발할 수 있다. 동일한 공유 자원에 대한 접근 순서가 보장되지 않으면 실행할 때마다 **다른 결과가 발생**할 수 있으며, 이는 시스템의 신뢰성과 안정성을 저하시킬 수 있다.

```objectivec
Thread A: 상품 재고 1개 확인
Thread B: 상품 재고 1개 확인

Thread A: 구매 처리
Thread B: 구매 처리

재고는 1개인데 2건의 주문이 승인됨
```

이러한 문제를 방지하기 위해 운영체제는 뮤텍스, 세마포어와 같은 락킹 기법을 제공하여 공유 자원에 대한 접근을 제어한다.

따라서 경쟁 상태는 멀티스레드 환경에서 발생할 수 있는 대표적인 동시성 문제이며, 공유 자원의 안전한 사용을 위해 적절한 동기화 기법이 필요하다.

## 데드락

데드락은 둘 이상의 프로세스 또는 스레드가 서로가 점유한 자원을 기다리면서 **무한히 대기하여, 어떠한 작업도 진행되지 못하는 상태를 의미한다.** 데드락이 발생하면 관련된 작업은 더 이상 진행되지 못하며, 시스템의 응답성과 성능에 심각한 영향을 줄 수 있다.

데드락은 일반적으로 다음 네 가지 조건이 동시에 만족될 때 발생한다.

첫 번째는, **상호 배제**다. 하나의 자원은 한 번에 하나의 프로세스만 사용할 수 있어야 한다.

두 번째는, **점유 대기**다. 프로세스가 이미 자원을 점유한 상태에서 다른 자원을 추가로 요청하여 대기하는 상황이다.

세 번째는, **비선점**이다. 이미 할당된 자원은 강제로 회수할 수 없으며, 해당 작업이 자발적으로 반납해야 한다.

마지막으로 네 번째는, **순환 대기**이다. 여러 프로세스들이 자원을 서로 기다리며 순환 구조(상호 대기)를 형성한다.

```objectivec
Thread A: lockA 획득
Thread A: lockB 요청 → 대기

Thread B: lockB 획득
Thread B: lockA 요청 → 대기

Thread A는 lockB를 기다림
Thread B는 lockA를 기다림
서로가 가진 락을 기다리므로 무한 대기 상태 발생
```

이 예시는 상호 배제, 점유 대기, 비선점, 순환 대기 조건이 모두 만족된 경우로, 데드락이 발생하기 위한 네 가지 조건을 모두 포함하고 있다.

데드락은 락을 이용한 동기화 과정에서 발생할 수 있는 대표적인 문제이며, 자원 획득 순서를 통일하거나 불필요한 락 사용을 줄이는 등의 방법으로 예방할 수 있다.

따라서 데드락은 동기화 기법이 제공하는 안전성과는 별개로 발생할 수 있는 문제이며, 멀티스레드 환경에서는 데드락을 고려한 락 설계가 필요하다.

## 성능 저하

락은 공유 자원을 안전하게 보호하고 경쟁 상태를 방지하는 데 효과적이지만, 잘못 사용하거나 과도하게 사용할 경우 시스템 성능 저하를 유발할 수 있다.

특히 많은 스레드가 동일한 락을 사용하거나 불필요하게 넓은 범위에 락을 적용하면 병렬성이 감소하여 전체 처리 성능이 떨어질 수 있다.

대표적인 원인 중 하나는 **락 경합**이다. 락 경합은 **여러 스레드가 동일한 락을 획득하기 위해 경쟁하는 상황**을 의미한다. 하나의 스레드가 락을 점유하고 있는 동안 다른 스레드들은 대기해야 하므로 병렬성이 감소하고 처리 성능이 저하될 수 있다.

```objectivec
Thread A: lock 획득 → 작업 수행
Thread B: lock 요청 → 대기
Thread C: lock 요청 → 대기
Thread D: lock 요청 → 대기

하나의 락을 여러 스레드가 경쟁하여 대기 시간 증가
```

두 번째로는 **기아 상태**다. 기아 상태는 특정 스레드가 자원을 계속 획득하지 못해 **장시간 실행되지 못하는 현상**이다. 우선순위가 높은 스레드가 반복적으로 자원을 점유하거나 락 경쟁에서 지속적으로 밀릴 경우 발생할 수 있다.

```objectivec
Thread1: lock 획득 → 작업 → unlock
Thread1: 다시 lock 획득
Thread1: 다시 lock 획득
Thread2: 계속 대기

특정 스레드가 반복적으로 자원을 획득하지 못하여 실행 지연
```

마지막으로 스레드가 반복적으로 대기하고 깨어나는 과정에서는 **컨텍스트 스위칭 오버헤드**가 증가할 수 있다. 컨텍스트 스위칭은 스레드 상태를 저장하고 복원하는 과정이므로 CPU 비용이 발생하며, 빈번하게 발생할 경우 성능 저하의 원인이 된다.

반면 **스핀락**은 컨텍스트 스위칭이 발생하지 않지만, 락이 해제될 때까지 반복적으로 확인하며 대기하므로 CPU 자원을 지속적으로 사용한다. 따라서 대기 시간이 길어질 경우 성능 저하를 유발할 수 있다.

```objectivec
Thread A 실행
↓
Thread B로 전환
↓
Thread C로 전환
↓
Thread A로 전환
↓
Thread B로 전환

CPU가 실제 작업보다 전환에 더 많은 시간 사용 -> 비용 발생
```

## 결론
멀티스레드 환경에서는 여러 스레드가 동일한 공유 자원에 접근하기 때문에 데이터 충돌과 같은 동기화 문제가 발생할 수 있다. 이를 해결하기 위해 운영체제는 락킹 기법을 제공하며, **뮤텍스, 스핀락, 세마포어와 같은 동기화 도구를 통해** 임계 영역에 대한 접근을 제어하고 공유 자원의 무결성과 일관성을 유지한다.

하지만 락이 잘못 설계될 경우 경쟁 상태와 데드락 같은 동기화 문제를 유발할 수 있으며, 과도한 락 사용은 시스템 성능 저하의 원인이 될 수 있다.

따라서 운영체제의 락킹 기법은 멀티스레드 환경에서 공유 자원을 안전하게 관리하기 위한 필수적인 수단이지만, **임계 영역의 길이와 대기 시간을 고려하여 뮤텍스, 스핀락, 세마포어와 같은 적절한 동기화 기법을 선택하는 락 설계가 필요하다.**
