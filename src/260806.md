# 260806

## 캐시 문제 해결하기
> 캐시는 데이터베이스의 부하를 줄이기 위한 장치. 잘못 설계하면 트래픽을 데이터베이스로 한꺼번에 전달하는 장애 증폭기가 될 수 있음

### 1. 캐시
- 자주 조회하거나 계산 비용이 큰 데이터를 빠르게 서빙하기 위해서 임시 저장소에 보관하는 방식
- 데이터베이스나 외부 API의 접근을 줄이는 방식
  - 응답 시간 감소
  - 데이터베이스 부하 감소
  - 처리량 증가
  - 외부 API 호출 비용 감소

### 일반적인 캐시 사용 방식
#### Cache Aside
1. 애플리케이션이 캐시를 조회한다
2. 캐시에 데이터가 있다 -> Cache Hit
- 캐시 데이터를 반환한다
3. 캐시에 데이터가 없다 -> Cache Miss
- 데이터베이스를 조회한다
- 조회 결과를 캐시에 저장한다
- 사용자에게 반환한다

---

#### 2. 캐시 문제가 발생하는 지점
존재하지 않는 데이터가 반복 조회된다
- Cache Penetration

인기 있는 하나의 캐시가 만료된다
- Cache Stampede / Cache Breakdown

많은 캐시가 한꺼번에 사라진다
- Cache Avalanche

특정 키에 요청이 집중된다
- Hot Key

캐시와 데이터베이스의 값이 달라진다
- Cache Consistency

---

### 캐시 문제
### 1. Cache Penetration
> 존재하지 않는 데이터를 반복적으로 조회하여, 요청이 계속 데이터베이스까지 도달하는 문제

#### 정상적인 캐시 미스
```
상품 ID 100 조회
-> 캐시에 없음
-> DB에서 상품 조회
-> 캐시에 저장
-> 이후 요청은 캐시에서 처리
```

#### Cache Penetration
```
존재하지 않는 상품 ID 999999 조회
-> 캐시에 없음
-> DB에도 없음
-> 캐시에 저장하지 않음

다시 상품 ID 999999 조회
-> 캐시에 없음 -> 다시 DB 조회
```
- 당연히 존재하지 않으니 디비에서 못찾음
  - 당연히 캐시에도 저장을 안함
  - 다음 요청 -> 캐시 미스 -> 디비 요청
- 무작위 공격 -> 디비 커넥션 점유하기

```
GET /privacy/v1.0.0
-> Cache Hit 
GET /privacy/v.111111.111111.11111
-> Cache miss
-> DB Query
-> 무한 반복
```

---

#### 어떤 문제를 만드나?
- 데이터베이스 쿼리 증가
- DB Connection Pool 고갈
- CPU 및 디스크 I/O 증가
- 정상적인 요청의 응답 시간 증가
- 무작위 키 요청을 이용한 공격 가능
- 캐시 적중률 저하

---

### 해결 방법
#### 1. 입력 값을 검증
- 데이터베이스 조회하기 전에 클라이언트 요청 값이 유효한지 검증
- 상품 아이디/유저 아이디는 양수
- 페이지 번호는 전체 게시글의 숫자를 넘지 않는다
- UUID 양식이 맞아야 한다

#### 2. 존재하지 않는 결과를 캐싱
- Negative Caching, Null Caching
- 데이터베이스에 값이 없더라도 값이 없다는 걸 캐싱
  - Null -> Cache
- 조심해서 사용해야함
  - 존재하지 않는 키를 저장
  - -> Redis (KV Store)
    - 저장 공간이 협소 -> 메모리 사용
- Eviction
  - 자주 접근하지 않는 키
  - 가장 오래 전에 들어온 키 <- 위험
- Null 캐싱은 TTL을 상당히 짧게 잡아야 함

#### 3. 블룸 필터
- 특정 데이터가 존재하지 않는다는걸 확률적으로 계산해서 리턴
- 자료 구조상 없는게 맞는 거 같다라고 계산
  - 거르는 필터
  - 확룔적

#### 4. Rate Limit
- 조회 자체를 많이 못하게 하면 되는거 아닌가? O
- Distributed
  - 분산되어 있는 공격자를 막을 수 없다

---

### 2. Cache Stamped
> 인기 있는 캐시 하나가 만료되는 순간, 많은 요청이 동시에 데이터베이스를 조회하는 문제

인기 상품
```
Key: product: 1
TTL: 10분 
초당 요청: 5,000건
```
딱 캐시가 만료되는 순간
```
요청 1 -> 캐시 없음 -> DB 조회
요청 2 -> 캐시 없음 -> DB 조회
요청 3 -> 캐시 없음 -> DB 조회
...
요청 5,000 캐시 없음 - DB 조회
```
- 각 요청은 다른 요청이 지금 같이 조회 중이라는걸 모름
- 완전히 동일 값을 얻으려고 동시에 수천 개의 쿼리가 데이터베이스로 들어감
- 서비스가 터짐

---

#### 문제
- 동일한 DB 쿼리 대량 실행
- DB Connection Pool 고갈
- CPU 사용량 급증
- 외부 API 중복 호출
- 동일 데이터 중복 계산
- 응답 지연 및 타임아웃
- DB 장애가 다른 서비스로 전파

---

### 해결 방법
#### 1. Request Coalescing
- 동일한 키에 대한 요청을 하나의 요청으로 합친다
- 요청 1~N -> 동시에 WAS 도착
- API도 똑같고, Request Body, 대상도 똑같다
- WAS 요청을 홀딩
- 특정 초동안 기다림 1000ms -> Single Flight
- 동일 인스턴스, 동일 파드, 동일 애플리케이션에서만 가능함

---

#### 2. 키 단위 락 걸기
- 캐시가 없을 때, 가장 먼저 도착한 요청만 락을 획득해서 디비를 조회하는 방식
```
요청 1
- 캐시 없음
-> LOCk 획득
-> DB 조회
-> 캐시 저장
-> LOCk 해제

요청 2~N
-> 캐시 없음
-> Lock 획득 실패
-> 잠시 대기
-> 캐시 다시 조회
```
분산 환경에서도 동작을 잘한다

#### 구현 주의 사항
- 락 자체가 병목이 될 가능성이 있음
- 락에 TTL을 걸기
- 락 획득 실패 <- 2~N 락 대기를 하고 있음
- 캐시에 주기적으로 문의 -> 아직 들어온 거 없나?
- 현재 락이 있나 없나 -> 락이 없으면 직접 찾음
- 락 획득 요청 <- 회수 제한을 걸어야 함

---

#### 3. Stale-While-Revalidate
- 캐시가 논리적으로 만료되어도 기존 데이터를 잠깐 반환 시키고 백그라운드에서 캐시를 갱신

```
10:00:01 요청
-> 논리적으로 만료됨
-> 기존 데이터는 사용자에게 반환
-> 하나의 작업만 백그라운드에서 캐시 갱신
```

#### 장점
- 사용자는 캐시 갱신을 기다리지 않는다
- DB에 요청이 한꺼번에 몰리지 않는다
- 인기 키를 캐시에서 완전히 제거하지 않을 수 있다

#### 단점 
- 사용자가 잠시 오래된 데이터를 볼 수 있다
- 엄격한 데이터 최신성이 필요한 영역에는 적합하지 않을 수 있다

---

#### 4. 만료 전 미리 갱신
```
TTL: 10분

9분 경과-> 백그라운드 갱신 시작

10분 경과 -> 이미 새로운 캐시가 준비됨
```

- 스케줄러
    - CronJob
    - 결국에 트래픽 발생을 시킴
    - 캐시가 특정 키만 조회되는 환경에서는 작업량이 일반 사용자 보다 많아짐
    - 인기 키만 골라서 갱신하는 방식
  
---

#### 실무 적용
```
인기 키 감지
->
만료 전 선제 갱신
->
만료되었다면 Request Coalescing
->
대표 요청 하나만 DB 조회
->
나머지는 이전 값 또는 제한된 대기
```
---

### 3. Cache Avalanche
> 많은 캐시 키가 동시에 만료되거나 캐시 서버 전체에 장애가 발생하여 대량의 요청이 한꺼번에 데이터베이스로 이동하는 문제

### 발생 원인
#### 1. 신규 파드, 신규 서비스 시작할 때
- 서비스 시작
- 여러 데이터를 한 번에 캐싱
- 정확히 60분 뒤에 모든 키가 만료
  - 캐시 미스 동시 -> 디비 -> 부하 -> 장애

#### 2. 캐시 서버 장애
- 레디스 서버 1대
  - 장애 -> 모든 캐시가 없어짐
  - 디비 -> 장애

#### 3. Cold Cache
- 캐시가 비어 있는 상태로 시작
  - 레디스 재시작
  - 캐시 클러스터 교체
  - 신규 리전 오픈
  - 신규 서버 오픈
- 캐시가 그냥 비어 있는 상태로 새로운 캐시 스토리지 추가

---

#### 문제
- 전체 DB 트래픽 급증
- Connection Pool 고갈
- DB CPU 및 I/O 포화
- 서비스 전체 응답 지연
- Timeout과 Retry 증가
- Retry로 인한 추가 부하
- 장애가 여러 서비스로 확산

---

### 해결 방법
#### 1. Jitter 적용
- 모든 캐시에 TTL 을 동일하게 설정하지 않게 하면 된다.
- 랜덤하게 캐시의 TTL 을 추가 하거나 빼면
- 만료 시간 분산 -> 디비 요청 분산
- 지터 한계가 있음
  - 캐시가 스프레드 넓을 때 캐시 자체가 많아지면, TTL 분산해도 용량이 커지면 똑같은 현상 발생함

#### 2. Cache Warm-Up
- 콜드 캐시
- 캐시 서버를 새롭게 만들 때 데이터를 미리 넣어두고, 캐시를 미리 해놓고
  - 준비가 되면, 그때 Redis에 요청을 전달하는 방식
1. 새로운 Redis 준비
2. 핵심 데이터부터 캐시 적재
3. 캐시 적중률 확인 
4. 트래픽을 점진적으로 전환

#### 3. 캐시 서버 장애 -> 고가용성 처리
- 캐시 서버 장애 -> 모든 캐시가 만료 -> 디비 폭증
  - 캐시 서버가 가용성이 없으니 
    - Redis -> 관리형
    - Primary -> replica
- 초보 개발자가 많이 실수함

---

### 4. Hot Key
> 전체 요청의 상당 부분이 하나, 소수의 캐시 키에 집중되는 문제

- 만날 수 있는데, 확률이 높지는 않음
- 문제가 생기는 경우
    - 인기 상품, 실시간 순위, 메인 페이지 설정, 콘서트 좌석 정보, 한정 판매 재고, 실시간 경기 점수

---

#### 문제
- 특정 Redis 노드의 CPU 사용량 증가
- 특정 노드의 네트워크 대역폭 포화
- 특정 키의 읽기·쓰기 지연
- Redis Cluster의 노드별 부하 불균형
- 같은 노드에 있는 다른 키까지 지연
- Hot Key 만료 시 Cache Stampede 발생

---

### 해결 방식
#### 1. 핫키 분산
- 키의 접근 횟수 카운트
- 특정 주기별로 분산

#### 2. 핫키 복제
- 여러 개의 레디스 노드
- 특정 노드에만 요청 집중
- 모든 핫키를 모든 노드에 배치

---

### 5. Cache Consistency
- 데이터베이스의 최신 값과 캐시에 저장된 값이 서로 달라지는 문제

### 해결 방법
#### 1. 데이터베이스 갱신 시 캐시 만료
1. DB 데이터 수정
2. Commit 성공
3. 관련 캐시 삭제
4. 다음 조회에서 DB 데이터를 다시 캐싱

- 캐시를 수정하면되는데 왜 굳이 만료? 
    - 캐시를 직접 수정
        - 하나의 비즈니스 로직
            - 데이터베이스를 두 개를 모두다 갱신하는 로직 관리
                - 디비 커밋
                - 캐시 수정 -> 커밋
            - 관리 포인트가 많이 는다
- 캐시는 만료일자를 지정하는 이유
  - 이 때까지는 이 값이 유효
  - 유효하지 않음 더 이상
    - 캐시 데이터를 수정하는거보다 캐시 자체를 부정 해서 새로운 캐시를 만드는게 더 정책으로 깔끔

#### 2. TTL 을 짧게 설정하기
- 설정 값이 변경되는 주기가 빠르거나 <- 캐시에 적합하지 않음
- 캐싱한 값이 꼭 사실이여야하는 경우
  - TTL 을 짧게 설정

#### 💡 정리

존재하지 않는 값을 계속 조회하는가?
- Cache Penetration

특정 인기 키가 만료되었는가?
- Cache Stampede

여러 키가 비슷한 시간에 만료되었는가?
- Cache Avalanche

Redis 서버 전체가 비어 있거나 장애 상태인가?
- Cache Avalanche

특정 Key 또는 특정 Node에만 부하가 몰리는가?
- Hot Key

DB 값과 캐시 값이 다른가?
- Cache Consistency
