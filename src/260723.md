# 260723 

## 1. Volume
> 컨테이너의 파일 시스템 외부에 별도의 저장 공간을 연결하여, 데이터를 보존하거나 Pod 내부 컨테이너끼리 공유할 수 있게 하는 기능

### 볼륨이 필요한 이유
- 컨테이너는 자신의 파일 시스템에 데이터를 저장할 수 있음
  - WAS Pod -> Was Container -> /data/logs/access.log
- 컨테이너 안에 있는 파일 시스템
  - 기본적으로 컨테이너 생명 주기 종속적이다
  - 컨테이너가 종료 - 파일 시스템도 같이 사라짐
- 하나의 파드 안에 여러 개의 컨테이너가 있을 수 있는데, 컨테이너 내부에 있는 파일 시스템은 같은 파드 내에 있는 다른 컨테이너가 접근할 수 없다

---

### 해결 하는 문제
#### 1. 컨테이너가 재시작될 때 데이터를 유지
볼륨은 동일한 파드 내에서 컨테이너가 재시작되더라도 데이터를 유지한다
```
Pod
- WAS Container
  -  access.log
  - .env
-> WAS Container <- Liveness Probe 의해서 재시작
- Volume 
  - access.log
  - .env
```
- 컨테이너가 재시작되더라도, 볼륨은 파드에 종속되기 때문에 컨테이너 재시작 해도 데이터가 유지된다

#### 2. 파드 내부 컨테이너간 데이터 공유
하나의 파드 안에서 여러 컨테이너가 동일한 볼륨을 서로 마운트
- 파일을 통해서 데이터를 공유할 수 있다
  - 애플리케이션 컨테이너가 로그
  - 로그 수집가가 읽어서 중앙 로그 처리 장치로 전달한다
- 볼륨을 사용하면 Pod 내에 컨테이너들이 공유 파일 시스템 사용하는 것처럼 공유할 수 있다

#### 3. 설정 , Secret 파일로 전달
- 볼륨을 데이터 저장하는 용도만 사용하지는 않음
- ConfigMap, Secret Volume을 연결하면 쿠버네티스에 저장된 값을 컨테이너 내부의 파일로 제공할 때 사용함
- Volume 사용할 때
  - 임시 데이터
  - 컨테이너 간 파일 공유
  - 설정, 시크릿 값을 전달할 때

---

### Volume YAML
#### Volumes
Pod 사용할 공간을 정의한 것
```
  volumes:
    - name: app-data
      emptyDir: {}
```
- app-data 라는 이름의 emptyDir Volume 을 생성한다

#### volumesMounts
사용하는 볼륨을 컨테이너의 어느 경로에서 사용할 지 정의한 것
```
volumeMounts:
  - name: app-data
    mountPath: /data
```
- 컨테이너 내부에서는 volume을 /data 디렉토리로 접근한다

---

### Volume 유형
- emptyDir
- hostPath

#### EmptyDir
> 파드가 생성될 때 만들어지고 파드가 삭제되면 함께 사라지는 임시 저장 공간
```
volumes:
  - name: temp-data
    emptyDir: {}
```
- emptyDir은 파드가 노드에 배치될 때, 생성되는 빈 디렉토리
- 초기 상태는 비어 있고, 생성은 파드가 노드에 배치될 때 생성
- 컨테이너가 재시작되면 데이터 유지
- 파드가 삭제 - 데이터 삭제
- 주용도: 캐시, 임시 파일, 컨테이너 간 파일 공유

#### hostPath
> Pod가 실행되는 노드의 특정 파일이나 디렉토리를 컨테이너에 직접 연결하는 볼륨
```
volumes:
  - name: host-data
    hostPath:
      path: /data
      type: DirectoryOrCreate
```
- 노드의 /data 디렉토리를 pod에서 사용할 수 있게 된다
```
Worker Node
└── /data
->
Pod
└── Container /mnt/data
```
- 저장되는 위치 -> 파드가 실행되는 노드의 파일시스템
- 파드 삭제 -> 노드의 데이터가 남아있음
  - 파드는 생성과 삭제가 자유로운 편
  - 특정 노드에서만 생성되지는 않는다
  - 다른 노드에서는 이전 노드의 데이터 접근할 수 없음
- 주용도: 노드의 로그, 시스템 파일, 런타임 소켓 접근

#### emptyDir <-> hostPath
| 구분 | emptyDir | hostPath |
| --- | --- | --- |
| 저장 위치 | Pod가 배치된 노드의 임시 저장 공간 | 노드의 지정된 경로 |
| 최초 상태 | 항상 빈 상태 | 기존 파일이 존재할 수 있음 |
| 컨테이너 재시작 | 유지 | 유지 |
| Pod 삭제 | 삭제 | 노드에는 남을 수 있음 |
| Pod가 다른 노드로 이동 | 기존 데이터 사용 불가 | 이전 노드의 데이터 사용 불가 |
| 주요 목적 | 임시 데이터, 컨테이너 간 공유 | 노드 파일 및 디렉터리 접근 |
| 일반 애플리케이션 데이터 저장 | 부적합 | 부적합 |

---

### Volume 의 한계점
#### 1. Volume은 "영구" 저장소가 아니다
- volume 에 저장되는 데이터들이 영구적으로 저장되어서 사용되기가 어렵다
- emptyDir X
- hostPath <- 노드에 붙어있으니 영구 저장되는거 아닌지?
  - 노드도 스케일링의 대상
  - EC2 <- 워커노드가 부족하다
    - CA -> 워커노드를 추가함
      - 워커노드를 제거하기도 함
- 반드시 보존해야하는 데이터에는 적합하지 않음

#### 2. 노드에 종속
- hostPath <- 노드에 호스트 파일시스템
- emptyDir <- 파드에 종속 <- 노드에 종속
- 파드가 다른 노드에서 만들어질 때 기존 볼륨을 사용할 수 없음

#### 3. 스토리지 운영을 직접 해야함
- 볼륨을 사용할 때는 "노드"에 종속
- 노드를 관리해야함
  - 필요한 저장 용량
  - 여러 파드들이 노드에 스토리지 사용
  - 외부 스토리지 연결
  - 파드 삭제 데이터를 어떻게 처리할지
- Volume <- 실무적으로 중요한 데이터를 처리할 때 사용하지 않고 "PV/PVC + StorageClass 해결"

---

#### 실무에서 볼륨을 사용하는 경우
- 임시 캐시
- 임시 작업 공간
- 파드 내부 컨테이너끼리 데이터 공유
- ConfigMap, Secret 마운트
- 노드 로그 수집
- 모니터링 시스템 에이전트 역할

---

#### 💡 정리
- Volume: Pod가 사용할 저장 공간을 정의하는 구조
- 해결하는 문제: 컨테이너 재시작 시 데이터 유지, 컨테이너 간 파일 공유
- emptyDir:  Pod 수명 동안 사용하는 임시 저장소
- hostPath: 노드의 특정 경로를 Pod에 연결
- 공통 한계: 노드 이동과 Pod 삭제 상황에서 영구성을 보장하기 어려움
- 영구 저장 필요: PV, PVC, StorageClass 사용

## 2. PV / PVC
- PV 는 클러스터에 준비된 “실제 저장공간”
- PVC 는 파드가 필요한 저장 공간을 요청하는 리소스

```
Pod (yaml, 저장공간이 필요해요.) -> PVC 저장공간을 요청해요 (요청서)
-> 조건에 맞는 PV 가 연결
PV <- 클러스터 단위로 관리되는 저장 공간
```

- PV 랑 PVC는 파드와 저장소를 직접적으로 연결하려고 하지 않고, 저장 공간을 제공하는 부분
- 사용하는 부분을 분리해서 사용함

---

#### 앞에서 배운 볼륨 한계
- emptyDir
  - 파드가 유지되는 동안에 저장할 수 있는 임시 공간
  - 컨테이너가 재시작되더라도 파드가 살아있으면 유지
  - 파드가 사라지면 같이 삭제
- hostpath
  - 노드의 호스트 파일 시스템에 연결 하는 방식
  - 특정 노드에 파일 시스템
    - 다른 노드에서는 해당 파일 시스템이 안보임
  - 파드는 여러 노드에서 사용할 수 있음
- 영구히 보존 , 장기간 보존
- 파드, 노드의 생명주기랑 상관없이 계속해서 보관되어야하는

- 어떤 파드, 어떤 노드에서든 전부다 접근 가능한 저장공간이 필요함

#### PV/PVC
- 파드랑 저장공간을 직접적으로 연결하려고 하지 않음
  - 생명주기를 같이 가져가지 않음
  - 파드가 죽어도, 저장공간은 그냥 살아 있음
  - 노드가 죽어도 저장공간은 살아 있음
- 파드와 별개의 리소스로 만들어서 사용한다

```
기존 방식
Pod
-> 저장소의 위치, 종류를 직접 정의

PV/PVC
Pod -> PV C (영구 저장소를 갖고 싶어 라고 원하는 상태를 정의)

PV 랑 연결 해준다
Persistence Volume (클러스터에서 관리되고 있는 영구 저장소)
```

---

### PV (PersistentVolumn)
> 클러스터에서 파드와 독립적으로 관리되는 저장 공간

- 애플리케이션이 사용할 수 있도록 미리 준비된 (혹은 동적으로 준비되는) 스토리지를 의미함
- 쿠버네티스 리소스로 표현한 것

`PVC 를 통해서 요청 -> 요청을 보고, 조건에 부합하는 PV를 할당해서 바인딩 하는 형식`

### PV의 역할
1. 저장 공간 제공
2. Pod와 수명 분리
3. 저장소 정보 캡슐화
4. 중앙 관리

---

### PV YAML
```
apiVersion: v1
kind: PersistentVolume
metadata:
  name: app-pv

spec:
  capacity:
    storage: 5Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  storageClassName: manual

  hostPath:
    path: /data/app
```
- capacity: 제공하는 저장 공간의 크기
- accessModes: 저장소에 접근할 수 있는 방식
- storageClassName: PV가 속한 스토리지 종류 또는 정책
- persistentVolumeReclaimPolicy: PVC 사용 종료 후 PV를 어떻게 처리할지 결정
- 스토리지 종류: NFS, CSI, local 등 실제 저장소 연결 정보

---

### PVC (PersistentVolumeClaim)
> 파드가 필요한 저장 공간의 조건을 작성한 요청서
- PVC는 저장소 자체가 아님
- 다음과 같은 조건의 저장공간이 필요하다고 요청하는 리소스
  - 필요한 용량, 읽기 쓰기 방식, 사용한 스토리지 종류

```
파드가 요청

“5Gi 이상의 저장 공간이 필요합니다.”
“하나의 노드에서 읽고 쓸 수 있어야 합니다.”
“manual이라는 스토리지 종류를 사용하겠습니다.” -> 적은 요청서 -> PVC
```

### 주요 역할
1. 저장 공간 요청
2. 저장소 추상화
3. PV와 연결
4. Pod에 제공

### PVC YAML
```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc

spec:
  accessModes:
    - ReadWriteOnce

  storageClassName: manual

  resources:
    requests:
      storage: 3Gi
```

- ReadWriteOnce: 하나의 노드에서 읽기·쓰기가 가능한 저장소 요청
- manual: manual StorageClass에 속한 PV 요청
- storage: 3Gi	최소 3Gi 이상의 저장 공간 요청

PVC 가 요청한 것 중에서 꼭 모든걸 다 똑같이 들어주지는 않음
- PVC 가 3GI 요청 -> 준비되어 있는 PV 가 3Gi 없음
    - 만약 남아있는 PV가 3Gi 큰 Pv 가 있으면 그냥 배정 함
      - 대신 PVC 에서 요청한 용량보다 작은 PV 가 있으면 전달하지 않음
      - PVC 10Gi 요청
        - PV 가 남아있는게 없거나, 더 작으면? -> Pending 상태로 대기
  - PV 가 있어야 하는 파드는? Pending 으로 대기함
      - 꼭 PV 가 미리 준비되어 있어야하나? -> StorageClass
                  
---

#### PV - PVC 를 비유
- 창고와 창고 신청서
```
PV: 5평짜리 냉장 창고가 준비
PVC: 최소 3평 이상의 냉장 창고가 필요
Kubernetes: 조건이 맞으므로 두 리소스를 연결
```
PVC가 직접 창고를 만들지 않고 자신의 조건과 맞는 PV를 찾아 사용하도록 요청

---

### PV PVC 의 바인딩
조건이 맞으면 PV - PVC 가 바인딩된다

#### 바인딩 조건
1. 용량
2. 접근 모드
3. StorageClass
4. VolumeMode
5. Selector

- 바인딩 조건이 안맞으면 `Pending` 된다
- 바인딩은 기본적으로 일대일 관계 (PV 1개 <-> PVC 1개)
- 스토리지 시스템이 NFS
- Access Mode 에 따라서 접근해서 사용할 수도 있음

---

#### 접근 모드
- ReadWriteOnce(RWO): 하나의 노드에서 읽기·쓰기로 마운트
- ReadOnlyMany(ROX): 여러 노드에서 읽기 전용으로 마운트
- ReadWriteMany(RWX): 여러 노드에서 읽기·쓰기로 마운트
- ReadWriteOncePod(RWOP): 하나의 Pod만 읽기·쓰기로 마운트

모든 스토리지에서 모든 접근 모드를 사용할 수 있지 않음
- 일반적인 블록 스토리 `EBS` ← 여기에서는 주로 RWO
- NFS <- RWX 를 지원함
- 필요한 접근 방식에 따라서 스토리지의 지원 여부를 확인해야 한다

---

#### PV의 회수 정책
PVC가 삭제되거나 파드에서 사용이 끝나면 PV는 클러스터에서 관리되는 리소스
- 그 안에 남아있는데이터를 어떻게 처리할까를 결정
- 회수 정책 `persistentVolumeReclaimPolicy: Retain`

---

#### 1. Retain
PVC 가 삭제되더라도, PV 안에 있는 데이터를 자동으로 삭제하지 않음
- PVC가 삭제 → PV의 상태가 Released 상태가 된 채로 그냥 대기
    - 관리자 데이터를 확인
    - 수동으로 삭제

#### 2. Delete
PVC가 삭제되면 PV와 연결된 스토리지를 삭제할 수 있음
- 주로 `StorageClass`(동적 프로비저닝)에서 사용
  - PVC를 요청하면 필요한 PV를 자동으로 생성
    - AWS EBS (사용한 만큼 비용 발생)
- 주의해야 함
  - PV에 `Delete`를 사용한다
    - 영구적인 저장에 대해서는 고려하지 않겠다는 의미

---

### Volume <-> PV/PVC
| 구분 | 일반 Volume | PV/PVC |
| --- | --- | --- |
| 주요 목적 | Pod에 저장 공간 연결 | Pod와 독립적인 저장소 관리 |
| Pod와의 관계 | Pod YAML에서 Volume 종류를 직접 정의 | Pod는 PVC만 참조 |
| 수명 | Volume 종류에 따라 Pod와 함께 종료 가능 | PV는 Pod와 독립적인 수명 주기 |
| 노드 이동 | 로컬 Volume은 기존 데이터 접근이 어려움 | 외부 스토리지 사용 시 다른 노드에서도 재연결 가능 |
| 저장소 추상화 | 낮음 | 높음 |
| 일반적인 영구 데이터 | 부적합한 유형이 많음 | 적합 |
| 운영 주체 분리 | 어려움 | 관리자와 개발자의 역할 분리 가능 |

---

#### 실무에서 사용 사례
```
PV 를 정적으로 만들어서 사용하지 않음
PV 를 미리 정적으로 생성해서, 그걸 할당한다 -> 불합리적인 프로세스
-> 하루에 쌓이는 로그가 100GB → PV 3TB
-> 평균치 항상 그렇지는 않음
동적 프로비저닝이 일반적이다
운영자 → PVC 를 만들고 → PV 가 없으면 → StorageClass 를 통해서 동적으로 PV 를 생성하고 할당
```

- PV 가 남아있는데 100Gi. 필요한게 3Gi 라면 → 3Gi 프로비저닝 하면 된다
- 데이터베이스 저장소로 많이 사용한다
  - 데이터베이스는 k8s로 관리하기 적절치는 않다
- 상태 기반 애플리케이션
  - 큐 사용하는 WAS
    - 큐가 컨테이너별로 만들어져도 괜찮은 경우
    - 작은 예매 시스템
- 사용자 파일: 이미지, 문서 보존

- 기존에 100Gi PV가 남아 있어도, 필요한 용량이 3Gi라면 3Gi PV를 새로 프로비저닝
- 데이터베이스 저장소로 많이 사용
  - 데이터베이스 자체를 k8s로 운영하는 것은 고려
- 상태 기반 애플리케이션
  - 큐를 사용하는 WAS
    - 컨테이너별로 큐가 생성되어도 괜찮은 경우
    - 작은 예매 시스템
- 사용자 파일: 이미지, 문서 보존

#### 실무에서 주의해야하는 것
#### 1. PVC 삭제 전 회수 정책 봐야한다
- PVC 삭제 했는데 회수 정책이 delete 
- `kubectl get pv`
  - 중요한 데이터라면 삭제 전에 반드시 백업

#### 2. PV는 영구 저장소이지, 자동 백업 저장소는 아님
- PV는 데이터를 영구적으로 저장하기 위한 저장소
- 자동 백업, 자동 복구은 제공하지는 않음
- 클러스터가 특정 리전에만 있다면
  - 서울 리전에 장애가 발생하면 데이터도 함께 영향을 받을 수 있음
- 중요도가 높은 데이터는 별도로 관리하는 것이 좋음
    - S3, 로컬 스토리지에 주기적으로 백업

#### 3. PV 는 자동으로 줄어들지 않음
- 처음 요청한 용량 그대로 유지
- 스토리지 드라이버 자동으로 용량 줄여주는 기능을 지원하는 경우도 있음
- PV 용량은 여유 있게 설정하지ㄷ, 과도하게 크게 만들 필요는 없음
- PVC와 PV를 불필요하게 많이 생성하면 스토리지 비용이 증가할 수 있음

#### 4. PV 정적으로 만들겠다
- 로컬 디스크를 사용해 PV를 만들 수도 있음
- 로컬 디스크가 가득 차지 않는지 지속적으로 확인해야 함
- 로컬 디스크로 PV를 잘 안만들고, 실무에서는 정적 PV보다 동적 프로비저닝을 더 많이 사용

#### 5. 네임스페이스 구분
- PV: 클러스터 전체 
- PVC: 네임스페이스
- Pod: 네임스페이스 

- 내가 쓰려고 만든 PV를 다른 네임스페이스에서 사용할 수도 있음 (라벨링)

#### 💡 정리
- Volume: Pod가 사용할 저장 공간을 연결하는 기본 구조
- PV: 클러스터에 준비된 실제 저장 공간을 표현하는 리소스
- PVC: 애플리케이션이 필요한 저장 공간을 요청하는 리소스
- Binding: 조건에 맞는 PV와 PVC를 연결하는 과정
- AccessMode: 저장소를 어느 범위에서 읽고 쓸 수 있는지 정의
- ReclaimPolicy: PVC 사용 종료 후 PV와 데이터를 어떻게 처리할지 정의

## 3. Storage Class
> PVC 요청에 따라 어떤 종류의 저장소를 어떤 정책으로 자동 생성한지 정의하는 스토리지 템플릿

`PVC: 10Gi 저장 공간이 필요 -> StorageClass: 이 방식으로 저장소를 만듬 -> Provisioner / CSI Driver: 실제 저장소와 PV를 생성`

- 스토리지 클래스 자체가 데이터를 저장하거나 생성하는거는 아님
- 스토리지 클래스는 실제 저장소를 생성할 때 사용할
  - 프로비저너, 스토리지 종류, 생성 시점, 삭제 정책 등의 “규칙”을 정의하는 것

---

### PV/PVC 의 한계지점
1. 관리자가 실제 저장소 준비 (EBS, Node Storage)
2. 관리자가 PV 생성
3. 사용자가 PVC 생성
4. 조건에 맞는 PV와 PVC 바인딩
5. Pod가 PVC 사용

이러한 방식을 정적 프로비저닝
- 사용하기 어려움
    - 관리자가 실제 저장소를 미리 준비해야 함
    - PV도 미리 생성해야 함
    - PVC 요청 용량과 PV 용량을 계속 맞춰야 함
    - 환경에 따라 스토리지 정책도 따로 관리해야 함
        - SSD 스토리지
        - HDD(자기 디스크) 스토리지
        - 여러 Pod가 동시에 접근 가능한 공유 스토리지(RWX)
        - 각각에 맞는 저장소를 별도로 준비해야 함
- 운영자가 실수할 가능성이 상당히 높아짐
---

### 스토리지 클래스가 해결하는 문제
- 동적 프로비저닝 -> 요청이 오면 요청에 맞춰서 PV 를 만들어서 사용함
- 관리자가 미리 저장소, PV 를 준비하지 않아도 된다
- PVC 생기면 Storage Class 에 정의한 정책을 기반으로 실제 저장소 + PV 를 만들어서 바인딩 -> 동적 프로비저닝

`1. PVC 생성 -> 2. StorageClass (어떻게 스토리지 만들어야해 라는 정의서) -> 3. Provisioner (실제 저장소 자동 생성, PV 자동 생성, PVC와 자동 바인딩)`

---

#### StorageClass 의 동작 구조
```
Pod
 │ PVC 참조
 ▼
PersistentVolumeClaim
- storage: 10Gi
- storageClassName: fast
 │ StorageClass 선택
 ▼
StorageClass: fast
- provisioner
- parameters
- reclaimPolicy
- volumeBindingMode
 │ 실제 저장소 생성 요청
 ▼
Provisioner / CSI Driver
 ├── 실제 Volume 생성
 └── PersistentVolume 생성
         │
         ▼
PVC와 PV 바인딩
         │
         ▼
Pod에서 Volume 사용
```

### YAML
```
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc

spec:
  storageClassName: fast-storage

  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 10Gi
```

```
# 스토리지 클래스
storageClassName: fast-storage
provisioner: ebs.csi.aws.com
```

- `provisioner`가 AWS EBS API를 호출
    - PVC에서 요청한 크기의 EBS 볼륨 생성
    - PV 생성 -> PV와 PVC 자동 바인딩

- 실제 Pod에서는 PVC만 연결해서 사용
```
volumes:
  - name: app-storage
    persistentVolumeClaim:
      claimName: app-pvc
```

### Provisioner
> PVC 요청을 보고 실제 저장소, PV 생성하는 담당자
- 스토리지 클래스가 정책을 정의
- 실제 저장소를 생성하는 기능은 프로비저너 CSI Drvier 수행
- 스토리지 클래서에서 10gi SSD 스토리지 사용 -> 만들 때는 EBS로 만들어야 함
- 프로비저너가 스토리지 시스템에 생성 요청을 보냄

---

### CSI (Container Storage Interface)
> CSI는 쿠버네티스와 외부 스토리지 시스템을 연결할 때 사용하는 표준 인터페이스

- 스토리지 공급자마다 저장소를 생성, 수정, 삭제하는 방식이 모두 다름
    - AWS EBS, GCP Persistent Disk, Azure Disk, NFS, Ceph, VMware 스토리지, 온프레미스 스토리지
- 각각의 스토리지마다 제어 방식이 다름
- CSI는 쿠버네티스와 스토리지 드라이버 사이의 표준 인터페이스
    - CSI Driver가 스토리지 종류에 맞게 생성, 수정, 삭제
  
---

### Storage Class 속성
#### 1. provisioner
- 어떤 스토리지 드라이버가 실제 볼륨을 생성할지 결정
- 프로버저너 이름이랑 사용하는 설정
    - CSI 드라이버 문서에서 확인하면 됨
---
#### 2. parmeter
```
parameters:
  type: gp3
  encrypted: "true"
```

- 생성할 스토리지 세부 속성
- 파라미터는 프로비저너에 따라서 다름
  - 디스크 종류, 암호화 여부, 파일 시스템, IOPS, 복제 방식
- 각 CSI Driver 마다 다르게 정의
---
#### 3. reclaimPolicy
- reclaimPolicy : Retain
- PVC가 삭제된 이후 동적으로 생성된 PV와 실제 저장소를 어떻게 처리할지 결정
    - Retain: PV와 실제 저장소를 유지
    - Delete: 데이터가 정말 지워져도 괜찮은 경우에만 사용하기
---
#### 4. allowVolumeExpasion
- PVC 요청 용량을 증가할 수 있도록 허용할지 결정
- PVC YAML에서 `resources.requests.storage` 값을 수정하면
    - 실제 볼륨도 함께 확장할 수 있음
- 조건이 필요함
    - StorageClass에 `allowVolumeExpansion: true` 설정
    - CSI Driver가 볼륨 확장을 지원
    - 실제 스토리지 시스템이 확장을 지원
    - 파일 시스템 확장이 가능해야 함
- 일반적으로 볼륨 확장은 가능하지만 축소는 대부분 지원하지 않음
--- 
#### 5. volumeBindingMode
PV와 PVC가 바인딩되는 시점, 실제 볼륨이 생성되는 시점을 결정

- StorageClass에서 설정 가능한 값
    - Immediate → Default
    - WatiForFirstConsumer

#### Immediate
`PVC 생성 -> 즉시 Volume 생성 -> PV와 PVC 바인딩 -> 이후 Pod 스케줄링`
- PVC가 생성되면 즉시 스토리지를 생성
- 생성된 PV를 PVC와 바로 바인딩
- 문제는 Pod가 어느 노드, 어느 가용 영역에 배치될지 결정되기 전에 스토리지가 먼저 생성됨

#### WaitForFirstConsumer
`PVC 생성 -> 아직 Volume 생성하지 않음 -> PVC를 사용하는 Pod 생성 -> Pod가 실행될 노드와 위치 고려 -> 적절한 위치에 Volume 생성`
- PVC를 사용하는 Pod가 결정된 후 스토리지를 생성
- Pod가 실행될 노드와 가용 영역(AZ)을 고려하여 적절한 위치에 볼륨 생성
- 클라우드 환경에서 유리
    - 가용 영역(AZ)을 고려하여 스토리지를 생성할 수 있음


### 서드파티 솔루션
#### 1. OpenEBS
- 쿠버네티스의 로컬 디스크와 분산 스토리지를 관리할 수 있도록 제공하는 클라우드 네이티브 스토리지 플랫폼
- OpenEBS에서 제공하는 기능
    - Local PV (HostPath)
    - 복제 스토리지 엔진
- 주로 온프레미스 환경에서 사용
- 고성능 로컬 디스크를 사용하면서 스토리지 구성을 직접 제어하고 싶을 때 적합
- 베어메탈 쿠버네티스 환경처럼 기본 StorageClass가 제공되지 않는 경우 많이 사용

#### 2. Ceph
Ceph 분산 스토리지를 Kubernetes Operator 방식으로 배포하고 관리하는 솔루션

- 여러 스토리지 노드를 하나의 분산 스토리지로 구성
- 노드 간 데이터 복제 지원
    - Node A
        - HostPath -> 데이터 복제
    - Node B
        - HostPath -> 데이터 복제
- 노드 장애가 발생해도 데이터를 유지할 수 있어 고가용성 구성 가능
- 구성과 운영이 비교적 복잡함

- StorageClass: 저장소를 생성하는 종류와 정책을 정의
- Provisioner: 실제 저장소와 PV를 생성
- CSI Driver: Kubernetes와 외부 스토리지를 연결하는 표준 드라이버
- 동적 프로비저닝: PVC 요청에 따라 저장소와 PV를 자동 생성

## 4. StatefulSet
> 각 Pod의 고유한 이름, 네트워크 주소, 스토리지를 유지하면서 상태가 있는 애플리케이션을 관리하는 컨트롤러
- 동일한 Pod를 여러 개 생성하는 것뿐만 아니라
    - 각 Pod를 서로 구분
    - 각 Pod에 고유한 이름을 부여
    - Pod가 재생성되어도 기존 이름과 스토리지를 다시 연결하여 관리
---

#### Stateless <-> Stateful
상태가 있느냐 없느냐에 따라 Stateful, Stateful

#### Stateless
- WAS 애플리케이션
- API Server
- 요청을 처리하는 Pod가 바뀌어도 문제가 없는 애플리케이션
  - -> stateless
  - -> Deployment Controller로 관리

#### Stateful
- 각 Pod가 자신의 데이터와 역할을 가지고 있는 애플리케이션
- 데이터베이스 클러스터
- 자신의 상태(State)와 역할(Role)을 유지해야 하는 애플리케이션
- 만약 `database-1`이 삭제되었다면 단순히 아무 Pod나 추가해서는 안 됨

`database-1 삭제 -> database-1이라는 이름으로 다시 생성 -> database-1이 사용하던 스토리지 다시 연결`

- Pod의 이름과 데이터는 재생성되어도 계속 유지되어야 함
- 이러한 애플리케이션을 Stateful이라고 함
- 이러한 Pod를 관리하는 컨트롤러가 StatefulSet

---

### StatefulSet 해결하는 문제
#### 1. 파드 재생성 시 이름 변경
- Deployment 생성한 파드는 일반적으로 이름이 뒤에 랜덤 텍스트
- Pod가 삭제되고 재생성되면 이름도 새롭게 변경됨
- 웹 서버, WAS처럼 모든 Pod가 동일한 역할이라면 문제가 되지 않음
- 데이터베이스 클러스터
  - 특정 인스턴스가 특정 역할을 담당
  - 특정 인스턴스를 구분할 수 있어야 함
  - 따라서 Pod의 이름이 변경되면 안 됨
- StatefulSet은 Pod에 고정된 이름을 부여하고, 재생성되어도 같은 이름을 유지

#### 2. 파드마다 다른 스토리지가 필요
- 데이터베이스 Pod가 3개라면 각 Pod는 자신의 저장소가 필요할 수 있음
- 모든 Pod가 하나의 PV를 공유하는 것이 아니라, 각 Pod가 독립적인 스토리지를 유지해야 하는 경우
- volumeClaimTemplates
  - 각 Pod마다 고유한 PVC를 자동으로 생성
- Pod가 삭제되어도 기본적으로 PVC는 유지
    - 같은 순번의 Pod가 재생성되면 기존 PVC를 다시 사용
    - 연결된 PV도 그대로 사용
  
#### 3. 특정 파드를 네트워크에서 찾아야함
- 일반적으로 서비스를 사용
- ClusterIP
  - backend-service->
- 데이터베이스를 위에 상황에서 사용한다
- 데이터베이스 클러스터는 특정 Pod에 직접 연결해야 하는 경우가 있음
```
# Headless Service 라는걸 사용함
db-0.db-service.default.svc.cluster.local
-> db-0.db-service -> 접근 하면 파드는 재생성될 수 있다.
	~~-> db-0 파드 10.244.10.4~~
	-> db-0 재생성 10.244.30.10
db-1.db-service.default.svc.cluster.local
db-2.db-service.default.svc.cluster.local
```
- Headless Service
  - 프록시나 로드밸런싱을 수행하지 않음
  - DNS 조회 시 서비스가 선택한 개별 Pod IP 주소를 리턴

#### 4. 파드의 생성과 삭제 순서가 중요
- 분산 애플리케이션
- 분산 디비, 분산 메시징 시스템
- 모든 인스턴스가 동시에 시작하면 안 되는 경우가 있음
    - 마스터 노드 초기화
    - 워커 노드 등록
    - 역할에 따라 초기화 순서를 맞춰야 함
- StatefulSet은 `OrderedReady` 정책을 통해 생성과 삭제 순서를 보장
---

#### Deplyment <-> StatefulSet
| 구분 | Deployment | StatefulSet |
| --- | --- | --- |
| 주요 목적 | Stateless 애플리케이션 관리 | Stateful 애플리케이션 관리 |
| Pod 관계 | 서로 대체 가능 | 각 Pod의 정체성 유지 |
| Pod 이름 | 임의 문자열 포함 | 순번 기반 고정 이름 |
| 예시 | `api-7b8d9c-x2k4p` | `mysql-0` |
| 생성 순서 | 일반적으로 병렬 | 기본적으로 순차 생성 |
| 삭제 순서 | 개별 순서 보장 없음 | 기본적으로 역순 삭제 |
| 스토리지 | 필요에 따라 PVC 연결 | Pod별 PVC 생성에 적합 |
| 개별 Pod DNS | 일반적으로 필요 없음 | Headless Service와 함께 제공 가능 |
| 대표 용도 | 웹 서버, API 서버 | 데이터베이스, 분산 시스템 |

### StatefulSet 실무에서 어디에 사용?
#### 1. 데이터베이스 클러스터 구성
- 직접 구성하면 생각보다 비용이 저렴할 수 있음
- RDS Multi-AZ
    - 추가 비용이 상당히 발생
    - AZ 간 데이터 통신 비용
    - AZ 간 고가용성 비용
```
MySQL
PostgreSQL
MongoDB
Cassandra
```

- Primary, replica, standby, sharding
- StatefulSet이 관리하는 범위
    - Pod 개수(`replicas`)
    - PVC, PV
    - Pod 이름 고정
    - Pod 생성 및 삭제 순서

StatefulSet이 아래 기능까지 제공하는 것은 아님
- 복제 구조
- 리더 선출
- 장애 조치
- 백업과 복원
- 버전 업그레이드
- 스토리지 장애 대응
- 데이터 정합성

#### 2. 메시징
```
Apache Kafka
ZooKeeper
RabbitMQ
Elasticsearch 또는 OpenSearch
```
- 메시지를 받아 다른 시스템으로 전달하는 메시지 브로커
- 여러 노드로 클러스터를 구성하여 고가용성 확보

---

#### 실무에서 주의해야할 것
#### 1. Liveness probe 과하게 설정하면 안됨
- 데이터베이스는 초기화 시간이 오래 걸릴 수 있음
- 커넥션 풀이 가득 차면 일시적으로 요청을 처리하지 못할 수 있음
- 초기화 지연이나 일시적인 응답 지연이 자주 발생

` 일시적인 응답 지연 -> Liveness 실패 -> 데이터베이스 컨테이너 재시작 -> 복구 중 다시 실패 -> 재시작 반복`

- 파드의 역할이 고정
  - MySQL Pod Master Pod
  - StatefulSet 으로 Pod 가용성
- Primary가 계속 재시작하면 쓰기 작업이 계속 실패할 수 있음
- Liveness Probe의 민감도를 낮게 설정하는 것이 중요

#### 2. StatefulSet이 데이터를 복제해 주는 것은 아님
StatefulSet이 데이터를 복제해 주는 것은 아님
- 고정된 Pod 이름 
- 고정된 네트워크 식별자
- Pod별 스토리지 연결 
- 생성 및 삭제 순서


StatefulSet이 제공하지 않는 기능
- 데이터베이스 복제
- Primary 선출
- 데이터 동기화
- 자동 백업
- 데이터 복원
- 애플리케이션 수준의 장애 조치

#### 3. PV, PVC는 삭제하지 않는다
- Stateless 애플리케이션의 PVC는 삭제해도 되는 경우가 많음
- 하지만 StatefulSet에서 사용하는 PVC는 함부로 삭제하면 안 됨
- PV는 클러스터 레벨 리소스이므로 관리 권한을 엄격하게 설정하는 것이 좋음
    - RBAC 등을 이용하여 삭제 권한 제한
- PVC를 삭제하면 데이터베이스 데이터가 함께 사라질 수 있음
    - 백업이 있다면 복구 가능
    - 하지만 백업 주기와 저장 기간도 직접 관리해야 함
- PVC를 삭제해야 하는 경우
    - 해당 PVC가 바인딩된 PV가 있는지 확인
    - 기존 PV 내부에 필요한 데이터가 남아있지 않은지 확인

#### 4. 순차 생성은 연쇄 에러의 원인이 될 수 있음
- OrderedReady 정책 을 통해서 파드의 생성 순서 보장
  - 앞 순번의 파드가 레디 되어야 다음 파드를 만듬
```
mysql-0 NotReady
->
mysql-1, mysql-2 생성 대기 가능
```
- 애플리케이션이 요구하는 초기화 순서와 StatefulSet의 생성 순서가 다르면 계속 대기할 수 있음
- 디버깅 시에는 생성되지 않은 Pod만 보지 말고 앞 순번 Pod부터 상태를 확인
- 생성 순서가 필요 없는 경우에는 `Parallel` 병렬 정책을 사용할 수 있음
---

#### 💡 정리
> Pod가 단순히 몇 개 존재하는지만 관리하는 것이 아니라, 각 Pod의 고유한 정체성과 스토리지 연결을 유지
1. 예측 가능한 Pod 이름
2. 안정적인 네트워크 식별자
3. Pod별 독립적인 PVC
4. 기본적으로 보장되는 생성•종료 순서

## 5. Node Scheduling
> 새로 생성된 Pod를 실행할 수 있는 노드들을 찾고, 그 중 가장 적합한 노드를 선택하여 배치하는 과정

- 쿠버네티스 기본 스케줄러인 kube-scheduler가 아직 노드가 정해지지 않은 파드들을 감시
- 두 단계를 거쳐서 파드가 실행될 노드를 결정
    1. Filtering - Pod 를 실행할 수 없는 노드를 제외
    2. Scoring - 실행 가능한 노드에서 점수를 계산해서 가장 적합한 노드를 선택
- 최종적으로 선택된 노드에 파드를 배치
```
Pod 생성 요청
->
kube-scheduler가 Pod 확인
->
실행 가능한 노드 필터링
->
후보 노드 점수 계산
->
가장 적합한 노드 선택
->
해당 노드의 kubelet이 Pod 실행
```
### 왜 노드 스케줄링 필요할까?
- 노드마다 사용할 수 있는 자원과 특성이 다르기 때문
- Pod마다 필요한 실행 환경이 다름
    - 일반적인 웹 서버 Pod
    - 많은 메모리가 필요한 데이터 처리 Pod
    - SSD가 필요한 데이터베이스 Pod
    - GPU가 필요한 머신러닝 Pod
- 스케줄링 기능이 없다면 사용자가 Pod마다 적절한 노드를 직접 선택해야 함
- `kube-scheduler`가 Pod의 요구사항과 노드의 상태를 고려하여 가장 적합한 노드에 자동으로 배치

### 사용 이유
1. 실행 가능한 노드 선택
2. 노드 특성 반영
3. 특정 노드의 과부하 방지
4. 워크로드 분리
5. 안정적인 운영

---

### 기본적인 스케줄링 동작
- 별도의 배치 조건을 작성하지 않으면 kube-scheduler가 자동으로 노드를 선택
- 노드의 리소스(CPU, Memory 등)를 기반으로 스케줄링
- 실행 가능한 노드 중 가장 적합한 노드에 Pod를 자동으로 배치

#### 1. Filtering
> 파드를 실행할 수 없는 노드를 후보에서 제외하는 단계
- Cpu가 200m 미만 -> 제외
- 확인하는 조건
  - 노드가 정상 상태인가?
  - Pod가 요청한 CPU와 메모리가 남아 있는가?
  - Pod가 요구한 노드 라벨을 만족하는가?
  - 노드에 Pod가 허용하지 못하는 Taint가 있는가?
  - 사용하는 스토리지를 해당 노드에서 연결할 수 있는가?
- Filtering 이후 후보 노드가 하나도 없으면 Pod는 `Pending` 상태에서 대기

#### 2. Scoring
> 필터링을 통과한 후보 노드들의 점수를 매기는 과정
- 각 후보 노드에 점수를 부여하고 가장 높은 점수를 받은 노드를 선택
- 점수를 계산할 때는 선호 조건도 고려
    - `preferred`
    - `Node Affinity`

---

### 노드 스케줄링이 제어하는 방법
- 노드 스케줄링에서 제어하는 방식 중에 대표적인 방법

#### 1. NodeName
> 노드 네임은 파드에 지정한 이름의 노드랑 직접 연결하는 방식
```
apiVersion: v1
kind: Pod
metadata:
  name: node-name-pod
spec:
  nodeName: worker-2
  containers:
    - name: nginx
      image: nginx:1.27
```

#### 특징
1. 노드 이름 직접 지정
2. 스케줄러 우회
3. 유연성 부족
4. 일반 배포에는 비권장

---

#### 2. nodeSelector
> 지정한 라벨을 모두 가진 노드에 파드를 배치하는 방법
```
kubeclt label node worker-1 disktype=ssd
```
```
apiVersion: v1
kind: Pod
metadata:
  name: node-selector-pod
spec:
  nodeSelector:
    disktype: ssd

  containers:
    - name: nginx
      image: nginx:1.27
```
- 이 Pod는 `disktype=ssd` 라벨을 가진 노드에만 배치 가능
```
worker-1: disktype=ssd  → 후보
worker-2: disktype=hdd  → 제외
worker-3: 라벨 없음      → 제외
```
```
spec:
  nodeSelector:
    disktype: ssd
    env: production
```
- 조건을 만족하는 노드가 없으면 필수(AND) 조건이므로 Pod는 `Pending` 상태가 됨

#### 언제 사용하냐
- SSD 노드에서만 데이터베이스 실행
- 운영용 노드와 개발용 노드 분리
- GPU가 설치된 노드에 특정 Pod 배치
- 특정 CPU 아키텍처의 노드 선택
- 특정 가용 영역의 노드 선택

---

#### 3. Node Affinity
> 노드 라벨을 기반으로 “필수 조건” 과 “선호 조건”을 세밀하게 표현하는 스케줄링 방식
- 실무에서는 대부분 `Node Affinity`를 사용
- `nodeSelector`와 비슷하게 라벨을 기준으로 노드를 선택
- 복잡한 조건을 표현
    - 여러 값 중 하나 선택
    - 특정 값 제외
    - 특정 라벨의 존재 여부 확인
    - 반드시 지켜야 하는 조건
    - 가능하면 지키는 선호 조건
    - 선호 조건별 가중치 부여

#### Node 어피니티에서 두 가지 조건식
1. requiredDuringSchedulingIgnoredDuringExecution: 스케줄링할 때 반드시 만족해야 하는 조건
2. preferredDuringSchedulingIgnoredDuringExecution: 가능하면 만족하는 노드를 선호하지만 필수는 아닌 조건

#### Required YAML
```
apiVersion: v1
kind: Pod
metadata:
  name: required-affinity-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd

  containers:
    - name: nginx
      image: nginx:1.27
```
- `disktype=ssd`인 노드에만 Pod를 배치
- 조건을 만족하는 노드가 없으면 Pod는 `Pending` 상태로 대기
  
#### 선호 조건 (preferred)
```
apiVersion: v1
kind: Pod
metadata:
  name: preferred-affinity-pod
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd

  containers:
    - name: nginx
      image: nginx:1.27
```
- 가능하면 `disktype=ssd`인 노드를 선호
- `weight`가 높을수록 해당 조건의 우선순위가 높음
- SSD 노드가 있으면 해당 노드에 배치
- SSD 노드가 없으면 다른 노드에도 배치 가능
    - `preferred`는 선호 조건이지 필수 조건은 아님

#### weight
- `preferred` 조건에서는 1~100 사이의 가중치를 지정
- 가중치가 높을수록 해당 조건을 만족하는 노드가 더 높은 점수를 받음
- `weight: 100`이라고 해서 반드시 해당 노드에 배치되는 것은 아님
    - `preferred`는 선호 조건
    - 다른 필수 조건과 함께 고려하여 최종 노드를 선택
  
#### Node Affinity 연산자
- In: 노드 라벨 값이 지정된 목록에 포함되어야 함
- NotIn: 노드 라벨 값이 지정된 목록에 포함되지 않아야 함
- Exists: 해당 라벨 키가 존재해야 함
- DoesNotExist: 해당 라벨 키가 없어야 함
- Gt: 라벨 값이 지정한 숫자보다 커야 함
- Lt: 라벨 값이 지정한 숫자보다 작아야 함

#### 여러 조건을 결합하는 방식
- Node Affinity 에서는 조건이 결합되는 위치에 따라서 AND 연산, OR 연산

```
env=production AND disktype=ssd
```
```
env=production OR disktype=ssd
```

#### 4. Taint <-> Toleration
> Taint는 노드가 일반 Pod를 밀어내는 제한 조건이고, Toleration은 Pod가 그 제한을 견딜 수 있도록 허용하는 설정

- 노드 어피니티: 파드 입장에서 특정 노드 선택
- 테인트: 노드 입장에 특정 파드를 거부

```
Node Affinity
Pod -> “나는 SSD 노드로 가고 싶다.”

Taint
Node -> “허용된 Pod가 아니면 들어오지 마라.”

Toleration
Pod -> “나는 이 노드의 제한을 허용할 수 있다.”
```

- 워커 노드에는
  - workload=gpu
  - 라벨이 붙지 않은 파드는 접근할 수 없다

```
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  tolerations:
    - key: workload
      operator: Equal
      value: gpu
      effect: NoSchedule

  containers:
    - name: nginx
      image: nginx:1.27
```
- 이 파드는 worker-2 배치할 수 있는 “자격” 이 생긴거
- taint 를 무시할 수 있다 ≠ taint 가 설정된 파드에 배치가 된다는 뜻은 아니다
    - taint - > 필터링에서 조건
    - 파드가 새롭게 배치될 때
        1. 필터링 - 후보가 아닌 애들 제외
            1. tainet 를 무시
        2. 스코어링 - 후보에 포함해서 `스코어링`
            1. 점수가 낮으면 배치 안함

#### Taint 의 Effect
- NoSchedule: 새 Pod를 받지 않음
- PreferNoSchedule: 가능하면 배치를 피함
- NoExecute: 새 Pod 제한과 기존 Pod 추출

### 실무에서 노드 스케줄링 어떻게 활용할까?
#### 1. 일반적으로는 기본 스케줄링 사용함
- 쿠버네티스는 스테이트리스한 애플리케이션을 타겟으로 만들어짐
    - WAS
    - 일반적으로는 k8s WAS, API 파드
- GPU 가 필요하거나
    - State 필요한 경우
    - k8s 내부보다는 외부에서 별도 관리하는 경우가 많음

#### 2. 하드웨어가 필요한 경우
- Label + Node Selector + Node Affinity
- GPU 연산
- SSD 배치 처리 ← 종종 데이터베이스
- 특정 가용 영역

#### 3. 전용 노드를 만드는 경우
- GPU 노드
- 데이터베이스 노드
- Taint/Toleration 같이 사용함
- 필요한 경우 `Node Affinity`도 함께 사용하여 원하는 Pod만 배치
