## 값 타입과 임베디드 매핑

### 1. 기본 값 타입
- 단일값(예; 이름,나이,금액)으로만 의미를 가지는 데이터를 엔티티의 필드로 직접 정의해 테이블 컬럼에 저장하는 방식

| 구분 | 설명 |
  | --- | --- |
  | **자바 기본형(primitive type)** | `int`, `long`, `double` 등 |
  | **래퍼 클래스(wrapper type)** | `Integer`, `Long`, `Double` 등 |
  | **문자열 타입** | `String` |

#### 사용이유
식별자나 연관관계가 필요 없는 단순한 값을 엔티티 내부에서 직접 다루어 **설계를 단순화**하고, **데이터베이스와 매핑**하기 위해서

* 기본과 래퍼클래스의 차이를 알아라 (long != null Long != null) 아이디는 래퍼클래스를 더 씀
  @Column(Null) < 추천

#### 사용방법
자바의 기본 자료형이나 문자열, 날짜 같은 단순 값을 엔티티 클래스의 필드로 직접 선언

---

### 2. 임베디드 타입
- 두 개 이상의 값을 하나의 객체로 묶어 엔티티에 포함시켜 사용하는, 재사용 가능한 타입
- 테이블은 그대로
- 엔티티 구조만 더 객체 지향적으로 만들어 코드 재사용성을 높임

#### 사용 이유
작성자 정보, 생성 일시처럼 의미 있는 값들의 묶음을 각각 하나의 객체로 만들어 **반복을 줄이고** **설계를 일관되게 유지**하기 위해서

#### 사용방법
값을 묶은 클래스를 @Embeddable로 선언하고, 이 클래스를 포함할 엔티티 필드에 @Embedded를 붙임

---

### 3. 컬렉션 값 타입
- 엔티티에 직접 연관되지 않는 여러 개의 값을 리스트나 세트 형태로 저장하기 위한 값 타입

#### 사용이유
- 여러 개의 단순 값을 엔티티 없이 테이블에 분리 저장
- 부모 객체와 함께 일괄적으로 관리하기 위해
- 엔티티에 직접 연관되지 않는 여러개의 값을 리스트나 세트 형태로 저장 (태그 목록, 주소 이력 등등)

#### 사용방법
@ElementCollection을 필드에 선언하고, 값 타입 클래스를 @Embeddable로 정의하여 리스트나 세트 형태로 매핑

## JPQL (Java Persistence Query Language)
- 엔티티 객체를 대상으로 데이터를 조회하거나 조작할 수 있도록 제공되는 객체 지향 쿼리 언어
- 객체 지향적 엔티티를 기반으로 한다

- 객체 중심으로 설계된 JPA
- SQL처럼 자유롭게 테이블과 컬럼을 다루기 힘든
- 단일 엔티티를 관리하는 것은 가능
- 복잡한 관계식, 조인, 조건 등은 처리 힘듬

### 왜 사용하나
- 문제: JPA를 통한 데이터 핸들링
  - 엔티티 기반으로 단순한 CRUD 가능

- 엔티티를 기준으로 쿼리를 작성해 객체 지향 설계를 유지하면서, 
데이터베이스에 독립적이고 유지보수하기 쉬운 코드를 작성할 수 있기 때문에

#### JPA 만으로 조건, 조회 시
- 엔티티와 연관 엔티티를 순차 조회
- 엔티티 기반으로 데이터 Get 이후 레포지토리 자바 코드에서 조건, 정렬, 검색 등 진행
게시글이 많으면 일단 DB에서 다 가져오고 자바에서 처리 -> 메모리 부담 + 불필요

#### JPQL 사용 시
- 한 번의 쿼리 조건으로 정렬 + 조건 처리
- Lazy 조회 없이 한번에 조회
- DB 레벨에서 데이터 처리 성능 유리함

---

### 특징
1. SQL이 아닌, 엔티티 중심의 쿼리 언어
-> DB 테이블이 아닌 entity 기준으로 쿼리 진행

2. 엔티티 모델을 기준으로, JPA 구현제가 사용하는 DB에 맞게 SQL문 작성
-> 데이터베이스 문법에 종속 안됨

* SQL을 작성하지 않고도, 객체 중심 개발 방식으로 필요한 데이터를 가져올 수 있다

---

### 사용방법

1. 문법
엔티티를 기반으로 쿼리 작성
엔티티에 별칭 필요

2. JPA에서 사용하기
엔티티 매니저를 통해 쿼리를 실행
- createQuery-쿼리 생성
- getResultList-여러 결과 가져오기
- getSingleResult-결과 하나만 가져오기
- executeUpdate-수정, 삭제 실행

3. 파라미터 바인딩
- 쿼리 내, 변수를 넣기 위한 파라미터 바인딩
  - 이름 기반
  - 위치 기반

4. 조건식
- NULLIF: 두 값이 동일하면 null, 아니면 첫 번째 값
- COALESCE: 여러 값 차례대로 확인하다, null이 아닌 첫 번째 값 반환
- CASE: 조건을 순서대로 검사 -> 일치하는 경우 해당 결과 값 반환 -> 일치 안하면 else 값 반환

5. 경로 표현식
- 묵시적 조인: join 키워드 없이, 경로만 표현해서 하는 방식. 항상 내부 조인
- 명시적 조인: join 키워드로 조인 직접 선언하기. 조인 구조 명확, 성능 최적화 용이
- JPQL에 조인을 선택한다면 명시적 조인을 권장

---

### N+1 문제
- JPA에서 지연 로딩(Lazy Loading) 사용 시 자주 발생하는 문제
- 연관 엔티티 조회 시, 처음 조회한 쿼리 이후 추가 조회 쿼리가 반복 발생함
- 조회 대상이 많을수록 DB 호출 횟수가 증가해 성능이 저하됨

### 1. fetch join
- 지연 로딩된 연관 엔티티를 한 번의 쿼리로 함께 조회하기 위해 사용하는 조인 방식
- JPQL에서 연관 엔티티 한 번에 가져오기

- n+1 문제 해결
- 필요한 데이터 미리 로딩

- 페이징 불가능
- 필요 이상의 데이터

---

### 2. projection
- 엔티티 전체가 아닌 필요한 필드만 선택해 조회할 수 있도록 지원하는 데이터 조회 방식

#### 사용이유
조회 성능을 높이고, 필요한 데이터만 명확하게 선택해 전달해 리소스 낭비를 줄이고 설계를 단순화하기 위해서

1. 엔티티 프로젝션
- SELECT 절에 엔티티 타입을 지정
- 엔티티 객체 자체를 결과로 받는 방식
- JPA 관리하는 영속 상태 엔티티
- 엔티티의 전체 컬럼을 가져오기

2. 임베디드 프로젝션
- SELECT 절에 엔티티에 포함된 임베디드 타입을 지정
- 해당 값 타입 객체로만 결과를 조회
- 소속 엔티티를 경로 표현식에 명시

3. 스칼라 프로젝션
- SELECT 절에 숫자, 문자열, 날짜 같은 단순 값(스칼라) 지정 조회
- 특정 컬럼만 선택해서 가져오기, 필요한 속성만 선별 조회
- 영속성 컨텍스트 관리 X

4. DTO 프로잭션
- SELECT 에서 필요한 필드 지정
- 필드 수와 타입이 정확히 일치하는 DTO 생성자 이용*
- 조회 시점에 바로 DTO 로 매핑

---

### 3. Paging
- 전체 데이터 중 일부만 조회할 수 있도록 범위를 지정해 나눠서 가져오는 기능
- JPQL 쿼리 실행 시 setFirstResult()와 setMaxResults()를 사용해 조회 시작 위치와 개수를 지정

#### 사용이유
- 대용량 데이터를 한 번에 불러오는 부담을 줄이고, 서버와 클라이언트의 성능을 안정적으로 유지하기 위해서

## Spring Data JPA
- JpaRepository 상속으로 CRUD 자동 제공
- 반복적인 CRUD 코드 없이 인터페이스만으로 리포지토리를 구현
- 메서드 이름 기반 쿼리 생성
- 개발 생산성과 유지 보수 효율 높임
- JPA 기반의 데이터 처리를 자동화해 인터페이스만으로 리포지토리를 쉽게 구현할 수 있도록 도와주는 Spring 모듈

### 순수 JPA
- EntityManager 직접 사용
- CRUD 메서드를 직접 구현
- 반복 코드 발생

> JpaRepository 인터페이스에서 자주 쓰이는 대부분의 JPA 동작들 미리 구현

---

### 사용방법
1. 기본 사용법 - Repository
- 새로운 리포지토리 interface 로 생성
- JpaRepository<엔티티, ID> 로 상속
- 기본 CRUD 제공 받음

---

2. Query Method
- 리포지토리 인터페이스의 메서드 이름을 기반으로 JPQL 쿼리를 자동으로 생성해주는 기능 (findBy~)
- 레포지토리 내 메서드 이름으로 JPQL 쿼리 자동 생성

### 사용처
1. 간단한 조회에 적합
2. 복잡한 조건, 동적 쿼리는 JPQL, QueryDSL 사용
3. 코드 가독성 + 생산성 향상
4. 메서드 이름만으로 실행될 쿼리 이해 가능

---

3. @Query
- 레포지토리 메서드에 직접 JPQL 또는 SQL을 작성할 수 있도록 제공하는 어노테이션

### 사용이유
- 메서드 이름으로 표현하기 어려운 복잡한 조건, 조인, 집계 쿼리를 명확하게 작성
- 메서드 이름으로 표현하기 어려운 복잡한 조건
- 다중 조건, 다중 조인, DTO 매핑 등등
- 쿼리를 직접 작성해서 성능 제어 가능

---

4. @EntityGraph
- 특정 엔티티 조회 시, 함께 로딩할 연관 엔티티 지정
- N+1 문제를 해결할 수 있게 하는 어노테이션

### 사용 이유
반복 쿼리가 발생하는 N+1 문제 방지, 연관 데이터 한 번에 조회하기 위해

---

5. Pageable
- 페이징과 정렬을 손쉽게 처리할 수 있도록 제공하는 객체

- 페이징 처리에 필요한 로직을 자동화해 쿼리 작성과 응답 설계를 단순화하고, 성능과 개발 효율을 함께 높이기 위해서

---

6. 사용자 정의 리포지토리
- 구현할 수 없는 복잡한 쿼리나 로직을 직접 구현하기 위해 커스텀 메서드를 추가한 리포지토리
- 자동화로 만들기 어려운 복잡한 로직을 구현해야할 때, 사용자 정의 리포지토리로 구현

2. 커스텀 구현 클래스 만들기

3. 레포지토리에 상속하기

## QueryDSL
자바 코드로 JPQL 이나 SQL을 직접 작성하지 않고, 
메서드 호출과 객체 지향 문법을 이용해 쿼리를 표현할 수 있도록 해주는 쿼리 라이브러리 

### 사용이유
복잡한 조건을 자바 코드로 안전하게 조립해 동적 쿼리를 유연하고 유지보수하기 쉽게 만들기 위해서

### JPQL 사용 시 한계
- 문자열 기반으로 쿼리를 작성
- 오타나 문법 오류를 컴파일 시점에 확인하기 어려움
- 엔티티 변경 시 런타임 오류 발생 가능
- IDE 자동완성 지원이 제한적임
- 동적 쿼리 작성 시 문자열을 직접 조합해야 함
- 조건이 많아질수록 가독성과 유지보수성이 떨어짐
- @Query는 동적 쿼리 작성이 불가능하며, JPQL로 구현할 경우 코드가 복잡해짐

### QueryDSL 사용 시
- 타입 안전한 쿼리 가능
- 동적 쿼리 최적화
- 문법 오류 발견 쉬움
- 복잡한 조건식 표현 쉬움
- 코드 재사용성 높음

---

| JPQL                  | QueryDSL                   |
| --------------------- | -------------------------- |
| 문자열로 쿼리 작성            | 자바 코드로 쿼리 작성 (타입 안전)       |
| 수동 바인딩 (`:name`)      | 메서드 체인으로 바인딩 (`u.name.eq`) |
| 동적 문자열 분기 복잡          | 동적 조건 객체 조립하듯이             |
| 필드명 변경시 런타임 오류        | Q 클래스 기반으로 컴파일 타임에 검증      |
| 조건 많아지면 읽기 힘듬         | 도메인 필드가 그대로 드러나 직관적        |
| IDE 에서 에러 파악 힘듬 (문자열) | IDE 자동완성 등 IDE 활용 가능       |
| 동일 조건이면 동일 성능         | 성능 동일 (둘다 JPQL → SQL 변환)   |

---

### Q클래스
- 빌드 시 QueryDSL의 메타 모델 클래스가 엔티티를 기반으로 Q클래스를 생성
- 타입 안전한 쿼리 작성에 사용
- JPAQueryFactory와 함께 사용

---

### BooleanBuilder
- QueryDSL에서 여러 조건을 조립하거나 동적으로 추가해 where 절을 구성할 수 있도록 도와주는 조건 빌더 객체
- 조건이 많은 동적 쿼리를 if문 없이 간결하게 구성해, 쿼리 가독성과 유지보수성을 높이기 위해서 사용한다

### where 다중 파라미터
- QueryDSL에서 where() 절에 여러 조건 메서드를 파라미터로 전달해, null인 조건은 자동으로 제외하는 동적 쿼리 작성 방식
- 조건을 메서드로 분리해 재사용성과 가독성을 높이고, null 조건을 자동으로 제외해 동적 쿼리를 간결하게 작성하기 위해서
