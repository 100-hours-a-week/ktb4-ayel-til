## Spring

- 자바를 자바답게 개발하기 위한 프레임워크
- 대규모 애플리케이션 개발을 쉽게 하기 위해 사용

### 스프링의 핵심 특징

1. AOP
- 관점 지향 프로그래밍
- 공통 관심사와 비즈니스 로직 분리

2. DI, IoC
- IoC : 제어 역전
- DI : 의존성 주입
- 객체 생명주기를 컨테이너가 관리
- 결합도 감소

3. POJO
- 순수 자바 객체 기반
- 외부 라이브러리 의존성 최소화

4. Bean
- 스프링이 관리하는 객체
- Bean 컨테이너에 등록 후 사용

---

### 왜 스프링을 만들었냐?
- 복잡한 설정(XML, JAVA) 단순화
- 의존성 관리
- 배포 편의성

## Spring Boot
> 스프링을 쉽게 사용할 수 있도록 만든 프레임워크

- 스프링을 대체하는 것이 아닌 래퍼(Wrapper)

### 스프링 부트의 핵심 기능

1. Auto-Configuration
- 라이브러리를 기반으로 Bean 자동 설정
- @SpringBootApplication 사용

2. Starter Dependencies
- 필요한 라이브러리를 묶음으로 제공
- 버전 호환성 자동 관리

3. Embedded Server
- 내장 Tomcat 제공
- 외부 WAS 없이 실행 가능

## Annotation
- 컴파일러와 런타임 엔진이 읽는 메타데이터
- 프로그램의 로직을 스스로 가지지 않음

### @Override
- 부모 메서드 오버라이드 검증
- 개발자 실수 방지

### 어노테이션을 왜 써야 하는지
1. 설정 응집
- 코드와 설정을 한 곳에서 관리
- @Entity, @Id

2. 검증 자동화
- 컴파일 시점, 런타임 시점 검증
- @NotNull
- @Size

### 주요 어노테이션

| 어노테이션 | 역할 |
| --- | --- |
| @Override | 오버라이드 검증 |
| @Deprecated | 사용 중단 표시 |
| @SuppressWarnings | 경고 숨김 |

- @NoArgsConstructor
  - 기본 생성자 생성
  - @Getter, @Setter
  - Entity, DTO, @Setter

## ORM
- 객체와 데이터베이스 테이블을 자동 매핑하는 기술

### 사용 이유
- 객체와 테이블의 차이를 연결
- SQL 매핑 작업 감소
- 생산성 향상

## 객체 지향 vs 관계형 데이터베이스 차이점
1. 상속과 다형성
- 객체 : 상속 지원
- RDB : 상속 개념 없음

2. 연관관계
- 객체 : 참조 기반 (단방향)
- RDB : 외래키 + JOIN (양방향)

3. 데이터 탐색
- 객체 : 그래프 탐색
- RDB : SQL 기반 탐색

- ORM
  - 객체와 RDB의 차이를 연결
  - 자동 매핑
  - 객체 모델링

### ORM 사용하는 방법
- RDB → 테이블
- 하이버네이트
  - SQL 자동 생성
  - JPA 구현체

- 자바 객체 (엔티티)
    - 매핑 설정
    - @Entity
    - @Column
    - @Id
    - @NotNull

---

## JPA (Java Persistence API)
> 자바 객체와 관계형 데이터베이스를 매핑하고, 객체 단위로 데이터를 저장조회할 수 있게 해주는 표준 ORM 인터페이스

- 객체를 DB에 저장, 조회
- JDBC를 직접 사용하지 않음

### JDBC (Java Database Connectivity)
- 데이터베이스에 쿼리를 전달할 수 있는 통로
- 개발자가 매번 연결, 해제, Raw SQL 직접 작성

### 동작
1. 엔티티 전달
2. 엔티티 구조 분석
3. SQL 생성
4. JDBC를 통해 실행

---

## Entity
> 데이터베이스와 1:1로 매핑되는 자바 객체

### 엔티티를 사용하는 이유
1. 데이터 규칙과 응집
- 이 엔티티에 데이터가 어떤 비즈니스 로직으로 들어가야 하는지
- 제약 조건과 비즈니스 로직을 함께 관리 (@Size, @NotNull)

2. 수정을 쉽게 할 수 있음
- 데이터와 규칙을 한 곳에서 관리해서, 엔티티 클래스 한 곳만 수정

### 엔티티 작성법
1. 기본 생성자 필요
2. final 클래스 사용 불가
3. enum, interface 사용 불가
4. final 필드 사용 불가

---

## DTO
> 계층 간 데이터 전달을 위한 전용 객체

### DTO를 사용하는 이유
1. 엔티티 내부 보안
- 민감 정보 보호
2. 소통 규격화
- 백엔드 ↔ 프론트엔드 통신 기준
3. 레이어 간 소통을 위해서 사용
- Controller ↔ Service ↔ Repository

### 중요한 것
- 비즈니스 로직 배제
- 소통 규격화

## @Id
> 엔티티 식별자를 지정하는 어노테이션
- 영속성 컨텍스트에서 엔티티를 식별하는 유일한 식별 값
  - 식별자가 없으면 @Entity로 등록안됨

### 할당 방법
1. 직접 할당
2. 자동 생성 방식
- 데이터베이스나 JPA 에 키 생성을 위임
- 실무에서는 데이터의 무결성 ← Id 에 대한 무결성이 필요

---

## 기본 키 생성 전략
- @GeneratedValue 사용

### 1. IDENTITY

> AUTO_INCREMENT에 식별자 생성 위임

- IDENTITY 는 DB 에 들어가야지만 ID 를 알 수 있음
- 쓰기 지연 무시

2. SEQUENCE
- 번호표 같은걸 별도의 테이블에서 관리하는 것
  1. 시퀀스에서 다음 ID 조회
  2. ID를 가진 엔티티 생성
  3. 쓰기 지연 저장소에 저장
  4. flush 시 DB 반영

3. TABLE
-별도 테이블로 시퀀스 구현
- 데이터베이스 종류 상관 없음
    - 키 생성 + 조회, 갱신 I/O 발생할 수 있다.
    - 일반적으로 속도가 느리다.
        - 보통 잘 안쓴다.
        - 호환성 요구가 있는 경우

4. AUTO
- DBMS 별로 기본적으로 키 생성 방식이 다르기에 맞게 알아서 키 식별자를 선택
    - MySQL, MariaDB, SQLite
        - 자동 증가 컬럼 (AUTO_INCREMENT)
    - Oracle, Postgres
        - 시퀀스

## 영속성 컨텍스트
- JPA가 엔티티를 관리하는 메모리 저장소
- 트랜잭션 내 변경 사항을 추적하고 DB와 동기화

### 사용 이유
- 엔티티 변경 관리
- DB 접근 최소화
- 성능 향상

### 특징

 1. 1차 캐시
- 엔티티와 식별자를 Map 형태로 저장
- 캐시에 있으면 DB 조회 안 함

2. 쓰기 지연
- 쿼리를 즉시 DB에 보내지 않음
- 쓰기 지연 저장소에 보관 후 flush 시 반영

3. 변경 감지
- 엔티티 상태를 스냅샷으로 저장
- flush 전 스냅샷과 비교
- 변경 시 UPDATE 쿼리 생성

---

## 영속성 컨텍스트와 트랜잭션

### 특징
- 트랜잭션과 생명주기를 함께 함
- 같은 트랜잭션이면 동일한 영속성 컨텍스트 사용

### 생명주기
1. 트랜잭션 시작
2. 영속성 컨텍스트 생성
3. 엔티티 관리
4. Commit
5. flush
6. 종료

---

### 엔티티 상태

1. 비영속
- 영속성 컨텍스트가 관리하지 않는 상태

2. 영속
- 영속성 컨텍스트가 관리하는 상태
- 1차 캐시
- 쓰기 지연
- 변경 감지 대상

3. 준영속
- 영속성 컨텍스트에서 분리된 상태

4. 삭제
- 삭제 예약 상태

---

### 주요 명령어
- persist() : 엔티티 등록
- flush() : 변경 내용 DB 반영
- remove() : 삭제 예약
- clear() : 전체 초기화
- detach() : 특정 엔티티 분리
- close() : 영속성 컨텍스트 종료
- merge() : 엔티티 재연결

## 연관관계 매핑
- 엔티티 객체 간의 관계를 정의하는 매핑

### 사용 이유
- 객체 관계와 DB 외래키 연결
- 데이터 정합성 유지
- 설계 일관성 유지

---

1. 단방향 연관관계
- @ManyToOne
- @OneToOne

- 한 엔티티만 다른 엔티티를 참조

#### 사용 이유
- 설계 단순화
- 불필요한 의존성 제거
- 코드 복잡도 감소

---

2. 양방향 연관관계
- @OneToMany
- @ManyToMany

- 두 엔티티가 서로를 참조
- 양쪽 모두 탐색 가능

### 연관관계의 주인 (Owner)
- 외래키를 관리하는 엔티티

### 사용 이유
- 양방향 조회 가능
- 탐색 범위 증가

- 게시글 → 작성자 조회
- 사용자 → 게시글 목록 조회

> 실무에서는 단방향으로 설계 후 필요 시 양방향 추가

## 프록시
- 지연 로딩 시 실제 엔티티 대신 사용하는 가짜 객체

### 즉시 로딩 (Eager Loading)
- 연관 엔티티를 즉시 조회
- LEFT OUTER JOIN 사용

### 단점
- 불필요한 JOIN 발생
- 성능 최적화에 불리

---

### 지연 로딩 (Lazy Loading)
- 조회 시 프록시 객체 반환
- 실제 사용 시 DB 조회

### 장점
- 성능 최적화
- 불필요한 조회 감소

---

## N + 1
- 지연 로딩 시 발생
- 조회 쿼리 1번 + 연관 엔티티 조회 N번 발생

### 해결 방법
- Fetch Join
- JPQL
- Batch Size 조절
