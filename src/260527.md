## HTTP 자격증명 헤더
> HTTP의 자격증명 헤더는 클라이언트와 서버 간의 인증과정에서 사용자의 자격을 확인하기 위해 사용되는 헤더

### 사용이유
- 보안이 필요한 웹 리소스에 접근할 때 사용자가 해당 리소스에 접근할 권한이 있는지를 검증하기 위해
- 웹 리소스에 접근할 때 필요한 사용자의 인증 정보를 서버에 전달하기 위해서

### HTTP는 어떻게 인증하는가?
- 특징
  - Stateless
  - 보호되어야 하는 리소스
    - 내 프로필 정보
    - 카드 번호
    - 접근 할 때마다 내가 누구인지 증명해야 한다
- 헤더를 통해서 인증하는 과정을 거친다

### WWW-Authenticate
- 서버가 발급하는 Response Header
- 서버가 클라이언트에게 인증이 필요함을 알리는 헤더로, 접근 권한을 요구하는 경우 사용됨
  - 401 ← Unauthroized
    - 응답할 때 자동으로 동봉

### Authorization
- 클라이언트가 서버에 자신을 인증하기 위해 필요한 정보를 제공하는 헤더
- “신분증의 내용” → Authorization 헤더에 담는다.
- RFC ← HTTP 의 약속을 정하는 곳이 있는데, 여기에 정의되어 있다.

## HTTP 인증 헤더 방식 3가지
### 1. 기본 인증 (Basic Authentication)
- 아이디 + 패스워드 <- 두 가지를 갖고 인증한다
  - 아이디 : 패스워드
    - Basic64 인코딩된 평문이다
  - Basic 인증 방식은 항상 HTTPS TLS 방식의 암호화된 통신에서만 사용

  - 서버는 아이디/패스워드를 직접 검증해야 한다
      - DB 값과 비교
      - 인증 여부 확인
      - 권한 확인
  -> 매 요청마다 검증이 필요하다
  -> 서버 자원에 부담이 된다

- 간단하게 인증해야할 때 사용함.

### 장점
- 구현이 상당히 간단하다
- 토이 프로젝트, 내부용 API 콜할 때

---

### 2. 다이제스트 인증 (Digest Authentication)
- Basic 인증의 보안 문제를 개선한 방식
- 비밀번호 대신 해시 값을 전달한다

### Basic 인증의 문제
- 권한이 필요한 모든 요청마다 비밀번호를 헤더에 담아서 보낸다
- HTTPS를 사용해도 탈취 위험은 존재한다
-> 비밀번호 대신 해시 값을 보내자

#### Nonce, Realm
- Nonce -> 서버가 클라이언트한테 딱 한 번 쓰고 버리라고 주는 일회성 난수
- Realm -> 서버가 관리하는 보안 공간의 범위를 표기하는 문자열

### 실행과정
1. 클라이언트가 보호된 리소스를 요청
2. 서버: 여기 보호되어 있고, 너한테만 nonce,realm 줄테니까 이거를 비밀번호할 함께 섞어서 해시 값으로 가져와
3. 클라이언트는 비밀번호+nonce+realm를 해시 함수로 구워서 헤더에 보냄

### 문제점
- 보안성이 올라가지만, 매번 요청마다 서버 Nonce 관리와 다시 해시화해서 확인

---

### 3. Bearer Token
### 기존 방식의 문제점
- Basic -> 비밀번호 매번 평문 -> 매 요청마다 서버가 비번체크
- Digest -> 비밀번호 암호화 -> 매 요청마다 서버가 체크 하는건 그대로
  
> 이 토큰을 소지한 요청은 "인증, 인가" 된 걸로 한다

### 베어러 토큰이란?
- Bearer 의미 
  - 토큰을 들고 있는 사람은 정당한 권한이 있는걸로 간주한다

### 장점
1. 유저의 비밀번호 보호
2. 범용성이 좋다
   - 과거 인증 방식 (Session+Cookie) -> 브라우저에서는 잘 작동한다
   - 모바일 앱에서는 동작하지 않는다
   - 도메인이 달라지면, 쿠키가 따라 붙지 않는다. 인증이 깨지는 불편함도 있다 
3. CSRF 방어 

### 단점
1. 토큰이 탈취당하면 위험하다
2. 토큰은 보관하기가 까다롭다
- Storage 저장 → XSS 취약
- Cookie 저장 → CSRF 취약

### 일반 베어러 토큰의 한계
- 오페이크 토큰, 불투명 토큰
  - 토큰 값이 의미가 없는 토큰
  - 서버에서는 이걸 보관해야한다
    - 결국 오페이크 토큰, 불투명 토큰을 사용하면, 어차피 서버가 부담해야 하는 자원

## JWT
>토큰 안에 회원 정보 들어 있고 위변조 여부까지 확인할 수 있는 토큰이라면
서버에서 굳이 DB 뒤져서 볼 필요 없지 않을까?

### 사용이유
- 사용자의 인증 상태를 유지하면서 서버 간의 부담을 줄이고 
- 무상태 인증을 가능하게 하기 위해

### JWT 토큰이란?
- JSON 객체 형태의 정보를 안전하고 가볍게 전송하기 위한 토큰 표준
- 서버는 서명만 검증하면 된다
- 내부 값이 위조되지 않았는지 확인할 수 있다

---

### 헤더영역
- 토큰의 타입, 서명에 사용된 알고리즘
- 
### 페이로드 영역
- JWT 토큰에 담을 정보들이 있는 곳
-  평문 영역 -> 인코딩, 디코딩
  - 노출되면 안되는 값을 넣으면 안됨 (주민등록번호, 카드번호, 비밀번호)

### 서명 영역
- 이 토큰이 위조 되었나? 를 검증하는 영역
- 내부 내용을 수정하면 시그니처가 달라진다 -> 유효성 검증

---

### JWT 왜 써야하나?
1. 완전한 무상태성 + 확장성
- Basic, Digest 결국엔 서버에서의 검증 로직
- 서버가 데이터를 관리하고 조회하는 자원을 써야했다
- 인증, 인가 필요한 정보가 이미 JWT 토큰에 작성되어 있다
  - 암호화된 서명만 검증하면 된다

2. DB 조회를 상당히 적게 한다.
- 기존 인증 방식은 매 요청마다 DB 조회가 필요했다
->  요청이 많아질수록 DB 병목이 발생한다
- JWT는 토큰 내용과 서명만 검증하면 된다
-> 별도의 DB 조회 없이 인증 처리가 가능하다

### 단점
1. 무효화가 어렵다.
- JWT는 클라이언트가 직접 보관한다
  - Storage
  - Cookie
- 토큰이 탈취되어도 즉시 만료시키기 어렵다
-> 그래서 Access Token + Refresh Token 구조를 사용한다

2. 네트워크 대역폭이 낭비된다.
- 토큰 내부 정보가 많을수록 길어진다
- 모든 요청마다 토큰을 함께 전송해야 한다

## Access Token과 Refresh Token

### 보안과 편의성의 딜레마
- 보안성을 높이면, 편의성 떨어짐
- 편의성 높이면 → 보안성 떨어짐

- Access Token 수명을 길게 하면
    - 유저는 편하다
    - 탈취 시 위험하다

- Access Token 수명을 짧게 하면
    - 보안성은 좋아진다
    - 자주 로그인해야 해서 불편하다

-> 유저가 인증하는건 Access Token (놀이기구 탈때마다 보여주는 15분짜리 일회용 탑승권)
-> 토큰을 재발급하는걸 Refresh Token (가방 속에 있는 연간 회원권)

---
| **구분** | Access Token (접근 토큰) | Refresh Token (재발급 토큰) |
| --- | --- | --- |
| **역할** | 실제 API 리소스에 접근하기 위한 출입증 | Access Token을 새로 발급받기 위한 인증서 |
| **수명 (유효기간)** | 15분 ~ 30분 | 2주 ~ 1달 (비교적 길게 설정함) |
| **저장 위치** | 프론트엔드 메모리 (변수) 또는 LocalStorage 또는 HttpOnly 쿠키 | 서버 측 저장소 (Redis 같은) 혹은 클라이언트 HttpOnly 쿠키 |
| **전송 빈도** | 매 API 요청마다 항상 보냄 (노출 위험 큼) | Access Token이 만료되었을 때만 딱 한 번 보냄 |
---
### 만약에 리프레시 토큰이 탈취 당하면?
- 우리 서버는 사용자인지 해커인지 판단 할 수 없다.
- 이 문제를 해결하려고 하는 기술이 RTR

---

## RTR (Refresh Token Rotation)
> Refresh Token 재사용하지말고, 한 번 쓰면 폐기하고 다시 새걸로 바꾸자.

- 작동 시나리오
    1. 유저의 엑세스 토큰(A1) 만료
    2. 유저가 리프레스 토큰 (R1) 을 서버에 보내면서 엑세스 토큰 다시만들어줘 라고 요청
    3. 서버는 본인의 저장소 (Redis) R1이 유효한지 확인한다. R1을 폐기한다.
    4. 서버는 유저한테 새로운 엑세스 토큰 A2 발급하고, + R2 도 발급한다.
    5. 서버는 R2를 저장소에 저장한다.

- 해커가 탈취한 경우
    1. 해커가 훔친 R1 토큰으로 새 토큰 요청
    2. 서버는 R1 지운다. 해커한테 새 토큰세트 (A2, R2) 준다.
    3. R2를 저장소에 저장함.
    4. 잠시 후, 진짜 유저가 자기가 들고 있던 R1 토큰으로 재발급 요청
    5. 저장소에서 R1을 검색합니다. → 없네?
    6. 어 R1 으로 발급된 유저는 지금 비정상 유저다.
        1. 해커가 쓴거아님?
        2. 서버는 해당 유저아이디 관련된 모든 리프레시 토큰을 다 만료 시킨다. → 저장소에서 삭제 시킨다.
    7. 해커가 들고있던 R2 ← 의미가 없어진다.

## Layered Architecture
- 시스템을 책임 분리해, 각 계층이 정해진 역할만 수행하도록 구성하는 구조
- 코드 간에 관심사 분리

### 사용이유
- 웹 요청 처리, 비즈니스 로직, 데이터 접근을 분리해 변경 범위를 국소화하고 테스트, 유지보수, 확장을 안정적으로 수행하기 위해서

### Controller
- 요청을 받아 처리 흐름을 시작하는 계층
- 요청을 해석하고 Service로 위임함
- 레이어별로 필요한 데이터가 다르다
- -> DTO
  - 전달할 데이터 구조 정의
  
- 외부 입출력 관련 처리

### Service
- 비지니스 로직 처리
- 요청이 어떤 의미를 가지는지 해석하고 여러 작업을 어떤 순서로 수행할지를 결정

### Repository
- 데이터 접근을 담당하는 계층
- 데이터를 조회하거나 저장함

- 데이터베이스와 객체 지향의 구조 차이
  - RDB 테이블 구조와 규칙을 객체화
  - -> Entity
    - 테이블 정의
    - 컬럼 매핑
    - 키 정의

### 알면 좋은것
- 헬퍼/매퍼 클래스
- 미들웨어
