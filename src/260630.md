## 1. Portainer
> Docker와 Kubernetes 같은 컨테이너 환경을 손쉽게 관리할 수 있도록 해주는 웹 기반 GUI 관리 도구

### 왜 필요한가?
- 기본적으로 Docker는 명령어로 동작
- CLI는 명령 자체가 잘 동작하고 자동화에 편하지만, 여러 컨테이너를 관리할 때 복잡하다
  - 상태 파악이 어려움, 명령어 실수, 운영 접근성 낮음, 여러 서버 관리 불편 등

### Portainer
- Docker Engine API를 통해 Docker를 관리, 여러 서버를 관리할 때는 Portainer Agent 사용
  - 도커의 연결 상태를 읽고 도커 명령어를 대신 실행할 수 있다.
    - GUI 기반으로 버튼 클릭 -> 도커 명령어로 전환해서 전달할 수 있다.
- 포테이너는 도커를 대체 X
  - docker GUI 기반으로 쉽게 사용할 수 있게 한다 O

### 사용 이유
> 여러 컨테이너 환경을 직관적인 웹 UI로 통합 관리하여 컨테이너 배포, 모니터링, 권한 설정 등 운영 작업을 효율화하고 관리 복잡도를 크게 줄여준다

### 기능
1. 컨테이너 조회: 실행, 중지, 종료 상태 확인
2. 컨테이너 시작, 중지, 재시작: 버튼으로 컨테이너 제어
3. 로그 확인: 브라우저에서 로그 조회
4. 콘솔 접속: 컨테이너 내부 셀 접속
5. 이미지 관리: 이미지 조회, Pull, 삭제
6. 볼륨 관리: 볼륨 생성, 연결, 조회
7. 네트워크 관리: 컨테이너 네트워크 연결 상태 확인
8. Stack 관리: Docker Compose 기반 서비스를 화면에서 배포
9. 자원 상태 확인: CPU, 메모리, 네트워크, I/O 사용량 확인

#### Docker Desktop vs Portainer
- 둘 다 도커를 GUI로 관리하는 툴
- Docker Desktop: 로컬 개발 환경 (로컬)
- Portainer: 서버, 운영 환경 관리 (서버 환경)

#### 포테이너의 역할
- 서비스가 제대로 동작하는지 확인
- 장애 컨테이너의 로그 확인
- 컨테이너 재시작
- 이미지 풀하고, 재시작
- 볼륨, 네트워크 확인
- 도커의 운영 관리 도구

### Portainer 구조
1. Portainer Server: 웹 UI와 관리 기능을 제공하는 중심 서버
2. Docker Engine: 실제 컨테이너, 이미지, 볼륨, 네트워크를 실행하고 관리하는 엔진
3. Portainer Agent: 원격 Docker 서버의 정보를 Portainer Server에 제공하는 에이전트
4. Edge Agent: 외부에서 직접 접근하기 어려운 원격 환경을 관리할 때 사용하는 방식

### 설치 전에 알아야 하는 개념
#### Docker Socket
- 리눅스에서 Docker CLI는 Docker 데몬들이랑 통신을 해야한다
  - 실제로는 Docker API랑 소통하기 위한 소켓
- Portainer 컨테이너에서 EC2 A - Docker Socket을 연결하면, 포테이너는 해당 도커 엔진을 제어할 수 있다

#### 보안적으로 위험할 수 있다
- 도커 소켓으로 연결되어 있는 인스턴스에는 포테이너 컨테이너 연결되어 있는 도커 엔진을 제어할 수 있다
- 도커 소켓으로 할 수 있는 작업
  - 컨테이너 생성, 중지, 삭제
  - 호스트 디렉터리 마운트
  - 민감한 환경 변수 조회 가능성
  - Docker Engine 설치된 서버에 큰 권한으로 접근 가능

### ⭐️중요
- 포테이너 컨테이너 안에서 절대로 외부 인터넷에 노출하면 안된다
- 항상 네트워크 접속 가능한 영역을 줄여놔야한다.
  - Private subnet에서 VPN 통해서만 접근
  - 특정 IP 대역에서만 접근을 허용

### 실무에서 Portainer를 언제 사용하는지
#### 1. 운영 가시성 확보
- 실무에서 장애가 발생 시 가장 먼저 필요한게 지금 어떤 컴포넌트, 컨테이너가 죽어있는지 확인
- Portainer
    - 컨테이너 상태 확인 (실행, 중지, 삭제)
    - 최근에 재시작 여부 확인
        - 문제가 생기는 컨테이너는 재시작 시도 회수가 비정상적으로 높다
    - 컨테이너가 어떤 이미지 버전으로 실행 중인지 확인
    - CPU, RAM 자원 사용량 확인

#### 2. 개발자 - DevOps 협업
- 포테이너 <- 도커를 보기 쉽게
- 개발자
  - 코드 만들어서
  - CI/CD 파이프라인 돌리고
  - 정상 테스트 통과하면 OK
- DevOps 팀
  - 실제로 배포가 안정적으로 되나

3. 소규모 운영
- 대형 중앙 집중 로그, 메트릭 수집 툴은 무겁고, 설치 및 관리하기가 까다롭다
- Grafana (Dashboard) 운영까지는 조금 무거우니 Portainer로 간단하게 설정하여 EC2 심플하게 운영한다.

### 주의사항
**1. GUI 바꾸면, 실제로 변경된다**
**2. RBAC 접근 제어해야 한다**
- 사용자 권한 권리
- 삭제할 수 있게 환경을 만든 사람이 책임진다
**3. Portainer 보안 사항을 준수해야한다**
- Private subnet
- VPN or Bastion Host
- Admin 계정에 대한 공유

## 2. Volume
> 비영속적인 컨테이너 간 데이터 공유 및 영속성을 제공하기 위해 호스트 파일 시스템에 생성되는 독립적인 저장소

### 컨테이너 안에 파일을 저장 시
- 컨테이너를 재시작해도 데이터 살아있지만 컨테이너를 삭제 시 같이 삭제
- 테이블을 생성하거나 데이터를(Row) 저장할 수 있다

### 왜 이렇게 되는지?
- 컨테이너는 이미지 위에 쓰기 가능한 임시 레이어 얹어서 동작한다
- 컨테이너가 실행되면서 파일을 만들거나 수정을 실행할 때 그 변경사항은 "이미지"에 저장되지 않는다
  - 컨테이너의 읽기/쓰기 레이어에 저장된다
- 쓰기 레이어가 컨테이너 생명 주기에 묶여있음

### 왜 이런 구조인지? 
- 원래 이 목적은 애플리케이션 실행 환경에서는 매우 좋다
    - 문제가 생기면 기존 컨테이너를 수정하는 것이 아니라 삭제 후 새로 실행하면 된다.
  ```
    docker rm -f backend
    docker run -d --name=backend backend:1.3.1
    ```
- K8s
  - 여러 컨테이너를 자동으로 운영하고 관리하는 도구

### Volume 해결하는 방법
> 컨테이너 내부에 데이터를 쓰지 않고 컨테이너 외부에 데이터를 작성한다
- /var/lib/mysql 에 저장하는 거 처럼 보이는데 실제 데이터는 Docker Volume을 통해 Host OS에 저장된다.
- 그렇기 때문에 컨테이너를 삭제 후 재생성 시에도 볼륨은 어차피 호스트 OS에 저장되어 있다

### 사용이유
> 컨테이너 종료 및 재시작에도 데이터를 영구적으로 유지하고 공유하기 위해서
1. 데이터 영속성
2. 컨테이너 재배포 안전성
3. 데이터 공유
4. Docker가 저장 위치 관리
5. 운영 안정성

### 사용방법

```
# 볼륨 생성
docker volume create mysql-data

# 볼륨 목록
docker volume list
docker volume ls

# 볼륨 내부 정보
docker volume inspect mysql-data

# 볼륨 컨테이너 연결
docker run -d \
--name mysql-test \
-e MYSQL_ROOT_PASSWORD=1234 \
-v mysql-data:/var/lib/mysql \
  mysql:8.0
```

### 현업에서 언제 사용하는가?
1. 데이터베이스 컨테이너
- 영속성 필요

2. 파일 업로드 임시 폴더
- 공용으로 보고 있는 업로드 파일 임시 저장하는 폴더

3. 설정 파일 마운트
- Nginx 설정, Spring env 파일 등

4. 로그 보관
- 컨테이너 로그가 기본적으로 컨테이너 내부에 생성된다
- 컨테이너가 삭제되면 로그도 같이 지워진다
  - 오류가 발생하면 삭제가 될 수 있다

‼️ Volume은 컨테이너 밖에 존재하므로 컨테이너를 삭제해도 Volume은 삭제되지 않는다
