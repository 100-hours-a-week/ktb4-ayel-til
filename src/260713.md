## 1. Kubernetes (k8s)

> 여러 서버에서 실행되는 많은 컨테이너를 자동으로 배치하고, 감시하고, 복구하고, 확장하기 위한 컨테이너 오케스트레이션 플랫폼

#### 하는 일
1. 컨테이너를 어느 서버에 배치할지 결정
2. 필요한 수만큼 컨테이너 실행
3. 장애가 발생한 컨테이너 복구
4. 서버와 컨테이너 상태 감시
5. 트래픽 증가 -> 컨테이너(파드)를 확장
6. 애플리케이션 실행 상태를 유지

#### k8s = Kubernetes
- 쿠버네티스는 명령어가 긴 편이라, 축약해서 쓴다 (kgp, kgn, kap)

---

### 무슨 문제를 해결하나?
그동안 애플리케이션은 어떻게 실행되고 있었나?

#### 1. 물리서버
- 하나의 물리 서버에 앱 설치
    - 프론트, 백엔드, DB, 웹서버 설치

##### 문제점
- 하나의 애플리케이션이 만약 느려지면 다른 애플리케이션도 느려진다
- 애플리케이션마다 필요한 라이브러리가 다르다 (충돌 가능성)
- 서버 한 대 장애 -> 전체 서비스가 죽음
    - 가용성이 떨어짐
- 물리서버는 확장하기도 어렵다

---

#### 2. 가상 머신
- 물리서버의 자원을 나눴다
- 이걸 클라우드에 띄우면 AWS -> 가상머신 사용하면 애플리케이션마다 독립적인 운영 체제 사용 할 수 있음

##### 해결된 문제
- 애플리케이션 간 격리
- 자원 사용량 분리
- 하나의 물리 서버 -> 여러 개의 가상머신
    - 확장성도 보장

##### 아직 문제점
- VM 마다 운영체제 -> 운영체제는 자원을 많이 필요로 해서 무겁다
- VM 이미지가 크기 크다
- 초기 실행시간이 느리다
    - 운영체제 <- 관리 포인트
        - 보안 패치 <- 원도우 서버가 이런 문제가 좀 심하다

---

#### 3. 컨테이너
- 컨테이너는 각 VM을 분리한거처럼 운영체제를 따로 만들지 않는다
- 호스트의 운영체제에 있는 커널을 공유해서 사용
    - 커널 -> HW

##### 장점
- 운영체제가 빠진다
    - VM 실행 속도가 빠르다
    - 이미지도 가볍다
        - 실행 환경 -> 하나의 작은 이미지
        - 해당 이미지를 통째로 옮겨서 사용할 수 있다
            - CICD -> Registry 이미지 통째로 올려서 다운받았음
            - CICD 통합이 잘된다

### 도커(컨테이너)에서 해결 안 되는 문제
> 도커는 컨테이너를 쉽게 실행해주는데, 많은 컨테이너가 있는 경우, 여러 서버에서 "운영" 하는 문제는 해결하지 못한다

- 개발자 로컬 PC 여기서는 작은 서비스를 몇 개 컨테이너로 띄울 수 있음
    - FE, BE, DB
    - Container 실행 시키기 편함 -> Docker compose
- 서비스가 커져서 많은 컨테이너 돌아가고 있다면?
- 이걸 사람이 수동으로 관리한다면, 여러가지 문제가 생긴다

---

### 문제 1. 컨테이너가 죽으면 어떻게 다시 실행하지?
- 컨테이너는 여러 이유로 종료
    - 애플리케이션 에러
    - 메모리 부족
    - 네트워크 장애
    - 명렁어를 잘못 -> Process Kill
- 컨테이너 한 두개면 명령어로 키면 된다
    - 어떤 컨테이너가 어디에서 왜 죽었는지, 다시 실행하기도 힘들다

#### 필요한 기능
- 컨테이너 상태 지속적으로 확인
- 컨테이너 종료 -> 자동으로 재시작
- 서버가 정상인지 확인 -> 비정상이면 다른 서버에서 실행
- 필요한 수의 컨테이너 유지

---

### 문제 2. 어느 서버에서 컨테이너 실행하지
- 여러 서버에서 많은 컨테이너를 실행하는데
- 백엔드 요청이 급증 -> 백엔드 컨테이너를 늘려야한다
- 새로운 컨테이너를 실행해야한다
    - 무슨 컨테이너를 실행하는데?
        - 그 컨테이너가 얼마나 어떤 자원이 필요한지?
- 컨테이너를 배치한다 -> 새로운 서버에 넣는다
    - 해당 서버의 유후 자원이 얼마나 있냐?
    - 컨테이너가 필요한 자원이 얼마냐?
    - 특정 서버에서는 실행하면 안되나?
        - 네트워크 이슈
        - 가용성 이슈
        - 디스크, 네트워크

#### 필요한 기능
- 서버의 자원 실시간 확인하기
- 컨테이너 자원의 요구 사항 확인
- 조건에 맞는 서버도 자동으로 선택
- 서버별로 컨테이너를 적절하게 분산

---

### 문제 3. 특정 서버가 장애를 일으키면?
- A, B, C 서버 중 B가 죽음
    - B 서버에 있는 컨테이너 요청을 릴레이 X, 응답 X
    - 똑같은 처리량이 필요함
        - 똑같은 처리량이 필요함
            - 해당 서버에서 처리하고 있는, 컨테이너의 수
            - 컨테이너의 종류
            - 재배치
            - 지금 자원 가용량 얼마지?

#### 필요한 기능
- 사용할 수 없는 서버를 감지
- 전체 서비스의 워크로드 분산

---

### 쿠버네티스가 해결하는 것들
1. 컨테이너를 자동으로 실행, 배치
2. 현재 클러스터 내에서 서버의 자원 사용량을 실시간 모니터링
3. 컨테이너가 사용하고 있는 자원량도 실시간 모니터링
4. 서버 자원을 알고 있으니 -> 필요한 컨테이너를 자원에 맞춰서 배치
5. 특정 서버가 에러가 나면 -> 필요한 컨테이너를 자동 재배치
6. 필요한 처리량에 따라서 필요한 컨테이너를 늘렸다가 줄였다가
7. 롤링 업데이트 지원
8. 중앙에서 관리할 수 있게 한다

컨테이너 오케스트레이션

---

### 컨테이너 오케스트레이션?
> 여러 서버에서 실행되는 많은 컨테이너를 배치하고, 연결하고, 감시하고, 복구하는 작업을 자동화하는 것
- 오케스트라 -> 오케스트레이션, 편성하고 지휘함
- 연주 -> 바이올린, 첼로, 타악기, 관악기
- 컨테이너 -> FE, BE, DB, Monitoring
- 여러 역할의 컨테이너 적절한 서버에서 수행
    - 필요한 수를 유지
    - 필요 없으면 날리고
    - 에러가 발생하면 복구하고
- Docker -> 컨테이너를 만들고 실행하는 도구
- Kubernetes -> 여러 서버에서 많은 컨테이너를 관리하는 도구

---

### 쿠버네티스 핵심 개념 ⭐️
쿠버네티스를 이해할 때 필요한 핵심 개념 3가지
1. 선언적 관리
2. 원하는 상태
3. 지속적인 상태 조정

---

### 1. 선언적 관리
> 사용자가 작업 방법을 하나씩 명령하는 것이 아니라, 최종적으로 원하는 상태를 정의하는 방식

### 명령형 관리 방식
운영자가 서버에 접속해서 필요한 명령을 순서대로 수행

```
1. 서버 접속
2. 백엔드 컨테이너 실행
3. 실행 상태 확인
4. 실패하면 대응
5. 컨테이너 부족하면 하나더 추가하시고
```

- 운영자가 직업 서버에 명령을 남겨야 한다

### 선언형 관리
운영자가 최종적으로 원하는 "상태"를 정의한다

```백엔드 애플리케이션을 3개 실행되면 좋겠어```

- 쿠버네티스가 알아서 백엔드 컨테이너가 2개라면 1개를 늘리고 4개라면 1개를 줄인다
- 운영자가 세부적인 명령어 실행하지 않음
    - 원하는 상태를 정의함
    - 쿠버네티스가 만들어 놓음

---

### 2. 원하는 상태, Desired State
사용자가 쿠버네티스한테 "나는 이 상태를 원해"

```
애플리케이션은 세개 실행 
각 앱 -> 500mb Memory
지정한 컨테이너 이미지를 사용해라
```

#### 현재 상태
실제 쿠버네티스 내에서 실행되고 있는 상태
```
애플리케이션은 2 개 실행 
한 서버가 장애 
컨테이너 하나가 죽었다
```

- 쿠버네티스에서는 `원하는 상태 <-> 현재 상태`를 지속적으로 비교

---

### 3. 지속적인 상태 조정
쿠버네티스는 현재 상태를 관찰, 원하는 상태와 다르면 필요한 작업을 수행

```
1. 원하는 상태 확인
2. 현재 상태 확인
3. 두 상태 비교
4. 차이가 있으면 수정
5. 다시 상태 확인
```

- 이 반복적인 조정이 쿠버네티스에서 자동화 핵심

---

### 쿠버네티스 요소

### 클러스터
> 쿠버네티스가 관리하는 여러 서버, 컨테이너, 리소스의 집합
- 쿠버네티스는 여러 서버를 묶어서 관리
```
Kubernetes Cluster
├── Control Plane
├── Worker Node 1
├── Worker Node 2
└── Worker Node 3
```
- 클러스터를 구성하는 각 서버는 모두 "Node"라고 부른다
- 노드는 "물리서버, 가상 머신, AWS EC2, 온프레미스 서버, 다른 클라우드의 VM" 일수도 있다
- 클러스터는 여러 노드로 구성하는 것이 일반적이며, 필요에 따라 노드 수를 늘리거나 줄인다
    - 일반적인 클러스터는 보통 하나의 노드 구성을 유지하는 경향이 있다
    - 운영 복잡도가 너무 높아져서 하나로 유지

---

### Control Plane (Mater Node)
> 클러스터 전체의 상태를 관리하고, 파드 배치 판단하는 중앙 제어 영역
1. kube-apiserver
2. etcd
3. kube-scheduler
4. kube-controller-manager

#### 컨트롤 플레인의 역할
- 사용자 요청 수신
- 클러스터의 상태 저장
- 현재 상태랑 원하는 상태 비교
- 실행 할 노드 결정
- 장애 감지
- 필요한 작업 조정
- Mater Node

#### 1. kube-apiserver
> 쿠버네티스 클러스터로 들어오는 모든 관리 요청의 중앙 출입구
- 사용자가 `kubectl` <- 명령어를 내리면, 워커 노드에 직접 전달되지 않는다
- kubectl get nodes
- 사용자 kubect!- control plane api-server 클러스터 내부 구성요소

##### API Server 하는 역할
- 사용자 요청 수신
- 사용자 인증
- 권한 확인
- 요청 내용을 검증
- 내부 구성 요소간 통신 중계
- 클러스터 상태 변경
- 상태 조회

API Server  <- 쿠버네티스 클러스터 모든 요청이 모이는 출입구

---

#### 2. etcd
> 클러스터의 설정, 상태를 저장하는 "분산" key-value 저장소
- etcd 에는 클러스터 내에 중요한 상태 정보가 저장
    - 클러스터 구성 정보
    - Node 정보
    - 현재 실행 상태
    - 원하는 상태
    - 각종 설정 정보

##### 중요하다 ⭐️
- etcd 데이터는 쿠버네티스가 하려고 하는 모든 정보가 저장
- etcd 데이터가 손실
    - 쿠버네티스 클러스터는 정상적으로 작동이 불가능함
- 운영 환경에서는
    - etcd 백업
    - 다중화 -> 고가용성
    - 복구 작업 준비
    - 접근 제한
- etcd 는 애플리케이션 데이터베이스가 X
    - 쿠버네티스 클러스터에서 필요한 자체적인 상태를 저장하는 KV 저장소

---

#### 3. kube-scheduler
> 새로운 실행 단위(파드)를 어느 워커 노드에 배치할지 결정하는 구성 요소
- 스케줄러는 아직 실행할 노드가 정해지지 않은 실행 단위를 적절한 워커를 선택하는 구성 요소

##### 스케줄러가 고려하는 정보
- Node CPU, Mem 자원
- 애플리케이션 요청한 자원
- Node 상태
- 배치 조건
    - 나는 이 컨테이너는 어떻게 배치되어야 할 거 같아
    - 이 컨테이너는 BE 컨테이너랑 떨어져 있어야 해
    - 이 컨테이너는 항상 Nginx Container 랑 같이 있어야 해
- 스토리지 조건
- 스케줄러 <- 컨테이너를 실행 하지는 않는다
    - 실행할 노드를 결정만 한다

---

#### 4. kube-controller-manager
> 현재 상태를 -> 원하는 상태로 맞추는 여러 제어 기능을 실행하는 구성 요소
- 클러스터의 상태를 계속 확인
- 현재상태 <-> 원하는 상태 다르면
- 현재 상태 확인 -> 다르면 필요한 작업을 실행한다

---

### Worker Node
> 실제 애플리케이션이 실행되는 서버
- 컨트롤 플레인 두뇌 역할
    - 워커 노드 -> 실제 작업을 수행하는 손발
```
Worker Node
├── kubelet
├── Container Runtime
├── kube-proxy
└── 애플리케이션 실행 단위
```

#### 워커노드의 역할 수행
- 컨테이너 이미지 다운로드
- 컨테이너 실행
- 컨테이너 상태 확인
- 실행 상태를 컨트롤 플레인 보고
- 네트워크 통신 처리
- 장애가 발생하면 컨테이너 재시작

---

#### 1. kubelet
> 각 워커노드에서 Pod 실행 상태 관리, 컨트롤 플레인에 보고 하는 에이전트
- kubelet, Worker node에 하나씩 붙어 있다
```
API Server
↓ 실행해야 할 내용 전달
kubelet
↓
Container Runtime
↓
Container 실행
```

##### kubelet 역할
- API Server 통신
- 실행해야 하는 작업 확인
- 컨테이너 런타임에 특정 작업을 요청
- 컨테이너 상태 확인
- Pod 상태점검
- Node 상태 보고
- 문제가 발생한 컨테이너를 재시작

*kubelet, Worker Node 에서 실제 실행 상태를 책임지는 에이전트*

#### 2. Container Runtime
> 컨테이너 이미지 가져오고, 실제 컨테이너 프로세스를 실행하는 소프트웨어
- 쿠버네티스는 "관리 소프트웨어"
- 컨테이너 프로세스를 직접 실행하지 않는다
- Container Runtime에 컨테이너 실행 요청
- 대표적인 Container Runtime
    - docker
        - k8s에서 요구하는 Container Runtime 필수 요소
        - docker에서 지원하지 않는다
    - container
    - CRI-O
- Docker Engine <- Docker Desktop 설치
- 쿠버네티스에서 "도커" 이미지를 사용한다고 해서 "도커"를 설치할 필요는 없다
- 도커
    - 컨테이너를 관리하기 쉽게 만든 컨테이너 관리 도구
    - 컨테이너는 도커가 아님!
    - 컨테이너를 실핼할 수 있는 런타임만 있으면 쿠버네티스는 동작한다

---

#### 3. kube-proxy
> Worker Node 에서 네트워크 트래픽 전달을 위한 규칙을 관리하는 구성 요소
- 클러스터 내에 노드들은 분산 되어 있고 여러 개의 노드가 실행
    - 여러 개의 컨테이너가 실행 되고 있다
    - 컨테이너간의 통신
        - 노드 내에서 이뤄지면 괜찮은데 노드 간의 통신 해야한다
- kube-proxy 는 워커 노드의 네트워크 규칙을 관리하고 트래픽이 적절한 목적지로 전달될 수 있도록 지원

```
kubelet
→ 실행 상태 관리

Container Runtime
→ 실제 컨테이너 실행

kube-proxy
→ 네트워크 트래픽 전달 지원
```
- 쿠버네티스에서 네트워킹 까다로운 문제
- kube-proxy 만으로 해결되지 않음
    - CNI 같은 것들이 필요함

---

#### 4. Pod
> 쿠버네티스가 컨테이너를 실행하고 관리하는 가장 작은 배포 단위
- 쿠버네티스는 일반적으로 컨테이너를 직접 실행 단위로 다루지 않고 Pod 라는 단위로 관리한다
- 하나의 파드에는 하나 이상의 컨테이너가 들어갈 수 있다
- 같은 파드 안에 있는 컨테이너들은
    - 네트워크
    - IP 주소
    - localhost
    - 스토리지
    - 생명주기

```
Pod
├── Main Container (BE)
└── Helper Container (JSON Exporter)
```

### 쿠버네티스 사용 이유

### 1. 자동 복구 (오토 힐링)
- 컨테이너가 종료되거나 애플리케이션에 문제 발생 -> 다시 실행하도록 구성
- 정상 실행 -> 컨테이너 장애 -> 장애 감지 -> 컨테이너 재시작
- 운영자가 재시작할 필요 없음
- 장애 대응 시간 감축
- 서비스 가용성이 높아진다

##### 주의해야 하는 점
- 쿠버네티스가 애플리케이션 오류를 수정하는게 아님
    - 컨테이너가 죽으면 복구 작업 자체 자동 (3개 필요-> 2개만 실행됨 -> 1개 실행시킴)
    -  하지만 잘못된 코드 + 설정은 자동으로 수정하지는 못한다
- 쿠버네티스는 컨테이너를 가축으로 본다
    - 가축 vs 애완동물
        - 애완 동물 -> 이름을 붙여준다
        - 가축 -> 이름을 안 붙이고 숫자를 붙임
        - 닭이 조류인플레인자 걸리면 살처분(매장)
    - 컨테이너 사용
        - 애완동물 다루듯이 다룬다
        - 이름도 붙이고 에러가 나면 직접 작업
    - 쿠버네티스 사용
        - 가축 다루듯이 다룬다
        - 숫자를 붙임 -> 1번, 2번
        - 에러나면 1번 죽이고 3번 만듬

## 2. CNI와 Flannel

### Pod 끼리는 어떻게 통신하는가?
- 쿠버네티스는 파드를 생성하고 어디 노드에서 실행할지 결정
- Pod에 IP를 부여하고, 서로 통신할 수 있는 네트워크는 직접 구현하지 않는다
- 네트워크 기능을 담당하는 것들이
    - CNI 플러그인
        - Flannel 이라는 플러그인

### Pod IP가 필요하다
- Pod도 다른 Pod랑 통신 해야할 수 있다
- 통신을 하려면 주소가
    - IP 주소가 필수

- Node IP: EC2 또는 물리 서버가 가진 실제 네트워크 IP
- Pod IP: 쿠버네티스 내부에서 Pod에 할당된 IP

- Node A, Node B 는 서로 실제 네트워크 연결
    - 서로의 Node IP 는 알고 있다
- 기존 네트워크 장비로는 다음 Pod 의 IP는 모른다
- 이 문제를 해결하려고 CNI, CNI 플러그인

### CNI? (Container Network Interface)
> CNI는 컨테이너 네트워크 설정하고, 제거하는 방법을 정의한 표준 규격 인터페이스
- 컨테이너 끼리 서로 통신하려면 이런 규격을 지키자 하는 약속
- 그리고 그 약속을 구현한 것들이 CNI 플러그인
    - 컨테이너, 파드에 네트워크 인터페이스 연결
    - IP 주소
    - 라우팅 설정
    - 컨테이너 삭제될 때 네트워크 자원 정리
- 인터페이스의 구현체가 CNI 플러그인
    - Flannel

### 왜 CNI를 굳이 사용하나?
- CNI가 없으면 쿠버네티스가 직접 모든 네트워크 환경을 지원해야한다
    - AWS, GCP, NCP, 온프레미스 네트워크
- CSP에 종속되지 않는다
    - AWS, GCP든 어디서든 사용할 수 있다
- 쿠버네티스는 "컨테이너 오케스트레이션 툴"이지, 네트워크 툴이 아님
- CNI를 사용하면
    - 쿠버네티스는 인터페이스로 규격만 설정하고
    - 그걸 구현한 구현체들을 우리가 사용한다
    - 라이브러리 같이 전문적인 네트워크 기능을 맡긴 것
- CNI 플러그인
    - Flannel CNI
    - Calico CNI
    - Cilium CNI

---

### Flannel?
> Flannel은 여러 노드에 있는 Pod들이 서로 통신할 수 있도록 Pod 네트워크를 구성하는 네트워크 플러그인

### 주요 역할
1. 노드별 Pod 대역 관리: 각 노드가 사용할 Pod IP 대역을 구분
2. Pod 네트워크 구성: Pod가 네트워크에 연결될 수 있도록 인터페이스와 경로 구성
3. 노드 간 통신 경로 제공: 서로 다른 노드의 Pod끼리 통신할 수 있도록 연결
4. 캡슐화: VXLAN 사용 시 Pod 패킷을 Node 간 전송 가능한 패킷으로 감쌈

### 필요한 이유
#### 1. 같은 노드에서의 필수
- 같은 노드에서는 Pod에서 노드 내부의 가상 네트워크를 통해서 서로 통신할 수 있음

#### 다른 노드에서 Pod 간 통신
- 이 문제해결하기 위해서 Flannel에서 VXLAN 방식을 사용

##### VXLAN (Virtual eXtensible LAN)
> VXLAN 은 Pod 패킷 Node 간 전달할 때, UDP 패킷 안에 한 번더 감싸는 터널링 기술
- Flannel VLAN
    - 원래 Pod 가 보내려고하는 패킷을 Node 간에 이동할 수 있도록 새로운 외부 패킷으로 감싼다
    - 그걸을 "캡슐화"

##### VXLAN 패킷 전달 과정
- Node A Pod - Node B Pod 에게 요청을 보낸다

##### 1. Pod 패킷 전달
- Pod A -> Pod B 를 향해서 패킷 만들기

##### 2. Node A 캡술화
- Node A → kube-proxy
    - NodeB 에는 어떤 서브넷 마스크 사용하냐
    - 10.244.2.0/24 서브넷을 사용한다
- 10.244.2.5 -> Node B 가야하네
- 기존 패킷을 Node B 로 전달 해야함
- 외부 UDP 패킷 으로 감쌈

##### 3. 물리 네트워크 전송
- 물리 네트워크에서는 pod IP 알 필요 없음
- Node B 로 간다는것만 알면 된다
- 왜냐하면 외부 패킷 목적지가 Node B

##### 4. Node B에서 캡슐 제거
- Node B 가 UDP 포트로 패킷 전달받고 UDP 패킷을 벗긴다
- 외부 VXLAN 헤더 벗기면, 내부 패킷이 보인다

##### 5. 목적지 Pod 로 전달
- Node B 원래 받아하는 Pod 에게 전달

##### 택배 상자를 이중 포장
- Pod 가 원래 보내는 패킷은 작은 택배 상자
    - 받는 사람: Pod B
    - IP: 10.244.2.5
- 일반 배송망은 10.244.2.5 라는 주소를 알지 못함
- 그래서 이걸 Flannel VXLAN 이라는 큰 상자에 넣는 것
    - 큰 상자 받는 사람: Node B
    - IP: 192.168.10.20
- NodeB 가 받으면 다시 상자 포장 뜯어서 내부 파드에 전달하는 구조

### 왜 UDP?
- VXLAN은 각각의 패킷을 독립적으로 캡슐화해서 운반하는 터널
- 연결 상태를 유지하지 않는 UDP를 사용한다

#### 1. 애초에 보내는 패킷이 TCP
- 우리가 감싼 원래 패킷 = TCP
    - TCP 사용하는 이유
    - 신뢰성
    - 연결 보장
    - 순서 보장
    - 확인 응답
    - 재전송
    - 혼잡 제어
- TCP로 보냈으면 그걸 중간에 UDP 로 감싸던 TCP 로 감싸던
- 애초에 보낸게 TCP 이니
    - 중간에 문제가 생기면
    - 어차피 신뢰성을 보장
    - TCP 로 1~10번까지 보냈다.
    - 근데 그걸 만약에
        - TCP 로 감싸던
        - UDP 로 감싸던
        - 애초에 TCP를 보냈다면서요
            - 수신 측에 Inner Packet 까서 TCP 응답해줘야하는데
            - 수신측에서 만약에 응답을 안하면 그럼 다시 보낼 수 있음
            - 왜냐- >
            - 애초에 보낸게 TCP 잖아요.

### ### 왜 TCP 가 아닌 UDP 를 사용하나? (TCP over TCP 문제)

- 중요한 포인트
- TCP 패킷을 TCP 터널로 감싸면 재앙이 일어남
- 우리가 보내려는 데이터는 이미 TCP 로 안전하게 포장 되어 있음
    - 그런데 이걸 나르는 터널까지 굳이 꼼꼼한 TCP 일 필요가 없음
    - 오히려 방해된다.
- 이유
    1. 과잉 친절의 부작용 (TCP Meltdown)
        - 만약 겉포장(터널) 도 TCP 를 사용하면 어떻게 될까?
        - 상황: 네트워크가 잠깐 느려저서 패킷이 늦게 도착함
            - 내부(Inner) TCP: “어? 데이터 안왔네? 재전송해” 라고 다시 보냄
            - 외부(Outer) TCP: “어? 터널링 패킷 안갔네? 나도 재전송해!” 하고 또 보냄
        - 결과:
            - 안그래도 길이 막히는데, 내부 TCP, 외부 TCP 에서 서로 재전송하겠다고 함
            - 데이터가 쏟아져서 네트워크가 완전히 멈춰버림
        - 이런 현상을 TCP Meltdown 현상이라고 함
    2. 빠르고 단순한 배송 (단순 운반)
        - UDP 의 역할
            - Flannel (VXLAN) 은 내용물이 뭔지 검사 하지 않고 A 지점에서 B 지점으로 빠르게 전달하는 역할만 하면 된다.
        - 신뢰성의 문제?
            - 만약 중간에 데이터가 깨지면
            - 내용물(Inner TCP) 이 알아서 감지하고, 재요청함
            - 트럭 기사 (UDP) 가 택배 상자 안의 물건 상태까지 걱정할 필요가 없음
    3. 헤더 오버헤드 감소
        - TCP 는 연결을 맺고, 순서를 맞추고, 잘받았나 확인 하느라 헤더가 무거움
        - 모든 패킷마다 이걸 하면 속도가 엄청 느려짐
        - 가벼운 UDP 를 써야 오버 헤드를 줄일 수 있음.
    - 예시
        - 우리가 중요한 도자기(데이터)를 서울에서 부산까지 보낸다고 치면
            1. 도자기 포장 (Inner TCP)
                1. 도자기를 뽁뽁이로 꼼꼼하게 감싸기
                2. 깨지면 다시 보내준다는 보증서도 들어 있음 (신뢰성 확보)
            2. 배송 트럭 (Outer UDP)
                1. 트럭은 고속도로 달리기만 하면 된다.
            - 만약 트럭 기사가 “혹시 도자기 깨진거 아님?” 이라고 생각하고 휴게소마다 멈춰서 포장을 뜯어보고 확인한다면? (Outher TCP) 부산까지 10시간도 걸릴 수도
            - 트럭(Flannel/UDP) 는 최대한 빨리 배달만 하면 된다.
            - 문제가 생기면 보낸 사람이 알아서 다시 보낼 것
            - 그래서 터널링 기술은 대부분 빠르고 가벼운 UDP 를 사용함
