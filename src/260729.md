## 1. AutoScaler - HPA (Horizontal Pod Autoscaler)
> 애플리케이션의 부하를 메트릭으로 관찰하고, Deployment와 같은 워크로드의 Pod 개수를 자동으로 늘리거나 줄이는 기능

리소스 사용량(CPU, 메모리 등)이나 사용자 정의 메트릭을 기반으로 Pod의 개수를 자동으로 조정하여 애플리케이션의 처리 능력을 관리하는 컨트롤러

### 해결하려는 문제
#### 고정된 파드의 숫자
- Deployment 
  - 직접 만들든 or GitOps -> ArgoCD Sync든
  - Pod의 수는 `고정` 되어 있다
  - `현재` 트래픽으르 기준으로 replicas 숫자가 변경되지 않는다

1. 트래픽 증가: Pod이 처리할 수 있는 요청보다 많은 요청이 들어와 응답 지연이나 오류가 발생할 수 있음
2. 트래픽 감소: 사용하지 않는 Pod이 계속 실행되어 CPU·메모리와 인프라 비용이 낭비됨
3. 갑작스러운 변화: 관리자가 직접 replicas를 변경하기 전까지 대응하기 어려움
4. 반복적인 운영: 부하를 확인하고 Pod 개수를 조절하는 작업을 계속 수동으로 수행해야 함

---

### 사용 이유
#### 1. 부하 대응을 자동화하기 위해서
- 쇼핑몰 행사, 쿠폰 발급, 이벤트, 광고 집행
- 트래픽이 순간적으로 몰리거나, 일반적으로 트래픽이 시간에 따라 변화하는 상황
- HPA를 사용하면 `CPU 사용률`, `메트릭을 기반으로 Pod 개수를 조정`할 수 있음
```
평상시
사용자 -> Service -> Pod 2개

트래픽 증가
사용자 -> Service -> Pod 5개
```
---
#### 2. 트래픽 감소 -> 파드 줄이기 위해서
- 리소스 측면에서는 사실 당장 큰 의미는 없다
- 트래픽이 감소 -> 파드를 줄인다고 해서 실제 비용이 줄지 않는다
- 그럼 왜? -> 여유 자원을 만들어두기 위해서
  - 비용적인 측면보다는 운영 안정성 측면에서 트래픽이 줄면 파드를 줄이려고 한다
---
#### 3. 수동 운영 줄임
- 약 3000개의 파드 중 Pod의 종류가 1~2개 있는게 아니다 -> 10개 이상 파드 카테고리가 있다
- 이러한 파드들의 개수를 제어 루프로 자동화한다

`현재 상태 측정 -> 목표 상태와 비교 -> 필요한 Pod 수 계산 -> replicas 변경 -> 새로운 상태를 다시 측정`

---

### HPA는 뭘 변경하는가
- HPA -> Pod를 직접 늘리거나 줄이지 않음
- Deployment Replicas를 수정
```
HPA -> replicas 변경
Deployment -> ReplicaSet 관리
ReplicaSet -> Pod 생성 또는 감소
```

`Deployment replicas: 2  -> HPA가 replicas를 5로 변경 -> Deployment와 ReplicaSet이 Pod 3개를 추가 생성`

- HPA: 필요한 Pod 개수를 계산하고 대상 워크로드의 스케일을 변경
- Deployment: 애플리케이션 배포와 ReplicaSet 관리
- ReplicaSet: 지정된 개수만큼 Pod이 실행되도록 유지

---

### HPA가 동작하기 위한 구성
- HPA는 리소스를 만든다고 해서 자동 확장 동작하지 않음
- 기본적으로 CPU 기반 HPA 구성
```
애플리케이션 Pod -> CPU 사용량
Kubelet -> 수집
Metrics Server -> Metrics API 제공 
HPA Controller -> 필요한 replicas 계산
Deployment
```

#### 구성 요소
- 대상 워크로드: HPA가 Pod 개수를 조정할 Deployment 등
- Metrics Server: 노드와 Pod의 CPU, 메모리 사용량을 수집하여 Metrics API로 제공
- HPA 리소스: 대상, 최소/최대 Pod 수, 목표 메트릭을 정의
- Resource requests: CPU, 메모리 사용률을 계산할 때 기준값으로 사용
- HPA Controller: 메트릭을 확인하고 필요한 복제본 수를 계산

--- 
### Metrics Server
> 각 Node와 Pod의 현재 CPU, 메모리 사용량을 수집하여, HPA와 Kubectl top이 사용할 수 있도록 제공하는 Kubernetes용 메트릭 수집 애플리케이션

#### 메트릭스 서버는 별도의 애플리케이션이다
- 쿠버네티스 내부에 내장된 기본 기능이 아님
- 클러스터에 별도로 설치하는 애플리케이션
- kube-system -> deployment 형태로 설치가 된다

```
각 Node의 Kubelet
-> CPU, 메모리 사용량 제공

Metrics Server
-> Metrics API로 제공
HPA / VPA / kubectl top
```
- 큐블렛에서 수집한 데이터를 Metrics Server가 다른 노드에서 사용할 수 있게 표현하는 역할

---
#### Metrics Server는 어디에 사용하나?
- PLG Stack의 Prometheus 비슷함
- Metrics Server는 장기간 데이터를 저장하고 분석하는 모니터링 시스템이 아니다
  - 현재 리소스 사용량을 보여주는 API다.
  
```
Metrics Server: 지금 속도계가 몇 km/h인지 알려주는 계기판

Prometheus: 지난 한 달 동안 속도가 어떻게 변했는지 저장하는 운행 기록 시스템
```
---

### PLG Stack 으로 Metrics 서버 대체 가능한 거 아닌지?
- 왜 굳이 Metrics Server 또 설치해야하나? (이미 PLG Stack 만들었는데?)
- 프로메테우스는 metrics server와 제공하는 역할이 다름


- 프로메테우스에서 뭔가를 얻으려면 PromQL 쿼리 언어를 사용
  - 쿼리 언어 -> 시간 복잡도
  - 실시간성이 상대적으로 떨어짐
- Metrics Server
  - kubelet 에서 실시간으로 수집하고 있는 OS 데이터를 바로 가져와서 API Result로 변경해서 전달하는 역할
  - 가볍고 실시간성이 높음
- 현재 트래픽 <-> 파드가 감당할 수 있는 트래픽을 비교
  - CPU Usage 
  - 파드를 늘리는 목적을 HPA
- 안 되는건 아니지만, 일반적으로 OS 레벨의 메트릭을 비교하는 HPA에서는 잘 사용하지는 않음

### PLG Stack으로 Metrics Server를 대체할 수 없는 이유
- 이미 PLG Stack(Prometheus, Loki, Grafana)을 구축했는데 왜 Metrics Server도 설치해야 할까?
- Prometheus와 Metrics Server는 역할이 다르다

#### Prometheus
- 메트릭을 조회하려면 PromQL 쿼리 언어를 사용한다
- 쿼리 언어를 사용하기 때문에 시간 복잡도가 있고, 실시간성이 상대적으로 떨어진다

#### Metrics Server
- Kubelet에서 실시간으로 수집하고 있는 OS 데이터를 바로 가져와 API Result로 변경해서 전달하는 역할을 한다
- 가볍고 실시간성이 높다
- 현재 트래픽 <-> 파드가 감당할 수 있는 트래픽을 비교
    - CPU Usage
    - Memory Usage

안 되는 건 아니지만, 일반적으로 OS 레벨의 메트릭을 비교하는 HPA에서는 잘 사용하지는 않음

#### 일반적으로 PLG Stack + Metricd Server 조합
`HPA -> metrics.k8s.io -> Metrics Server`

```
Metrics Server
→ HPA, VPA
→ kubectl top
-> 현재 CPU, 메모리 기반 자동화

Prometheus
-> 장기간 메트릭 저장
-> Grafana 대시보드
-> 장애 분석 및 알림
-> 사용자 의 메트릭 기반 확장
```
```
웹API
-> CPU 평균 사용률 60% 기준으로 확장
-> Metrics Server 사용

메시지 처리 Worker
-> 대기 메시지 수를 기준으로 확장
-> Prometheus와 Metrics Adapter 사용
```
---

#### 💡 Metrics Server 정리
1. Metrics Server는 클러스터에 별도로 설치하는 애플리케이션이다
2. Kubelet에서 Node와 Pod의 CPU·메모리 사용량을 수집한다
3. 수집한 데이터를 metrics.k8s.io API로 제공한다
4. HPA, VPA, kubectl top이 이 데이터를 사용한다
5. 장기 저장, 그래프, 알림을 위한 모니터링 시스템은 아니다
6. Prometheus는 메트릭을 장기간 저장하고 분석하기 위한 도구다
7. 기본 CPU·메모리 HPA에서는 Metrics Server를 사용한다
8. Prometheus 메트릭으로 HPA를 동작시키려면 별도의 Metrics Adapter가 필요하다

---

#### ⭐️ request 중요
- HPA -> Metrics Server -> CPU, Memory Average usage
- 현재 사용량 -> request 비교해서 본다
- HPA -> averageUtilization: 60
  - 노드 전체의 CPU가 60% 라는 것을의미하지 않음
  - 각 컨테이너에 설정된 CPU가 requests 대비 실제 CPU 의 사용량 비율을 의미

```
CPU 사용량 = ( 실제 CPU 사용량 / CPU request ) * 100
예시 케이스= (80/ 100)* 100 => 80% -> Pod 를 늘리려고 한다
```

Node 전체의 CPU 사용량을 보는게 아니라 request 대비 실제 파드에서 사용하고 있는 사용량이 얼마인지를 의미

- requests.cpu: CPU 사용률 계산의 기준 요
- limits.cpu: 컨테이너가 사용할 수 있는 CPU 상한
- requests.memory: 메모리 사용률 방식에서 계산 기준
- limits.memory: 초과 시 OOM 종료 가능성이 있는 메모리 상한

---

### HPA는 필요한 파드 수를 어떻게 계산하나
- 기본 계산 공식

`필요한 파드 수 = 올림((현재 Pod 수 x 현재 메트릭 값)/목표 메트릭 값)`

```
현재 파드 수 = 3개
평균 CPU 사용률 = 110%
목표 CPU 사용률 = 60%

올림 (( 3 x 110)/ 60)

5.5 => 6

필요한 파드 수 = 6개
-> deployment. replicas = 6
```

---
#### YAML
- scaleTargetRef: HPA가 관리할 대상 워크로드
- minReplicas: HPA가 유지할 최소 복제본 수
- maxReplicas: HPA가 확장할 수 있는 최대 복제본 수
- metrics: 스케일링 판단에 사용할 메트릭
- `type: Resource`: CPU·메모리와 같은 리소스 메트릭 사용
- `averageUtilization: 60`: 모든 대상 Pod의 평균 사용률을 request 대비 60%에 맞춤

---

#### 메트릭의 종류
- Resource Metric: Metrics Server를 통해 비교적 쉽게 구성 (ex. CPU, 메모리)
- Container Resource Metric: 사이드카를 제외하고 핵심 컨테이너만 기 준으로 삼을 때 유용 (ex. 특정 컨테이너의 CPU, 메모리)
- Custom Metric: 별도의 메트릭 수집 및 어댑터 구성 필요 (ex. 초당 요청 수, 큐 길이)
- External Metric: 클러스터 외부 시스템의 상태를 기준으로 확장 (ex. 외부 메시지 큐 길이, 클라우드 서비스 지표)

```
메시지 큐 소비자 -> CPU는 낮지만 처리 대기 메시지가 계속 쌓일 수 있음

외부 API 응답을 기다리는 서버 -> 요청은 많지만 I/O 대기 때문에 CPU는 낮을 수 있음

메모리 캐시 애플리케이션 -> 메모리가 부하 감소 후에도 바로 반환되지 않을 수 있음
    
--
HTTP 요청 수
응답 지연 시간
메시지 큐 길이
동시 연결 수
처리 대기 작업 수
```

---

### 스케일링 속도 제어
- HPA가 부하 변화마다 Pod를 즉각적으로 수정
  - 부하 증가 -> Pod 바로 늘리기
  - 부하 조금 떨어짐 -> 파드 줄이기
  - 부하 증가 -> 재생성
- 파드는 생성될 때 시간이 노드 스케줄링, 노드 affinity -> 파드가 배치될 때 필요한 시간이 있다 <- 플래핑
  - 서비스 안정성이 떨어짐 
- behavior: 속도 조정

---

#### ArgoCD 사용한다면? 
- ArgoCD GitOps를 통해서 배포 환경 == 깃에 선언된 "단일 진실 공급원" 일치 수행
- 배포되어 있는 클러스터에서 Usage 보면서 replicas를 수정
  - k8s 클러스터에 스스로 수행 -> Git에 있는 replicas를 돌린다
- HPA를 사용할 때는 워크로드의 복제본 관리 주체가 누구인지 명확하게 명시해야 함

---

### 해결 방법
#### 1. Deployment replicas 제거하기
- 복제본 관련 HPA에게 맡기기
- 관리 주체가 분리
  - Git, ArgoCD -> 이미지, 환경변수, 프로브, 서비스, deployment
  - HPA -> 현재 필요한 Replicas를 관리하는 주체
- 주의 사항
  - deployment -> replicas 이미 관리하고 있으면 적용 시점에 따라서 문제가 생길 수 있다
  - 다음 버전으로 인프라 구조 변경 or 새로운 인프라 구축할 때 사용
  
#### 2. ArgoCD spec.replicas 무시하는 방법
- ignoreDifferences <- 얘만으로는 충분하지 않다
  - ArgoCD가 해당 차이를 `OutOfSync`로 판단하지 않도록 하는 설정
  - 동기화 시 `replicas` 차이를 무시한다
  - 확실하게 제외하려면 `RespectIgnoreDifferences=true`를 함께 적용해야 한다
- 실제 변경이 이뤄져도 놓칠 수 있다
- "변경"된 값을 무시하는 것이지, 초기 생성 값은 무시하지 못한다
    - 차이를 비교하려면 비교 대상이 있어야 한다
        - 클러스터에 최초 설치할 때는 비교할 대상이 없다
        - Git에 선언된 `replicas` 값을 그대로 적용한다
    - `RespectIgnoreDifferences=true`도 동기화 단계에서 차이를 무시한다
        - 최초 리소스 생성 시에는 기존 라이브 리소스가 없으므로,
        - Git에 선언된 `replicas` 값이 그대로 생성

#### 실무 조합
- deployment replicas X
- HPA replicas 관리
- ArgoCD에서도 replicas에 대해서 무시하도록 설정함

---

#### 💡 HPA 정리
1. HPA는 Pod 한 개의 성능이 아니라 Pod의 개수를 조절한다
2. HPA는 메트릭을 관찰하고 대상 워크로드의 replicas를 변경한다
3. CPU Utilization은 CPU limit이 아니라 CPU request를 기준으로 계산한다
4. 기본 CPU·메모리 메트릭을 사용하려면 Metrics Server가 필요하다
5. Pod이 늘어나려면 노드에 충분한 CPU와 메모리가 있어야 한다
6. 새 Pod이 실제 트래픽을 받기까지는 생성과 초기화 시간이 필요하다
7. 빠른 확장과 안정적인 축소를 위해 behavior 정책을 조정할 수 있다
8. HPA는 Stateless하고 수평 확장이 가능한 애플리케이션에서 효과적이다
9. HPA는 애플리케이션 장애나 데이터베이스 병목을 자동으로 해결하지 않는다
10. 운영에서는 requests, minReplicas, maxReplicas, Readiness Probe를 함께 설계해야 한다

⭐️ HPA가 복제본 수를 늘려도 항상 성공하는 것은 아니고, 노드에 배치할 리소스 부족 시 실패 처리
- 배치할 리소스가 없을 때
  - 필터링
    - NodeSelector
      - Pod = Label - env.production
    - Node Label
    - Request Resource
  - 스코어링

## 2. AutoScaler - VPA (Vertical Pod Autoscaler)
> Pod의 실제 CPU, 메모리 사용 이력을 분석하여, 컨테이너의 적절한 requests 값을 추천하거나 자동으로 조정하는 오토스케일러

#### VPA도 기본 제공 기능이 아님
- HPA랑 같은 API Group -> 추가 설치하는 애플리케이션, 애드온

---
### 사용 이유

- 앱이 얼마나 리소스가 필요한지는 실제 실행 전까지 모른다.

#### requests가 너무 적으면

- 실제 필요한 CPU: `400m`
- request CPU: `100m`

- 스케줄러 판단 기준
    - request
    - Node 유휴 자원: `200m`
        - request가 `100m`이므로 배치

- 하지만 실제로는 `400m`를 사용
    - CPU Throttling이 발생
    - 다른 Pod들에게도 영향을 미침

- Memory request가 작게 설정된다면
    - OOM으로 종료됨
---
#### VPA가 해결하는 문제는
VPA는 실제 리소스 사용량을 보고 분석해서

1. 너무 작은 requests -> 필요한 수준까지 상향 추천
2. 너무 큰 requests -> 실제 사용량에 맞게 하향 추천
3. 반복적인 수동 튜닝 -> 사용 이력을 기반으로 자동 분석
4. 잘못된 요청량으로 인한 스케줄링 문제 -> 실제 사용량에 가까운 요청값 제공
5. 리소스 낭비 -> 과도하게 예약된 CPU, 메모리 감소

> 파드에 필요한 리소스를 실제 사용량에 가깝게 RightSizing 도구. 
자동화 기능을 넣으면 파드를 request에 맞게 재배치하는 기능도 있다

---

#### VPA가 무엇을 변경하는가? 
- 주로 request를 변경
- request는 단순히 참고하는 값이 아님
  - 실제로 노드 스케줄러가 스케줄링할 때 사용하는 "기준 값"
- 실제 사용량, request는 차이가 있음
  - 실제 사용량: 현재 컨테이너가 실제 사용하는 CPU, 메모리
  - requests: 스케줄러에게 이 Pod가 필요하다고 선언한 CPU, 메모리

### 구성 요소

```
Metrics API
     │
     ▼
Recommender
     │ 권장값 계산
     ▼
VPA 객체의 status.recommendation
     │
     ├── Updater
     │     └── 기존 Pod의 변경 필요 여부 판단
     │
     └── Admission Controller
           └── 새로 생성되는 Pod에 권장값 적용
```
---
#### 1. Recommender
> 파드의 사용량 분석 후 적정한 리소스 값을 추천

- 각 컨테이너의 현재 사용량을 분석
  - 과거의 사용량 분석 사용
- 분석 결과를 가지고 VPA 객체 -> status.recommendataion 저장
- 추천 값은 크게 계산 할 때
  - target: 일반적으로 적용하기 적절한 권장값
  - lowerBound: 권장 가능한 최소 범위
  - upperBound: 권장 가능한 최대 범위
  - uncappedTarget: 정책의 최소/최대 제한을 적용하기 전 계산값

---
#### 2. Updater
> 실행 중인 파드의 요청값, 권장값을 비교 후 변경이 필요한지 여부를 판단

`기존 Pod의 requests -> VPA 권장값과 비교 -> 차이가 충분히 큼 -> Pod Eviction(퇴출) (예전 방식. 최신 기술 In-place) -> DepLoyment가 새 Pod 생성`

#### Updater 하는 역할
1. Recommender가 만든 값이랑 현재 파드 값을 비교
2. 변경 대상인지 아닌지만 구분
   - a. Eviction 대상이면 제거
   - b. In-place

---
#### 2. Admission Controller
> 새롭게 생성되는 파드에 VPA 권장 리소스 값을 주입하는 역할

`DepLoyment가 새 Pod 생성 요청 -> API Server -> VPA Admission Controller -> Pod 생성 -> 권장 requests를`

#### Initial
- 파드 생성될 때만 권장값을 적용
- 실행 중인 파드에는 새로운 권장 값을 적용하지 않고, 새로운 파드가 생성될 때만 Admission Controler 동작

#### Recreate
- 권장 값 적용하려면 Pod Eviction -> 새로 생성

`권장값 변경 -> Updater가 변경 필요 판단 -> 기존 Pod Eviction -> Deployment가 새 Pod 생성 -> Admission ControlLer가 권장값 적용`

#### InPlace / InPlaceOrRecreate
- 실행 중인 Pod의 리소스를 변경
- 리소스 변경이 불가능할 때
    - 현재 노드의 남은 자원: `300m`
    - VPA
        - Pod 리소스: `100m` → `500m`
        - 현재 노드에서는 안 되어서 -> Pod Eviction
            - Deployment가 `replicas` 수만큼 다시 생성 요청
            - API Server → Scheduler → Node에 재배치

#### HPA vs VPA

| 구분 | HPA | VPA |
| --- | --- | --- |
| 확장 방식 | 수평 확장 | 수직 확장 |
| 변경 대상 | Pod 개수 | Pod CPU·메모리 |
| 대표 설정 | `minReplicas`, `maxReplicas` | `minAllowed`, `maxAllowed` |
| 주된 기준 | 현재 메트릭과 목표값 | 현재·과거 리소스 사용량 |
| 결과 | 여러 Pod으로 부하 분산 | 각 Pod의 리소스 크기 최적화 |
| 중단 가능성 | 일반적으로 새 Pod 추가·삭제 | 모드에 따라 기존 Pod 재생성 가능 |
| 기본 설치 | Kubernetes API에 포함 | 별도 설치 필요 |

#### 💡 VPA 정리
- VPA는 별도로 설치해야 하는 애드온이다
- Pod 개수가 아니라 CPU·메모리 requests를 조정한다
- 현재 뿐 아니라 과거 사용량도 분석한다
- 모드에 따라 Pod이 재생성될 수 있다
- 처음에는 `Off` 모드로 추천값을 확인하는 것이 안전하다
- HPA와 같은 CPU·메모리 지표를 동시에 관리하면 충돌할 수 있다
- `minAllowed`, `maxAllowed`로 조정 범위를 제한해야 한다
- VPA가 Pod을 크게 만들어도 Node 용량이 자동으로 늘어나는 것은 아니다

## 3. AutoScaler - CA (Cluster Autoscaler)
> Pod을 배치할 공간이 부족하면 워커 노드를 늘리고, 불필요한 노드가 생기면 줄이는 노드 단위의 자동 확장 도구

### 해결하는 문제
#### 1. 파드를 늘릴 때 배치할 노드가 없으면?
- HPA, VPA <- 파드의 사이징, 개수를 늘린다
- Node 자원은 유한함
- 모든 노드가 자원이 충분하지 않으면 파드는 펜딩 상태에서 대기하고 있음
- 노드 자체를 새롭게 추가해서 클러스터에 배치하는 방식

1. 노드를 추가 배치
2. 필요없는 노드를 제거

---

#### CA가 확인하는 값
- HPA, VPA <- 파드의 자원 사용량, 커스텀 사용량
- CA는? 사용량을 보지 않음

파드들이 노드에 스케줄링이 가능한가? 지금 펜딩인게 얼마나 않은지?
```
Pod 생성
   ↓
kube-scheduler가 배치 가능한 노드 검색
   ↓
배치 가능한 노드가 없음
   ↓
Pod: Pending / Unschedulable
   ↓
CA가 확장 필요성 검토

# Pending 되어 있는 파드의 수
# 각 파드가 필요한 request 의 양을 보고 CA 가 결정한다
# 너무 작은 양의 reqeust라면, 그러면 CA 는 무시할 수 있음
```
---

### CA는 "직접" 노드를 추가하지 않는다.
- AWS Auto Scaling Group(ASG)
  - min EC2: `2`
  - max EC2: `10`
  - Worker Node들이 여기에 포함되어 있다

- CA는 현재 필요한 노드 개수만 변경한다 `2 → 3`

- CA 종류에 따라 다르다
    - 일반적으로 사용하는 CA -> ASG Desired Capacity를 증가시킨다

- Karpenter
    - CA Tool
    - ASG를 사용하는 것이 아니라 직접 EC2 템플릿을 골라 생성 요청
    - 생성 시간이 조금 더 빠르고, 예민하게 움직일 수 있다
    - 만들어야 하는 인스턴스 타입에 맞춰 EC2 개수를 늘릴 수 있다

- ASG Desired Capacity: `2 → 3`
- EC2가 바로 생성되지는 않는다.
    - CSP의 한계
      - IDC의 물리적인 장비를 기반으로 서비스를 제공한다
      - 물리 장비 A → 300GB
        - `t3.small`을 할당할 수 있는 장비
      - 생성 대기 시간이 생길 수 있다.
    - CA의 예민도가 높아야 한다.
    - Karpenter 사용도 고려할 수 있다.
---
#### Node가 줄어들 때 어떻게 동작하는지
- CA는 더 이상 사용량 많지 않은 노드가 있으면 제거할 수 있는지 검토
- 사용량이 없다고 해서 노드 지우지 않음

1. 다른 노드로 이동 가능한가 
2. 리소스가 충분한가 
3. 스케줄링 조건을 만족하는가 
4. 안전하게 퇴거 가능한가 
5. 로컬 데이터가 있는가

#### HPA, VPA, CA
| 구분 | HPA | VPA | CA |
| --- | --- | --- | --- |
| 확장 대상 | Pod 개수 | Pod의 requests | Worker Node 개수 |
| 확장 방향 | 수평 확장 | 수직 확장 | 클러스터 수평 확장 |
| 주요 판단 기준 | CPU, 메모리, 사용자 정의 메트릭 | CPU·메모리 사용 이력 | 스케줄할 수 없는 Pod |
| 변경 결과 | `replicas` 변경 | CPU·메모리 requests 변경 | 노드 그룹 크기 변경 |
| 인프라 연동 | 일반적으로 불필요 | 일반적으로 불필요 | 필수 |

### kubeadm과 CA 연동
- `kubeadm` <- Kubernetes 클러스터를 초기화하고 노드를 참여시키는 도구
- 인프라 레벨에서 CA가 동작하려면
    - 인프라 프로비저너가 필요하다
        - Worker Node를 만든다고 해서 바로 클러스터에 참여할 수 있는 것은 아니다
        - `containerd`, `CNI`, `Kernel`, `Security Group` -> 인프라 프로비저너가 수행
        - 새롭게 만들어진 EC2가 클러스터에 참여할 수 있게 된다
- EKS가 아니면 CA를 사용하기 힘들다

#### 1. 워커 노드용 AMI 준비
- 새롭게 만들어질 ec2에 필요한 패키지를 미리 설치
  - containerd, kubelet, kubeadm, CNI 동작에 필요한 커널 설정, 필요한 AWS 또는 운영 에이전트
- AMI로 구워놓기

#### 2. 새 노드가 k8s 클러스터에 join 할 수 있게 해야함
- EC2 실행
- User Data
  - EC2가 시작되고나서 실행할 명령어를 적어둘 수 있음

#### 3. ASG
- 최소 값, 최대값, 희망 구성값
- EC2 개수를 적어주고 그 안에서 EC2 개수가 움직임

#### 4. AWS 권한 부여하기
- CA -> AWS API를 호출
  - ASG 정보 조회
  - 크기 변경 요청
- 우리의 노드들이 수행할 수 있어야 함
